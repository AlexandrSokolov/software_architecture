## Orchestration & Choreography

Two ways to run a process across services: one service drives the steps, or each service reacts to events.

<details><summary>Show topics</summary>

- Choreography: each service listens to events and sends its own; no central service.
- Orchestration: an orchestrator sends commands to each service and waits for the replies.
- Who knows where the process is: in choreography nobody, unless one service tracks status per order; in
  orchestration the orchestrator.
- Stuck process: alert on a status held too long; the orchestrator's timeout per step.
- Costs: choreography hides the flow and can tie services in cycles; orchestration adds a central service that can
  grab all the logic.
- When to pick which: number of steps, how often the flow changes, how many teams own it.
- Where the orchestrator keeps its state; workflow engines → Durable Execution.

</details>

То, что ты описал — это абсолютно валидный подход. По сути, ты изобрел паттерн **Process Manager** (или примитивный **State Machine / Workflow Engine**).

Твоя логика: сохранить стейт всех нужных действий в БД (`false`, `false`, `false`), затем делать сетевой вызов -> получать ответ -> делать `UPDATE` во флаг `true` -> коммит.

Ты правильно заметил главное: это гарантирует **at-least-once** доставку. Если приложение падает после отправки уведомления боссу, но до `UPDATE boss_notified = true`, после рестарта оно снова увидит `false` и отправит уведомление повторно. Следовательно, принимающие системы должны быть **идемпотентными** (уметь безопасно проглатывать дубликаты).

Однако в enterprise-разработке у такого "ручного" подхода с синхронными вызовами и множественными коммитами есть серьезные минусы (блокировка потоков, медлительность, жесткая связность). Вот как эту проблему (Multi-Write / Distributed Workflow) решают архитектурно:

### 1. Outbox + Pub/Sub Fan-out (Хореография)

Это золотой стандарт для задач типа «уведомить 3 разные системы», когда порядок не важен.
Вместо того чтобы основное приложение дергало 3 системы и трекало 3 флага, оно делает **только один write**:

1. Основное приложение сохраняет бизнес-сущность и **одно** событие в Outbox-таблицу (например, `EntityCreatedEvent`) в одной транзакции.
2. Background Relay забирает событие из Outbox и кладет его в брокер (Kafka/RabbitMQ).
3. В брокере настроен **Fan-out** (например, Fanout Exchange в RabbitMQ или Consumer Groups в Kafka). Брокер сам размножает это событие в 3 независимые очереди: `customer-notifications`, `boss-notifications`, `dept-notifications`.
4. Три независимых микросервиса (или воркера) читают свои очереди и отправляют уведомления.

**Плюс:** Главная БД свободна от мусора. Отказ отправки боссу никак не тормозит отправку клиенту (у каждого свой retry на уровне брокера).

### 2. Saga Pattern / Orchestrator (Оркестрация)

Если шаги должны выполняться строго последовательно, либо требуют компенсации (rollback-логики — например, если отдел отказал, нужно отправить боссу отмену), таблица с флагами быстро превращается в спагетти.
Вместо самописной таблицы используют готовые движки оркестрации (Temporal, Camunda, AWS Step Functions).

1. Ты пишешь код бизнес-процесса так, будто он выполняется синхронно сверху вниз.
2. Движок сам сохраняет каждый шаг в свою внутреннюю БД (event sourcing).
3. При падении приложения движок автоматически поднимает стейт и продолжает с того места, где упал (с нужными ретраями).

### 3. Asynchronous Routing Slip (Улучшенная версия твоей идеи)

Если инфраструктуры с брокером или Camunda нет, твою идею можно реализовать безопасно, убрав логику из основного потока (HTTP-реквеста):

1. В транзакции создания сущности ты добавляешь запись в таблицу `tasks` (или JSONB-колонку): `["NOTIFY_CUST", "NOTIFY_BOSS", "NOTIFY_DEPT"]`.
2. HTTP-запрос завершается, клиент получает `200 OK`.
3. Отдельный асинхронный воркер (по шедулеру или через блокирующую очередь) читает эту таблицу. Берет первый невыполненный шаг -> отправляет по сети -> апдейтит массив в БД -> коммит -> берет следующий шаг.

**Резюме:** Твоя идея с флагами рабочая и страхует от потери данных. Но чтобы не держать открытые транзакции и не блокировать потоки ожиданием сетевых ответов от 3-х систем, эту логику всегда выносят в фон (Outbox + Broker, либо Background Worker), перекладывая задачу повторных попыток (retries) на инфраструктуру.
