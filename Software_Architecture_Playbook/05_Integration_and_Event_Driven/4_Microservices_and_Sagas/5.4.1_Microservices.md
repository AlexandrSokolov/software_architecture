### What is SOA?
<details><summary>Show answer</summary>

**Service-oriented architecture** — an application built as services that call each other over the network.

</details>

### What is a microservices architecture?
<details><summary>Show answer</summary>

A refined evolution of SOA. Each service:
- has one well-defined purpose (e.g. S3 — file storage),
- be highly decoupled from other services.

</details>

### SOA vs microservices — what's the difference?
<details><summary>Show answer</summary>

Same idea — services over the network. They differ in size and coupling:
- **SOA** (2000s) — large services shared across the company. They often share a central database and talk through
  heavy middleware: a central bus (ESB) that routes and transforms messages.
- **Microservices** — one purpose and one team per service, deployed on their own, no shared data store. The network
  only carries messages; the logic stays in the services.

</details>

### What are the primary benefits of a microservices architecture?
<details><summary>Show answer</summary>

- **Independent deploys** — each team ships its service without waiting for the others.
- **Independent scaling** — each service gets the hardware it needs (more instances, more memory, a GPU), so you pay
  only for what it uses.
- **Encapsulation** — the API hides the internals, so owners can rewrite them without touching clients.
- **Technology freedom** — each team picks the language and database that fit its service.
- **Fault isolation** — a crash or memory leak in one service doesn't take the whole app down, if callers handle the
  failure.

</details>

### How do microservices store data?
<details><summary>Show answer</summary>

Each service has its own database; other services get its data only through its API or events. 
A shared database causes:
- **The schema becomes API** — every service depends on the table structure, so no one can change it alone.
- **Shared load** — one service's heavy queries slow down the others.

</details>

### Microservices — what do they cost?
<details><summary>Show answer</summary>

- **Operations** — each service needs its own deploys, scaling, logs, monitoring, alerts, and tracing to follow one
  request across services. Kubernetes is the usual base for this.
- **Testing** — to test one service you must run the services it calls, or fake them.
- **API Evolution** — API changes break clients, often found only in staging or production. 
  Needs backward compatibility or versions; API definitions (OpenAPI, gRPC) catch breaks earlier.
- **Network Reliability** — slower than an in-memory call, and they can time out or fail halfway.
- **Data Consistency** — no shared database, so no ACID commit across services: data becomes consistent
  eventually, and a failed step is undone by a compensating action (saga).

</details>

### What is serverless (FaaS)?
<details><summary>Show answer</summary>

You deploy short, stateless functions; the cloud provider runs one only when an event comes in (HTTP request, queue
message, database change, file upload). E.g. AWS Lambda, Azure Functions. Key traits:
- **No servers to manage** — the provider handles OS, runtime patches and capacity.
- **Scale to zero** — instances grow with demand and drop to zero when idle.
- **Pay per use** — billed per call and run time, not for idle time.

</details>

### Serverless vs microservices — what's the difference?
<details><summary>Show answer</summary>

Not opposites: microservices is how you split an app; serverless is how you run code. A microservice can run on FaaS.
- **Uptime and cost** — a service runs all the time (e.g. in a container), so you pay even when it's idle. A function
  starts per event, so you pay only for run time.
- **Management** — a service needs containers, Kubernetes and autoscaling rules. A function is just deployed code;
  the provider does the rest.
- **Speed** — a service stays warm and answers at once. A function scaled to zero has cold starts: the first call
  waits while a new instance boots. Functions also have run-time limits.
- **Fits** — a service: steady load, long connections. A function: bursty or rare work.

</details>
