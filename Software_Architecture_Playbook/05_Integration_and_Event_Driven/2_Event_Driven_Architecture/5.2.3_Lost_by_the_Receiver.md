- Auto-commit is on. When does it lose messages, and when does it not?

- The handler catches an exception, logs it, and confirms the message. What did you just do?

- You mark the message ID as "seen" before doing the work, then crash. What happens on redelivery?

- You skip updates that look older than your data, but the sender's clock was off. What is lost?
- A new message type or field arrives that your code doesn't know. Error or silent skip?

### How does a receiver lose a message?
<details><summary>Show answer</summary>

Every receiver-side loss has one root: the receiver said "done" — an ack, an offset commit, an HTTP 200 — while the
message was not yet safely handled. After that, nobody sends it again. Four ways it happens:

- **Confirmed too early** — before the work is saved:
  - [crash after confirm](#confirmed-on-receipt-then-crashed--whats-lost)
  - [in-memory pool](#work-handed-to-an-in-memory-pool--risk)
  - [webhook 200 first](#webhook-answered-200-first--whats-the-risk)
  - [slow work vs short timeout](#sender-waits-5-s-work-takes-30-s)
  - [DB commit fails](#confirmed-then-db-commit-failed--now-what)
  - [auto-ack buffer](#auto-ack-with-100-pushed-ahead--how-many-lost)
  - [deploy](#deploy-stops-the-service-mid-work--whats-lost)
- **Wrong position saved** — one Kafka offset per partition means "all below is done":
  - [auto-commit](#kafka-auto-commit--when-does-it-lose-messages)
  - [parallel threads](#ten-threads-one-partition--which-offset-to-save)
  - [partly failed batch](#batch-of-500-3-failed--commit-it)
  - [rebalance](#partition-taken-away-mid-work--whats-lost)
- **Error swallowed** — the error path ends in a confirm:
  - [catch and log](#catch-log-confirm--what-did-you-do)
  - [retries used up](#retries-used-up--where-does-the-message-go)
  - [Spring default](#spring-kafka-retries-used-up--default)
  - [can't parse](#message-cant-be-parsed--what-happens)
  - [dead-letter send fails](#dead-letter-send-fails--is-the-message-gone)
- **Dropped by your own logic** — confirmed correctly, but the code chose to skip it:
  - [seen before done](#marked-as-seen-then-crashed--redelivery)
  - [coarse dedup key](#two-messages-one-dedup-key--whats-lost)
  - [clock-based "older"](#skipped-as-older-but-the-clock-was-off)
  - [unknown type](#unknown-message-type-arrives--error-or-skip)

Handle: too early, wrong offset, swallowed error, wrong skip.

</details>

## When you confirm

### Confirmed on receipt, then crashed — what's lost?
<details><summary>Show answer</summary>

The message. A confirm tells the other side "I have it, you may forget it":

- **Queue** (RabbitMQ, JMS) — the broker deletes the message.
- **Kafka** — the group's saved offset moves past it; it stays in the log, but this group never reads it again.
- **Webhook** — the sender marks it delivered and stops retrying.

The crash comes after the confirm and before the work, so nobody has the message any more. This is
**at-most-once** delivery.

Fix: confirm only after the work is done and saved. Cost: a crash between work and confirm brings the message again,
so the handler must [handle duplicates](#marked-as-seen-then-crashed--redelivery) — **at-least-once** delivery.

Handle: a confirm is permission to forget; give it only when forgetting is safe.

</details>

### Work handed to an in-memory pool — risk?
<details><summary>Show answer</summary>

The listener puts the message on a thread pool's queue and returns. The container sees a normal return and confirms
(acks, or commits the offset). Now the only copy is a Java object in the heap:

- **Crash, OOM, deploy** — the pool's queue is gone; the broker already forgot those messages.
- **No back pressure** — the listener takes messages faster than the pool finishes them. The queue grows until memory
  runs out, which crashes the service and loses the whole queue.

Fixes:

- **Work on the listener thread** — scale with more partitions or consumers, not with a hidden pool.
- **Save first** — write the message to a DB table, confirm, let workers process from the table.
- **Confirm when the work ends** — manual ack from the worker. In Kafka, workers finish out of order, so the saved
  offset must [wait for gaps](#ten-threads-one-partition--which-offset-to-save).

</details>

### Webhook answered 200 first — what's the risk?
<details><summary>Show answer</summary>

To the sender, 200 means "delivered": it stops retrying. If your service crashes, fails on the DB, or is redeployed
before the work is done, the event is gone. Most senders don't keep events for you to fetch again, so often the only
way back is a nightly compare with the sender's data.

Rule: answer 200 only after the event is saved somewhere that survives a crash. If saving fails, answer 5xx, so the
sender retries. Doing the whole work before 200 is also correct, but
[may not fit the sender's timeout](#sender-waits-5-s-work-takes-30-s).

</details>

### Sender waits 5 s, work takes 30 s?
<details><summary>Show answer</summary>

Both obvious answers fail:

- **Work, then answer** — the sender times out after 5 s, counts it as failed, and retries: the work runs again.
  After enough failures some senders give up or disable your endpoint.
- **Answer, then work** — [lost on a crash](#webhook-answered-200-first--whats-the-risk).

Fix — save, answer, then work:

- **In the request** — insert the raw event into an inbox table (event ID unique, status `NEW`), answer 200. Takes
  milliseconds.
- **In a worker** — pick `NEW` rows, do the work, set `DONE` in the same transaction as the work's own writes.
- **Failures** — worker crash → the row is still `NEW` and is picked again; sender retry → the unique event ID
  rejects the copy.

Field term: **inbox pattern**.

</details>

### Confirmed, then DB commit failed — now what?
<details><summary>Show answer</summary>

The message is lost: the broker forgot it, and the DB rolled the change back. Typical causes: deadlock, unique key
violation, connection lost at commit.

The broker and the DB can't commit together, so the order decides what a crash costs:

- **Confirm, then commit** — commit fails → message lost.
- **Commit, then confirm** — confirm fails → message comes again → duplicate. Safe if the handler
  [records the message ID in the same transaction](#marked-as-seen-then-crashed--redelivery).

Spring gets the order right when the listener method is `@Transactional`: the DB commits when the method returns, and
the container acks or commits the offset after that.

Kafka-only option: store the consumer's offset in the DB, in the same transaction as the data, and read it from there
on start (`seek`). Then data and position can't disagree.

Handle: commit, then confirm — a duplicate can be fixed, a loss can't.

</details>

### Auto-ack with 100 pushed ahead — how many lost?
<details><summary>Show answer</summary>

Maybe far more than 100. RabbitMQ pushes messages to consumers ahead of time:

- **Auto-ack** — the broker treats each message as done the moment it sends it, and the prefetch limit doesn't apply:
  it sends as fast as the client takes them. Thousands can sit in the client's buffer. Crash → all lost, plus the one
  being processed.
- **Manual ack, prefetch 100** — up to 100 unacked messages wait in the client. Crash → the connection closes, and the
  broker puts them back in the queue for another consumer. Duplicates, not loss.

Watch the names: Spring AMQP's `AcknowledgeMode.AUTO` (the default) is a manual ack that Spring sends after the
listener returns — safe. RabbitMQ's auto-ack is Spring's `NONE`.

Kafka doesn't push: `poll()` brings up to 500 records into memory, but nothing is confirmed until the offset is
committed — [unless auto-commit does it](#kafka-auto-commit--when-does-it-lose-messages).

</details>

### Deploy stops the service mid-work — what's lost?
<details><summary>Show answer</summary>

Every message that was confirmed but still lives only in memory: queued in a thread pool, half-processed, held for a
batch write. Messages not yet confirmed come back to another instance.

A deploy normally sends SIGTERM, waits (Kubernetes: 30 s by default), then kills the process. A crash or an OOM kill
gives no warning at all.

Fixes:

- **Graceful shutdown** — on SIGTERM stop taking new messages, finish or hand back the ones in progress, confirm,
  then exit. Spring stops its listener containers when the context closes and waits for the current batch. The drain
  must fit in the grace period.
- **Never confirm what is only in memory** — the only fix that also covers a kill without warning.

Handle: drain on SIGTERM; against a hard kill only "confirm after save" helps.

</details>

## Which position you save

### Kafka auto-commit — when does it lose messages?
<details><summary>Show answer</summary>

`enable.auto.commit=true` is the plain client's default. The commit runs inside `poll()`: every
`auto.commit.interval.ms` (5 s), a call to `poll()` commits the offsets of everything returned by earlier polls.

- **No loss** — you process each batch fully on the polling thread before calling `poll()` again. Every committed
  record is already done. A crash costs only duplicates (up to 5 s of work).
- **Loss** — you hand records to other threads and call `poll()` at once. The next poll commits records still waiting
  in those threads; a crash loses them.

Spring Kafka turns auto-commit off by default and commits itself after the listener returns (`AckMode.BATCH`).

Handle: auto-commit is safe only if `poll()` comes after the work is done.

</details>

### Ten threads, one partition — which offset to save?
<details><summary>Show answer</summary>

Save 7. A committed offset is one number per partition, and it means "everything below this is done; start here":

- **Save 7** — after a restart 7, 8, 9, 10 are read again: 8–10 are duplicates.
- **Save 11** — 7 is never read again: lost.

Rule: commit the first offset that is not done yet. Each worker marks its offset done; a tracker moves the commit
forward only across an unbroken run of finished offsets.

Ready-made: Confluent Parallel Consumer tracks every message and commits up to the first gap; Spring Kafka manual
acks with `asyncAcks=true` hold the commit until the gap closes.

Cost: one stuck message holds the commit back for the whole partition. It must end in
[a retry or a dead-letter topic](#retries-used-up--where-does-the-message-go), never wait forever.

</details>

### Batch of 500, 3 failed — commit it?
<details><summary>Show answer</summary>

Not as is. Committing the batch moves the offset past all 500, so the 3 failed ones are never read again — lost, with
no error.

Two correct ways:

- **Commit up to the first failure** — commit everything before it, read again from it. Spring Kafka: throw
  `BatchListenerFailedException` with the failed record's index; the container commits the records before it and
  retries from it. Cost: records after the failure are processed again.
- **Move the failures aside** — send the 3 to a dead-letter topic, wait until the send is confirmed, then commit the
  batch.

Handle: an offset can't jump over a hole — stop at it, or fill it with a dead-letter copy.

</details>

### Partition taken away mid-work — what's lost?
<details><summary>Show answer</summary>

A rebalance moves the partition to another consumer, which starts at the last committed offset.

- **Loss** — an offset was committed for work still running in the background. Your consumer then drops that work or
  dies, and the new owner starts after it.
- **Duplicate** (more common) — you finished the work, but the commit fails (`CommitFailedException`) because the
  partition is no longer yours. The new owner does it again.

A frequent trigger: handling one `poll()` batch takes longer than `max.poll.interval.ms` (5 min), so the consumer is
thrown out of the group while still working.

Fixes:

- in `ConsumerRebalanceListener.onPartitionsRevoked`, finish or stop the work in progress and commit only what is
  done;
- keep a batch well under `max.poll.interval.ms` (fewer records per poll);
- cooperative rebalancing (`CooperativeStickyAssignor`, or the new consumer protocol in Kafka 4.0) takes away only the
  partitions that really move.

</details>

## When the error is swallowed

### Catch, log, confirm — what did you do?
<details><summary>Show answer</summary>

Dropped the message on purpose, leaving only a log line. The listener returned normally, so the container confirmed
it: no retry, no dead-letter copy. Logs rotate, and nobody searches them for lost orders.

Fix: let the exception reach the framework's error handler, which retries and then
[moves the message aside](#retries-used-up--where-does-the-message-go). Catch only to add context and rethrow, or for
a case you really handle (e.g. "already exists" on an idempotent insert).

Handle: a swallowed exception is a confirm.

</details>

### Retries used up — where does the message go?
<details><summary>Show answer</summary>

To a **dead-letter queue or topic** (DLQ, DLT) — never into a log line or nowhere. Keep what is needed to fix it: the
original payload (raw bytes), the error and stack trace, the source topic, partition and offset, the time.

Around it:

- **Owner** — the team of the consuming service; alert as soon as the DLQ is not empty.
- **Replay** — after the fix, send the messages back to the main topic or queue; the handler must accept duplicates.
- **Retention** — a Kafka DLT deletes by time like any topic; keep messages longer than anyone takes to look.
- **Before giving up** — tell the two kinds of failure apart: a DB that was down for a second needs retries with a
  growing wait; a bad payload will never work and should go to the DLQ at once.

RabbitMQ has it built in: a dead-letter exchange gets messages that were rejected without requeue, or expired. Kafka
has no broker-side DLQ — the client or framework writes to another topic.

</details>

### Spring Kafka retries used up — default?
<details><summary>Show answer</summary>

The record is logged and skipped — lost. `DefaultErrorHandler` (default since Spring Kafka 2.8) tries 10 times in
total with no wait (`FixedBackOff(0, 9)`), then calls its recoverer. The default recoverer only logs the record at
ERROR, and the offset is committed.

To keep it: give the handler a `DeadLetterPublishingRecoverer`. It sends the record to `<topic>.DLT` (same partition
number), with the error in headers.

Some exceptions skip the retries and go to the recoverer at once, since a retry can't fix them: e.g.
`DeserializationException`, `MessageConversionException`, `ClassCastException`.

These retries block the partition while they run. For long waits, non-blocking retries (`@RetryableTopic`) move the
record through retry topics and then to a `-dlt` topic.

</details>

### Message can't be parsed — what happens?
<details><summary>Show answer</summary>

In Kafka the bytes are turned into objects inside `poll()`, before your code runs. A bad record makes `poll()` throw
(`RecordDeserializationException`, which carries its partition and offset):

- **Plain client** — your loop must catch it and `seek` past the record. Otherwise every `poll()` hits it again and
  the partition is stuck: the messages behind it never arrive.
- **Spring Kafka** — wrap the real deserializer in `ErrorHandlingDeserializer`. It catches the failure and passes the
  record on with the error attached; the error handler sends it to the recoverer without retries.

Loss is decided by the recoverer: log-and-skip loses it, a DLT keeps it. Store the raw bytes — there is no parsed form.

Handle: a retry can't fix bad bytes; move them aside and keep the partition moving.

</details>

### Dead-letter send fails — is the message gone?
<details><summary>Show answer</summary>

Only if you commit the original anyway. The DLT send is a normal produce and can fail: broker down, record too large,
no permission on the topic.

Rule: commit the original offset only after the DLT send is confirmed (`acks=all` on that producer). If the send
fails, don't commit; the record is read again and the error path runs again.

Spring Kafka: `DeadLetterPublishingRecoverer` waits for the send result; if publishing fails, the error handler
doesn't commit, and the record is delivered again. A fire-and-forget DLT send in your own code loses it.

Two more traps:

- the DLT is usually in the same cluster, so when Kafka is down both fail — the consumer stalls, which beats losing;
- a DLT with short retention [loses the messages later](#retries-used-up--where-does-the-message-go).

</details>

## When your own code drops it

### Marked as seen, then crashed — redelivery?
<details><summary>Show answer</summary>

The redelivered copy is skipped as a duplicate, and the work never happens. Each step causes the next:

- **ID saved** — the message ID is inserted into a "processed" table and committed.
- **Crash** — before the work.
- **Copy arrives** — ID found → "already done" → confirm → lost.

Fix: record the ID in the same DB transaction as the work. Commit → both happened; rollback → neither, and the retry
finds no ID.

When the work is outside your DB (a call to a payment API), one transaction is impossible. Use a status instead:
`PENDING` before the call, `DONE` after. A copy that finds `PENDING` means "maybe done" → call again with the same
idempotency key, so the API itself drops the copy.

Handle: "seen" must mean "done" — write both in one commit.

</details>

### Two messages, one dedup key — what's lost?
<details><summary>Show answer</summary>

The second message. The dedup check finds the key, decides "duplicate", and confirms without doing the work.

How a key gets too coarse:

- **Entity ID only** — `orderId` as the key: "order paid" and "order shipped" share it; "shipped" is dropped.
- **Business data** — "same customer, same amount, same day": two real equal payments look like one.
- **IDs that repeat** — the sender's counter restarts after a deploy, or one ID covers a whole batch.

Fix: a unique message ID made once by the sender when the event is created (UUID), kept the same on every retry. Or a
key that names the change itself: entity ID + event type + version.

Handle: key too fine → duplicates slip through; key too coarse → real messages are dropped.

</details>

### Skipped as older, but the clock was off?
<details><summary>Show answer</summary>

The newer update is lost. The rule "drop an update whose timestamp is older than the stored one" trusts clocks.
Clocks on different machines can be seconds apart, and a clock can jump back after a sync. Then a newer change
carries a smaller timestamp and is dropped — confirmed, with no error. Two updates with the same timestamp lose one
too.

Fix: compare a version that one owner hands out in order — a version column the source DB increments, or a sequence
number per entity. Inside one Kafka partition, the offset gives the order of all messages with the same key.

Handle: order by a counter from one owner, never by clocks of many machines.

</details>

### Unknown message type arrives — error or skip?
<details><summary>Show answer</summary>

- **Unknown type → park it.** It usually lands in a `switch` default that logs and returns, so it is confirmed and
  gone. After the sender deploys a new event type, every such event is dropped silently until someone notices. Fix:
  send unknown types to the DLQ or a parking topic and alert; replay them once your code knows the type.
- **Unknown field → ignore it.** That lets the sender add optional fields without breaking you (forward
  compatibility). The risk: a new field that changes meaning (e.g. `currency` added next to an amount) is ignored, and
  your code computes the wrong result. A renamed field arrives as a missing one — `null`.

Jackson: a plain `ObjectMapper` fails on unknown fields (`FAIL_ON_UNKNOWN_PROPERTIES=true`); the one Spring Boot
configures ignores them.

For both: check schema compatibility before deploy (schema registry), and count unknown types and fields in metrics.

Handle: unknown field → ignore; unknown type → park, never drop.

</details>
