### Sender stopped retrying — event missed?
<details><summary>Show answer</summary>

Find out:
- **Sender's side** — most webhook senders log failed deliveries and alert when they disable an endpoint.
- **Your side** — a [gap in versions](#missing-events--notice-before-customers) (got v5 after v3), or no events for
  longer than usual.

Fix:
- ask the sender to resend — many offer redelivery from a dashboard or an API;
- fetch the current state of the affected records from the sender's API;
- run the [nightly comparison](#nightly-check-without-pulling-all-data).

Events can't prove that nothing is missing; you need a way to pull data back from the sender.

</details>

### Endpoint down three hours — recover what?
<details><summary>Show answer</summary>

It depends on the sender's retry window:
- **Retries longer than 3 hours** (often a day or more) — nothing lost, but a flood arrives when you are back, often out
  of order.
- **Shorter, or no retries** — the events of those 3 hours are gone from the push.

Get them back:
- ask the sender to resend that window, or pull "changed since T" from its API;
- otherwise run the [nightly comparison](#nightly-check-without-pulling-all-data) for that window.

Know each sender's retry window: it is how long you can be down without losing data.

</details>

### Nightly check without pulling all data?
<details><summary>Show answer</summary>

**Reconciliation** — compare your data with the source of truth and fix the differences. To keep it small:
- **Only what changed** — ask the sender for records with `updated_at` after the last run (minus a safety margin).
- **Versions, not records** — compare pairs of (ID, version). Fetch full data only where they differ.
- **Summaries first** — per day or ID range, compare a count and a hash; look closer only at ranges that differ.

Then fetch and apply what is missing or newer, and flag records you have but the sender doesn't.

Narrow by time, then by summary; fetch full data only where the two sides disagree.

</details>

### Nightly check and live event overlap?
<details><summary>Show answer</summary>

Both paths must write the same way, keyed by record and version:
- write "set the record to version N" (upsert), not "apply this change" — doing it twice is harmless;
- skip if your stored version is already N or higher — this also stops an old nightly result from overwriting a newer
  live event.

A message-ID check doesn't help: the two paths carry different IDs, so
[check by business key](#duplicate-check-message-id-or-business-data).

Make both paths safe to repeat on (record, version), and the overlap stops mattering.

</details>

### Missing events — notice before customers?
<details><summary>Show answer</summary>

- **Gaps in versions** — last was v5, now v7 → v6 is missing.
- **Silence** — alert when an event type drops below its usual rate for that hour (no orders for 20 minutes on a
  weekday).
- **Broken flows** — an order "paid" but not "shipped" after N hours.
- **Nightly fixes** — count what the [nightly comparison](#nightly-check-without-pulling-all-data) had to fix; a rising
  count means events are being lost.
- **Sender alerts** — failed deliveries, a disabled endpoint.

Watch for what should have arrived, not only for errors on what did.

</details>

### Why events if nightly check exists?
<details><summary>Show answer</summary>

- **Speed** — events arrive in seconds; the nightly check is up to a day late. Order confirmations, stock and payments
  can't wait a day.
- **Load** — events carry only what changed, when it changed. Pulling everything often would be heavy for both sides.
- **Small nightly work** — events deliver almost everything, so the nightly check fixes only a handful of records.

They do different jobs: events are the fast path; the nightly check is the safety net for the rare miss.

</details>

## Lost Messages Where and When

### Where can a message get lost?
<details><summary>Show answer</summary>

At every hop of its way:

- **[Sender](#sender)** — the DB change is saved, but the message never reaches the broker, and nobody notices.
- **[Broker](2_Lost_in_the_Broker.md)** — it confirmed, but the message sat on too few disks or copies when a node died;
  or the broker never kept it for you, or deleted it before you read it.
- **[Receiver](3_Lost_on_Receive.md)** — it confirmed (ack, saved offset, `200 OK`) before the work was done, or caught
  an error and confirmed anyway. A poller can also [skip rows](Polling_for_Changes.md) and never see them.

Trigger: each hop loses the message the same way — it says "done" before the message is safe at the next step.

</details>

### When is losing a message fine?
<details><summary>Show answer</summary>

When the next message makes it useless anyway:

- A courier's location every 5 seconds — a missed point is replaced by the next one.
- A live price, a metric sample, an "online" ping — only the newest value matters.

This works only if each message carries the full current value, not a change. "Balance is 50" can be lost — the next
message fixes it. "Add 10" or "order placed" can't — that change exists nowhere else.

What you gain: send once, no retries, no waiting for confirms, no extra copies, no duplicates to handle. This is
**at-most-once** delivery — each message arrives once or not at all.

</details>

## Lost Messages on Send

### Crash between DB commit and broker publish
<details><summary>Show answer</summary>

**Dual-write problem:** the DB and the broker commit separately, so a crash between them splits them (Kafka has no XA).

- **DB first, crash before publish:** the event was only in memory and is lost. Receivers never learn about the change.
- **Publish first, crash before commit:** the DB rolls back → **phantom event**. Receivers act on an entity that does
  not exist.

**Fix:** the app writes only to the DB; the event goes out later from what the DB saved.
- **Transactional Outbox:** insert the event into an `outbox` table in the same transaction as the entity.
  Both save, or neither. A relay reads the table and publishes to the broker.
- **CDC (Change Data Capture):** a tool (like Debezium) reads committed changes from the database's log (WAL, binlog)
  and turns them into events.

**Cost:**
- **Infrastructure:** a relay or a CDC tool to run.
- **Delay:** the event reaches the broker a moment after the commit.
- **Duplicates:** the relay publishes, gets the ACK, and crashes before deleting the outbox row. On restart it sends
  the event again. Receivers must handle duplicates.

</details>

### DB save and broker send in one @Transactional method — safe?
<details><summary>Show answer</summary>

No. The commit runs when the method returns, which is after the send.

```java
@Transactional
void placeOrder(Order o) {
  repo.save(o);
  kafka.send("orders", event).get(); // message is out here
} // commit here
```

- **Helps only if the send fails:** exception → rollback → nothing saved, nothing sent.
- **Commit fails or app crashes after the send:** DB rolls back, message is already out → phantom event.
- **Async send** (no `.get()`): the failure arrives after the commit → no rollback, event lost.
- **Send after commit** (`@TransactionalEventListener(phase = AFTER_COMMIT)`): crash between → event lost.

No order fixes it: rollback covers only the DB, not the broker. Fix: [outbox or CDC](#crash-between-db-commit-and-broker-publish).

</details>

### No broker confirm (Fire and Forget) — what can be lost?
<details><summary>Show answer</summary>

**Any message that fails to safely reach the broker.** Because the sender does not wait for an acknowledgment (ACK), it
assumes success and never retries. The loss is completely silent.

Messages are permanently lost if:

- Network drops while the message is in transit.
- Broker is down (e.g., restarting or changing leaders).
- Broker rejects it (e.g., disk is full, message is too large).

Examples: Kafka with `acks=0`; RabbitMQ without publisher confirms.

The trade-off:

- **Gain:** Maximum throughput and lowest latency. Use only for data [you can afford to lose](#when-is-losing-a-message-fine)
  (like click tracking).
- **The fix:** Waiting for an ACK and retrying stops the loss, but introduces duplicates (if the ACK itself drops in the
  network, the sender resends).

</details>

### Async send failure only logged — what happens?
<details><summary>Show answer</summary>

```java
producer.send(record, (meta, ex) -> {
  if (ex != null) log.error("send failed", ex); // the message is gone; nothing retries it
});
```

The async `send()` runs in the background. If the client's internal retries time out,
it passes the error to the callback. The callback logs it, and that is the end of the message.
Because the local database transaction was already committed, the systems are now permanently out of sync.


**Why not retry inside the callback?**
Retrying from inside the callback does not help: that retry lives in memory and dies with the process.


**The Fixes:**
- **Minimal fix (Blocking):** Call `send(...).get()` to wait for the broker's ACK.
  This throws the error back to the caller instead of swallowing it.
  However, if the DB was already committed, you still suffer from
  [the Dual-Write problem](#crash-between-db-commit-and-broker-publish).
- **Real fix:** Use the **Transactional Outbox** pattern. Keep the event in an outbox row;
  the relay retries it until the broker confirms.


**The Cost:**
- Blocking with `.get()` adds network latency to every call;
- the outbox adds a table and a relay.

</details>

### App stops with messages still buffered?
<details><summary>Show answer</summary>

**Graceful vs. Hard Shutdown**
Async `send()` only puts the message into the client's memory buffer and returns.
A background thread sends the buffer in batches shortly after.
Stop the app before it does, and those messages are gone, even though `send()` returned without an error.

**The Fixes:**
- **Graceful Shutdown (SIGTERM):** call `producer.close(timeout)` (or `flush()`) on shutdown.
  This blocks the app from exiting until the buffer is fully sent and confirmed by the broker.
  Give it a time limit: if the broker is down, waiting forever blocks the shutdown, and giving up loses the rest.
- **Hard stop** (`kill -9`, out of memory, power loss): no hook runs, and the buffer is lost. Only an event kept in an
  [outbox row](#crash-between-db-commit-and-broker-publish) until the broker confirms survives this.

Trade-off: a bigger buffer and a longer batching wait give more throughput, but more messages sit in memory at risk.

</details>

### Outbox Relay marks as "sent", then crashes?
<details><summary>Show answer</summary>

If the relay reads the outbox row, marks it as "sent" (or deletes it), and then crashes before the broker confirms,
the event is permanently lost. On restart, the relay ignores the row, assuming it succeeded.
The outbox just failed its primary purpose.


**Fix:**
Strict ordering. You must only delete or mark the row as "sent" after receiving the broker's ACK
(e.g., inside the success callback). For async batch sending, process DB updates based on individual ACKs,
not just because the batch was read into memory.


**Cost:** a crash after the confirm but before the mark sends the row again, which is a duplicate.
This is why the Outbox pattern inherently guarantees At-Least-Once delivery and
strictly requires **idempotent consumers** - receivers must drop copies.

</details>
