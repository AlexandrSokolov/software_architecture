### Kafka broker — architecture?
<details><summary>Show answer</summary>

Kafka has two architectural levels:

- **Outside — Producers & Consumers.** Your services use Kafka. A **producer** sends a message to a topic 
  ("order updated"); **consumers** pull it. To your code the broker looks like one thing.
  - **Goal:** Decouple external microservices and enable asynchronous communication.
  - **Questions:** who gets the message, duplicates, order, consumer groups.
- **Inside — the cluster (leader & followers).**
  It works like a distributed database: each partition is stored on several machines (brokers).
  One broker is the **leader** of the partition; the other brokers are **followers**: they copy from the leader.
  The client library finds the leader itself: the producer writes to it, and consumers read from it too (by default).
  - **Goal:** Data durability and High Availability of the broker itself.
  - **Questions:** a broker died — is the message safe, and can producers still write?

Where the levels meet:

- The producer writes to the leader, and consumers read from the leader too (by default).
- A consumer sees a message only after every in-sync follower (one that keeps up with the leader) has copied it, 
  so it never reads a message that a leader crash could still erase.

This is single-leader replication, the same as a database with replicas: producers and consumers are its clients,
leader and followers are how it stores data. Followers fetch from the leader the same way consumers do, but they
keep a copy instead of processing the message.

</details>

### Consumer reads — which broker serves them?
<details><summary>Show answer</summary>

Two ways in Kafka:

- [**The leader**](#reading-from-the-leader--how) — the default in every version.
- [**A nearby follower**](#reading-from-a-nearby-follower--how) — opt-in since Kafka 2.4, to read inside your own
  zone.

</details>

### Reading from the leader — how?
<details><summary>Show answer</summary>

- The consumer reads each partition from its leader — the same broker the producer writes to.
- It sees only messages that every in-sync follower has already copied.
- Config: none — this is the default. Before Kafka 2.4 it was the only way.

</details>

### Reading from a nearby follower — how?
<details><summary>Show answer</summary>

Why: in the cloud a cluster spans several data centers (availability zones). Reading from a leader in another zone
costs network money and time.

- The consumer asks the leader; the leader names a follower in the consumer's zone; the consumer reads from it.
- Config:
  - each broker: `broker.rack=<its zone>`
  - each broker: `replica.selector.class=org.apache.kafka.common.replica.RackAwareReplicaSelector`
  - consumer: `client.rack=<its zone>`
- Cost: a follower learns which messages are safe to show a moment after the leader does, so messages reach the
  consumer slightly later.

</details>

### How can a broker lose a message?
<details><summary>Show answer</summary>

- **Too few copies** — the ACK came before the message was safe on enough machines:
  - [the leader dies right after confirming](#kafka-leader-confirmed-then-died--why-is-it-lost)
  - ["all copies" shrinks to one](#kafka-leader-waits-for-all-copies--how-is-it-lost)
  - [an out-of-date copy takes over](#kafka-out-of-date-copy-becomes-leader--whats-lost)
  - [the leader is cut off but keeps taking writes](#kafka-leader-cut-off-from-the-cluster--whats-lost)
- **Only in memory** — confirmed, but not yet on disk:
  - [power cut on all copies](#kafka-power-cut-on-all-copies--whats-lost)
  - [the broker restarts](#rabbitmq-restarts--why-is-the-queue-empty)
- **Deleted by a rule** — removed on time or size, read or not:
  - [kept shorter than the consumer was down](#kafka-consumer-down-longer-than-messages-are-kept)
  - [the saved read position is deleted](#kafka-group-with-no-saved-position--where-does-it-start)
  - [the queue is full or the message too old](#rabbitmq-queue-full-or-message-too-old--what-happens)
- **Nobody to deliver to** — the broker had nowhere to put it:
  - [the subscriber was offline](#subscriber-offline-during-publish--gets-it-later)
  - [no queue matched](#rabbitmq-send-confirmed-but-no-queue-got-it--why)

A message survives only if it is on enough disks, kept long enough, and has somewhere to go.

</details>

### Broker acked, then died — why lost?
<details><summary>Show answer</summary>

Each Kafka partition is stored on several brokers:

- **Leader** — producers write to it, and it sends the ACK.
- **Followers** — they fetch new messages from the leader and add them to their own copy.

This is single-leader replication, the same as a database with read replicas. When the leader sends the ACK depends
on the producer's `acks` setting.

**`acks=1`** — the ACK goes out once the message is in the leader's own log; followers copy it a moment later. If
the leader dies in between:

- A follower that never got the message becomes the new leader.
- The old leader comes back as a follower and cuts its log to match the new leader, so its copy is deleted too.
- The producer already got the ACK, so it never resends. The message is gone, and nobody gets an error.

**`acks=all`** — the ACK goes out only after every follower that keeps up with the leader (the **in-sync
replicas**, ISR) has the message. The new leader is picked from them, so it has the message too. Two gaps remain:

- The ISR shrank to the leader alone (followers fell behind or died), so `acks=all` waited for nobody else — same
  as `acks=1`.
- No in-sync follower is alive, and an out-of-sync one is made leader anyway.

</details>

### Broker crash — how to keep acked messages?
<details><summary>Show answer</summary>

- **`acks=all`** (producer) — ACK only after every in-sync replica has the message. Default since Kafka 3.0;
  older clients default to `acks=1`.
- **`min.insync.replicas=2`** (topic or broker), with 3 copies of each partition — the leader accepts an `acks=all`
  write only if at least 2 replicas, itself included, are in sync. Otherwise the write fails and the producer
  retries. So every ACKed message is on at least 2 brokers. Default is 1, which lets `acks=all` fall back to
  `acks=1`.
- **`unclean.leader.election.enable=false`** (default) — only an in-sync follower can become leader. `true` brings
  the partition back sooner but loses the messages the new leader lacks.

Speed — Kafka has no sync or async followers. All followers fetch the same way; the producer's `acks` decides
whether the leader waits. Waiting for every follower would be slow, so:

- **A follower that falls behind is dropped from the ISR**, and the leader stops waiting for it. It rejoins once it
  catches up. The cost that stays: each `acks=all` send waits for the slowest follower still in the ISR.
- **`min.insync.replicas` is the floor.** 3 copies with a floor of 2 is close to semi-synchronous replication: each
  ACK means the leader and at least one follower have the message, and one broker can be down while writes still
  go through.

</details>

### Kafka leader waits for all copies — how is it lost?
<details><summary>Show answer</summary>

`acks=all` waits for all **in-sync** copies, not all copies. A follower that falls behind (slow disk, long GC pause,
network trouble) is dropped from the in-sync list. The list can shrink to the leader alone. Then the ACK comes when one
machine has the message. If that machine's disk is lost, or an
[out-of-date copy takes over](#kafka-out-of-date-copy-becomes-leader--whats-lost), the message is gone.

**Fix:** `min.insync.replicas=2` (with 3 copies; it applies only with `acks=all`). When fewer than 2 copies are in sync,
the leader refuses the write, and the producer gets an error instead of an ACK. Cost: writes fail while followers are
behind. You give up writing for a while to avoid losing confirmed messages.

</details>

### Kafka out-of-date copy becomes leader — what's lost?
<details><summary>Show answer</summary>

The leader dies, and every copy left had fallen behind (none is in sync). If one of them is allowed to lead
(`unclean.leader.election.enable=true`), every message the old leader had and this copy didn't is gone, even ones
confirmed with `acks=all`. When the old leader returns, it cuts those messages from its log to match.

The other choice is to wait for an in-sync copy to come back. Nothing is lost, but the partition takes no reads or
writes until then. Kafka waits by default (`false`): it picks not losing data over staying up.

</details>

### Kafka leader cut off from the cluster — what's lost?
<details><summary>Show answer</summary>

The leader loses contact with the controller and the other brokers, but some producers can still reach it. The
controller picks a new leader from the in-sync copies. The old leader doesn't know yet and keeps taking writes, so for
a while there are two leaders (**split brain**):

- **`acks=1`:** the old leader confirms each write with only its own copy. When it reconnects, it learns about the new
  leader and cuts those messages from its log → confirmed messages are lost.
- **`acks=all`:** the followers now copy from the new leader, and the old leader can't shrink the in-sync list on its
  own; that change needs the controller. No write gets all its copies, so the producer gets a timeout, retries, and
  finds the new leader. Nothing confirmed is lost.

</details>

### Kafka power cut on all copies — what's lost?
<details><summary>Show answer</summary>

Kafka confirms a message once it is in the operating system's memory (the page cache). The OS writes it to disk a bit
later. Kafka doesn't force each write to disk; it counts on copies on other machines instead.

If all copies lose power at the same moment (same rack, same power line), every message not yet on disk is lost on all
of them, even ones confirmed with `acks=all`.

**Fix:** put the copies in different racks or zones (`broker.rack`), so one power cut can't hit them all. Forcing every
write to disk (`flush.messages=1`) also works, but makes writes much slower.

</details>

### Kafka consumer down longer than messages are kept?
<details><summary>Show answer</summary>

Kafka deletes old messages by time or size (`retention.ms`, `retention.bytes`), whether anyone read them or not. A
consumer that was down longer comes back with a saved position that points at deleted messages.
[`auto.offset.reset`](#kafka-group-with-no-saved-position--where-does-it-start) decides where it continues:

- `earliest` → the oldest message still kept. The deleted ones are skipped.
- `latest` → the end. Everything still kept is skipped too.
- `none` → an error; the consumer stops.

Both skips are silent. **Fix:** keep messages longer than the longest outage you plan for, and alert on consumer lag
well before it reaches that limit.

</details>

### Kafka group with no saved position — where does it start?
<details><summary>Show answer</summary>

A consumer group has no saved position when it is new, or when the broker deleted it. The broker deletes a group's
positions once the group has had no running consumers for `offsets.retention.minutes`.

Then `auto.offset.reset` decides. Its default is `latest`: start at the end. Every message already in the topic is
skipped, with no error.

**Fix:**

- set `earliest` if the group must see messages that are already there;
- set `offsets.retention.minutes` longer than the group's longest planned downtime.

</details>

### Subscriber offline during publish — gets it later?
<details><summary>Show answer</summary>

Only if something kept the messages for it.

- **No** — the broker delivers only to who is connected right now. Offline → missed for good:
  - JMS non-durable subscriber
  - Redis Pub/Sub
  - RabbitMQ queue deleted when its consumer disconnects (exclusive or auto-delete)
- **Yes** — the messages are kept until the subscriber comes back:
  - JMS durable subscription
  - durable RabbitMQ queue that stays bound while the subscriber is away
  - Kafka: the consumer continues from its saved position, but only
    [as long as messages are kept](#kafka-consumer-down-longer-than-messages-are-kept)

Cost of yes, for queues: messages pile up for a subscriber that never comes back.

</details>
