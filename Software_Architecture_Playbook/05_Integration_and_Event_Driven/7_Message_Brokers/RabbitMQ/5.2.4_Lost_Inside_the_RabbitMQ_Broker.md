
### RabbitMQ restarts — why is the queue empty?
<details><summary>Show answer</summary>

The messages were sent as non-persistent. In a classic queue, two separate settings decide what survives a restart:

- **Durable queue** — the queue itself comes back. Not durable → the queue is gone, with its messages.
- **Persistent message** (`delivery_mode=2`) — the message comes back. Non-persistent messages are thrown away at
  restart, even in a durable queue.

You need both. Cost: every persistent message must be written to disk, so sending is slower.

</details>


### RabbitMQ queue full or message too old — what happens?
<details><summary>Show answer</summary>

A queue can have limits: message age (`x-message-ttl`) and length (`x-max-length`). When one is hit, the broker removes
messages:

- **Too old** → the message is removed.
- **Queue full** → by default the oldest message is removed to make room (`drop-head`).

With no dead-letter exchange, removed messages are gone, with no error to anyone.

**Fix:**

- set a dead-letter exchange (`x-dead-letter-exchange`): removed messages go there, where you can see and replay them;
- or set overflow to `reject-publish`: a full queue refuses new messages, and a publisher with confirms on gets a nack.

</details>


### RabbitMQ send confirmed, but no queue got it — why?
<details><summary>Show answer</summary>

The publisher sends to an exchange, not to a queue. The exchange copies the message to every queue bound with a matching
key. No matching queue → the exchange drops it. Publisher confirms still ACK it: the ACK means "the broker took it",
not "a queue got it".

**Fix:**

- `mandatory=true`: the broker sends an unroutable message back to the publisher (`basic.return`);
- an alternate exchange: catches every message that matched no queue.

</details>
