## Retry safely

### Which HTTP methods are safe to retry?
<details><summary>Show answer</summary>

- **GET, HEAD** — read only.
- **PUT, DELETE** — idempotent by the HTTP spec: a second call leaves the same state ("set status to PAID", "delete
  order 42").
- **POST, PATCH** — not guaranteed: a second POST creates a second order.

The spec is a promise, not a check: a PUT that adds 10 to a counter is not idempotent. Retry by what the endpoint
really does.

</details>

### POST retried — how does the server avoid a second order?
<details><summary>Show answer</summary>

The client sends an `Idempotency-Key` header, the same on every retry. The server:

- **First request** — saves the key, does the work, saves the response with the key.
- **Retry, work done** — returns the saved response and does nothing again.
- **Retry while the first is still running** — answers 409 (or waits); never starts a second run.

The key and the work's result must be saved in one transaction, or a crash between them repeats the work.

The server remembers the key and replays the first answer.

</details>

### Idempotency key — who creates it, and when?
<details><summary>Show answer</summary>

The client, once per business action — not once per HTTP attempt:

- **New key per attempt** (a new UUID on each retry) — the server sees new requests → duplicates.
- **Key kept only in memory** — your service crashes, restarts, retries with a new key → a duplicate.

Save the key with the business row before the first call (e.g. the order in
[`PAYMENT_PENDING`](5.3.2_Remote_Call_&_Transaction.md#payment-call-in-the-middle-of-an-order--how) with its key),
and reuse it on every retry, from any instance.

The key belongs to the action, so it must outlive the process.

</details>

### Same idempotency key, different body?
<details><summary>Show answer</summary>

A client bug, or a key reused for a new order. If the server replays the old response, the client thinks the new
request succeeded, and nothing was done.

Fix on the server: store a hash of the request body with the key. Same key with a different body → an error (422),
not a replay.

</details>

### Key remembered for a limited time — when does it bite?
<details><summary>Show answer</summary>

Servers drop stored keys after a while (Stripe: after at least 24 hours). A retry after that is a new request:

- a sweeper retries a payment stuck in `PENDING` for two days;
- a reconciliation job resends a week later.

Before retrying an old action, [check its status](#call-timed-out--retry-or-check-status) instead of trusting the key.

An idempotency key protects only inside its time window.

</details>

### API accepts no request ID — avoid doing it twice?
<details><summary>Show answer</summary>

- **Your reference in the request** — many APIs take your own order number and reject a second request with the same
  one (it is unique on their side). That is a key under another name.
- **Check first** — search by your reference ("is there a payment for order 42?") before retrying. A small gap is
  left: the first call may still be running.
- **Accept the duplicate** where it is harmless, or [compare both sides later](5.3.6_Reconciliation.md) and undo it.

</details>

## Unknown outcome

### Call timed out — retry or check status?
<details><summary>Show answer</summary>

After a timeout the outcome is [unknown](5.3.1_Dual_Write.md#db-saved-remote-call-timed-out--now-what):

- **The API takes an idempotency key** — retry with the same key; if the work was done, the server replays the result.
- **No key** — first ask for the status by your reference (`GET /payments?orderId=42`); retry only on "not found".

Turn "unknown" into "done" or "not done" before acting again.

</details>

## Repeated user action

### Double click on "Pay" — charge once?
<details><summary>Show answer</summary>

Disabling the button helps, but a second tab, a browser retry, or a mobile app resend still sends two requests.

Fix on the server: the checkout gets a key when it opens (or the order is created first and its ID is the key), and
both clicks send the same key → the second request
[gets the first answer](#post-retried--how-does-the-server-avoid-a-second-order).

The key belongs to the user's action and is created before the first click.

</details>

## Long work

### Work takes minutes — how does the API answer?
<details><summary>Show answer</summary>

Don't hold the request open: the client times out and retries, and the work runs twice.

- Answer `202 Accepted` at once, with a job ID and a status URL (`Location: /jobs/17`).
- The client gets the result by [polling the status or by a callback](#status-polling-or-callback).

Save the job before answering 202, or a crash loses it — the same rule as the
[inbox](5.3.4_Receiver_Side.md#inbox-or-idempotent-consumer--difference).

</details>

### Status polling or callback?
<details><summary>Show answer</summary>

- **Polling** (`GET /jobs/17` until done) — simple, works through firewalls; costs requests and adds up to one poll
  interval of delay.
- **Callback** (the server calls your webhook when done) — fast, no wasted requests; but now you are a webhook
  receiver: callbacks can be lost, duplicated, or arrive before you saved the job ID → the
  [receiver side rules](5.3.4_Receiver_Side.md) apply.

Usual: a callback for speed, polling as the fallback when no callback comes.

</details>
