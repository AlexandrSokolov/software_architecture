# Dual Write

### Dual write — what are the concerns?
<details><summary>Show answer</summary>

## What and where

### Save to DB, then send to Kafka — what problem?
<details><summary>Show answer</summary>

[**Dual write**](#what-is-a-dual-write) — two systems written in one action, each commits on its own; a crash between
leaves one done and the other not.

</details>

### What is a dual write?
<details><summary>Show answer</summary>

Your code changes two systems in one business action, and each system commits on its own. Example: send
"OrderPlaced" to Kafka, then call the payment API. Nothing makes both succeed or both fail.

- **Not only DB + something** — any two systems that don't share a commit: two brokers, two REST calls, a broker and
  a cache.
- **Not only two** — "dual" means at least two; ten writes from one action are the same problem with more places to
  break.

</details>

### Dual write — which systems can take part?
<details><summary>Show answer</summary>

Any system that commits on its own:

- **Stores — data kept**:
  - DB — your own, a second datasource, an in-memory one (Redis, Hazelcast);
  - cache — DB updated, cache not cleared → readers get old data;
  - search index — Elasticsearch next to the DB;
  - file storage — S3 file and its DB row.
- **Sends — something goes out**:
  - broker — Kafka, RabbitMQ;
  - remote call — REST, gRPC;
  - email / SMS — can't be taken back once sent.

Check: one action, two systems, no shared commit.

</details>

## How it breaks

### DB commit and broker send — what can go wrong?
<details><summary>Show answer</summary>

`@Transactional` covers only the DB; the broker commits on its own. A crash or a failure between the two steps leaves
one done and the other not:

- **[Phantom event](#broker-send-before-db-commit--crash-between)** — send first, then the commit fails → the message
  is out, the order doesn't exist.
- **[Lost event](#db-commit-before-broker-send--crash-between)** — commit first, then the send fails → the order is
  saved, no message.
- **[Both](#async-broker-send-in-transactional--what-breaks)** — an async send, nobody waits for its result.

No order of the two steps fixes it; the order only picks how it breaks.

</details>

### Broker send before DB commit — crash between?
<details><summary>Show answer</summary>

```java
@Transactional
void placeOrder(Order o) {
  repo.save(o);
  kafka.send("orders", event).get(); // message is out here
} // DB commit here
```

The commit fails or the app crashes after the send → the DB rolls back, but the message is already out → **phantom
event**: receivers act on an order that doesn't exist. A sent message can't be taken back.

</details>

### DB commit before broker send — crash between?
<details><summary>Show answer</summary>

**Send after the transactional call:**

```java
void placeOrder(Order o) {
  orderService.save(o);              // own transaction: DB commit here
  kafka.send("orders", event).get(); // crash or send failure → no message
}
```

**Send in an after-commit listener:**

```java
@Transactional
void placeOrder(Order o) {
  repo.save(o);
  events.publishEvent(new OrderPlaced(o.getId()));
} // DB commit here

@TransactionalEventListener // phase = AFTER_COMMIT by default
void on(OrderPlaced e) {
  kafka.send("orders", e).get(); // crash or send failure → no message
}
```

The send fails or the app crashes after the commit → the order is saved, no message → **lost event**: receivers
never learn about the order. Between the commit and the send, the event lives only in memory; nothing remembers that
the send is still to do.

</details>

### Async broker send in @Transactional — what breaks?
<details><summary>Show answer</summary>

```java
@Transactional
void placeOrder(Order o) {
  repo.save(o);
  kafka.send("orders", event); // no .get(): returns at once, the send runs in the background
} // DB commit here
```

The send and the commit race, so both failures can happen:

- **Phantom event** — the message goes out before the commit, then the commit fails → DB rolls back, message is out.
- **Lost event** — the send fails after the commit; the method never waited for it, so nothing rolls back and nothing
  retries → DB saved, no message.

Without waiting for the send, you can't even tell which way it broke.

</details>

### Dual write, crash between — what decides the outcome?
<details><summary>Show answer</summary>

Whether the caller that started both writes (broker, webhook sender, client) **sends the request again** when you
haven't confirmed processing:

- **Sends again (at-least-once)** — both writes repeat → the first system gets a **duplicate**, the second gets it
  for the first time. Nothing lost; receivers must drop copies.
- **Doesn't send again (at-most-once)** — nobody repeats → the second write is **lost**.

Confirm processing (commit the offset, ack, reply 2xx) only after both writes are done.

Example: a Kafka consumer reads "OrderPlaced", sends it on to Kafka and to RabbitMQ, and crashes after the first send.
Offset not committed → read again → duplicate in Kafka. The same sends from a user's HTTP request → the client is
gone → lost in RabbitMQ.

Caller redelivers → duplicates; no redelivery → loss.

</details>

### Messaging consumer crashes mid-work — who sends again?
<details><summary>Show answer</summary>

The broker side, as long as you haven't confirmed the message:

- **Kafka** — confirm = commit the offset. Not committed → after a restart or rebalance the consumer group reads
  again from the last committed offset; the broker doesn't push, the consumer re-reads.
- **RabbitMQ** — confirm = ack. No ack and the channel closes → the message goes back to the queue and is delivered
  again (to any consumer), marked `redelivered`.
- **JMS** — an API; the broker behind it (ActiveMQ Artemis, IBM MQ) delivers again. Confirm = ack, or commit in a
  transacted session.

Confirm after the work is done → a crash means a repeat, not a loss.

</details>

### Webhook handler crashes before replying 2xx — sent again?
<details><summary>Show answer</summary>

Depends on the sender — check its docs:

- **Retries** — Stripe: any non-2xx or no reply → sent again with backoff, for up to 3 days.
- **No retries** — GitHub: a failed delivery stays failed; only a manual or scripted redelivery through its API.

A reply that comes too late counts as a failure → the sender retries an event you already processed → duplicate.

No retries from the sender → missed events must be fetched by you (its events API, a periodic compare).

</details>

### Scheduled job crashes mid-run — is the work repeated?
<details><summary>Show answer</summary>

Only if the job finds its work from saved state:

- **State-driven** — each run selects what is not done yet (`WHERE status = 'PENDING'`) → the next run finds the
  unfinished rows again.
- **Time-driven** — "at 3:00 send yesterday's report", nothing records done or not done → a crashed run is not
  repeated; a run missed while the app was down is not caught up either (`@Scheduled` has no catch-up).

The schedule only decides when to look; saved state decides what is still to do.

</details>

### Dual write, crash between — where does confirming go wrong?
<details><summary>Show answer</summary>

The confirm goes out before both writes are done → the caller never sends again. From then on the message is yours:

- **Saved durably first** (a DB table, an inbox) → a crash loses nothing; your own worker finishes the writes later.
- **Kept only in memory** (an in-memory queue, a local cache, a thread pool's task queue) → a crash, restart or
  deploy → the message is gone, and nobody will send it again → **loss**.

Example: a webhook handler replies 200 at once and puts the event into an in-memory queue for a background thread →
the app restarts → the event is lost.

Confirm only when the message is done or saved durably — never while it lives only in memory.

</details>

### Caller resends until you confirm — what does that cost?
<details><summary>Show answer</summary>

Every unconfirmed message comes again, so you pay for the repeats:

- **Duplicates** — a crash between the writes repeats the first one → receivers must drop copies.
- **Poison message** — a message that always fails is sent again forever: it blocks its Kafka partition or loops in
  RabbitMQ → after N tries move it to a dead-letter queue.
- **Slow processing (Kafka)** — a batch takes longer than `max.poll.interval.ms` → the consumer leaves the group, its
  partition goes to another consumer, which reads the same batch again → processed twice, possibly at once.

No loss, but every message may come more than once.

</details>

### Two requests write DB and broker at once?
<details><summary>Show answer</summary>

The order in which the broker gets the events is not controlled — it can differ from the order of the DB writes.

Example: two requests change the same record: A sets X = 1, B sets X = 2. Each writes the DB, then sends:

- **DB** — A writes first, then B → the DB has 2.
- **Broker** — B's message goes out first, then A's → receivers end with 1.

No step failed and no error was logged, yet the DB and the receivers disagree until the next change to that record.

Cause: two systems, and nothing makes them apply the changes in the same order.

</details>

### DB write, then remote call timed out — now what?
<details><summary>Show answer</summary>

A timeout means "no answer", not "failed". The other side may:

- never have got the request;
- have done the work, and its answer was lost;
- still be working on it.

You can't tell which, so both obvious moves can be wrong:

- **Roll back your DB** — if the other side did the work, it now has a change you don't.
- **Retry** — if the other side did the work, it happens twice (a second card charge).

You need an [idempotent retry or a status check](5.3.5_Synchronous_Calls.md) first.

Treat a timeout as "unknown", never as "failed".

</details>

## Fixes that fall short

### Broker send fails after commit — how does a retry work out?
<details><summary>Show answer</summary>

A retry helps only while the app is alive: between the commit and a confirmed send, the event exists only in the
app's memory, and the caller won't send it again.

- **Broker down for a few seconds** — retries with a wait work; the event goes out late.
- **App crashes or restarts during retries** — the memory is gone → the event is lost, the order stays in the DB.
- **Broker down longer than the retries last** — the retries run out → the event is lost.

A retry can't survive a crash; only a [second write that was saved first](#dual-write--ways-out) can.

</details>

### Distributed transaction over DB and broker — how and at what cost?
<details><summary>Show answer</summary>

A distributed transaction — in Java usually an **XA transaction** (XA: eXtended Architecture, the X/Open standard;
JTA in Java) — makes several participants commit together or not at all, using **two-phase commit (2PC)**:

- **Phase 1, prepare** — a coordinator asks every participant to prepare: save the change durably and promise it
  can commit. Each votes yes or no.
- **Phase 2, commit** — all said yes → the coordinator tells all to commit; any no → all roll back.

In practice:

- **Rarely available**:
  - most relational DBs and older JMS brokers (ActiveMQ, IBM MQ) support XA;
  - Kafka — no XA, but since 4.1 it can join an external 2PC (KIP-939), off by default;
  - RabbitMQ doesn't; REST APIs and email can't take part.
- **Blocking** — the coordinator dies after prepare → participants can't commit or roll back on their own and hold
  their row locks until it comes back.
- **Slow and fragile** — two network rounds per action, every action waits for the slowest participant, and any one
  participant being down fails the action.

2PC turns several commits into one only where every side supports it and you can pay for the locks.

</details>

### Kafka transaction plus DB write — what's covered?
<details><summary>Show answer</summary>

Only the Kafka writes — the DB is not part of it.

- **Covered** — messages to several topics and partitions plus the consumer's offsets commit together
  (read → process → write back to Kafka).
- **Not covered** — Spring can run a DB transaction and a Kafka transaction in one method, but they commit one after
  the other; a crash between the two commits is the same dual write.

A real single commit over Kafka and a DB needs an external
[2PC](#distributed-transaction-over-db-and-broker--how-and-at-what-cost) (Kafka 4.1+).

Kafka's "exactly once" ends at Kafka's edge; add a DB, and you are back to two commits.

</details>

## Way out

### Dual write — ways out?
<details><summary>Show answer</summary>

Make one write durable first. The second write is driven from it and retried until confirmed, so it happens only if
the first one did:

- **Your DB is the first write**:
  - **[outbox](5.3.3_Outbox.md)** — save the event in an outbox table in the same DB transaction as the order; a
    relay sends it to the broker;
  - **[CDC](5.3.3_Outbox.md)** — a tool (Debezium) reads committed changes from the DB's log and sends them.
- **Broker + broker** — send only to the first; a forwarder reads it and sends to the second, and moves its read
  position only after the second confirms.
- **REST + REST**:
  - **save the plan first** — write "charge, then ship" to a table of your own; a worker runs each step and marks it
    done (an [outbox](5.3.3_Outbox.md) for calls);
  - **[saga](../../08_Integration/5_Microservices_and_Sagas/)** — each step is idempotent and retried until done; if
    a step can never succeed, earlier steps are undone with compensations (a refund).
- **The broker as the only write**:
  - **listen to yourself** — send the event only to the broker; your own consumer updates your DB from it;
  - **[event sourcing](../../08_Integration/3_Event_Driven_Architecture/)** — the event log is the only store;
    everything else is built from it.
- **A call whose answer you need now** (payment authorization) — it
  [can't be moved out](5.3.2_Remote_Call_&_Transaction.md); make it [idempotent](5.3.5_Synchronous_Calls.md).
- **Safety net for all of them** — [compare both sides later](5.3.6_Reconciliation.md) and repair the difference.

Cost of all of them:

- the second write happens a moment later;
- delivery is at least once → receivers must [drop duplicates](5.3.4_Receiver_Side.md).

One durable write first; the second follows from it.

</details>
