# Dual Write

### Dual write — what are the concerns?
<details><summary>Show answer</summary>

One business action writes to two systems that don't share a commit. Four groups:

- **What and where**:
  - [what it is](#what-is-a-dual-write)
  - [where it hides](#where-does-a-dual-write-hide)
- **How it breaks**:
  - [DB + broker, crash between](#db-commit-and-broker-send--crash-between)
  - [two brokers, crash between](#send-to-two-brokers--crash-between)
  - [two REST calls, crash between](#two-rest-calls--crash-between)
  - [two requests at once](#two-requests-write-db-and-broker-at-once)
  - [a timeout with no answer](#db-saved-remote-call-timed-out--now-what)
- **Fixes that fall short**:
  - [retry the send](#broker-send-failed-after-commit--retry)
  - [XA](#xa-over-db-and-broker--use-it)
  - [Kafka transactions](#kafka-transaction-plus-db-write--whats-covered)
- **Way out**:
  - [one durable write drives the other](#dual-write--ways-out)

Trigger: two commits can't become one, so make one write durable and drive the second from it.

</details>

## What and where

### What is a dual write?
<details><summary>Show answer</summary>

Your code changes two systems in one business action, and each system commits on its own. Example: send
"OrderPlaced" to Kafka, then call the payment API. Nothing makes both succeed or both fail.

</details>

### Where does a dual write hide?
<details><summary>Show answer</summary>

In any business action that writes to two of these:

- a broker;
- a REST call;
- a cache.

Your own DB counts as one of the two.

Check: one action, two systems, no shared commit.

</details>

## How it breaks

### DB commit and broker send — crash between?
<details><summary>Show answer</summary>

```java
@Transactional
void placeOrder(Order o) {
  repo.save(o);
  kafka.send("orders", event).get(); // message is out here
} // DB commit here
```

`@Transactional` covers only the DB; the broker commits on its own. A crash or a failure between the two steps leaves
one done and the other not:

- **Send first, then commit** (the code above) — the commit fails or the app crashes → the DB rolls back, but the
  message is already out → **phantom event**: receivers act on an order that doesn't exist.
- **Commit first, then send** — the send fails or the app crashes → the order is saved, no message → **lost event**:
  receivers never learn about the order.

No order of the two steps fixes it; the order only picks how it breaks.

</details>

**What doesn't work:**
- Rollback only covers the DB, not the broker.
- No order of the calls fixes it. The order only picks how it breaks: send first → phantom event,
  commit first → lost event.

This is known as the **dual-write problem**: the DB and the message broker commit separately.
Kafka can't join the DB transaction (no XA), so a rollback undoes only the DB. A crash between them splits the operation.
Wrapping them in a single `@Transactional` method does not work:

```java
@Transactional
void placeOrder(Order o) {
  repo.save(o);
  kafka.send("orders", event).get(); // message is out here
} // commit here
```

- **Publish first, commit fails or app crashes** (the code above): The DB rolls back, but the message is already out →
  **phantom event**. Receivers act on an entity that does not exist.
- **DB commits first, publish fails or app crashes** (`@TransactionalEventListener(phase = AFTER_COMMIT)`):
  The DB saves, but the event was only in memory and is lost. Receivers never learn about the change.
- **Async send** (no `.get()`): both risks. The message can go out before a failed commit, and a send failure shows
  up after the commit, too late to roll back.

</details>

### Send to two brokers — crash between?
<details><summary>Show answer</summary>

Example: send "OrderPlaced" to Kafka for other services and to RabbitMQ for the email service. The app crashes after
the first send:

- **First broker has it, second doesn't** — half the receivers act, the other half never hear about the order.
- **Send both again on restart** — works only if something remembered the send; then the first broker gets a copy →
  duplicates.

Each broker commits on its own: two brokers are two commits, the same as DB + broker.

</details>

### Two REST calls — crash between?
<details><summary>Show answer</summary>

Example: call the payment service (charge the card), then the shipping service (create the shipment). Your service
crashes after the first call:

- **Charged, not shipped** — the payment service has the change; the shipping service never hears about it.
- **Nobody remembers step 2** — the plan "charge, then ship" lived only in your service's memory; neither API knows
  about the other.
- **No rollback** — the charge is already committed in another system; the only undo is a new call (a refund), and
  that call can fail too.

Swapping the order only swaps the damage: shipped, not charged.

Two REST calls have no shared commit and no place that remembers the plan; you must add both.

</details>

### Two requests write DB and broker at once?
<details><summary>Show answer</summary>

Two requests change the same record: A sets X = 1, B sets X = 2. Each writes the DB, then sends:

- **DB** — A writes first, then B → the DB has 2.
- **Broker** — B's message goes out first, then A's → receivers end with 1.

No step failed and no error was logged, yet the DB and the receivers disagree until the next change to that record.

Cause: two systems, and nothing makes them apply the changes in the same order.

</details>

### DB saved, remote call timed out — now what?
<details><summary>Show answer</summary>

A timeout means "no answer", not "failed". The other side may have:

- never got the request;
- done the work, and its answer was lost;
- still be working on it.

You can't tell which, so both obvious moves can be wrong:

- **Roll back your DB** — if the other side did the work, it now has a change you don't.
- **Retry** — if the other side did the work, it happens twice (a second card charge).

You need an [idempotent retry or a status check](5.3.5_Synchronous_Calls.md) first.

Treat a timeout as "unknown", never as "failed".

</details>

## Fixes that fall short

### Broker send failed after commit — retry?
<details><summary>Show answer</summary>

Between the commit and a confirmed send, the event exists only in the app's memory. A retry helps only while the app
is alive:

- **Broker down for a few seconds** — retries with a wait work; the event goes out late.
- **App crashes or restarts during retries** — the memory is gone → the event is lost, the order stays saved.
- **Broker down longer than the retries last** — the retries run out → the event is lost.

A retry can't survive a crash; only a [second write that was saved first](#dual-write--ways-out) can.

</details>

### XA over DB and broker — use it?
<details><summary>Show answer</summary>

XA is the standard for [two-phase commit](../2_Distributed_Transactions/): a coordinator asks the DB and the broker to
prepare, then tells both to commit. In practice:

- **Mostly not available** — Kafka and RabbitMQ don't support XA; REST APIs and email can't take part. Only older JMS
  brokers (ActiveMQ, IBM MQ) do.
- **Blocking** — the coordinator dies after "prepare" → the DB holds the row locks until it comes back.
- **Slow and fragile** — every action waits for the slowest side, and any one side being down fails the action.

XA turns two commits into one only where every side supports it and you can pay for the locks.

</details>

### Kafka transaction plus DB write — what's covered?
<details><summary>Show answer</summary>

A [Kafka transaction](../../08_Integration/6_Message_Brokers/Kafka/) makes several Kafka writes atomic: messages to
several partitions plus the consumer's offsets (read → process → write back to Kafka). The DB is not part of it.

Spring can run a DB transaction and a Kafka transaction in one method, but they still commit one after the other. A
crash between the two commits is the same dual write.

Kafka's "exactly once" ends at Kafka's edge; add a DB, and you are back to two commits.

</details>

## Way out

### Dual write — ways out?
<details><summary>Show answer</summary>

Make one write durable first. The second write is driven from it and retried until confirmed, so it happens only if
the first one did:

- **Your DB is the first write**:
  - **[outbox](5.3.3_Outbox.md)** — save the event in an outbox table in the same DB transaction as the order; a
    relay sends it to the broker;
  - **[CDC](5.3.3_Outbox.md)** — a tool (Debezium) reads committed changes from the DB's log and sends them.
- **Broker + broker** — send only to the first; a forwarder reads it and sends to the second, and moves its read
  position only after the second confirms.
- **REST + REST**:
  - **save the plan first** — write "charge, then ship" to a table of your own; a worker runs each step and marks it
    done (an [outbox](5.3.3_Outbox.md) for calls);
  - **[saga](../../08_Integration/5_Microservices_and_Sagas/)** — each step is idempotent and retried until done; if
    a step can never succeed, earlier steps are undone with compensations (a refund).
- **The broker as the only write**:
  - **listen to yourself** — send the event only to the broker; your own consumer updates your DB from it;
  - **[event sourcing](../../08_Integration/3_Event_Driven_Architecture/)** — the event log is the only store;
    everything else is built from it.
- **A call whose answer you need now** (payment authorization) — it
  [can't be moved out](5.3.2_Remote_Call_&_Transaction.md); make it [idempotent](5.3.5_Synchronous_Calls.md).
- **Safety net for all of them** — [compare both sides later](5.3.6_Reconciliation.md) and repair the difference.

Cost of all of them:

- the second write happens a moment later;
- delivery is at least once → receivers must [drop duplicates](5.3.4_Receiver_Side.md).

One durable write first; the second follows from it.

</details>
