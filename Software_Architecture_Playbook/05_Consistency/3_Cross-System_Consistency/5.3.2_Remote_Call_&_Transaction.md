# Remote Call & Transaction

### Remote call and local transaction — where to put it?
<details><summary>Show answer</summary>

Your service writes its DB and calls another system (REST or broker). Two questions decide the place:

- **Do you need the answer to finish your own write?** ([markers](#when-must-the-call-stay-before-commit))
  - yes → the call goes [before](#remote-call-before-the-transaction--what-breaks) or
    [inside](#remote-call-inside-the-transaction--trade-off) the transaction, or between
    [two transactions with a saved status](#payment-call-in-the-middle-of-an-order--how);
  - no → it [moves after commit](#when-can-the-call-move-after-commit).
- **After commit: can you lose the call?**
  - yes → [after-commit listener](#remote-call-after-commit--whats-the-gap);
  - no → [outbox](5.3.3_Outbox.md).

Traps on the way:

- [the call succeeded, the commit failed](#remote-call-succeeded-then-commit-failed);
- [an async send inside the transaction](#async-broker-send-in-transactional--what-breaks);
- listeners: [phases](#what-are-the-transactionaleventlistener-phases),
  [a DB write after commit](#db-write-inside-an-after_commit-listener),
  [no transaction at all](#transactionaleventlistener-with-no-transaction).

Trigger: need the answer → call first and make it repeatable; don't need it → call after commit, durably if a loss
matters.

</details>

## Before or inside the transaction

### Remote call before the transaction — what breaks?
<details><summary>Show answer</summary>

Call first, then save locally:

- **The local write fails** (unique key, deadlock, DB down) → the other side has the change, you have nothing: a
  charge with no order.
- **The app crashes after the call** → the same, and nobody knows the call happened.
- **The whole action is retried** → the call runs again → a second charge, unless the call is
  [idempotent](5.3.5_Synchronous_Calls.md).

So a call made first needs two things:

- an idempotency key, so a retry repeats nothing;
- an undo (a refund) or a [later compare](5.3.6_Reconciliation.md) for when the local write never succeeds.

A call made first must be safe to repeat and possible to undo.

</details>

### Remote call inside the transaction — trade-off?
<details><summary>Show answer</summary>

```java
@Transactional
void placeOrder(Order o) {
  repo.save(o);
  payment.charge(o); // REST call: DB connection and row locks are held while it waits
}
```

- **Gain** — a call that clearly fails (exception, 4xx) rolls back your write: no order without a charge.
- **Cost**:
  - the DB connection and row locks are held for the whole call; a slow remote side → other requests wait for the
    locks, the connection pool runs out, the whole service stalls;
  - a timeout is [unknown, not failed](5.3.1_Dual_Write.md#db-saved-remote-call-timed-out--now-what): the rollback
    may undo your order while the charge went through;
  - the commit can [still fail after the call succeeded](#remote-call-succeeded-then-commit-failed).

A read-only call (GET) inside costs only the held connection; it is not a dual write.

Inside the transaction buys a rollback on a clear failure, paid with locks held for the network's time.

</details>

### Remote call succeeded, then commit failed?
<details><summary>Show answer</summary>

The other side has the change, your DB rolled back: a charge with no order. The commit fails more often than it seems:

- **Error found only at commit** — JPA/Hibernate sends the SQL at flush, usually at commit. `save()` returned fine;
  the unique key violation comes after the call.
- **Deadlock or lost connection** at commit time.
- **Transaction timeout** ran out during the slow call.

Partial fix: `flush()` before the call, so DB errors show up first. It doesn't help when the commit itself fails.

A successful call before the commit is no promise that the commit happens; plan the undo.

</details>

### Payment call in the middle of an order — how?
<details><summary>Show answer</summary>

Three steps, with a status on the business row:

- **Transaction 1** — save the order with status `PAYMENT_PENDING` and an
  [idempotency key](5.3.5_Synchronous_Calls.md#idempotency-key--who-creates-it-and-when); commit.
- **The call** — outside any transaction, with that key.
- **Transaction 2** — save the result: `PAID` or `PAYMENT_FAILED`.

A crash between the steps leaves the row in `PAYMENT_PENDING`. A
[sweeper job](5.3.6_Reconciliation.md#stuck-in-pending--who-finishes-it) finds old pending rows and retries with the
same key, or asks for the status.

No locks are held during the call, and nothing is forgotten: the saved status is the record that the call is still to
do — the same idea as an [outbox](5.3.3_Outbox.md#status-column-as-the-outbox).

A saved status between two short transactions replaces one long transaction.

</details>

## After commit

### Remote call after commit — what's the gap?
<details><summary>Show answer</summary>

```java
@Transactional
void placeOrder(Order o) {
  repo.save(o);
  events.publishEvent(new OrderPlaced(o.getId()));
}

@TransactionalEventListener // phase = AFTER_COMMIT by default
void on(OrderPlaced e) {
  kafka.send("orders", e);
}
```

- **Gain** — the call runs only after the DB committed: no phantom events, no locks held during the call.
- **Gap** — between the commit and the send, the event lives only in memory. A crash, a restart, a deploy or a failed
  send → the order is saved, the call never happens, and nothing retries it.

Fine when a loss is acceptable (a cache refresh, a nice-to-have notification). If not → [outbox](5.3.3_Outbox.md),
or [Spring Modulith](5.3.3_Outbox.md#spring-modulith-event-publication-registry), which saves the event in the same
transaction.

After-commit fixes the order of the two writes, not their durability.

</details>

### What are the @TransactionalEventListener phases?
<details><summary>Show answer</summary>

- `BEFORE_COMMIT` — inside the transaction, right before the commit; a failure still rolls it back.
- `AFTER_COMMIT` (default) — after a successful commit.
- `AFTER_ROLLBACK` — only after a rollback.
- `AFTER_COMPLETION` — after a commit or a rollback.

The listener runs only for an event published inside a transaction —
[otherwise it is skipped](#transactionaleventlistener-with-no-transaction).

</details>

### DB write inside an AFTER_COMMIT listener?
<details><summary>Show answer</summary>

The write is not saved, and there is no error. After the commit, the finished transaction's connection is still
bound to the thread; repository calls join that transaction, and nothing commits it again.

Fix: run the listener in a new transaction — `@Transactional(propagation = REQUIRES_NEW)` on the listener method.
Since Spring 6.1, a plain `@Transactional` on a `@TransactionalEventListener` fails at startup; only `REQUIRES_NEW`
or `NOT_SUPPORTED` are allowed.

After the commit there is no open transaction left to join; open a new one.

</details>

### @TransactionalEventListener with no transaction?
<details><summary>Show answer</summary>

The listener is not called at all: no error, the event is dropped. Happens when the event is published from a method
without `@Transactional`, or from a call path that has none (a scheduler, a test, a self-call that skips the proxy).

Fix: publish inside the transaction, or set `fallbackExecution = true` if the listener must also run without one.

A transactional listener waits for a transaction; with none, it never fires.

</details>

## Markers

### When must the call stay before commit?
<details><summary>Show answer</summary>

When your own write depends on the answer:

- **A check owned elsewhere** — "is this customer allowed to order?"
- **An ID you must store** — a reservation ID, a shipment number.
- **Money** — a payment authorization before you confirm the order.
- **Uniqueness owned elsewhere** — a username registry in another service.

Then make the call safe:

- an [idempotency key](5.3.5_Synchronous_Calls.md), so a retry repeats nothing;
- an undo (refund, release) or a [reservation](../../08_Integration/5_Microservices_and_Sagas/) (try → confirm or
  cancel), for when your commit fails.

If you can't finish without the answer, the call comes first and must be repeatable and undoable.

</details>

### When can the call move after commit?
<details><summary>Show answer</summary>

When nobody waits for the answer: an event for other services, a notification, an email, a cache refresh.

Then pick by what a lost call costs:

- **A loss is acceptable** → [after-commit listener](#remote-call-after-commit--whats-the-gap).
- **A loss is not acceptable** → [outbox](5.3.3_Outbox.md).

No answer needed → no reason to call before the commit.

</details>
