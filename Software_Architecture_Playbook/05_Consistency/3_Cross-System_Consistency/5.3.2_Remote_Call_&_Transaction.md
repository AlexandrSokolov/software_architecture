## Remote Call & Transaction

Where to put a remote call relative to your own DB transaction, and what each place costs. 
This file is the decision in your code: call before, inside, between two transactions, or after commit — 
and what that choice holds and breaks.

## Deciding the place

### DB write plus remote call — where does the call go?
<details><summary>Show answer</summary>

Decided by one thing: does your own write need the call's answer?

- **Before commit — the write needs the answer** ([which pattern](#call-needed-before-commit--which-pattern)):
  - a check owned elsewhere — is this customer allowed to order?
  - an ID to store — a reservation ID, a shipment number;
  - money — a payment authorization before the order is confirmed;
  - uniqueness owned elsewhere — a username registry in another service.
- **After commit — nobody waits for the answer** ([how to send it](#remote-call-after-commit--how-to-send-it)):
  - an event for other services;
  - a notification or an email;
  - a cache refresh.

Can't finish without the answer → call first; no answer needed → call after the commit.

</details>

### Call needed before commit — which pattern?
<details><summary>Show answer</summary>

Depends on what the call leaves behind and what else your write depends on:

- **Nothing — a check or a read** (credit limit, price) → call, then write; a failed call → don't open the
  transaction. A failed write leaves nothing to clean up —
  [why](#credit-check-over-rest-then-the-order-save-fails--whats-left).
- **A lasting effect** (money, a shipment) → a crash after the call must not hide it → save the intent before the
  call — [how](#payment-succeeded-then-your-write-failed--how-not-to-lose-it).
- **The write also depends on a DB read** (the order must still be `OPEN`) → a lost update with the call in the
  middle, the gap grows to seconds — [how](#write-depends-on-a-db-read-and-a-remote-call--how):
  - lock the row and call inside;
  - call outside, check the value at the write;
  - set a status before the call.
- **Several calls** — two succeed, the third fails: a rollback undoes only your DB, the done calls stay done:
  - checks only → call them all first; any fails → stop;
  - with lasting effects → record the intent first, undo the done calls with compensations (a saga). 

Nothing left behind → just call first; lasting effect → record the intent first; a DB read involved → protect it
like a lost update; several calls with lasting effects → a saga.


</details>

### Credit check over REST, then the order save fails — what's left?
<details><summary>Show answer</summary>

Nothing — the order simply wasn't placed, and the other side changed nothing. So the call can go before the
transaction.

The same holds when:

- **The effect expires on its own** — a reservation with a timeout: never confirmed → the other side releases it.
- **The whole action comes again** — the caller resends it (an unconfirmed message) and the call is idempotent →
  the repeat finishes your write without a second effect.

A call that leaves nothing behind needs no protection — call first, then write.

</details>

### Payment succeeded, then your write failed — how not to lose it?
<details><summary>Show answer</summary>

Save the intent before the call — a durable record that the call is starting:

- **Transaction 1 — the intent** — save the row as `PAYMENT_PENDING` with an
  [idempotency key](5.3.5_Synchronous_Calls.md#idempotency-key--who-creates-it-and-when); commit. Not business data:
  it exists only so a crash can't hide the call — an [outbox](5.3.3_Outbox.md#status-column-as-the-outbox) for a
  call made first.
- **The call** — outside any transaction, with that key.
- **Transaction 2 — the business write** — save the result: `PAID` or `PAYMENT_FAILED`.

After a crash the row stays in `PAYMENT_PENDING` → a
[sweeper job](5.3.7_Reconciliation.md#stuck-in-pending--who-finishes-it) finds old pending rows and either finishes
the work (asks for the status, retries with the same key) or undoes it (refund). No rollback across systems — only a
new call.

Bonus: nothing is held during the call — no locks, no DB connection.

Record the intent before a call you can't take back; then no crash can hide it.

</details>

### Write depends on a DB read and a remote call — how?
<details><summary>Show answer</summary>

It is a [lost update](../1_DB_Consistency/5.1.03_Lost_Updates.md) with a network call in the middle: read → call →
write on the same row, and the call stretches the gap between read and write from milliseconds to seconds.

The write needs both: the order is still `OPEN` **and** the payment succeeded. A cancel that comes in between must
not be overwritten. Three ways:

- **Pessimistic — call inside the transaction** — `SELECT … FOR UPDATE` → call → set `PAID` → commit. The cancel
  waits for the lock; no conflict, but the lock, the DB connection and the thread are held for the whole call.
- **Optimistic — call outside** — read `OPEN`, call, then a short transaction:
  `UPDATE … SET status = 'PAID' WHERE id = ? AND status = 'OPEN'`. Nothing is held; 0 rows → the order was cancelled
  meanwhile → undo the payment (refund). Not a retry: repeating the action would charge again.
- **Semantic lock — status, two transactions** — transaction 1: `OPEN` → `PAYMENT_PENDING`; call; transaction 2:
  `PAYMENT_PENDING` → `PAID`. A cancel sees `PAYMENT_PENDING` and leaves the order alone (waits or refuses). Nothing is
  held, and no conflict: the business status does the locking.

Lock in the DB and pay with the network wait; check at the write and pay with an undo; or lock with a status and pay
with one more state.

</details>

### Spring: remote call inside @Transactional — how to move it out?
<details><summary>Show answer</summary>

No transaction around the call; each DB step gets its own short transaction:

```java
// no @Transactional here
void placeOrder(Order o) {
  orders.markPending(o);          // another bean, @Transactional: commit 1
  var result = payment.charge(o); // no transaction open
  orders.saveResult(o, result);   // another bean, @Transactional: commit 2
}
```

- **The outer method — no `@Transactional`** — it only orders the steps. Check its callers too: a transaction
  opened above still holds everything ([call tree](#remote-call-deep-in-a-call-tree--whose-transaction-holds-it)).
- **The short DB steps — each its own transaction**, two ways:
  - **annotations on another bean** — `@Transactional` or `REQUIRES_NEW` on the step methods; a call from the same
    class skips the proxy → no transaction at all;
  - **`TransactionTemplate`** — wraps each step in code; works inside the same class, no proxy needed.
- **`REQUIRES_NEW` vs plain `@Transactional`** — with no transaction above, both open a new one. `REQUIRES_NEW` also
  commits on its own when called from inside a transaction, but that outer one is only paused — its connection and
  locks stay held during your call.
- **Open Session in View off** — `spring.jpa.open-in-view=false`; otherwise a read before the call keeps the DB
  connection until the request ends.

Out of the transaction means no transaction anywhere above the call, not only none on the method itself.

</details>

### Remote call after commit — how to send it?
<details><summary>Show answer</summary>

Decided by what a lost call costs:

- **A loss is acceptable** (a cache refresh, a nice-to-have notification) → send after the commit
  (`@TransactionalEventListener`, or `TransactionSynchronization.afterCommit()` it is built on):
  - gain — the call runs only after the DB committed: no phantom events, nothing held during the call;
  - gap — between the commit and the send the call lives only in memory; a crash, a restart, a deploy or a failed
    send → [lost](5.3.1_Dual_Write.md#db-commit-before-broker-send--crash-between), nothing retries it.
- **A loss is not acceptable** (an event other services rely on) → save the call as a row in the same transaction
  as your write; a separate sender delivers it, a crash → sent later:
  - [outbox](5.3.3_Outbox.md);
  - [Spring Modulith](5.3.3_Outbox.md#spring-modulith-event-publication-registry) — keeps the event in the same
    transaction.

After-commit fixes the order of the two writes, not their durability; durability needs a row saved with your write.

</details>

## Costs and traps

### Remote call before the transaction — what breaks?
<details><summary>Show answer</summary>

The call succeeds, then your side fails — the other side keeps the change:

- **The local write fails** (unique key, deadlock, DB down) → the other side has the change, you have nothing: a
  charge with no order.
- **The app crashes after the call** → the same, and nobody knows the call happened.
- **The whole action is retried** → the call runs again → a second charge.

So a call made before your commit must be:

- **Repeatable** — an [idempotency key](5.3.5_Synchronous_Calls.md): a retried action repeats nothing on the other
  side.
- **Undoable** — an undo call (refund, release), or a reservation (try → confirm or cancel): the change can be taken
  back when your write never commits.
- **Checked later** — a [compare of both sides](5.3.7_Reconciliation.md) catches what slipped through.

A call made first must be safe to repeat and possible to undo.

</details>

### Remote call inside the transaction — trade-off?
<details><summary>Show answer</summary>

```java
@Transactional
void placeOrder(Order o) {
  repo.save(o);
  payment.charge(o); // REST call: everything below is held while it waits
}
```

**Gain** — a clear failure (exception, 4xx) rolls back the writes made before the call. Needed only when the call
depends on those writes (an ID your own insert generates); usually avoidable — generate the ID in the app (UUID),
or call before the transaction.

**Cost** — everything the transaction took now waits on the network:

- **DB**:
  - row locks held — explicit (`SELECT … FOR UPDATE`) and implicit (any plain `UPDATE`) → other transactions, jobs
    and services on those rows wait → lock timeouts, deadlocks;
  - a long open transaction → Postgres can't clean old row versions; tables bloat for everybody.
- **Your service** — held for the whole wait, so the pools run out, even for requests that never call out:
  - the DB connection;
  - the request thread;
  - the HTTP client connection.
- **Stuck for good**:
  - no timeout on the call → it waits forever, nothing is released;
  - the remote side calls back → it needs a thread from your exhausted pool, or the row you locked; the DB can't
    see that cycle.
- **Spreads** — your service stalls → your callers' pools fill up the same way → cascade upstream.
- **Half done**:
  - a call timeout or the transaction timeout → rollback, while the remote side may have done the work
    ([unknown, not failed](5.3.1_Dual_Write.md#db-write-then-remote-call-timed-out--now-what));
  - the commit can still fail after the call succeeded
    ([save() returned](#spring-data-jpa-save-returned-remote-call-succeeded-then-commit-failed--why)).

Virtual threads don't fix it: DB connections and row locks stay limited and held. A read-only GET inside isn't a
dual write, but still holds the connection and the thread.

Inside buys a rollback on a clear failure, paid with everything held for the network's time — the remote side's
problems become yours.

</details>

### Remote call deep in a call tree — whose transaction holds it?
<details><summary>Show answer</summary>

The one opened at the top of the tree — the method making the call may have no `@Transactional` at all:

- **`REQUIRED` (default)** — an outer method opened the transaction, every method below joins it → a remote call
  deep down holds the outer locks and connection, while the method itself looks clean in review.
- **`REQUIRES_NEW` below** — the outer transaction is paused, but its connection and locks stay held; the new one
  takes a second connection → under load every thread waits for a second connection → pool deadlock.
- **Open Session in View** (`spring.jpa.open-in-view=true`, the Spring Boot default) — once the request touched the
  DB, the connection can stay held until the request ends, remote calls included, even without `@Transactional`.
- **After-commit listener below** — fires after the outer commit, not after its own method.

The transaction boundary is set at the top; that's where a remote call is in or out.

</details>

### Network call kept inside a transaction — how to limit the cost?
<details><summary>Show answer</summary>

Keep the hold short and the wait bounded:

- **Bound the wait**:
  - a timeout on every call, shorter than the transaction timeout → the call gives up first, nothing waits forever;
  - a circuit breaker → a dead remote side fails fast instead of holding everything (06_Resilience).
- **Shrink what's held**:
  - call first, lock last → the call before any `UPDATE` / `SELECT … FOR UPDATE`, locks only for the short write
    after it;
  - a separate pool (bulkhead) for these calls → a slow remote side can't take all threads (06_Resilience).
- **See it** — watch transaction duration, connection pool usage, lock waits.

Trap: `flush()` before the call catches DB errors early, but takes the row locks early too — it works against "lock
last".

If the call must stay inside, bound how long it can hold and hold as little as possible.

</details>

### Spring Data JPA: save() returned, remote call succeeded, then commit failed — why?
<details><summary>Show answer</summary>

`save()` usually only queues the change; the SQL goes out at flush, usually at commit. A unique key violation or a
constraint error shows up after the call — the charge is done, the order is rolled back.

Fix: `flush()` before the remote call, so DB errors come first. It doesn't help when the commit itself fails (deadlock, 
lost connection) — the call must still be [repeatable and undoable](#remote-call-before-the-transaction--what-breaks).

A returned `save()` is no proof the write will commit; flush before calling out.

</details>

### Send an email only if the order really saved — which listener phase?
<details><summary>Show answer</summary>

`AFTER_COMMIT` (the default) — runs only after a successful commit; a rolled-back order sends nothing.

</details>

### Extra write that must commit or roll back with the order — which listener phase?
<details><summary>Show answer</summary>

`BEFORE_COMMIT` — runs inside the same transaction, right before the commit; its write joins the commit, its failure
rolls everything back. Example: an audit row, or the outbox row for the event.

</details>

### React only when the order transaction failed — which listener phase?
<details><summary>Show answer</summary>

`AFTER_ROLLBACK` — runs only after a rollback. Example: release a reservation made in another system before the
failed commit, or alert on the failure.

</details>

### Clean up after the transaction, whatever the outcome — which listener phase?
<details><summary>Show answer</summary>

`AFTER_COMPLETION` — runs after a commit or a rollback. Example: release a lock, record a metric, clear per-request
state.

</details>

### DB write inside an AFTER_COMMIT listener?
<details><summary>Show answer</summary>

The write is not saved, and there is no error. After the commit, the finished transaction's connection is still
bound to the thread; repository calls join that transaction, and nothing commits it again.

Fix: run the listener in a new transaction — `@Transactional(propagation = REQUIRES_NEW)` on the listener method.
Since Spring 6.1, a plain `@Transactional` on a `@TransactionalEventListener` fails at startup; only `REQUIRES_NEW`
or `NOT_SUPPORTED` are allowed.

After the commit there is no open transaction left to join; open a new one.

</details>

### Event published, after-commit listener never runs, no error — why?
<details><summary>Show answer</summary>

The event was published outside a transaction — a `@TransactionalEventListener` is then skipped silently. Happens
when the publishing method has no `@Transactional`, or the call path has none: a scheduler, a test, a self-call that
skips the proxy.

Fix: publish inside the transaction, or set `fallbackExecution = true` if the listener must also run without one.

A transactional listener waits for a transaction; with none, it never fires.

</details>
