## The idea

### What is the transactional outbox?
<details><summary>Show answer</summary>

In the same DB transaction as the business change, your code also inserts the event into an `outbox` table. A
separate relay reads the table and sends the events to the broker. Both rows are saved or neither, so an event exists
only if the change does.

</details>

## The table

### Outbox table — what columns?
<details><summary>Show answer</summary>

- `id` — the event ID; receivers [drop duplicates](#where-does-the-event-id-come-from) by it.
- `aggregate_type` — what changed (order, customer); picks the topic.
- `aggregate_id` — which one; becomes the Kafka message key, so the events of one order stay in order.
- `event_type` — `OrderPlaced`, `OrderCancelled`.
- `payload` — the event body (JSON).
- `headers` — the trace context, so the [trace goes through the outbox](#trace-through-the-outbox).
- `created_at` — for the lag alert and cleanup.
- `sent_at` or a status — only for a [polling relay](#polling-relay--how-does-it-work); CDC doesn't need it.

</details>

### One outbox table or one per aggregate?
<details><summary>Show answer</summary>

- **One table** — one relay, one query, one cleanup job. The usual choice.
- **One per aggregate** (`order_outbox`, `customer_outbox`) — a slow or broken one doesn't hold up the others, and
  each can have its own cleanup; but more tables and relays to run.

Start with one; split when one kind of event needs its own speed or owner.

</details>

### Build the event when saving or when sending?
<details><summary>Show answer</summary>

- **When saving** (inside the business transaction) — the payload is a snapshot of that moment.
- **When sending** (the row holds only the order ID; the relay loads the order and builds the event) — the relay sees
  the current state, not the state at the event:
  - three quick changes → three events with the same, latest data;
  - a deleted order → nothing left to build the event from.

Build the full event inside the business transaction; the relay only sends.

Whether the event carries all the data or only an ID is a separate
[event design choice](../../08_Integration/3_Event_Driven_Architecture/).

</details>

### Where does the event ID come from?
<details><summary>Show answer</summary>

Create it once, when the outbox row is inserted, and send the same ID on every resend. Receivers
[drop duplicates](5.3.4_Receiver_Side.md#message-arrives-twice--do-work-once) by it.

Trap: a relay that builds a new message with a new UUID on each send. A resend after a crash looks like a new event,
and the receivers' duplicate check lets it through.

</details>

## Relay by polling

### Polling relay — how does it work?
<details><summary>Show answer</summary>

A scheduled job reads unsent rows, sends each one, waits for the broker's ACK, and marks the row as sent:

```sql
SELECT * FROM outbox WHERE sent_at IS NULL ORDER BY id LIMIT 100;
```

- **Gain** — no extra infrastructure, just a job in your service.
- **Cost** — the DB is queried even when there is nothing to send, and an event waits up to one poll interval.

</details>

### How often should the relay poll?
<details><summary>Show answer</summary>

It is a trade-off between delay and DB load:

- **Delay** — an event waits up to one interval. 100 ms → near real time; 5 s → fine for emails, too slow for a flow
  a user is waiting on.
- **DB load** — every poll is a query, on every instance, even when nothing is waiting.

Make frequent polls cheap:

- **Index only unsent rows** — a partial index `WHERE sent_at IS NULL`; a poll stays cheap even when the table holds
  millions of sent rows.
- **Full batch → poll again at once** — 100 of 100 returned means more are waiting; don't sleep.
- **Empty → wait longer** — back off up to a maximum.

Traps: a short interval with no index scans the whole table every 100 ms; a long interval quietly adds seconds to
every flow.

Pick the interval from how long an event may wait, then make each poll cheap.

</details>

### After-commit send plus scheduled poll — why both?
<details><summary>Show answer</summary>

- **After-commit listener** — right after the business commit, it sends this event at once and marks the row. In the
  normal case there is no polling delay.
- **Scheduled poll** — every few seconds, it sends what is still unsent: events whose instant send failed, or was
  lost in a crash.

The listener gives speed, the poll gives safety, and the row in the table makes both safe.

Trap: both can pick the same row at once → it is sent twice. Lock the row (`FOR UPDATE SKIP LOCKED`), or accept the
duplicate — receivers [drop copies](5.3.4_Receiver_Side.md) anyway.

</details>

### Several relay instances — who sends a row?
<details><summary>Show answer</summary>

`@Scheduled` runs on every instance of your service. Three instances → three relays read the same unsent rows → each
event is sent three times, in random order.

Two ways:

- **One relay at a time** — a lock that only one instance gets (ShedLock, leader election). Simple and keeps the
  order; one instance's speed is the limit.
- **Rows split between relays** — `SELECT … FOR UPDATE SKIP LOCKED`: each relay locks a batch, the others skip it.
  Scales out, but [breaks order per aggregate](#skip-locked-relays--order-per-aggregate).

Decide who owns a row before you run a second instance.

</details>

### Polling by "ID greater than last seen" — what's skipped?
<details><summary>Show answer</summary>

Transaction A gets ID 10, transaction B gets ID 11. B commits first. The relay reads up to 11 and remembers 11. A
commits a moment later → row 10 is never read.

IDs and timestamps are given out at insert, but rows become visible at commit, in a different order.

Fix: poll by status (`sent_at IS NULL`), not by "after the last ID". A late row is still unsent and is found on the
next poll.

Poll for what is not done yet, not for what is newer than last time.

</details>

### SKIP LOCKED relays — order per aggregate?
<details><summary>Show answer</summary>

Order 42 has two rows: `OrderPlaced` (ID 10) and `OrderCancelled` (ID 11). Relay 1 locks a batch with row 10; relay
2 skips it and takes row 11. Relay 2 is faster → `OrderCancelled` reaches the broker first.

Ways to keep the order per aggregate:

- **One relay** — the simplest.
- **Split by aggregate, not by row** — each relay owns a set of aggregate IDs (hash of the ID mod N), so all rows of
  one order go through one relay.
- **CDC** — reads the log in commit order.

The broker keeps order per key only if the sender sends in order.

</details>

### Mark as sent or delete after send?
<details><summary>Show answer</summary>

- **Mark** (`sent_at = now()`) — keeps a history for debugging and resending; the table grows →
  [cleanup](#outbox-cleanup--how).
- **Delete** — the table stays small; no history.

Either way, only after the broker's ACK.

</details>

### Outbox Relay marks as "sent", then crashes?
<details><summary>Show answer</summary>

If the relay reads the outbox row, marks it as "sent" (or deletes it), and then crashes before the broker confirms,
the event is permanently lost. On restart, the relay ignores the row, assuming it succeeded.
The outbox just failed its primary purpose.

**Fix:**
Strict ordering. You must only delete or mark the row as "sent" after receiving the broker's ACK
(e.g., inside the success callback). For async batch sending, process DB updates based on individual ACKs,
not just because the batch was read into memory.

**Cost:** a crash after the confirm but before the mark sends the row again, which is a duplicate.
This is why the Outbox pattern inherently guarantees **At-Least-Once delivery** and
strictly requires **idempotent consumers** - receivers must drop copies.

</details>

### One row the broker keeps rejecting?
<details><summary>Show answer</summary>

Example: the payload is too large, or the topic was deleted. The relay retries it on every poll:

- **Strict order** (one relay, stop at a failure) — every row behind it waits: the whole outbox stops.
- **No order** — it is retried forever and fills the logs.

Fix: count attempts and keep the last error in the row. After N attempts, mark it `FAILED`, alert, and go on (if
order matters, hold back only that aggregate's rows). After the fix, reset the status to send it again.

A relay needs its own "failed" state, or one bad row stops all events.

</details>

## Relay by CDC

### Log-tailing relay — how does it work?
<details><summary>Show answer</summary>

A CDC tool (Debezium) reads the DB's commit log — the Postgres WAL, the MySQL binlog — and turns each committed
insert into the outbox table into a broker message. Debezium's Outbox Event Router picks the topic from
`aggregate_type` and uses `aggregate_id` as the message key.

Your app only writes the outbox row; nothing polls the table.

</details>

### Polling relay or CDC — which?
<details><summary>Show answer</summary>

- **Polling** — a job in your service, no new infrastructure. Costs: DB queries, a delay of up to one interval,
  ordering work when you scale out.
- **CDC** — no polling load, low delay, commit order for free. Costs: Kafka Connect and Debezium to run and watch,
  DB settings (logical replication, a replication slot), and the [WAL trap](#cdc-connector-stopped--what-grows).

Polling until its load or delay hurts; CDC when you already run Kafka Connect or need the volume.

</details>

### Outbox table that stays empty — how?
<details><summary>Show answer</summary>

With CDC, nothing reads the table, only the log:

- **Insert and delete in the same transaction** — the table stays empty; the log still has the insert, and the
  Outbox Event Router sends it and skips the delete.
- **Postgres `pg_logical_emit_message`** — writes the event straight into the WAL, with no table at all; Debezium
  reads it as a message.

No cleanup and no table growth.

</details>

### CDC connector stopped — what grows?
<details><summary>Show answer</summary>

Postgres keeps the WAL until the replication slot's reader confirms it. The connector is down for a weekend → the WAL
piles up on the main DB's disk → the disk fills → the DB stops taking writes.

Also: a connector restart resends from the last saved position → duplicates.

Watch the slot's lag and alert on it. Set `max_slot_wal_keep_size`: past that size Postgres gives up on the slot
instead of filling the disk, and the connector must start over with a new snapshot.

A replication slot turns a stopped reader into a full disk on the main DB.

</details>

### CDC on business tables, no outbox?
<details><summary>Show answer</summary>

Debezium can send every change of the `orders` table directly. The events are then row changes, not business events:

- your table design becomes a public contract — renaming a column breaks the consumers;
- "status changed from 3 to 4" instead of `OrderShipped` — receivers must guess the meaning;
- one business action that touches three tables → three unrelated events.

The outbox row is an event designed for others; the business table stays private.

</details>

## Running it

### Outbox cleanup — how?
<details><summary>Show answer</summary>

Sent rows pile up, and a big table slows down polling.

- **Delete job** — delete sent rows older than N days, in small batches; one huge delete locks and bloats the table.
- **Table split by day** (partitioning) — drop the old day's partition; no row-by-row delete.
- **Delete right after the send** — no cleanup, no history.

Keep rows as long as you may need them for debugging or resending.

</details>

### Outbox — what to watch?
<details><summary>Show answer</summary>

- **Age of the oldest unsent row** — the main signal: how late events are. Growing → the relay is stuck or too slow.
- **Unsent count** — the size of the backlog.
- **Failed rows** — rows in `FAILED`, or with many attempts.
- **CDC: slot lag** — WAL not yet read.

Alert on the age, not only on errors: a stopped relay logs no errors.

</details>

### Trace through the outbox?
<details><summary>Show answer</summary>

The trace stops at the commit: the relay sends later, in another thread, without the request's trace context.

Save the trace context (`traceparent`) in the row's `headers` at insert; the relay copies it into the message
headers. Then [one trace](../../09_Operability/2_Observability/) runs from the HTTP request through the broker to the
consumer.

</details>

## Other shapes

### Status column as the outbox?
<details><summary>Show answer</summary>

Example: the order row has the status `PAYMENT_PENDING`. A worker picks orders in that status, calls the payment API,
and moves the status to `PAID`. No outbox table: the status written in the business transaction is the saved
"still to do".

- **Fits** — one pending action per row at a time, and the action follows from the business state (a state machine).
- **Doesn't fit** — several events per change, or events others must get in order: a status keeps only the current
  step, not a list of events.
- **Same rules as an outbox** — the worker must [own its rows](#several-relay-instances--who-sends-a-row), use an
  [idempotency key](5.3.5_Synchronous_Calls.md), and keep failed rows visible.

</details>

### Outbox for outgoing REST calls?
<details><summary>Show answer</summary>

The same table, but the row is a command: "call the shipping API with this body". A worker makes the call with the
row's ID as the [idempotency key](5.3.5_Synchronous_Calls.md) and marks the row done after a success.

Retries survive crashes; the API must accept the key, or the call must be safe to repeat.

</details>

### Spring Modulith event publication registry?
<details><summary>Show answer</summary>

An outbox built into Spring. When you publish an application event inside a transaction, Modulith saves one
publication row per listener in the same transaction. After the commit, the `@ApplicationModuleListener` runs; on
success the row is marked complete.

Rows left incomplete (a crash, a failure) can be sent again — on restart if configured, or by your own scheduled job.
With `@Externalized` the event also goes to Kafka.

A durable after-commit with no table of your own; it ties you to Modulith and still delivers at least once.

</details>

### Event first, then own DB from it?
<details><summary>Show answer</summary>

"Listen to yourself": send the event only to Kafka; your own consumer reads it and updates your DB, like any other
consumer. One write, no outbox.

- **Your own reads lag** — a user who reads right after the request may not see the change yet.
- **Checks must come before the send** — once the event is out, it is a fact; a failing DB update can't reject it.

Fits when the event is the main thing and your DB is just one more reader.

</details>

### Own outbox or a framework?
<details><summary>Show answer</summary>

- **Own** — a table and a job; you control everything, and you solve locking, order, cleanup and monitoring yourself.
- **Spring Modulith** — the [publication registry](#spring-modulith-event-publication-registry), for Spring apps.
- **Debezium** — [CDC](#log-tailing-relay--how-does-it-work): no relay code, but infrastructure to run.
- **Eventuate Tram** — an outbox plus sagas framework.

</details>
