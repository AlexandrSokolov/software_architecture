# Receiver Side

### Q: When you confirm

- You confirm the message on receipt, then crash before doing the work. What is lost?
- You confirm, then hand the work to an in-memory thread pool. What is the risk?
- You answer 200 to a webhook first, then do the work. What does that risk?
- The sender waits 5 s, the work takes 30 s. How do you answer in time without risking loss?
- You confirmed, then your DB commit failed. What now?
- A deploy stops the service while messages sit in memory. What is lost?

### Q: When your own code drops it

- You mark the message ID as "seen" before doing the work, then crash. What happens on redelivery?
- Two different messages get the same dedup key. What does the second one lose?
- You skip updates that look older than your data, but the sender's clock was off. What is lost?
- A new message type or field arrives that your code doesn't know. Error or silent skip?

## Losing: confirmed too early

### How does a receiver lose a message?
<details><summary>Show answer</summary>

Every receiver-side loss has one root: the receiver said "done" — an ack, an offset commit, an HTTP 200 — while the
message was not yet safely handled. After that, nobody sends it again. Four ways it happens:

- **Confirmed too early** — before the work is saved:
  - [crash after confirm](#confirmed-on-receipt-then-crashed--whats-lost)
  - [in-memory pool](#work-handed-to-an-in-memory-pool--risk)
  - [webhook 200 first](#webhook-answered-200-first--whats-the-risk)
  - [slow work vs short timeout](#sender-waits-5-s-work-takes-30-s)
  - [DB commit fails](#confirmed-then-db-commit-failed--now-what)
  - [deploy](#deploy-stops-the-service-mid-work--whats-lost)
- **[Wrong position saved](../../08_Integration/6_Message_Brokers/Kafka/)** — one Kafka offset per partition means
  "all below is done": auto-commit, parallel threads, a partly failed batch, a rebalance.
- **[Error swallowed](../../08_Integration/3_Event_Driven_Architecture/)** — the error path ends in a confirm: catch and
  log, retries used up, a message that can't be parsed, a failed dead-letter send.
- **Dropped by your own logic** — confirmed correctly, but the code chose to skip it:
  - [seen before done](#marked-as-seen-then-crashed--redelivery)
  - [coarse dedup key](#two-messages-one-dedup-key--whats-lost)
  - [clock-based "older"](#skipped-as-older-but-the-clock-was-off)

Handle: too early, wrong offset, swallowed error, wrong skip.

</details>

### Confirmed on receipt, then crashed — what's lost?
<details><summary>Show answer</summary>

The message. A confirm tells the other side "I have it, you may forget it":

- **Queue** (RabbitMQ, JMS) — the broker deletes the message.
- **Kafka** — the group's saved offset moves past it; it stays in the log, but this group never reads it again.
- **Webhook** — the sender marks it delivered and stops retrying.

The crash comes after the confirm and before the work, so nobody has the message any more. This is
**at-most-once** delivery. Typical cause: confirming on receipt — auto-ack, or handing the message to a background
thread and confirming at once.

Fix: confirm only after the work is done and saved. Cost: a crash between work and confirm brings the message again,
so the handler must [handle duplicates](#crash-after-the-work-before-confirming) — **at-least-once** delivery.

Handle: a confirm is permission to forget; give it only when forgetting is safe.

</details>

### Crash after the work, before confirming?
<details><summary>Show answer</summary>

The broker never got the confirm, so it delivers the message again — after a timeout, or to another consumer (Kafka:
the next consumer starts from the last saved offset). The work runs a second time.

This is **at-least-once**: nothing is lost, but duplicates happen. So the handler must be
[safe to run twice](#message-arrives-twice--do-work-once).

Work and confirm are two steps, and a crash can fall between them. No order of the two avoids both loss and duplicates
— that is [why delivery can't be exactly once](../../08_Integration/3_Event_Driven_Architecture/).

</details>

### Work handed to an in-memory pool — risk?
<details><summary>Show answer</summary>

The listener puts the message on a thread pool's queue and returns. The container sees a normal return and confirms
(acks, commits the offset, or a webhook answers 200). Now the only copy is a Java object in the heap:

- **Crash, OOM, deploy** — the pool's queue is gone; the broker or the sender already forgot those messages.
- **No back pressure** — the listener takes messages faster than the pool finishes them. The queue grows until memory
  runs out, which crashes the service and loses the whole queue.

Fixes:

- **Work on the listener thread** — scale with more partitions or consumers, not with a hidden pool.
- **Save first** — write the message to a DB table, confirm, let workers process from the table.
- **Confirm when the work ends** — manual ack from the worker. In Kafka, workers finish out of order, so the saved
  offset must [wait for gaps](../../08_Integration/6_Message_Brokers/Kafka/).

A memory buffer behind a confirm loses data on every restart.

</details>

### Webhook answered 200 first — what's the risk?
<details><summary>Show answer</summary>

To the sender, 200 means "delivered": it stops retrying. If your service crashes, fails on the DB, or is redeployed
before the work is done, the event is gone. Most senders don't keep events for you to fetch again, so often the only
way back is a [nightly compare](5.3.6_Reconciliation.md) with the sender's data.

The other order has its own risk: work first, then 200 → a crash means no 200, so the sender retries → a duplicate;
slow work can also [hit the sender's timeout](#sender-waits-5-s-work-takes-30-s).

Rule: answer 200 only after the event is saved somewhere that survives a crash. If saving fails, answer 5xx, so the
sender retries.

200 means "it's safe with me", not "it's done".

</details>

### Sender waits 5 s, work takes 30 s?
<details><summary>Show answer</summary>

Both obvious answers fail:

- **Work, then answer** — the sender times out after 5 s, counts it as failed, and retries: the work runs again, maybe
  in parallel. After enough failures some senders give up or disable your endpoint.
- **Answer, then work** — [lost on a crash](#webhook-answered-200-first--whats-the-risk).

Fix — save, answer, then work:

- **In the request** — check the signature and format, insert the raw event into an inbox table (event ID unique,
  status `NEW`), answer 200. Takes milliseconds.
- **In a worker** — pick `NEW` rows, do the work, set `DONE` in the same transaction as the work's own writes.
- **Failures** — worker crash → the row is still `NEW` and is picked again; sender retry → the unique event ID
  rejects the copy.

Field term: **inbox pattern**.

</details>

### Confirmed, then DB commit failed — now what?
<details><summary>Show answer</summary>

The message is lost: the broker forgot it, and the DB rolled the change back. Typical causes: deadlock, unique key
violation, connection lost at commit.

The broker and the DB can't commit together, so the order decides what a crash costs:

- **Confirm, then commit** — commit fails → message lost.
- **Commit, then confirm** — confirm fails → message comes again → duplicate. Safe if the handler
  [records the message ID in the same transaction](#marked-as-seen-then-crashed--redelivery).

Spring gets the order right when the listener method is `@Transactional`: the DB commits when the method returns, and
the container acks or commits the offset after that.

Kafka-only option: store the consumer's offset in the DB, in the same transaction as the data, and read it from there
on start (`seek`). Then data and position can't disagree.

Handle: commit, then confirm — a duplicate can be fixed, a loss can't.

</details>

### Deploy stops the service mid-work — what's lost?
<details><summary>Show answer</summary>

Every message that was confirmed but still lives only in memory: queued in a thread pool, half-processed, held for a
batch write. Messages not yet confirmed come back to another instance.

A deploy normally sends SIGTERM, waits (Kubernetes: 30 s by default), then kills the process. A crash or an OOM kill
gives no warning at all.

Fixes:

- **Graceful shutdown** — on SIGTERM stop taking new messages, finish or hand back the ones in progress, confirm,
  then exit. Spring stops its listener containers when the context closes and waits for the current batch. The drain
  must fit in the grace period.
- **Never confirm what is only in memory** — the only fix that also covers a kill without warning.

Handle: drain on SIGTERM; against a hard kill only "confirm after save" helps.

</details>

## Losing: dropped by your own code

### Marked as seen, then crashed — redelivery?
<details><summary>Show answer</summary>

The redelivered copy is skipped as a duplicate, and the work never happens. Each step causes the next:

- **ID saved** — the message ID is inserted into a "processed" table and committed.
- **Crash** — before the work.
- **Copy arrives** — ID found → "already done" → confirm → lost.

Fix: record the ID in the same DB transaction as the work. Commit → both happened; rollback → neither, and the retry
finds no ID.

When the work is outside your DB (a call to a payment API), one transaction is impossible. Use a status instead:
`PENDING` before the call, `DONE` after. A copy that finds `PENDING` means "maybe done" → call again with the same
idempotency key, so the API itself drops the copy.

Handle: "seen" must mean "done" — write both in one commit.

</details>

### Two messages, one dedup key — what's lost?
<details><summary>Show answer</summary>

The second message. The dedup check finds the key, decides "duplicate", and confirms without doing the work.

How a key gets too coarse:

- **Entity ID only** — `orderId` as the key: "order paid" and "order shipped" share it; "shipped" is dropped.
- **Business data** — "same customer, same amount, same day": two real equal payments look like one.
- **IDs that repeat** — the sender's counter restarts after a deploy, or one ID covers a whole batch.

Fix: a unique message ID made once by the sender when the event is created (UUID), kept the same on every retry. Or a
key that names the change itself: entity ID + event type + version.

Handle: key too fine → duplicates slip through; key too coarse → real messages are dropped.

</details>

### Skipped as older, but the clock was off?
<details><summary>Show answer</summary>

The newer update is lost. The rule "drop an update whose timestamp is older than the stored one" trusts clocks.
Clocks on different machines can be seconds apart, and a clock can jump back after a sync. Then a newer change
carries a smaller timestamp and is dropped — confirmed, with no error. Two updates with the same timestamp lose one
too.

Fix: compare a version that one owner hands out in order — a version column the source DB increments, or a sequence
number per entity. Inside one Kafka partition, the offset gives the order of all messages with the same key.

Handle: order by a counter from one owner, never by clocks of many machines.

</details>

## Duplicates: do the work once

### Where do duplicates come from?
<details><summary>Show answer</summary>

- **Sender** — the broker saved the message, but its confirm was lost → the sender resends; an outbox relay
  [crashed after the send, before the mark](5.3.3_Outbox.md#outbox-relay-marks-as-sent-then-crashes).
- **Receiver** — a [crash after the work, before the confirm](#crash-after-the-work-before-confirming); a Kafka
  rebalance or a handler slower than the poll or lock time limit
  ([Kafka](../../08_Integration/6_Message_Brokers/Kafka/)).
- **Webhook sender** — your answer was [slower than its timeout](#sender-waits-5-s-work-takes-30-s).
- **User** — a [double click on "Pay"](5.3.5_Synchronous_Calls.md#double-click-on-pay--charge-once).
- **Your own repair paths** — the
  [nightly check and a live event](5.3.6_Reconciliation.md#nightly-check-and-live-event-overlap),
  a [replay of old events](../../08_Integration/3_Event_Driven_Architecture/).

Every path ends the same way: the handler must be [safe to run twice](#message-arrives-twice--do-work-once).

</details>

### Message arrives twice — do work once?
<details><summary>Show answer</summary>

You can't stop the copy from arriving; you make the second run do nothing. Two ways:
- **Remember what you handled** — save the message ID in a table with a unique key, in the same DB transaction as the
  work. The copy finds the ID (or its insert fails) → skip and confirm.
- **Make the work safe to repeat** — "set status = PAID" instead of "add 10", upsert by key, update only if the version
  matches; [turn "add 10" into a repeatable step](#make-add-10-safe-to-repeat).

The ID record and the work must commit together. If not, a crash between them either skips the work or runs it twice.

A handler is **idempotent** when running it twice gives the same result as running it once.

</details>

### Duplicate check: message ID or business data?
<details><summary>Show answer</summary>

- **Message ID** — catches the same message delivered again by the broker, or a retry with the same ID. Misses the same
  fact sent again with a new ID: a double click, a sender that builds a new message on retry, the nightly check.
- **Business key** — payment ID, invoice number, order ID + action. Catches the same fact however it arrives. Risk: if
  the key is too wide, two real events look the same — two real €10 payments from one customer.

Use a business key when one truly names the fact; fall back to the message ID.

Check on what makes the business fact unique, not on the message that carried it.

</details>

### Two copies at once — both pass check?
<details><summary>Show answer</summary>

"Check, then act" is two steps: both threads read "not seen" before either writes. Make the check and the claim one
step:
- **Unique key** — insert the message ID into a table with a unique constraint, in the same transaction as the work.
  The second insert fails → rollback, skip. The DB does the locking.
- **Conditional update** — `UPDATE orders SET status = 'PAID' WHERE id = ? AND status = 'NEW'`. Only one thread gets
  "1 row updated".
- **Same key, same thread** — route by key so all copies go to one consumer in sequence (Kafka partition by key). This
  avoids the race instead of resolving it.

Doesn't work: a check in an in-memory set (other instances don't see it), or SELECT then INSERT without a unique key.

Let one atomic write decide who wins.

</details>

### PostgreSQL: insert message ID, catch duplicate key?
<details><summary>Show answer</summary>

The transaction can't go on. In PostgreSQL any error inside a transaction marks it as failed: every next statement
fails with "current transaction is aborted" until the rollback. In Spring, the exception from the repository also
marks the transaction rollback-only, even if you catch it.

Ways that work:

- **`INSERT … ON CONFLICT DO NOTHING`** — check the row count: 0 → duplicate, skip; 1 → do the work. No error, the
  transaction stays usable.
- **Savepoint** — set one before the insert and roll back to it on the error.
- **Let it roll back** — treat the error as "already done"; fine when nothing else in the transaction must survive.

In PostgreSQL an error ends the transaction; avoid the error instead of catching it.

</details>

### How long to keep handled IDs?
<details><summary>Show answer</summary>

At least as long as a copy can still arrive:
- the sender's retry window — it retries for 3 days, you keep IDs longer than 3 days;
- the broker's retention, if you might replay from it;
- your own replays and nightly checks.

Then drop old IDs — a TTL, or a table split by day where old days are dropped.

If the window has no end (replay from the start), check by business state instead — version check or upsert. That needs
no memory of IDs.

Keep IDs for the longest window a copy can come back in.

</details>

### Make "add 10" safe to repeat?
<details><summary>Show answer</summary>

Tie the change to something that can be used only once:
- **Ledger** — insert a row `(txId, +10)` with a unique `txId`; balance = sum of rows. The copy fails on the unique key.
- **Expected version** — the event carries the version it applies to:
  `UPDATE account SET balance = balance + 10, version = 6 WHERE id = ? AND version = 5`. The copy finds version 6 → no
  change.
- **Processed-ID table** — [save the message ID](#message-arrives-twice--do-work-once) in the same transaction as the
  `+10`.

An increment becomes safe once it is bound to an ID or version that can be used only once.

</details>

### Old update arrives after a newer one?
<details><summary>Show answer</summary>

Version 5 was applied; then a copy of version 4 arrives (a retry, a replay, the nightly check). Applying it writes old
data over new.

Fix: every event carries a version from its owner; write only if it is newer:

```sql
UPDATE customer SET name = ?, version = ? WHERE id = ? AND version < ?
```

0 rows updated → older or the same → skip and confirm.

This also drops plain duplicates with no ID table — but only for "set to" updates, not for "add 10". The version must
come from one owner, [not from clocks](#skipped-as-older-but-the-clock-was-off).

Newer version wins; an older one is dropped.

</details>

## Duplicates: effects outside your DB

### Duplicate hits DB write and API call?
<details><summary>Show answer</summary>

The API call is the problem. The DB write you can
[protect in the same transaction](#message-arrives-twice--do-work-once). The API is outside that transaction:
- the copy sends the email or charges the card again;
- if the DB rolls back after the call, you can't take the email back.

Fixes:
- **Idempotency key** — pass a key built from the message ID (e.g. Stripe's `Idempotency-Key` header). The provider
  drops the repeat.
- **Outbox for outgoing calls** — in the same transaction save "email pending"; a separate step makes the call and marks
  it "sent". A duplicate message finds the row already there.
- **Neither available** — check first ("was it done?") and accept a small gap, or accept duplicates where they are
  harmless.

Your duplicate check covers only what shares your transaction; outside calls need their own key.

</details>

### Duplicate sends a second email — preventable?
<details><summary>Show answer</summary>

Not fully. The mail server takes no idempotency key, and a sent email can't be taken back:

- **Send, then crash before saving "sent"** → the copy sends it again.
- **Save "sent", then crash before sending** → no email at all.

You choose which failure you accept. To make the gap small, save an
[outbox row](5.3.3_Outbox.md#outbox-for-outgoing-rest-calls) "email pending" with a unique key on the message ID: a
duplicate input finds the row and adds nothing. Only a crash in the short gap between the send and the mark repeats
the email.

An action with no key can be at most once or at least once, never exactly once.

</details>

### Handler sends its own event — duplicate input?
<details><summary>Show answer</summary>

Your handler reads `OrderPaid` and sends `InvoiceCreated`. A copy of `OrderPaid` gets through (a crash after the send,
before your confirm) → `InvoiceCreated` is sent twice. With a new UUID each time, the receivers further down can't
tell the two are copies.

Fix: derive the output's ID from the input's — `UUID.nameUUIDFromBytes((orderPaidId + "InvoiceCreated").getBytes())`
— or give the outbox row a unique key on the input ID. Every copy of the input gives the same output ID, and the next
receiver drops it.

Same input → same output ID, so copies stay recognizable down the chain.

</details>

## Receive fast, work later

### Inbox or idempotent consumer — difference?
<details><summary>Show answer</summary>

- **Idempotent consumer** — do the work in the handler and save the message ID in the same transaction as the work.
  Simple; the message waits in the broker until the work is done.
- **Inbox** — first save the raw message in your inbox table (unique ID), confirm at once, then do the work later from
  the table.

Use an inbox when the confirm can't wait for the work: a
[webhook sender with a short timeout](#sender-waits-5-s-work-takes-30-s), slow work, or raw messages you want to keep
for a replay. Both drop duplicates by a unique ID.

</details>


### Unknown message type arrives — error or skip?
<details><summary>Show answer</summary>

TODO - probably to move it to unknown message type or field → 08/1 (Encoding & Evolution)

- **Unknown type → park it.** It usually lands in a `switch` default that logs and returns, so it is confirmed and
  gone. After the sender deploys a new event type, every such event is dropped silently until someone notices. Fix:
  send unknown types to the DLQ or a parking topic and alert; replay them once your code knows the type.
- **Unknown field → ignore it.** That lets the sender add optional fields without breaking you (forward
  compatibility). The risk: a new field that changes meaning (e.g. `currency` added next to an amount) is ignored, and
  your code computes the wrong result. A renamed field arrives as a missing one — `null`.

Jackson: a plain `ObjectMapper` fails on unknown fields (`FAIL_ON_UNKNOWN_PROPERTIES=true`); the one Spring Boot
configures ignores them.

For both: check schema compatibility before deploy (schema registry), and count unknown types and fields in metrics.

Handle: unknown field → ignore; unknown type → park, never drop.

</details>
