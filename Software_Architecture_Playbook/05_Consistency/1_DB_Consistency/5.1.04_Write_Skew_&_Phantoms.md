### What is write skew?
<details><summary>Show answer</summary>

Two transactions read the same data, decide based on it, then each writes a different row.
Neither write overwrites the other, but together they break a rule that each one checked.


**Example:**
A hospital requires at least 1 doctor on call.
- Alice and Bob are both on call.
- They concurrently check the schedule, see 2 doctors, and both update their own status to "off".
- Result: 0 doctors on call.

</details>

### Write skew vs lost update — difference?
<details><summary>Show answer</summary>

- [**Lost update**](5.1.03_Lost_Updates.md#what-is-a-lost-update) — both transactions write the same object. The second write is based on
  an old read and overwrites the first.
- [**Write skew**](#what-is-write-skew) — both read the same data, check a rule against it, then each writes a
  different object. Nothing is overwritten and both writes survive. Each is fine alone, but together they break the
  rule they checked.

It is not a [dirty write](5.1.03_Lost_Updates.md#dirty-write-vs-lost-update--difference) either: 
neither transaction writes over uncommitted data.

Same pattern — read, decide, write — but the writes land on different objects. When they land on the same object,
you get a lost update or a dirty write, depending on timing.

</details>

### Write skew — how to fix?
<details><summary>Show answer</summary>

[Lost-update fixes](5.1.03_Lost_Updates.md#lost-update--how-to-fix) guard the row being written, 
so they miss write skew, where the conflict is in the rows that were read. 
[Atomic writes](5.1.03_Lost_Updates.md#atomic-write-operations---how) and
[automatic detection](5.1.03_Lost_Updates.md#automatic-lost-update-detection--how) don't catch it.

- **Serializable isolation** — the database makes transactions behave as if they ran one after another. The best fix.
- **Lock the rows you read** — the second-best fix, when serializable is not an option:

```sql
  BEGIN;
  SELECT * FROM doctors WHERE on_call = true AND shift_id = 1234 FOR UPDATE; -- locks every row the check reads
  -- app checks: at least 2 on call?
  UPDATE doctors SET on_call = false WHERE name = 'Alice' AND shift_id = 1234;
  COMMIT;
```

Bob's transaction now waits at its own locked read, then counts 1 and is refused.

</details>

### Locking the rows a check reads — what goes wrong?
<details><summary>Show answer</summary>

The fix is `FOR UPDATE` on every row the check counts, then the write:

```sql
SELECT id FROM doctors WHERE on_call AND shift_id = 1234 FOR UPDATE; -- app counts the rows; fewer than 2 → ROLLBACK
UPDATE doctors SET on_call = false WHERE name = 'Alice' AND shift_id = 1234;
```

- **The wrong rows are locked:** only the row you write (Alice's) gets the lock, while the count runs unlocked. Bob
  locks Bob's row, both counts see 2, and both pass.
- **`FOR UPDATE` on a count fails:** PostgreSQL rejects `FOR UPDATE` with aggregate functions like `COUNT(*)`. Fetch
  the rows with the lock and count in the app.
- **An empty result locks nothing:** when the write adds a row (a booking, a username), the check returns 0 rows, so
  there is nothing to lock: a [phantom](#phantoms--how-to-fix).

Lock exactly the rows the check counts, as rows, and only when they exist.

</details>

### Write skew — common scenarios?
<details><summary>Show answer</summary>

- Meeting room booking: check that no booking overlaps the time slot, then insert one. 
  Two bookings for the same room and time.
- Multiplayer game: a lock stops two players moving the same figure, but not moving two different figures to the
  same square.
- Claiming a username: check the name is free, then create the account. Two accounts with the same name (a unique
  constraint fixes this one).
- Double-spending: insert a spending item, sum all items, check the balance stays positive. Two spendings together go
  negative, and neither sees the other.

</details>

### Write skew — what causes it?
<details><summary>Show answer</summary>

Every write skew follows the same three steps:
- **Check:** a `SELECT` tests a rule by searching for rows that match a condition: at least two doctors on call, no
  booking for this room and time, the square is empty, the username is free, money is left.
- **Decide:** the app looks at the result and decides to go ahead or to abort with an error.
- **Write:** if it goes ahead, it makes an `INSERT`, `UPDATE` or `DELETE` and commits.

The write changes the answer to the check. Run the same `SELECT` after the commit and you get a different result: one
doctor fewer on call, the room booked, the square taken, the name taken, less money. So when two transactions run
these steps at the same time, both check the old state, both pass, and both write. Together the writes break the rule
each one checked.

The order can differ: write first, then `SELECT`, then commit or abort based on the result. Same problem.

There are two kinds of check, and the kind decides how hard the fix is:
- **The write changes a row the check returned** (doctors on call). 
  [Lock the rows the check finds](#write-skew--how-to-fix) with `SELECT ... FOR UPDATE`.
- **The write makes a new row match the search** (a new booking, a figure moved onto the square, a new account with
  that name, a new spending item). The check never returned that row, and often returned no rows at all, so
  `FOR UPDATE` has nothing to lock. A write in one transaction that changes the result of another transaction's
  search is a [phantom](#what-is-a-phantom).

Check, decide, write — and the write changes what the check saw.

</details>

### What is a phantom?
<details><summary>Show answer</summary>

A transaction searches for rows that match a condition. Another transaction then inserts, updates, or deletes a
row matching that condition, so the first transaction's search result is already out of date.


**Example:**
E.g., two users book room 101 for 12:00. Each checks "any booking for room 101 at 12:00?", sees none, and inserts one.
Result: double booking.

Also called **phantom read**.

</details>

### Phantoms — how to fix?
<details><summary>Show answer</summary>

A [phantom](#what-is-a-phantom) has no row to lock: the check never returned it, so `FOR UPDATE` locks nothing.
Fixes:

- **Constraint** — the database rejects the second `INSERT`; only for rules a constraint can express:
    - **Unique** — "no two rows with the same value" (username).
    - **Exclusion** (PostgreSQL) — "no two rows that overlap" (bookings)
      ([how](#no-overlapping-bookings--can-the-database-enforce-it)).
- **Give the conflict a row** — every transaction able to break the rule must touch one shared row, so the phantom
  turns into a conflict on that row ([how](#phantom--how-to-give-the-conflict-a-row)).
- **Serializable isolation** — all cases. The database tracks what each search depended on, not just the rows it
  returned.

Locks need a row: use one you have, create one, or let the database guard the search.

</details>

### No overlapping bookings — can the database enforce it?
<details><summary>Show answer</summary>

Yes, in PostgreSQL: an exclusion constraint. Like unique, but a conflict is any operator you name, here "same room and
overlapping time":

```sql
CREATE EXTENSION btree_gist;                                                   -- needed for room_id WITH =
ALTER TABLE bookings ADD EXCLUDE USING gist (room_id WITH =, during WITH &&); -- during: a tstzrange column
```

- **The second overlapping `INSERT` fails**, even when both run at once. No check, no lock, no guard table in code.
- **Catches:**
    - PostgreSQL only.
    - The time must be stored as one range column, not two separate columns.
    - The error comes from the `INSERT`, so handle it there as "room taken".

A rule the database can state is a rule no code path can forget.

</details>

### Phantom — how to give the conflict a row?
<details><summary>Show answer</summary>

A [phantom](#what-is-a-phantom) has no row to lock, so you give the conflict one: a row that stands for the group the
rule checks. Every transaction that can break the rule must touch it before its check. Two independent choices:

- **Where the row comes from:**
    - **Existing parent** — the business model already has one row per group: `room` for its bookings.
    - **Row created only for the conflict** — no parent fits: e.g. one row per room per 15 minutes.
- **How the row is guarded:**
    - **Pessimistic** — lock it with `FOR UPDATE` before the check; the second transaction waits.
    - **Optimistic** — read its version before the check, bump it at the end; the second transaction gets 0 rows and
      retries.

Names:
- **Coarse-Grained Lock** (Fowler) — parent, pessimistic ([SQL](#coarse-grained-lock--how)).
- **Aggregate root version** (DDD) — parent, optimistic ([SQL](#aggregate-root-version--how)).
- **Materializing conflicts** (DDIA) — created row, pessimistic; a last resort, locking leaks into the schema
  ([SQL](#materializing-conflicts--how)).
- **Guard row with a version** (no standard name) — created row, optimistic
  ([SQL](#guard-row-with-a-version--how)).

Pick the row (parent or created), then guard it (lock or version).

</details>

### Coarse-grained lock — how?
<details><summary>Show answer</summary>

Lock the parent row before the check, so every transaction for that parent queues on it:

```sql
BEGIN;
SELECT * FROM rooms WHERE id = 1 FOR UPDATE;                           -- every booking for room 1 waits here
SELECT COUNT(*) FROM bookings
WHERE room_id = 1 AND start_time < '13:00' AND end_time > '12:00';     -- 0: no overlap
INSERT INTO bookings (room_id, start_time, end_time) VALUES (1, '12:00', '13:00');
COMMIT;                                                                -- lock released
```

A second booking for 12:30–13:30 waits at the room lock. After the first commits, its check counts 1 and it is
refused.

Catches:
- **Read committed only:** at repeatable read the second transaction's snapshot predates the first commit, so its
  check still counts 0.
- **Every write path must lock the parent**, or it 
  [skips the queue](5.1.03_Lost_Updates.md#explicit-locking--what-can-go-wrong).
- **Coarse:** a booking for 15:00 in the same room waits too.

</details>

### Aggregate root version — how?
<details><summary>Show answer</summary>

Read the parent's version before the check, bump it at the end:

```sql
BEGIN;
SELECT version FROM rooms WHERE id = 1;                                -- 5
SELECT COUNT(*) FROM bookings
WHERE room_id = 1 AND start_time < '13:00' AND end_time > '12:00';     -- 0: no overlap
INSERT INTO bookings (room_id, start_time, end_time) VALUES (1, '12:00', '13:00');
UPDATE rooms SET version = 6 WHERE id = 1 AND version = 5;             -- 0 rows → ROLLBACK, retry
COMMIT;
```

A second booking for 12:30–13:30 also read version 5. Its `UPDATE` waits for the first one's row lock, then matches
0 rows: rollback. The retry reads version 6, counts 1 and is refused.

Catches:
- **Read the version before the check:** read it after, and the first can commit in between: an old count, a new
  version, and the bump passes.
- **Every write path must bump the version**, even when the parent itself doesn't change.
- **Coarse:** a booking for 15:00 in the same room also fails and retries.

</details>

### Phantom guard table — how to set up?
<details><summary>Show answer</summary>

One row per unit the rule covers (here: room × 15 minutes), no business data. The row set must exist before any
transaction needs it.

- **Pessimistic** — the key is enough, the rows are only locked with `FOR UPDATE`:

    ```sql
    CREATE TABLE room_slots (
      room_id    BIGINT    NOT NULL,
      slot_start TIMESTAMP NOT NULL,
      PRIMARY KEY (room_id, slot_start)
    );
    ```

- **Optimistic** — add a version to bump:

    ```sql
    CREATE TABLE room_slots (
      room_id    BIGINT    NOT NULL,
      slot_start TIMESTAMP NOT NULL,
      version    BIGINT    NOT NULL DEFAULT 0,
      PRIMARY KEY (room_id, slot_start)
    );
    ```

- **Fill ahead** — e.g. 6 months (PostgreSQL):

    ```sql
    INSERT INTO room_slots (room_id, slot_start)
    SELECT r.id, s
    FROM rooms r,
         generate_series(date_trunc('day', now()), now() + interval '6 months', interval '15 minutes') AS s
    ON CONFLICT DO NOTHING;                          -- safe to rerun
    ```

- **Keep the window moving** — a scheduled job (e.g. nightly) reruns the fill, so there are always 6 months ahead. A
  new room needs its slots created in the same transaction that adds the room.

Trap: **a missing row means no protection, silently.** A booking beyond the window locks or bumps nothing and goes
through. Check that you got every slot you expected (4 slots for 12:00–13:00), and refuse the booking if not.

Guard rows are only as good as their coverage: create them ahead, keep creating them, refuse what they don't cover.

</details>

### Guard row with a version — how?
<details><summary>Show answer</summary>

No parent fits, so create rows only to carry a version, e.g. `room_slots` with one row per room per 15 minutes,
created ahead of time. Read the slots' versions before the check, bump each at the end:

```sql
BEGIN;
SELECT id, version FROM room_slots
WHERE room_id = 1 AND slot_start >= '12:00' AND slot_start < '13:00';  -- 4 slots, e.g. id 101, version 3
SELECT COUNT(*) FROM bookings
WHERE room_id = 1 AND start_time < '13:00' AND end_time > '12:00';     -- 0: no overlap
INSERT INTO bookings (room_id, start_time, end_time) VALUES (1, '12:00', '13:00');
UPDATE room_slots SET version = 4 WHERE id = 101 AND version = 3;      -- one per slot; any 0 rows → ROLLBACK, retry
COMMIT;
```

A second booking for 12:30–13:30 bumps the 12:30 and 12:45 slots too, so one of its `UPDATE`s matches 0 rows and it
retries. A booking for 15:00 touches other slots and goes through.

Catches:
- **The rows must exist:** a missing slot is never bumped, and nothing tells you.
- **Every write path must bump the slots it covers.**
- **Locking leaks into the data model**, as with [materializing conflicts](#materializing-conflicts--how).

</details>

### Materializing conflicts — how?
<details><summary>Show answer</summary>

No parent row fits, so you create rows whose only job is to be locked.

Room booking: a `room_slots` table with one row per room per 15 minutes, created ahead
([setup](#phantom-guard-table--how-to-set-up)). No booking data, only rows to lock.

```sql
BEGIN;
SELECT * FROM room_slots
WHERE room_id = 1 AND slot_start >= '12:00' AND slot_start < '13:00'
FOR UPDATE;                                                            -- locks the 4 slots of 12:00–13:00
SELECT COUNT(*) FROM bookings
WHERE room_id = 1 AND start_time < '13:00' AND end_time > '12:00';     -- 0: no overlap
INSERT INTO bookings (room_id, start_time, end_time) VALUES (1, '12:00', '13:00');
COMMIT;                                                                -- locks released
```

A second booking for 12:30–13:30 needs the 12:30 and 12:45 slots too, so it waits until the first commits. Then,
under read committed, its check sees the new booking and it is refused. A booking for 15:00 locks other slots and
does not wait.

</details>

### Phantom: guard rows vs serializable — which to choose?
<details><summary>Show answer</summary>

- **Guard rows** ([setup](#phantom-guard-table--how-to-set-up)) — pick when one rule is hot and the rest of the system
  must stay at read committed.
    - Plus: only the transactions for that rule pay; real conflicts collide, nothing else does.
    - Cost:
        - **Hard and error-prone:**
          - you must pick the slot size;
          - create the rows ahead and keep creating them;
          - your code must cover [every write path](5.1.03_Lost_Updates.md#explicit-locking--what-can-go-wrong): 
            one that skips the guard rows is unprotected, and nothing warns you.
        - **Locking leaks into the data model:** the table exists only for concurrency control.
- **Serializable** — pick when there are many rules or complex checks (sums, several tables), or you can't trust every
  write path.
    - Plus: no per-rule code, no path can forget.
    - Cost: every transaction on that data must run serializable, and it is slower:
      - waits on locks (MySQL, SQL Server);
      - aborts and retries (PostgreSQL).

Guard rows: a local fix you must maintain. Serializable: a global fix you pay for in speed.

</details>

### Write skew vs phantom — difference?
<details><summary>Show answer</summary>

- [**Write skew**](#what-is-write-skew) — the problem: two transactions
  [check, decide and write](#write-skew--what-causes-it), and each write changes what the other's check saw. Together
  they break the rule.
- [**Phantom**](#what-is-a-phantom) — an effect: a write in one transaction adds a row that another transaction's
  search never returned. In read/write transactions it causes the harder kind of write skew.

Two kinds of write skew, depending on whether the changed row was in the check's result:
- **Yes** (doctors on call): the row exists and the check returned it, so you can lock it with `FOR UPDATE`.
- **No** (booking, username): the write adds a row the check never returned. That is a phantom, and there is nothing
  to lock.

Fixes:
- Serializable isolation fixes both kinds.
- [Locking the rows you read](#write-skew--how-to-fix) fixes only the first kind.
- [The phantom kind](#phantoms--how-to-fix) needs serializable or
  [a row for the conflict](#phantom--how-to-give-the-conflict-a-row). 
  Simple cases like the username can use a unique constraint.

Write skew is the problem; a phantom is the hard version of it, where the row to lock doesn't exist yet.

</details>
