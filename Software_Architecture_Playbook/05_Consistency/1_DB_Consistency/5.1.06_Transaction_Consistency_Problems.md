## Transaction Consistency Problems

Organised by the problems a code shape causes, not by mechanism. The mechanisms live in other files; this file brings
them together around one question: what breaks, which approaches fix it, and where each approach still causes trouble.
The links to other files are the point of this file, not duplicates to clean up.

### Transaction consistency problems — which kinds?
<details><summary>Show answer</summary>

- **[Atomicity](#several-writes-must-all-happen--what-can-go-wrong)** — all writes or none: several writes must
  succeed together; a failure in between leaves half the change.
- **[Read skew](#several-reads-must-fit-together--what-can-go-wrong)** — reads that must fit: several
  reads must show one moment; another commit in between mixes before and after.
- **[Lost update](#read-a-row-write-it-back--what-can-go-wrong)** — read one row, write the same row: the new value
  is computed from an old read, so another write in between is overwritten.
- **[Write skew, phantom](#read-a-set-of-rows-write-another--what-can-go-wrong)** — read a set of rows, write
  another row: each write changes what the other's check read, and new rows in the set can't be locked.

All together → see one moment → don't overwrite one row → don't break a rule over a set.

</details>

### Several writes must all happen — what can go wrong?
<details><summary>Show answer</summary>

E.g. a debit and a credit, an order and its lines: each write is fine alone, half of them is wrong data.

- **Breaks — half the change stays:** each write commits on its own (auto-commit, or each call in its own
  transaction). A crash or error after the first write leaves it in place.
- **Fix — one transaction:** all writes commit together; on any failure the database undoes them all
  ([atomicity](5.1.01_Transactions.md#writes-fail-halfway--how-to-avoid-partial-data)), so the app can just retry.

Several writes that belong together go into one transaction.

</details>

### Several writes in one transaction — what still breaks?
<details><summary>Show answer</summary>

- **Retry after a timeout runs it twice:** the commit succeeded, only the reply was lost
  ([fix](5.1.01_Transactions.md#commit-succeeded-reply-lost-retry--fix)).
- **Effects outside the database stay:** an email or HTTP call is not undone by a rollback
  ([fix](5.1.01_Transactions.md#retry-repeats-an-external-side-effect--fix)).
- **JPA and Spring Data — the transaction isn't really there:**
    - **No proxy, no transaction:** a call through `this`, or a method without `@Transactional`, makes each
      repository call commit on its own.
    - **A checked exception commits:** by default Spring rolls back only on unchecked exceptions.

One transaction covers only database writes, and only if it really spans them and really rolls back.

</details>

### Several reads must fit together — what can go wrong?
<details><summary>Show answer</summary>

E.g. a report sums many accounts, an integrity check compares orders with invoices.

- **Breaks — a mix of before and after:** at read committed each query sees the latest commit. A commit between two
  queries makes each value right, but together they don't fit ([read skew](5.1.02_Isolation_Levels.md#what-is-read-skew)).
- **Fix:**
    - **One query** — a `JOIN` or subquery sees one moment, even at read committed.
    - **Snapshot isolation** — the whole transaction sees one moment; for reads that need many queries: reports,
      backups, checks ([how](5.1.02_Isolation_Levels.md#read-skew--how-to-fix)).

Reads that must fit come from one moment: one query, or one snapshot.

</details>

### Several reads must fit together — where do the fixes go wrong?
<details><summary>Show answer</summary>

- **Fix applied wrong:**
    - **The reads run in separate transactions:** no `@Transactional`, or auto-commit, so each query is its own
      transaction and gets its own moment. The snapshot never covers the whole report.
    - **The wrong level is asked for:** PostgreSQL and MySQL call snapshot repeatable read, Oracle calls it
      serializable, SQL Server needs the admin to allow it
      ([which to ask for](5.1.02_Isolation_Levels.md#snapshot-isolation-wanted--which-level-to-ask-for-in-each-database)).
- **Fix applied right, still costs:**
    - **A long snapshot holds old row versions:** the database can't clean them up while the snapshot may need them,
      so busy tables grow ([why](5.1.02_Isolation_Levels.md#snapshot-isolation--implementation)). Solution:
      - run long reports and backups on a replica 
      - don't keep the transaction open longer than the reads.

All reads in one transaction, at the level your database really calls snapshot; long ones off the main database.

</details>

### Read a row, write it back — what can go wrong?
<details><summary>Show answer</summary>

E.g. a counter, a stock count, a balance, a page edited and saved.

- **Breaks — one change is lost:** two transactions read the same value, each computes a new one, and the second
  write overwrites the first ([lost update](5.1.03_Lost_Updates.md#what-is-a-lost-update)).
- **Fix** ([overview](5.1.03_Lost_Updates.md#lost-update--how-to-fix)):
    - **Pessimistic — the second writer waits:**
        - **Atomic write** — the database computes the new value in one statement, `SET x = x + 1`
          ([how](5.1.03_Lost_Updates.md#atomic-write-operations---how),
          [watch: hot row](5.1.03_Lost_Updates.md#hot-row-under-many-writers--what-helps)).
        - **Lock on read** — `FOR UPDATE` when app logic sits between read and write
          ([how](5.1.03_Lost_Updates.md#explicit-locking--how),
          [watch: forgotten lock, deadlock, lock in app memory](5.1.03_Lost_Updates.md#explicit-locking--what-can-go-wrong)).
    - **Optimistic — the second writer fails and retries:**
        - **Version check** — `WHERE version = ?`; 0 rows → retry. The only one that works across user think time
          ([how](5.1.03_Lost_Updates.md#compare-and-set--how)).
            - Watch:
                - [the check runs against a snapshot](5.1.03_Lost_Updates.md#compare-and-set--when-is-it-unsafe)
                - [the version must come from the user's read](5.1.03_Lost_Updates.md#version-check-across-requests--where-must-the-version-come-from)
        - **Database detection** — PostgreSQL at repeatable read aborts the second writer
          ([how](5.1.03_Lost_Updates.md#automatic-lost-update-detection--how),
          [watch: not on MySQL](5.1.03_Lost_Updates.md#automatic-lost-update-detection--which-databases)).
    - **Across replicas — merge** — no single copy to lock or check
      ([how](5.1.03_Lost_Updates.md#lost-updates-across-replicas--fix)).

Let the database do the math, make the second writer wait, or make it fail and retry.

</details>

### Read a set of rows, write another — what can go wrong?
<details><summary>Show answer</summary>

E.g. doctors on call, a room booking, a free username, a balance summed from ledger rows.

- **Breaks — a rule over the set, nothing overwritten:** both transactions check the same set, both pass, and each
  writes a different row ([write skew](5.1.04_Write_Skew_&_Phantoms.md#what-is-write-skew)). When the write adds a new
  row to the set, the check had nothing to lock ([phantom](5.1.04_Write_Skew_&_Phantoms.md#what-is-a-phantom)).
- **Fix** ([overview](5.1.04_Write_Skew_&_Phantoms.md#write-skew-vs-phantom--difference)):
    - **Pessimistic — the second writer waits:**
        - **Lock the rows the check reads** — `FOR UPDATE` on the check; only when those rows exist
          ([how](5.1.04_Write_Skew_&_Phantoms.md#write-skew--how-to-fix),
          [watch: wrong rows, COUNT, empty result](5.1.04_Write_Skew_&_Phantoms.md#locking-the-rows-a-check-reads--what-goes-wrong)).
        - **Lock one shared row** — a parent or a row created for it; works for phantoms too
          ([how](5.1.04_Write_Skew_&_Phantoms.md#phantom--how-to-give-the-conflict-a-row)).
            - Watch:
                - [read committed only, every path](5.1.04_Write_Skew_&_Phantoms.md#coarse-grained-lock--how)
                - [guard rows upkeep](5.1.04_Write_Skew_&_Phantoms.md#phantom-guard-rows-vs-serializable--which-to-choose)
    - **Optimistic — the second writer fails and retries:**
        - **Bump a shared row's version** — the same shared row, guarded by a version
          ([how](5.1.04_Write_Skew_&_Phantoms.md#aggregate-root-version--how)).
            - Watch:
                - [read the version first](5.1.04_Write_Skew_&_Phantoms.md#aggregate-root-version--how)
                - [version on the written row](5.1.05_Lost_Updates_and_Write_Skew_with_ORM.md#orm-version--why-no-help-against-write-skew)
    - **The database guards it:**
        - **Constraint** — unique for "no two equal values" (username), exclusion in PostgreSQL for "no two overlaps"
          (bookings) ([how](5.1.04_Write_Skew_&_Phantoms.md#phantoms--how-to-fix),
          [watch: PostgreSQL only, one range column](5.1.04_Write_Skew_&_Phantoms.md#no-overlapping-bookings--can-the-database-enforce-it)).
        - **Serializable isolation** — all cases; the database tracks what each check read
          ([how](5.1.06_Serializability.md#serializable-isolation--how-is-it-built)).
            - Watch:
                - [retry the whole transaction](5.1.06_Serializability.md#serialization-failure--what-must-the-app-do)
                - [every transaction serializable](5.1.04_Write_Skew_&_Phantoms.md#phantom-guard-rows-vs-serializable--which-to-choose)

Make the two transactions meet: on the rows read, on one shared row, on a constraint, or in the database's tracking.

</details>
