### Transfer crashes between debit and credit — what happens?
<details><summary>Show answer</summary>

**Verdict:** if both `UPDATE`s run in one transaction, nothing is lost: the database undoes the debit. If each ran as
its own auto-committed statement, the money is gone.

**Reasoning:** [several writes must all happen](5.1.06_Transaction_Consistency_Problems.md#several-writes-must-all-happen--what-can-go-wrong).
After a crash, the database uses its log to roll back every transaction that did not commit, so the app can simply
retry the whole transfer.

**Trade-off:** the app must handle the failure itself:
- **Retry or not:** only transient errors are worth a retry
  ([which](5.1.01_Transactions.md#transaction-failed--how-to-handle-it)).
- **The retry has its own traps:** e.g. the commit succeeded but the reply was lost, and a blind retry moves the
  money twice ([traps](5.1.01_Transactions.md#retry--when-does-it-go-wrong)).

</details>

### Report from many queries shows money missing — why?
<details><summary>Show answer</summary>

**Verdict:** the report read some accounts before a transfer committed and others after it. Run the whole report in
one snapshot: snapshot isolation (`REPEATABLE READ` in PostgreSQL).

**Reasoning:** [several reads must fit together](5.1.06_Transaction_Consistency_Problems.md#several-reads-must-fit-together--what-can-go-wrong).
A transfer moves $100 from A to B. Query 1 reads B before the transfer, query 2 reads A after it: the total is $100
short. Rerun the report and it is correct, because the problem is the timing, not the data.

**Trade-off:** a long snapshot makes the database keep old row versions until it ends, and busy tables grow
([what to do](5.1.06_Transaction_Consistency_Problems.md#several-reads-must-fit-together--where-do-the-fixes-go-wrong)).

</details>

### Page-view counter loses increments under load — why?
<details><summary>Show answer</summary>

**Verdict:** the app reads the count, adds 1 in code and writes the result back. Two requests read 42 and both write
43. Let the database do the math:

```sql
UPDATE pages SET views = views + 1 WHERE id = 7;
```

**Reasoning:** [read a row, write it back](5.1.06_Transaction_Consistency_Problems.md#read-a-row-write-it-back--what-can-go-wrong).
The one-statement version is safe: the database locks the row from its read to its write.

**Trade-off:** every increment of one row now waits for the previous one
([hot row](5.1.03_Lost_Updates.md#hot-row-under-many-writers--what-helps)).

</details>

### Last item in stock sold twice — fix?
<details><summary>Show answer</summary>

**Verdict:** check and write in one statement, then look at the row count:

```sql
UPDATE products SET stock = stock - 1 WHERE id = 42 AND stock > 0; -- 1 row: sold; 0 rows: sold out
```

**Reasoning:** [read a row, write it back](5.1.06_Transaction_Consistency_Problems.md#read-a-row-write-it-back--what-can-go-wrong).
"Read stock, if it is above 0 then update" lets both buyers see 1. In the one-statement version the second buyer's
`UPDATE` waits for the first one's row lock, then checks `stock > 0` again on the new value and changes 0 rows. A
`CHECK (stock >= 0)` constraint is a cheap safety net on top.

**Trade-off:** all buyers of one product queue on one row
([hot row](5.1.03_Lost_Updates.md#hot-row-under-many-writers--what-helps)).

</details>

### Two agents edit one ticket, one edit vanishes — fix?
<details><summary>Show answer</summary>

**Verdict:** an optimistic check with a version. The page gets `version = 5` with the ticket and sends it back on
save:

```sql
UPDATE tickets SET body = ?, version = 6 WHERE id = 7 AND version = 5; -- 0 rows: someone saved first
```

On 0 rows, show the agent the newer ticket instead of overwriting it.

**Reasoning:** [read a row, write it back](5.1.06_Transaction_Consistency_Problems.md#read-a-row-write-it-back--what-can-go-wrong).
The edit spans user think time across two requests. A row lock lives only inside an open transaction, so it can't
wait for the agent; a version can travel with the page
([where it must come from](5.1.03_Lost_Updates.md#version-check-across-requests--where-must-the-version-come-from)).

**Trade-off:** the second agent has to redo or merge the edit. If conflicts are common, save per field or show
"someone else is editing".

</details>

### Moved to MySQL, overwrites go unnoticed — why?
<details><summary>Show answer</summary>

**Verdict:** the code relied on PostgreSQL's repeatable read, which aborts the second of two transactions that
overwrite the same row. MySQL InnoDB's repeatable read does not detect lost updates, so the second write simply wins
([which databases](5.1.03_Lost_Updates.md#automatic-lost-update-detection--which-databases)). Protect the writes
explicitly: an atomic `UPDATE`, `SELECT ... FOR UPDATE`, or a version check.

**Reasoning:** [read a row, write it back](5.1.06_Transaction_Consistency_Problems.md#read-a-row-write-it-back--what-can-go-wrong).
Isolation level names are not portable: "repeatable read" gives different guarantees in different databases.

**Trade-off:** explicit protection is more code, but it works on any database and shows the intent in the code.

</details>

### Multi-region cart loses items — why?
<details><summary>Show answer</summary>

**Verdict:** the database settles concurrent writes with last write wins: it keeps one write and drops the others.
Keep both versions (siblings) and merge them, e.g. as a union of the carts, or use a CRDT set.

**Reasoning:** [read a row, write it back](5.1.06_Transaction_Consistency_Problems.md#read-a-row-write-it-back--what-can-go-wrong),
across replicas. Multi-leader and leaderless replication accept writes on several nodes at once, so there is no single
up-to-date copy to lock or compare against ([merge](5.1.03_Lost_Updates.md#lost-updates-across-replicas--fix)).

**Trade-off:** removals don't merge cleanly: a union brings deleted items back, unless each delete is kept as a marker
(a tombstone).

</details>



### Both on-call doctors went off call — why?
<details><summary>Show answer</summary>

**Verdict:** write skew. Both checked "at least 2 on call", both passed, and each took itself off call. Lock the rows
the check reads, or run the transaction at serializable:

```sql
SELECT id FROM doctors WHERE on_call AND shift_id = 1234 FOR UPDATE; -- app counts the rows
```

**Reasoning:** [read a set of rows, write another](5.1.06_Transaction_Consistency_Problems.md#read-a-set-of-rows-write-another--what-can-go-wrong).
Each transaction wrote a different row, so nothing was overwritten. Fixes that guard the written row (versions,
PostgreSQL's lost-update detection) see no conflict: it sits in the rows that were read.

**Trade-off:** the lock makes every change to that shift wait in line, and it must lock the counted rows, not a
`COUNT` ([traps](5.1.04_Write_Skew_&_Phantoms.md#locking-the-rows-a-check-reads--what-goes-wrong)). Serializable
needs no lock in the code, but it needs a retry on abort.

</details>

### Meeting room double-booked despite a check — fix?
<details><summary>Show answer</summary>

**Verdict:** the check finds no overlapping booking, so there is no row to lock, and both inserts pass: a phantom. On
PostgreSQL, let the database reject overlaps with an exclusion constraint
([how](5.1.04_Write_Skew_&_Phantoms.md#no-overlapping-bookings--can-the-database-enforce-it)). Elsewhere: lock the
room's row before the check, or run at serializable.

**Reasoning:** [read a set of rows, write another](5.1.06_Transaction_Consistency_Problems.md#read-a-set-of-rows-write-another--what-can-go-wrong).
`FOR UPDATE` on the check locks only the rows it returns, and it returns none. The constraint compares the new row
with all rows, including ones still being inserted by other transactions.

**Trade-off:** the constraint is PostgreSQL-only. Locking the room's row works anywhere, but it also blocks bookings
that don't overlap, and it is safe only at read committed
([coarse-grained lock](5.1.04_Write_Skew_&_Phantoms.md#coarse-grained-lock--how)).

</details>

### Same username registered twice — fix?
<details><summary>Show answer</summary>

**Verdict:** a unique constraint on the username, and the violation is handled as "name taken".

**Reasoning:** [read a set of rows, write another](5.1.06_Transaction_Consistency_Problems.md#read-a-set-of-rows-write-another--what-can-go-wrong).
"Check the name is free, then insert" checks for a row that doesn't exist yet, so nothing can be locked. The unique
index is checked at insert time: the second insert waits for the first transaction, then fails
([constraint](5.1.04_Write_Skew_&_Phantoms.md#phantoms--how-to-fix)).

**Trade-off:** the error now comes from the insert, not from the check, so the code must handle it there. For
case-insensitive names, put the index on `lower(username)`.

</details>

### Concurrent purchases drive a balance negative — why?
<details><summary>Show answer</summary>

Each purchase inserts a ledger row, sums the account's rows and checks that the sum stays at or above 0.

**Verdict:** write skew through inserts: each sum misses the other purchase's new row. Two fixes:
- Lock the account row first (`SELECT ... FROM accounts WHERE id = ? FOR UPDATE`), then sum and insert. Safe at read
  committed ([coarse-grained lock](5.1.04_Write_Skew_&_Phantoms.md#coarse-grained-lock--how)).
- Keep a balance column and spend with one conditional statement:
  `UPDATE accounts SET balance = balance - 50 WHERE id = ? AND balance >= 50` (0 rows: not enough money).

**Reasoning:** [read a set of rows, write another](5.1.06_Transaction_Consistency_Problems.md#read-a-set-of-rows-write-another--what-can-go-wrong).
The rows that matter are new rows the sum never saw, so locking the summed rows doesn't help. The account row is one
existing row that every purchase can queue on.

**Trade-off:** purchases on one account run one at a time, which is usually fine. The account lock works only if
every path that spends takes it.

</details>
