### Writes fail halfway — how to avoid partial data?
<details><summary>Show answer</summary>

A **transaction**: group the reads and writes into one unit that runs as a single operation.
- All succeed → **commit**.
- Any fails → **abort** (**rollback**): nothing is left half-written, so the app can safely retry.

</details>

### Transactions — main gain for the app?
<details><summary>Show answer</summary>

Any failure undoes the whole unit, so the app never has to find and clean up half-done changes.
Result: **simple error handling** — on failure, just retry or report the error.

</details>

### Transactions — what do they cost?
<details><summary>Show answer</summary>

- **Performance**, always: concurrent transactions must be coordinated — locks, waiting for each other, conflict checks.
- **Availability**, when one transaction spans several nodes: all of them must be reachable to commit. One node down
  or cut off by the network → the transaction waits or aborts.

So not every app needs full transactions: some weaken the guarantees, some drop them entirely.

</details>

### Transactions or not — which default?
<details><summary>Show answer</summary>

**Keep transactions by default.** 
- With them, some spots get slow, and you fix those bottlenecks when they show up. You pay in a few places, later.
- Without them, all app code must handle half-done writes itself. You pay everywhere, always.

Exception: some systems need [speed or availability more than these guarantees](#transactions--what-do-they-cost).

</details>

### Does NoSQL support transactions?
<details><summary>Show answer</summary>

Early NoSQL (late 2000s) dropped transactions or weakened what the word meant, believing transactions can't scale.
That belief turned out wrong: **NewSQL** databases (e.g., Spanner, CockroachDB, TiDB) scale with full transactions.
Many NoSQL stores have since added transactions back, often with limits.

</details>

### Transactions — what safety do they guarantee?
<details><summary>Show answer</summary>

Transactions provide **ACID** guarantees to ensure data integrity:
- **Atomicity** (all or nothing): if any step fails, the whole transaction is rolled back.
  [No partial updates](#writes-fail-halfway--how-to-avoid-partial-data).
- **Consistency** (valid state): data moves from one valid state to another, obeying the app's rules.
- **Isolation** (independent): concurrent transactions do not interfere; they act as if run one after the other.
- **Durability** (permanent): once committed, changes are saved to disk (or copied to other nodes) and survive a crash.

**Pronunciation** (stressed syllable in caps):
- **ACID** — one word, like "acid": /ˈæsɪd/, "AS-id" (the "a" as in *apple*)
- **Atomicity** — /ˌætəˈmɪsəti/, "at-uh-MIS-uh-tee"
- **Consistency** — /kənˈsɪstənsi/, "kun-SIS-tun-see"
- **Isolation** — /ˌaɪsəˈleɪʃən/, "eye-suh-LAY-shun"
- **Durability** — /ˌdʊrəˈbɪləti/, "door-uh-BIL-uh-tee"

</details>

### ACID consistency — what can the database enforce?
<details><summary>Show answer</summary>

To enforce consistency and ensure the database only moves between valid states, you declare invariants as part of the
schema. These are implemented as constraints, such as:
- Foreign-key constraints
- Uniqueness constraints
- Check constraints

</details>

### What does Isolation (in ACID) guarantee, and how is it implemented in practice?
<details><summary>Show answer</summary>

- **Ideal — serializability**: 
  ensuring concurrent transactions don't interfere and the result is as if they ran one after another.
- **Practice — weaker levels** (e.g., snapshot isolation): serializability costs performance, so most databases use
  weaker levels by default, and some race conditions remain. Oracle's "serializable" is really snapshot isolation.

</details>

### Atomicity vs. Isolation: Why is the un-updated email counter an Isolation issue?
<details><summary>Show answer</summary>

Same transaction: (1) insert an email, (2) increase the unread counter.
- **Atomicity (deals with failures)**: if the database crashes after step 1, the insert is rolled back. 
  It gives all or nothing in the end, but it doesn't hide work in progress.
- **Isolation (deals with concurrency)**: while the transaction is between steps 1 and 2, no other query can see the
  half-done state.

The user sees the email with a counter of 0 and nothing has failed, so their read wasn't isolated from the in-progress
write. Atomicity steps in only if the write fails and must be undone.

</details>

### Atomic — Java vs ACID meaning?
<details><summary>Show answer</summary>

- **Java atomic — concurrency and consistency:** several threads always see a consistent state, never a half-done
  one (`incrementAndGet()`, `synchronized`). In ACID terms this is
  [isolation](#what-does-isolation-in-acid-guarantee-and-how-is-it-implemented-in-practice).
- **ACID atomicity — failures:** if the work fails halfway,
  [everything is undone](#writes-fail-halfway--how-to-avoid-partial-data). Plain Java has no such undo: a
  `synchronized` block that updates one of two fields and then throws keeps that first update.

A better name for ACID atomicity would be **abortability**.

</details>

### ACID durability — what does it promise?
<details><summary>Show answer</summary>

Once a transaction is committed, its data is not lost, even if the database crashes or the power goes out.

</details>

### Commit acknowledged — durability considerations?
<details><summary>Show answer</summary>

A commit guarantees only what your setup promises. A confirmed write can still be lost when it was confirmed too early:
- **Before other nodes have a copy:** the leader confirms, then dies; the new leader doesn't have the write.
  - Database with async replication.
  - Kafka with `acks=1` - only the leader broker has the message when it confirms.
- **Before it reaches disk:** a crash loses the last moment of writes.
  - PostgreSQL with `synchronous_commit = off` (default is `on`; turned off on purpose for speed, often per
    transaction).

Durability is a setting you choose, usually traded for speed.

</details>

### Transaction failed — how to handle it?
<details><summary>Show answer</summary>

Classify the error first:
- **Transient → retry** (a few times, with backoff): the next attempt can succeed.
  - Deadlock.
  - Serialization / isolation conflict (PostgreSQL `40001`).
  - Short network outage, failover.
- **Permanent → don't retry, report the error:** a retry fails the same way.
  - Constraint violation, invalid data.

</details>

### Retry — when does it go wrong?
<details><summary>Show answer</summary>

- [The commit succeeded, only the reply was lost](#commit-succeeded-reply-lost-retry--fix) → it runs twice.
- [Overload or heavy contention](#retries-under-overload--fix) → retries add load and make it worse (retry storm).
- [Side effects outside the database](#retry-repeats-an-external-side-effect--fix) (e.g., an email) → they repeat on
  every retry.
- [The client crashes while retrying](#client-crashes-mid-retry--fix) → the retry lived only in its memory, the write
  is lost.

</details>

### Commit succeeded, reply lost, retry — fix?
<details><summary>Show answer</summary>

- A unique id per operation, checked by the database (unique key).
- A duplicate is answered as success.

</details>

### Retries under overload — fix?
<details><summary>Show answer</summary>

- Few attempts.
- Backoff with jitter.
- A retry budget.
- A circuit breaker.

</details>

### Retry repeats an external side effect — fix?
<details><summary>Show answer</summary>

- Send after commit.
- Send via an outbox.

</details>

### Client crashes mid-retry — fix?
<details><summary>Show answer</summary>

Keep the work in a durable place until done:
- A queue.
- An uncommitted Kafka offset.

</details>
