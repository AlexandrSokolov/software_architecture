### One-to-many data: relational or document?
<details><summary>Show answer</summary>

Example: a user profile with many jobs, many schools and many contacts. Each list belongs only to this one profile.

- **Relational**: users, jobs, schools and contacts sit in separate tables. To load one profile, you run one query per
  table (by `user_id`), or one big join across all of them.
- **Document**: the whole profile is one JSON document, with the lists nested inside. One read returns everything,
  which is faster and simpler.

Why the document fits: one-to-many links from one owner make the data a **tree**. The document stores the tree as it is, 
while tables cut it into pieces that must be joined back. Keeping related data in one place is called **locality**.

This holds only while the profile is read as a whole. 
If you search across the parts, like all users who went to one university, tables win: 
flat rows are easier to search than lists nested inside many documents.

</details>

### Why pick the document model?
<details><summary>Show answer</summary>

- **Flexible schema** — records can have different fields, and adding a field needs no table change.
- **Faster reads** — the whole record sits in one place ([locality](#one-to-many-data-relational-or-document)), so one
  read returns it.
- **Closer to app objects** — for some apps, a document looks like the object in code, so less translation is needed.

</details>

### Why pick the relational model?
<details><summary>Show answer</summary>

- **Strong joins** — the database combines rows from many tables for you.
- That is what **many-to-one** and **many-to-many** links need: a shared record (one city for many users) is stored
  once and joined back, not copied into every record. In a document database, the same links mean copies, or joins
  written in your own code.

</details>

### Relational vs document databases — when?
<details><summary>Show answer</summary>

Today the two have grown toward each other (**convergence**):
- Relational databases added JSON columns, queries inside JSON, and indexes on fields inside a document (e.g. `jsonb`
  in Postgres).
- Document databases added joins, secondary indexes and declarative query languages (MongoDB, Couchbase, RethinkDB).

**The answer:** pick by the shape of the data, part by part, often inside one database:
- a [tree read as a whole](#one-to-many-data-relational-or-document) → document style
- shared records, [many-to-one and many-to-many](#why-pick-the-relational-model) → relational style

Each model needs a bit of the other: documents need references to other documents, and tables have parts where a
flexible schema helps. A hybrid gets both.

</details>
