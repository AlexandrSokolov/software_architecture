### What is the relational model?
<details><summary>Show answer</summary>

Data is organized into **relations** (**tables** in SQL). 
Each relation is an unordered collection of **tuples** (**rows** in SQL).

</details>

### What is the common problem of SQL in object-oriented code?
<details><summary>Show answer</summary>

Application code works with objects, but the database stores tables, rows and columns. 
The two shapes do not match, so every read and write needs a translation layer: 
objects into rows, and rows back into objects. That layer is awkward.

This disconnect is called **impedance mismatch** (two parts that do not fit together), 
or the **object-relational mismatch**.

</details>

### What are the common ORM problems?
<details><summary>Show answer</summary>

**It leaks** — an ORM cannot fully hide the mismatch.
- You still think in both shapes: objects and tables.
- The table schema still matters. ORMs are used for OLTP only, and data engineers for analytics read the tables, not
  the objects.

**It is narrow** — it works for one kind of store.
- Most ORMs support only relational OLTP databases. Search engines, graph databases and NoSQL stores often lack support.

**It hides cost** — it is easy to write slow queries by accident.
- N+1 query problem: one query for the list, then one more query for each item.
- Lazy loading: reading a plain field in code can fire a SQL query.

</details>

### What are the benefits of an ORM?
<details><summary>Show answer</summary>

**Less code** — translating between objects and rows is needed anyway.
- The ORM removes the repeated code for it. It covers the simple, repetitive cases; complicated queries may still go
  outside the ORM.

**Less database load**
- Some ORMs cache query results.

**Less admin work**
- Some ORMs help with schema migrations and other admin tasks.

**Safer queries**
- Values are sent as parameters, which helps against SQL injection.

</details>

### What is a many-to-one relationship?
<details><summary>Show answer</summary>

Many records point to one record. Example: many users live in one city.

In tables, the "many" side holds the link: each `users` row has a `city_id` that points to one row in `cities`.

Seen from the other side, the same link is **one-to-many**: one city has many users.

</details>

### What is a many-to-many relationship?
<details><summary>Show answer</summary>

Each side links to many records of the other side. Example: a student takes many courses, and a course has many
students.

In tables, neither side can hold the link, because one column holds only one ID. A third table holds the pairs:
`enrollments(student_id, course_id)`, one row per link.

</details>

### What is normalization?
<details><summary>Show answer</summary>

- **Normalized** (using IDs): the text people read (e.g. "Washington, DC") is stored in exactly one place. All other
  records refer to it by a database ID.
- **Denormalized** (using text): the text is copied into every record that uses it.

Normalization means replacing copied text with references to one shared ID.

Example:
- Denormalized: `users(id, name, city)`, where every row holds `"Washington, DC"`.
- Normalized: `users(id, name, city_id)` + `cities(id, name)`, where every user row holds `17`, and `"Washington, DC"`
  sits once in `cities`.

</details>

### Normalization — trade-offs?
<details><summary>Show answer</summary>

**Pros** — the readable text lives in one place:
- **One place to change** — a rename updates one row, not every copy.
- **Same spelling everywhere** — no variants of the same city name.
- **No mix-ups** — two cities with the same name get different IDs.
- **Translation** — the name can be shown in the user's language.

**Cons** — the text is not in the record:
- **Slower, more complex reads** — every time you show a record, an extra lookup turns the ID into readable text. In a
  relational database, that lookup is a [join](#what-is-a-join).

</details>

### What is a join?
<details><summary>Show answer</summary>

A query operation that combines rows from two or more tables by matching a shared column, usually an ID.

Why it exists: normalization splits data into tables, and a join puts the pieces back together when you read them.

Example: `users` holds a `city_id`, and `cities` holds the name. 
The join matches `users.city_id = cities.id` and returns one combined row: the user with the city name.

</details>

### When should you normalize vs. denormalize?
<details><summary>Show answer</summary>

- **Normalized** — faster writes (one copy), slower reads (joins).
- **Denormalized** — faster reads (fewer joins), slower writes (more copies to update, more disk).

The most scalable approach may involve denormalizing some things and leaving others normalized.

Pick by:
- **Reads vs writes** — mostly reads → denormalize; many writes → normalize.
- **How often the value changes** — rarely (a country name) → a copy is cheap; often (a stock count) → keep one copy.
- **Cost of a wrong copy** — if stale data hurts, normalize: copies drift when one of the updates fails.
- **Common mix** — a normalized source of truth, plus denormalized copies built from it for fast reads (a cache, a
  materialized view).

</details>

### Customer renamed, but old orders show the old name. Why?
<details><summary>Show answer</summary>

- **Verdict:** each order holds a copy of the name, and the rename updated only the customer record.
- **Reasoning:** copies do not follow the source. Every copy must be updated on a write, or they drift apart.
- **Trade-off:** the fix is to store only `customer_id` and join on read: one place to change, but slower reads. Keep
  the copy when the order must show the name as it was at purchase time (an invoice). Then it is a snapshot on purpose,
  not a bug.

</details>

### A page joins six tables and is slow. What do you try?
<details><summary>Show answer</summary>

- **Verdict:** first check that the joins use indexes. If the page is still slow and reads dominate, keep a stored
  copy of the result for this page:
    - a materialized view
    - a denormalized read table
    - a cache
- **Reasoning:** joins on indexed keys are cheap at normal scale. A copy trades write cost for read speed.
- **Trade-off:** every write must also update or refresh the copy, and the copy can lag. The normalized tables stay
  the source of truth.

</details>

### "Berlin", "berlin", "Berlin " in thousands of rows. Why?
<details><summary>Show answer</summary>

- **Verdict:** the city is stored as free text in every row, with no single list to pick from.
- **Reasoning:** every write types the name again, so the spelling drifts. An ID pointing to one `cities` row allows
  only one spelling.
- **Trade-off:** reads now need a join, and the fix needs a cleanup that maps every variant to one ID.

</details>

### Posts have many tags, tags have many posts. How do you store it?
<details><summary>Show answer</summary>

- **Verdict:** three tables:
    - `posts`
    - `tags`
    - `post_tags(post_id, tag_id)`, one row per link
- **Reasoning:** each side links to many on the other side, and one column holds only one ID, so neither side can
  hold the link.
- **Trade-off:** reads join through the link table. A document store would copy tag names into each post: fast reads,
  but renaming a tag means updating every post.

</details>
