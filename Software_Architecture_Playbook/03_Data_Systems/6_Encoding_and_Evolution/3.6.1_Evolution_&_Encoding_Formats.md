### Backward vs forward compatibility?
<details><summary>Show answer</summary>

Old and new code run at the same time: a rolling deploy updates nodes one by one, and client apps update only when
users decide to. So data has to work in both directions:

- **Backward** — new code reads data written by old code. Easy: you wrote the new code, so you know the old format and
  can keep the old reading code.
- **Forward** — old code reads data written by new code. Harder: the old code must skip additions it has never seen.

</details>

### API calls — which compatibility where?
<details><summary>Show answer</summary>

Root: look at who reads the message. A newer reader needs [backward](#backward-vs-forward-compatibility); an older
reader needs forward.

- **Old client → new service** — the request needs backward (the new service reads it), and the response needs forward
  (the old client reads it).
- **New client → old service** — the request needs forward, and the response needs backward.

</details>

### Old code saves a new record — what's lost?
<details><summary>Show answer</summary>

New code adds a field and stores a record with it. Old code reads the record into a model object that has no slot for
that field, changes something, and writes it back. The new field is silently gone.

Fix: decode in a way that keeps fields you don't know and writes them back. Protobuf does this by default; with
Jackson, collect them with `@JsonAnySetter` and write them out with `@JsonAnyGetter`.

</details>

### What are data encoding and decoding?
<details><summary>Show answer</summary>

Data has two forms:
- **In memory** — objects, lists, maps linked by pointers. Pointers mean nothing outside the process.
- **As bytes** — a self-contained byte sequence (no pointers), to write to a file or send over the network.

So data must be translated between them:
- **Encoding** (serialization, marshaling) — in-memory representation → self-contained byte sequence.
- **Decoding** (deserialization, parsing, unmarshaling) — the reverse: byte sequence → in-memory representation.

</details>

### When is encoding not needed?
<details><summary>Show answer</summary>

When the bytes on disk or on the wire can be used as they are, with no step that turns them into objects:
- **A database running queries** — works directly on compressed data loaded from disk.
- **Zero-copy formats** (Cap'n Proto, FlatBuffers) — the same byte layout is used at runtime and on disk/network,
  so code reads fields straight from the bytes.

</details>

### What are language-specific formats?
<details><summary>Show answer</summary>

Encoding built into a programming language, or a library for one language. 
It turns that language's objects into bytes and back with almost no code from you.

- Java — `java.io.Serializable`; third-party: Kryo
- Python — `pickle`
- Ruby — `Marshal`

</details>



### What are the drawbacks of language-specific encoding formats?
<details><summary>Show answer</summary>

Built for convenience: save and restore your objects with little code, inside one language.
Each drawback comes from one part of that:

- **Language lock-in** (one language) — other languages can hardly read the data. You stay tied to your language
  for as long as the data lives, and can't easily integrate with other companies' systems.
- **Security risk** (restore your objects) — the decoder must create any class the bytes name. An attacker
  who gets your app to decode their bytes can create any class, often leading to remote code execution.
- **Poor compatibility** (convenience first) — versioning (backward/forward compatibility) is usually neglected.
- **Inefficiency** (convenience first) — slow to encode/decode, large output (Java's built-in serialization is the
  known example).

Verdict: use it only for very short-lived (transient) data.

</details>

### What are textual formats?
<details><summary>Show answer</summary>

Standard formats that store data as human-readable text, so any language can write and read them. 

- **JSON** — objects (key-value pairs) and arrays
- **XML** — nested elements with tags and attributes
- **CSV** — rows of values separated by commas

</details>

### JSON vs XML vs CSV — own problems?
<details><summary>Show answer</summary>

- **XML** — verbose and needlessly complicated.
- **CSV** — no schema at all: the app decides what each row and column means, and handles a new column by hand.
  Vague escaping (a value that contains a comma or a newline); parsers differ.
- **JSON** — the only one that tells numbers from strings, but its numbers still have
  [gaps shared with the others](#what-problems-do-all-textual-formats-share).

</details>

### What problems do all textual formats share?
<details><summary>Show answer</summary>

Root: the text does not say what type a value is, so the meaning must come from a schema or from your code.

- **Number ambiguity** — in XML and CSV, a number and a digit-only string look the same. JSON tells them apart, but not
  integers from floats, and sets no precision. Integers above 2^53 don't fit exactly in a double, so JavaScript reads
  them wrong; X sends each post ID twice, as a number and as a string.
- **No binary data** — only Unicode text fits, so bytes are sent as Base64. It's a workaround, ~33% larger, and only the
  schema says the value is Base64.
- **Schema dependency and complexity** — reading numbers and Base64 correctly needs a schema. XML Schema and JSON Schema
  are powerful but complex, so apps that don't use them hardcode the decoding logic.

</details>

### Why does JSON Schema exist?
<details><summary>Show answer</summary>

Without it, plain JSON has no strict types (integer vs float), no rules on values, and no list of required fields, so
every app hardcodes its own checks and decoding.

JSON Schema gives one standard way to define types and add rules on values (e.g. port: min 1, max 65,535) when data is
exchanged or stored.

</details>

### What makes JSON Schema hard?
<details><summary>Show answer</summary>

- **Open by default** — fields not in the schema are allowed, with any type (`additionalProperties: true`). So a schema
  says what is forbidden, not what is allowed. `additionalProperties: false` closes it.
- **Complexity** — conditionals, regex patterns, remote references: hard to read and reason about, and remote schemas
  must be resolved.
- **Evolution** — changing a schema in a backward/forward-compatible way is hard.

The same applies to XML Schema.

</details>

### How do you make textual formats smaller?
<details><summary>Show answer</summary>

- **[Binary JSON/XML](#what-is-binary-json)** (MessagePack, BSON) — they still store every field name, so all of them
  save only a little space and parse slightly faster. It's unclear whether that is worth losing human-readable data.
- **[Protocol Buffers](#what-are-protocol-buffers)** — Google's format: the bytes carry a field number, not the name.
- **[Apache Avro](#what-is-apache-avro)** — Hadoop's format: the bytes carry only values; the reader needs the writer's
  schema.

</details>

### What is binary JSON?
<details><summary>Show answer</summary>

JSON's data model written as bytes instead of text: MessagePack, CBOR, BSON (MongoDB), Smile. 
XML has WBXML and Fast Infoset. 
More compact and sometimes faster to parse, but each lives in a niche; none is as widely used as text JSON/XML.

</details>

### What are Protocol Buffers?
<details><summary>Show answer</summary>

A widely used binary format from Google. It needs a schema, written in its own IDL (Interface Definition Language),
where each field gets a type and a number:

```protobuf
message Person {
  string user_name = 1;      // number 1 goes into the bytes, the name does not
  int64 favorite_number = 2;
}
```

A code generator turns the schema into classes for many languages, which encode and decode the data.

</details>

### What is Apache Avro?
<details><summary>Show answer</summary>

A binary format from the Hadoop project. The schema is written in JSON (or Avro IDL). The bytes hold only the values,
one after another, with no field names and no field numbers. That makes it very compact, but the schema must be present
both when writing and when reading: the reader decodes only with the exact schema the data was written with (the
writer's schema).

</details>

### What do schemas give you?
<details><summary>Show answer</summary>

Root: the schema is a separate file, and the reader needs it to decode. Each merit follows from that:

- **Smaller data** — field names live in the schema, not in every record.
- **Docs that stay correct** — the data can't be read without the right schema, so the schema can't drift from it.
- **Checks before deploy** — keep every schema version, and test a new one against the old ones before it ships.
- **Type checks at compile time** — generate classes from the schema, and the compiler catches type mistakes.

</details>

### Protobuf vs Avro — when which?
<details><summary>Show answer</summary>

Root: Protobuf writes a field number into the bytes; Avro writes only the values. Everything below follows from that.

- **Protocol Buffers** — a reader decodes with its own schema and skips numbers it doesn't know.
    - Prefer for: calls between services (gRPC), where schemas are written by hand and both sides compile them into code.
    - Cost: field numbers are managed by hand and never reused, and the bytes are a bit larger. Awkward when the
      structure isn't known in advance, or when you don't want a code-generation step.
- **Avro** — the smallest bytes and no numbers to manage, so schemas can be generated from data (e.g. one per database
  table) and code generation is optional.
    - Prefer for: large files with many records of one schema (Hadoop, data lakes), schemas generated from data, and
      Kafka with a schema registry (the registry also supports Protobuf, so Kafka alone doesn't decide).
    - Cost: the reader needs the writer's schema, either in the file header or in a schema registry, which is extra
      infrastructure. Without it, the bytes can't be read.

</details>

### JSON vs binary formats — when which?
<details><summary>Show answer</summary>

Root: JSON is text that carries its own field names; Protobuf and Avro are bytes that need a schema.

- **JSON** — anyone can read it with no schema and no code generator, and you can check it by eye.
    - Prefer for: public APIs, browsers, data exchanged with other companies (getting everyone to agree on a format
      matters more than size), debugging.
    - Cost: larger and slower, has the [shared number and binary problems](#what-problems-do-all-textual-formats-share),
      and has no built-in compatibility checks.
- **Protobuf / Avro** — smaller and faster, and the schema is enforced and checked.
    - Prefer for: high-volume traffic between your own services (gRPC, Kafka) and large stored data.
    - Cost: both sides need the schema and tools, and you can't read the bytes by eye.
    - Which one: [Protobuf vs Avro](#protobuf-vs-avro--when-which).

</details>
