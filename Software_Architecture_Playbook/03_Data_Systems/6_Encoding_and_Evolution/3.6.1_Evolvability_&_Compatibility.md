### What is evolvability?
<details><summary>Show answer</summary>

How easily a data system can be changed when requirements change. It is agility applied at the data system level. 
It is a core aspect of maintainability.


The three parts of maintainability:
- operability (easy to run)
- simplicity (easy to understand)
- evolvability (easy to change)

</details>

### What makes a data system evolvable?
<details><summary>Show answer</summary>

- **Loose coupling** — parts talk only through small, stable interfaces (abstractions), so you can change what's
  behind one without breaking the others.
- **Compatibility** — parts still share data, and during an upgrade old and new versions
  [run at the same time](#why-do-old-and-new-versions-mix). Each must read the other's data, so you can upgrade one
  part at a time instead of all at once.

Loose coupling cuts down what parts share; compatibility keeps what they still share working across versions.

</details>

### Why do old and new versions mix?
<details><summary>Show answer</summary>

A feature change usually changes the data too: a new field, a new record type. 
The change can't reach everything at once:
- **Stored data** — records written earlier stay in the old format until a migration rewrites them.
- **Code** —
  - **Server-side** — rolling upgrades (staged rollouts) deploy new code to a few nodes at a time to avoid downtime.
  - **Client-side** — clients — mobile or desktop apps — update only when users decide to.

So old and new code read and write the same data at the same time, and each must handle the other's format. 
That is [compatibility](#backward-vs-forward-compatibility).

</details>

### Backward vs forward compatibility?
<details><summary>Show answer</summary>

Old and new code run at the same time: a rolling deploy updates nodes one by one, and client apps update only when
users decide to. So data has to work in both directions:

- **Backward** — new code reads data written by old code. Easy: you wrote the new code, so you know the old format and
  can keep the old reading code.
- **Forward** — old code reads data written by new code. Harder: the old code must skip additions it has never seen.

</details>

### What decides compatibility?
<details><summary>Show answer</summary>

Old and new code share data: one process writes it, another reads it. Three things decide whether the reader
understands what the writer wrote:
- **[Data model](#how-do-data-models-handle-data-changes)** — how it's stored: does the database keep old and new
  formats side by side (schema-on-read), or convert them in a migration (schema-on-write)?
- **[Encoding format](3.6.2_Encoding_Formats.md#what-are-data-encoding-and-decoding)** — how it's turned into bytes:
  can a reader handle fields from another version?
- **[Mode of dataflow](3.6.3_Dataflow_Databases_&_Service_APIs.md#modes-of-dataflow--who-encodes-who-decodes)** — how
  it travels: who writes and who reads, which decides whether you need backward, forward, or both.

</details>

### How do data models handle data changes?
<details><summary>Show answer</summary>

Example: split `name` into `first_name` and `last_name`.

- **Schema-on-write** (relational) — one schema at a time. A migration (`ALTER TABLE`, then fill the new columns)
  converts the stored rows. Old servers still use `name` during the deploy, so drop it only after every server is
  new (expand/contract).
- **Schema-on-read** (document, called "schemaless") — no schema in the database; old and new records stay side by
  side, and the reading code handles both: if `first_name` is missing, split `name`.

</details>
