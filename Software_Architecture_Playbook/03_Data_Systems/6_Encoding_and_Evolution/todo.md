**What "deploy order" means.** When you change a format, the writer and the reader can't both switch at the same instant. One goes first, and during the gap one side is old and the other is new. Which side goes first decides which direction must work in that gap:

- **Readers first.** New readers see old data for a while, so you need **backward**. Once all readers are new, the writers start sending the new format.
- **Writers first.** Old readers see new data, so you need **forward**.
- **Both directions guaranteed.** Order doesn't matter.

Two concrete cases:
- **Kafka event gets a new field.** Upgrade consumers first, so they handle the field being there or not. Then producers start sending it. Schema Registry enforces this through its mode: `BACKWARD` (the default) allows only changes where consumers can go first, `FORWARD` only changes where producers can go first, and `FULL` allows either. Teams get bitten when the mode is `BACKWARD` and they deploy the producer first.
- **REST response gets a new field.** The server goes first, and old clients must ignore the field (forward). If you want clients to send a new request field, the server must first accept requests without it (backward); only then do clients start sending it.

**Where it belongs.** It's the practical side of "Backward vs forward": knowing the direction tells you which side to deploy first. In fact, "API calls — which compatibility where?" is already a deploy-order card for REST without saying so. Its last line is "servers are usually deployed first".

So there are two homes:
- **3.6.1**, as a general card right after "Backward vs forward", covering APIs and events.
- **3.6.3**, rewriting "API calls — which compatibility where?" into this card.

I'd pick 3.6.1, since the rule is the same for any writer and reader.

## Gemini

Here is a set of flashcards that builds the bridge from the architectural concept of evolvability down to the mechanics of data formats and compatibility, formatted according to your flashcard rules.

### What is the relationship between application evolvability and data formats?

* **Evolvability** is the architectural goal of building systems that make it easy to adapt to change.
* When an application's features change (e.g., capturing a new field or changing a record type), the underlying data
  format must usually change to match.
* Because data updates and code deployments happen independently, this leads to situations where old and new versions
  of code, and old and new data formats, must coexist seamlessly.

### How do relational and schema-on-read databases differ when handling data format changes?

* **Relational databases:** Assume all data conforms to a single schema at any given time. Evolving the data requires
  explicit schema migrations (e.g., using `ALTER` statements).
* **Schema-on-read databases:** Do not enforce a strict schema on write. This allows the database to naturally contain
  a mixture of older and newer data formats written at different times without migrating old records.

### What is the difference between backward and forward compatibility for data formats?

* **Backward compatibility:** Ensures newer code can successfully read data written by older code. This is easier
  because the author of the new code knows the old format and can explicitly handle it.
* **Forward compatibility:** Ensures older code can successfully read data written by newer code. This is trickier
  because it requires the older code to gracefully ignore new additions it doesn't understand.

### What compatibility is needed when older and newer clients and services interact via APIs?

* **Older client calling a newer service:** Requires backward compatibility on the request (service reads old request)
  and forward compatibility on the response (client ignores new response fields).
* **Newer client calling an older service:** Requires forward compatibility on the request (service ignores new request
  fields) and backward compatibility on the response (client handles old response format).

### How can forward compatibility lead to data loss during an update?

* A record might contain a new field added by newer code.
* If an older version of the code reads this record, it won't recognize the new field.
* If the older code then updates the record and writes it back to the database, it must preserve the unknown field.
* If the record is decoded into a model object that strictly drops or ignores unknown fields, the new data is
  accidentally deleted during the write back.
