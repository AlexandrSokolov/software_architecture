### Dataflow modes — how long must old formats keep working?
<details><summary>Show answer</summary>

All modes need both directions. They differ in how long the old format lives:
- **Database** — years, until a [migration](#breaking-schema-change-without-downtime--how) rewrites old records.
- **Service call**:
  - internal API — only while versions overlap during a deploy
  - [public API](#you-need-a-breaking-change-to-a-public-api--how) whose clients may never upgrade — years,
- **Async message** — as long as the broker keeps old messages and the slowest consumer hasn't upgraded.
- **Workflow** — until every running workflow started by old code finishes; that can take months.

</details>

### Which API changes keep clients working?
<details><summary>Show answer</summary>

An API's compatibility comes from its encoding. gRPC follows the rules of
[Protobuf](3.6.2_Encoding_Formats.md#what-are-protocol-buffers);


For REST with JSON:
- **Safe** — add an optional request parameter, or add a field to a response. Old clients must ignore fields they
  don't know — plain Jackson fails on them by default; Spring Boot turns that off.
- **Breaking** — remove or rename a field, make an optional field required, change a field's type or meaning.

</details>

### Which side do you deploy first when a format changes?
<details><summary>Show answer</summary>

A new field — in a [REST or gRPC call](#api-call-changes--who-deploys-first) or a
[Kafka event](#kafka-event-changes--who-deploys-first) — has a writer and a reader that deploy separately. The order
depends on which compatibility holds during the gap:
- **Reader first** — needs [backward](3.6.1_Evolvability_&_Compatibility.md#backward-vs-forward-compatibility)
  compatibility. The new reader gets old data, so it must handle the field
  [missing](#new-code-meets-a-missing-field--options).
- **Writer first** — needs forward compatibility. The old reader gets new data, so it must
  [handle a field it doesn't know](#old-code-meets-a-new-field--options).
- **Any order** — needs full compatibility: both of the above hold.

</details>

### API call changes — who deploys first?
<details><summary>Show answer</summary>

Usually the server, because you can't make every client upgrade at once. A call is two messages, one each way:
- **Request** (client → server) — the new server reads old requests, so a new request field must be optional. Clients
  send it only after every server is new.
- **Response** (server → client) — old clients read new responses, so they must ignore new fields.

Client first (a mobile app released early) — both flip: the old server must ignore fields the new client sends, and
the new client must handle responses without the new fields.

</details>

### Old code meets a new field — options?
<details><summary>Show answer</summary>

New code adds a field to a record. Old code, whose DTO has no slot for it, reads the record. Root: who keeps the new
field?

- **Nobody — ignore it.** Configure Jackson not to fail on unknown properties (`FAIL_ON_UNKNOWN_PROPERTIES = false`,
  or `@JsonIgnoreProperties(ignoreUnknown = true)`). Fits code that only reads: a consumer of an external API or
  events. Cost: the field is thrown away, so writing the record back
  [loses it](#old-code-saves-a-new-record--whats-lost).
- **The storing side — send only what changed.** Partial update: REST `PATCH`, SQL `UPDATE` of named columns,
  MongoDB `$set`, Postgres `jsonb_set`. The old code never holds the whole record, so it can't drop fields it doesn't
  know. Fits when the storing side can merge. Catch: send only the changed fields — serialize the whole old DTO and
  its unset fields go out as `null`, which in JSON Merge Patch means "delete this field".
- **Your code — keep it and write it back.** Fits when you must write the whole record yourself: a `PUT` with the
  full resource, saving a whole JSON document or blob, or a pipeline step that changes one field and passes the
  message on.
  - **Protobuf** — does it by default, in the binary format: unknown fields stay in the parsed message and are written
    back with it. Converting the message to JSON drops them.
  - **JSON** — Jackson needs a [map for unknown fields in the DTO](#jackson--how-to-keep-unknown-fields).
  - Both work only if you write back the same object you read.

</details>

### Old code saves a new record — what's lost?
<details><summary>Show answer</summary>

New code adds a field and stores a record with it. Old code reads the record into a model object that has no slot for
that field, changes something, and writes it back. The new field is silently gone.

To avoid it,
[send only the changed fields, or keep unknown fields and write them back](#old-code-meets-a-new-field--options).

</details>

### Jackson — how to keep unknown fields?
<details><summary>Show answer</summary>

Give the old DTO a map for fields it doesn't know. Reading puts every unknown JSON property into the map; writing puts
the map's entries back as normal properties.

```java
public class CustomerDto {
  private String name;  // the only field old code knows

  private final Map<String, Object> unknown = new LinkedHashMap<>();

  @JsonAnySetter  // reading: a JSON property with no matching field goes here
  public void putUnknown(String key, Object value) {
    unknown.put(key, value);
  }

  @JsonAnyGetter  // writing: each entry comes out as a normal top-level property
  public Map<String, Object> getUnknown() {
    return unknown;
  }
  // getter/setter for name
}
```

With `@JsonAnySetter`, unknown properties go into the map instead of failing, so `FAIL_ON_UNKNOWN_PROPERTIES` no
longer matters for that class. The map's own name - `unknown` is never written. 
Its entries come out as top-level properties, so the JSON looks the same as what was read.

Limits:
- **Must already be in the old code** — added before any new field exists. A version shipped without it can't keep
  fields, and that can't be fixed later.
- **Write back the object you read** — if the DTO is mapped to an entity or domain object (MapStruct) and a new DTO is
  built for the save, the map is lost on the way, unless every layer carries it.
- **Nested objects need their own map** — an unknown field inside `address` is kept only if `AddressDto` has its own
  `@JsonAnySetter` / `@JsonAnyGetter`.

</details>

### New code meets a missing field — options?
<details><summary>Show answer</summary>

New code adds `discount`. Old records and requests from old clients don't have it.

- **Compute it from the old shape.** Old data holds the same fact in other fields: no `first_name` → split `name`.
  Cost: the reader must handle every old shape.
- **Set a default.** One value is right for every old record (`status` missing → `ACTIVE`): initial value in the class,
  column `DEFAULT`, default in the Avro schema. Proto3 can't declare one — set it in code.
- **Mark it absent.** No default is right: use a type that can say "not set" and handle it in code — `Integer` instead
  of `int`, nullable column, proto3 `optional` (`hasDiscount()`), Avro union `["null", "int"]` with default `null`.
  Trap: a plain `int` or plain proto3 field reads as `0` and looks like "no discount".
- **Reject it.** The data is not valid without the field: `@NotNull` on the field and `@Valid` on the controller
  parameter → `400` for old clients. Cost: old clients break until they upgrade. In Avro this happens by accident —
  a new field with no default can't read old data at all.

</details>

### Breaking schema change without downtime — how?
<details><summary>Show answer</summary>

Use **Expand/Contract** (also called Parallel Change) pattern. 
During a rolling deploy, old and new versions run side by side, so split the change into backward-compatible phases, 
one release each. Example: split `name` into `first_name` and `last_name`.

- **Expand** (database)
  - Add `first_name` and `last_name` as nullable columns. Old code ignores them.
- **Dual write & backfill** (application and database)
  - Deploy code that writes both `name` and the new columns, but still reads `name`.
  - Once it runs on every instance, a batch migration fills the new columns for old rows.
- **Migrate read** (application)
  - Deploy code that reads only the new columns and still writes both.
- **Contract** (application and database)
  - Deploy code that stops writing `name`.
  - Drop `name` from the database.

Trade-off: more releases, and while both columns exist they can drift apart. 
If downtime is allowed, one migration in one release is simpler.

</details>

### Breaking change to a public API — how?
<details><summary>Show answer</summary>

Publish a new version (e.g. `/v2/`) and run both versions side by side.

- **Constraint (public API)** — you don't control the clients (other companies, installed mobile apps). 
  You can't make them upgrade at the same time, so the old version stays up for months or years.
- **Cost** — every version must be supported, tested and patched until the old one can be shut down.
- **vs. internal API** — if you control every client, no new version is needed: make the API accept both shapes,
  move the clients, then remove the old shape ([expand/contract](#breaking-schema-change-without-downtime--how)).
  Clients and the API deploy separately, so a one-step change still breaks calls in between.

</details>

### How does a client choose an API version?
<details><summary>Show answer</summary>

There is no standard. Common ways:

- **In the URL** — `/v2/orders`.
  - Gain: easy to see in logs, try in a browser or with `curl`, and route (a gateway sends `/v2/` to the new
    service). Caches work as usual.
  - Cost: the version covers the whole API, so every endpoint gets a new URL, even ones that didn't change, and
    clients change every URL when they upgrade. Breaks a REST rule: one resource now has several URLs.
- **In a header** — `Accept: application/vnd.example.v2+json`, or a custom one like `X-API-Version: 2`.
  - Gain: one stable URL per resource.
  - Cost: the version is hidden — not in the URL, hard to try in a browser. Caches and CDNs must key on the header
    (`Vary: Accept`), or a v1 client may get a cached v2 response. Routing on a header needs more setup.
- **Pinned per client (The "Stripe Model")** — the server stores a version for each client.
  - How, client side: a new account is pinned to the current version on its first request. Requests without a
    version get that version. A header (`Stripe-Version: 2023-10-16`) overrides it for one request, so the client can
    test the new version. When ready, the client moves the pin in the dashboard.
  - How, server side: the code only knows the latest shape. Before the response goes out, it passes through one
    small converter per breaking change, newest to oldest, until it matches the client's pinned version.
  - Gain: nothing to send, and a client that does nothing never breaks — its version is frozen until it upgrades on
    purpose. One codebase instead of one per version.
  - Cost: every breaking change needs a converter, kept for years. The request alone doesn't show which version
    answers it. Needs every client to be identified by a key.

</details>

### Broker messages — why does compatibility matter?
<details><summary>Show answer</summary>

- **Separate deploys** — producers and consumers update on their own schedules. Old consumers read new messages, and
  new consumers read old ones.
- **Republishing** — an old consumer that reads a new message, changes it, and publishes it to another topic must keep
  the fields it doesn't know, or
  [that data is lost](#old-code-saves-a-new-record--whats-lost).
- **Long-lived messages** — a broker that keeps messages for years (Kafka with event sourcing) works like a database:
  new code must still read events written long ago.

</details>

### Messages via a broker — how is compatibility kept?
<details><summary>Show answer</summary>

The broker treats a message as bytes and never looks inside, so compatibility comes from the encoding (Protobuf, Avro,
JSON Schema) and is checked by a **schema registry**.

The registry is the central check. When a producer brings a new schema version, the registry compares it with earlier
versions. If the change breaks the backward or forward compatibility rule set for the topic, the registry rejects it,
and the producer can't publish with it.

</details>

### Kafka event changes — who deploys first?
<details><summary>Show answer</summary>

The Schema Registry mode sets the order:
- `BACKWARD` (default) — the new schema reads old data → consumers first.
- `FORWARD` — the old schema reads new data → producers first.
- `FULL` — both → any order. The choice when a topic has many consumer teams and you can't wait for all of them.

</details>
