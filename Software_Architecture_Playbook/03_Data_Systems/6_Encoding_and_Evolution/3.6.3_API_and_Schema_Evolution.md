### Dataflow modes — how long must old formats keep working?
<details><summary>Show answer</summary>

All modes need both directions. They differ in how long the old format lives:
- **Database** — years, until a [migration](#breaking-schema-change-without-downtime--how) rewrites old records.
- **Service call**:
  - internal API — only while versions overlap during a deploy
  - [public API](#you-need-a-breaking-change-to-a-public-api--how) whose clients may never upgrade — years,
- **Async message** — as long as the broker keeps old messages and the slowest consumer hasn't upgraded.
- **Workflow** — until every running workflow started by old code finishes; that can take months.

</details>

### Which API changes keep clients working?
<details><summary>Show answer</summary>

An API's compatibility comes from its encoding. gRPC follows the rules of
[Protobuf](3.6.2_Encoding_Formats.md#what-are-protocol-buffers); 


For REST with JSON:
- **Safe** — add an optional request parameter, or add a field to a response. Old clients must ignore fields they
  don't know — plain Jackson fails on them by default; Spring Boot turns that off.
- **Breaking** — remove or rename a field, make an optional field required, change a field's type or meaning.

</details>

### Which side do you deploy first when a format changes?
<details><summary>Show answer</summary>

Why does the order of deploys matter when a format changes?

A change to a format — a new field in an API request or response, or in an event — has a writer and a reader. They
are separate deploys (other instances, often other teams), so they can't switch at the same moment: one side ships
first, and for a while old and new code talk to each other.

Why the order matters: a producer starts sending events with a new field before consumers can handle it. A consumer
that fails on unknown fields then fails on every new event and stops processing.

Root: who reads during the gap? A newer reader needs
[backward](3.6.1_Evolvability_&_Compatibility.md#backward-vs-forward-compatibility) compatibility; an older reader
needs forward.
- **Reader ships first** — new readers get old data until the writers switch. The reader must handle the field being
  [missing](#new-code-meets-a-missing-field--options). Then the writers start sending it.
- **Writer ships first** — old readers get new data, so they must
  [handle a field they don't know](#old-code-meets-a-new-field--options).

Applied:
- **REST or gRPC call** — two messages: the request (client writes, server reads) and the response (server writes,
  client reads). The server usually ships first:
  - **Request** — the new server reads old requests, so a new request field must be optional. Clients start sending
    it only after every server is new.
  - **Response** — old clients read new responses, so they must ignore new fields.
  - **Client first** (a mobile app released early) — both flip: the old server must ignore fields the new client
    sends, and the new client must handle responses without the new fields.
- **Events (Kafka)** — the producer writes, consumers read. Schema Registry checks each new schema against a mode
  that fixes the order:
  - `BACKWARD` (default) — the new schema reads old data → consumers first.
  - `FORWARD` — the old schema reads new data → producers first.
  - `FULL` — both → any order. The choice when consumers belong to many teams and you can't wait for all of them.

Rule: the direction your change supports sets the order — backward → readers first, forward → writers first, both →
any order. Ship in the wrong order and the side that is still old breaks.

</details>

### Old code saves a new record — what's lost?
<details><summary>Show answer</summary>

New code adds a field and stores a record with it. Old code reads the record into a model object that has no slot for
that field, changes something, and writes it back. The new field is silently gone.

Ignoring unknown fields doesn't prevent this — it is how the field gets lost. To avoid it,
[send only the changed fields, or keep unknown fields and write them back](#old-code-meets-a-new-field--options).

</details>

### Old code meets a new field — options?
<details><summary>Show answer</summary>

New code adds a field to a record. Old code, whose DTO has no slot for it, reads the record. Root: who keeps the new
field?

- **Nobody — ignore it.** Configure Jackson not to fail on unknown properties (`FAIL_ON_UNKNOWN_PROPERTIES = false`,
  or `@JsonIgnoreProperties(ignoreUnknown = true)`). Fits code that only reads: a consumer of an external API or
  events. Cost: the field is thrown away, so writing the record back
  [loses it](#old-code-saves-a-new-record--whats-lost).
- **The storing side — send only what changed.** Partial update: REST `PATCH`, SQL `UPDATE` of named columns,
  MongoDB `$set`, Postgres `jsonb_set`. The old code never holds the whole record, so it can't drop fields it doesn't
  know. Fits when the storing side can merge. Catch: send only the changed fields — serialize the whole old DTO and
  its unset fields go out as `null`, which in JSON Merge Patch means "delete this field".
- **Your code — keep it and write it back.** Fits when you must write the whole record yourself: a `PUT` with the
  full resource, saving a whole JSON document or blob, or a pipeline step that changes one field and passes the
  message on.
  - **Protobuf** — does it by default, in the binary format: unknown fields stay in the parsed message and are written
    back with it. Converting the message to JSON drops them.
  - **JSON** — Jackson needs a [map for unknown fields in the DTO](#jackson--how-to-keep-unknown-fields).
  - Both work only if you write back the same object you read.

</details>

### Jackson — how to keep unknown fields?
<details><summary>Show answer</summary>

Give the old DTO a map for fields it doesn't know. Reading puts every unknown JSON property into the map; writing puts
the map's entries back as normal properties.

```java
public class CustomerDto {
  private String name;  // the only field old code knows

  private final Map<String, Object> unknown = new LinkedHashMap<>();

  @JsonAnySetter  // reading: a JSON property with no matching field goes here
  public void putUnknown(String key, Object value) {
    unknown.put(key, value);
  }

  @JsonAnyGetter  // writing: each entry comes out as a normal top-level property
  public Map<String, Object> getUnknown() {
    return unknown;
  }
  // getter/setter for name
}
```

With `@JsonAnySetter`, unknown properties go into the map instead of failing, so `FAIL_ON_UNKNOWN_PROPERTIES` no
longer matters for that class.

Limits:
- **Must already be in the old code** — added before any new field exists. A version shipped without it can't keep
  fields, and that can't be fixed later.
- **Write back the object you read** — if the DTO is mapped to an entity or domain object (MapStruct) and a new DTO is
  built for the save, the map is lost on the way, unless every layer carries it.
- **Nested objects need their own map** — an unknown field inside `address` is kept only if `AddressDto` has its own
  `@JsonAnySetter` / `@JsonAnyGetter`.

</details>

### New code meets a missing field — options?
<details><summary>Show answer</summary>

New code adds `discount`. Records written by old code, and requests from old clients, have no `discount`. What new
code sees:
- **Jackson** — the field is left as constructed: `null` for objects, `0`/`false` for primitives, or the initial value
  the class sets.
- **Protobuf (proto3)** — the zero value (`0`, `""`, `false`). "Not set" and "set to 0" look the same, unless the field
  is declared `optional`, which adds `hasDiscount()`.
- **Avro** — the default from the reader's schema. A new field with no default can't read old data at all.
- **SQL** — `NULL` in old rows, or the column's `DEFAULT`.

The trap: a missing `int discount` reads as `0` and looks like real data ("no discount"), while the truth is "unknown".

Root: where does the missing value come from?
- **A fixed default** — one value is right for every old record (`status` missing → `ACTIVE`): schema default, column
  `DEFAULT`, or an initial value in the class.
- **Other old fields** — old records hold the same facts in another shape: no `first_name` → split `name`.
- **The stored data** — a migration writes the value into old rows, so new code sees one shape. Only for data you
  own: requests from old clients and messages already in a topic still arrive without it.
- **Nowhere** — no default is right: keep "not set" visible with a nullable type (`Integer`) or proto3 `optional`,
  and handle it in code.

</details>

### Breaking schema change without downtime — how?
<details><summary>Show answer</summary>

Example: split `name` into `first_name` and `last_name`, with a rolling deploy.

- **Verdict** — first look for a safe change: for a plain rename, map the new field name to the old column in code
  (`@Column(name = "name")`) and leave the table alone. If the table must change, do it in steps (expand/contract):
  - **Expand** — add `first_name` and `last_name` as nullable columns (old code's inserts don't fill them).
  - **Write both** — deploy code that writes `name` and the new columns, and still reads `name`.
  - **Fill old rows** — a migration copies `name` into the new columns for old rows, in batches on a big table.
  - **Read new** — deploy code that reads the new columns and still writes `name`: old instances still read it.
  - **Stop old writes** — deploy code that no longer writes `name`, once no instance reads it.
  - **Contract** — drop `name`, once no running code touches it.
- **Reasoning** — during a rolling deploy, the old and the new version run side by side on one schema. Each step is
  its own release and works with the version before it and after it, so no instance meets a schema or data it can't
  handle.
- **Trade-off** — several releases instead of one, and for a while the data lives in two places: a code path that
  updates only `name` gets them out of sync. With a hard stop (one instance, downtime allowed), one migration that
  changes the table in one go is simpler.

</details>

### You need a breaking change to a public API — how?
<details><summary>Show answer</summary>

- **Verdict** — first look for a [safe change](#which-api-changes-keep-clients-working). If the break is real,
  publish a new version and keep the old one running next to it.
- **Reasoning** — the clients belong to other companies, or are apps users don't update. You can't make them upgrade,
  so the old version must keep working for years, maybe forever.
- **Trade-off** — you run and fix two versions until the last client moves. When you control every client (an
  internal API), move them over, then remove the old behavior — no long-lived second version.

</details>

### How does a client choose an API version?
<details><summary>Show answer</summary>

There is no standard. Common ways:
- **In the URL** — `/v2/orders`. Easy to see, test and route; but every version gets new URLs.
- **In the `Accept` header** — `Accept: application/vnd.example.v2+json`. URLs stay the same; but the version is
  hidden, harder to try in a browser, and caches must take the header into account.
- **Stored per API key** — the server remembers each client's version, changed through an admin interface (Stripe
  works this way). Nothing extra in the request; but the request alone doesn't show which version answers it.

</details>

### How is a service API defined?
<details><summary>Show answer</summary>

A client must know each endpoint, what to send and what comes back. 
An IDL (Interface Definition Language) writes this down in one file:
- OpenAPI for JSON/REST, 
- [Protocol Buffers](3.6.2_Encoding_Formats.md#what-are-protocol-buffers) for gRPC. 


From that file, tools make:
- **Docs** built from the file, so they don't go out of date.
- **Client libraries** in many languages, generated instead of hand-written.
- **Compatibility checks** — a changed definition is compared with the old one, so a change that breaks backward or
  forward compatibility is caught before it ships.

</details>

### Messages via a broker — how is compatibility kept?
<details><summary>Show answer</summary>

The broker treats a message as bytes plus metadata, so the encoding decides compatibility — usually Protobuf, Avro
or JSON, with a schema registry that stores every schema version and checks each new one. AsyncAPI documents message
schemas, as OpenAPI does for REST. Where it matters:
- **Separate deploys** — producers and consumers update on their own schedules, so new code reads old messages and
  old code reads new ones.
- **Republishing** — a consumer that passes a message on to another topic must keep fields it doesn't know, or
  [they're lost](3.6.3_Dataflow_Databases_&_Service_APIs.md#old-code-saves-a-new-record--whats-lost).
- **Long-lived messages** — a broker that keeps messages forever (event sourcing) works like a database: new code
  reads messages written years ago.

</details>

### Code-first vs contract-first — when which?
<details><summary>Show answer</summary>

Root: what is written first — the server code or the [IDL](#how-is-a-service-api-defined) file.

- **Code-first** — write the server; the framework generates the IDL from the code (FastAPI).
    - Prefer for: an internal API where one team owns the server and its clients, and changes are frequent.
    - Cost: the contract is a side effect — a refactoring can change the API without anyone noticing; clients
      wait until the server exists.
- **Contract-first** — write the IDL; generate server stubs and clients from it (gRPC).
    - Prefer for: APIs used by other teams or companies. Teams agree on the file, then build server and clients in
      parallel, and every API change is reviewed as a change to the file.
    - Cost: an extra file and tools to maintain, and the server must fit the generated stubs.

</details>
