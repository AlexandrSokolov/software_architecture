## Gemini

What you experienced is an infrastructure-level solution: deploying completely separate binaries for `v1` and `v2`. That is a valid way to avoid codebase complexity, but it creates operational nightmares—you have to maintain and monitor multiple applications, and database migrations become a massive headache because both apps share the same database.

When you want to support multiple versions **inside a single Java application** (like a Spring Boot service), the architecture must shift. The fundamental rule is: **Isolate the boundary, share the core.**

Here are the three standard approaches to structuring multiple API versions in Java, along with the traps to avoid.

### Approach 1: The Standard Spring Way (Controller & DTO Versioning)

This is the most common pattern in Java enterprise applications. You version the entry points and the data payload, but keep the business logic unified.

**How it works:**

1. **Packages:** You create distinct packages for the API layer: `controller.v1`, `controller.v2`, `dto.v1`, `dto.v2`.
2. **Shared Service:** The `UserService` and the database entity (`User`) remain unversioned. They represent the current "true" state of the system.
3. **The Controllers:** You have two controllers.
* `V1UserController` listens to `/v1/users` (or a specific header). It receives `UserDtoV1`.
* `V2UserController` listens to `/v2/users`. It receives `UserDtoV2`.


4. **The Translation:** Both controllers call the exact same `UserService.createUser(User user)`. The controller's job is to use a mapper (like MapStruct) to translate `UserDtoV1` into the domain `User`, and vice versa.

**Trade-offs:**
It is easy to reason about and relies on standard Spring `@RestController` mechanics. However, if the business logic diverges significantly between versions, you might be forced to create `UserServiceV1` and `UserServiceV2`, which leads to massive code duplication.

### Approach 2: The "If-Else" Parameter Approach (Anti-Pattern)

Instead of new controllers, developers keep one controller and one endpoint, but add optional fields to a single massive DTO and handle the logic via `if` statements.

**How it works:**
The client sends a header `X-API-Version`. The controller injects this version, and passes it down into the service layer:
`if (version == 1) { return oldLogic(); } else { return newLogic(); }`

**Trade-offs:**
Do not do this. It creates spaghetti code. The HTTP version leaks deep into your business logic and database queries. When it comes time to delete `v1`, you have to hunt through hundreds of `if/else` blocks across your entire codebase, risking breaking `v2` in the process.

### Approach 3: The Mutation Pipeline (The "Stripe" Model in Java)

This is the most advanced approach, used by companies with strict API guarantees. The application codebase is completely ignorant of versions; it only knows about the latest, current version of the data.

**How it works in Spring:**

1. You write a single `UserController` that speaks the latest JSON schema (say, `v4`).
2. You implement a series of Spring `Filter` or `ResponseBodyAdvice` classes.
3. If a client requests `v2`, the controller executes its normal `v4` logic and returns `v4` JSON.
4. Before the JSON hits the network, the interceptor catches it. It passes the JSON tree (using Jackson's `JsonNode`) through a chain of downgraders: `V4toV3Migrator`, then `V3toV2Migrator`.
5. The migrators mechanically rename fields, split strings, or drop data to match the old shapes.

**Trade-offs:**
Your controllers and business logic remain pristine—there is zero code duplication. But writing and testing JSON tree mutators is difficult. You are effectively building an API gateway inside your Spring application.

### Major Traps and Considerations

* **Database Schema Coupling:** This is the deadliest trap. An API version is a contract with a client; a database schema is how you store data efficiently. Never map a versioned `OrderDtoV1` directly to a database row. If `v2` requires splitting `name` into `first_name` and `last_name`, you must run a database migration to split the columns for *everyone*. The `V1Mapper` then concatenates them back together on the fly when old clients request data.
* **MapStruct Hell:** If you use Approach 1, your mapping layer will grow exponentially. You will need mappings from Domain to V1, Domain to V2, Domain to V3. Ensure you have rigorous unit tests specifically for the mappers, as they will contain hidden business logic (like computing fallback values for missing fields).
* **Swagger/OpenAPI Pollution:** Supporting multiple versions in one app will break default Swagger setups. You must configure SpringDoc/Springfox to group APIs by version (using `GroupedOpenApi` beans), otherwise clients will see `V1User` and `V2User` schemas mashed together in the same documentation page.
* **Deprecation Paralysis:** Before writing a single line of `v2`, define exactly how and when `v1` will die. If you don't track which clients are still calling `v1` (using metrics/logs on the specific endpoints), you will be too terrified to ever delete the `v1` code, and your application will slowly turn into a museum.


## Claude

What you did is a real approach. The versions just lived in separate deployments instead of in the code.

**Why all clients had to move with the server.** The likely cause is a shared Java interface that the server and the clients both compile against. It could be a JAX-RS interface, a Feign or `@HttpExchange` interface, or a generated client in an `api.jar`. That interface is the contract, so changing it changes both sides at once. To serve two versions, you publish two contracts side by side, for example `orders-api-v1` and `orders-api-v2` in different packages. The server implements both, and each client compiles against the one it needs.

**Four places the versions can live**

1. **Separate deployments** (yours). `/v1` goes to the old app and `/v2` to the new one; a gateway routes by path. The old code is never touched. This works as long as the two apps share nothing, but they usually share the database. Then:
    - The old app isn't really frozen. Every schema change made for v2 must still work for it (expand/contract).
    - Rows written through v2, such as a new status or a split field, are read by v1 code that has never heard of them.
    - Every bug fix and security patch goes into two codebases, and the old app's libraries and JDK keep aging.

2. **One app, one controller per version.** This is the usual Java answer. Both controllers call the same service and domain model, which only know the latest shape. Each version has its own DTOs and mapper, so the version exists only at the edge:

```java
@RestController
@RequestMapping("/v1/orders")
class OrderControllerV1 {
  private final OrderService service;  // shared, speaks only the latest model

  OrderControllerV1(OrderService service) { this.service = service; }

  @GetMapping("/{id}")
  OrderV1Dto get(@PathVariable long id) {
    return OrderV1Mapper.toDto(service.find(id));  // the version lives only in DTO + mapper
  }
}
// OrderControllerV2: same shape, "/v2/orders", OrderV2Dto, OrderV2Mapper
```

A bug fix in the service fixes both versions. The cost is duplicate controllers, DTOs, mappers and tests. Also, v1's mapper has to fake anything the domain no longer has.

3. **One controller with `if (version == 1)` inside.** Avoid this. Version checks spread into every method, then into the service.

4. **Convert at the edge** (the Stripe model). Only the latest controllers exist. A filter upgrades v1 requests to the latest shape and converts latest responses back to v1, with one converter per breaking change. The core stays cleanest. The cost is a converter for every change, kept for years. It also only works for changes in shape. A change in behavior, such as new validation or a different calculation, can't be converted; it needs a flag in the service.

**Routing a request to the right version**

- **Spring 6 and earlier** has no built-in versioning. You map on one of these:
    - the path: `@RequestMapping("/v1/orders")`
    - a header: `@GetMapping(headers = "X-API-Version=1")`
    - the media type: `@GetMapping(produces = "application/vnd.example.v1+json")`
- **Spring Framework 7** (Spring Boot 4) adds it built in:
    - `@GetMapping(path = "/orders/{id}", version = "1")`, plus one config that says where the version comes from: header, path segment, query parameter or media type.
    - On the client side, `RestClient` sends it with `.apiVersion("1")`.
    - It can mark old versions as deprecated with `Deprecation` and `Sunset` response headers.
- **JAX-RS (Jakarta)** has nothing built in. Use `@Path("/v1/orders")`, or two methods on the same path with different `@Produces` media types. JAX-RS picks the method by the `Accept` header without extra setup. Header-based versioning needs a `ContainerRequestFilter`.

**Traps**

- **Versioning every change.** A new optional field or a new endpoint isn't breaking if clients ignore unknown fields. Version only breaking changes, or you end up with ten versions.
- **One DTO shared by v1 and v2.** A field added for v2 silently shows up in v1, or a rename breaks it. Freeze the v1 DTOs: copy them, don't share them.
- **New enum values.** v2 adds `ON_HOLD`, and a v1 client's Jackson fails on it. Decide the v1 mapping on the server (`ON_HOLD` → `PENDING`). Make your own clients tolerant with `READ_UNKNOWN_ENUM_VALUES_USING_DEFAULT_VALUE` and `@JsonEnumDefaultValue`.
- **v1 writes over v2 data.** A v1 client sends a full `PUT` for an order created through v2 and wipes the v2-only fields. v1's write path must merge, not replace.
- **Never knowing when v1 can go.** Log the version and the client on every request. You can only remove v1 when its traffic is zero. Set a policy up front, for example "current and previous version only, 12 months' notice."
- **Same JSON, different meaning.** For example, `amount` now includes tax. Versioning by DTO doesn't catch this, but it is still a breaking change.

**Trade-offs in short**

- Separate deployments keep the code apart but not the data, and every patch is done twice.
- Per-version controllers on one model are the default: cheap, one deploy, one database.
- Edge conversion keeps the core cleanest and needs the most infrastructure.
- If you control every client, skip versions and use expand/contract.

### Core Architecture & Routing

**Card 1: Infrastructure vs. Application Versioning**

* **Question:** What are the two high-level ways to host multiple API versions, and what is the trade-off?
* **Core Answer:** Infrastructure level (deploy separate `v1` and `v2` apps; easy code, operational nightmare) vs. Application level (one app routes `v1` and `v2`; complex codebase, easy operations).

**Card 2: The Standard Spring Pattern (Controller/DTO Versioning)**

* **Question:** What is the standard way to structure a Spring app to support multiple API versions?
* **Core Answer:** Isolate at the boundary. Create separate controllers (`V1UserController`, `V2UserController`) and separate DTOs, but map them to a single, unversioned Domain Entity and Business Service.

**Card 3: The Anti-Pattern (Logic Branching)**

* **Question:** Why is passing an `X-API-Version` header down into the service layer to use `if (version == 1)` an anti-pattern?
* **Core Answer:** It leaks HTTP concerns into business logic, creates spaghetti code, pollutes database queries, and makes safely deleting old versions nearly impossible.

**Card 4: The Mutation Pipeline (The Stripe Model in Spring)**

* **Question:** How do you implement API versioning using a "Mutation Pipeline" (interceptors) in Java?
* **Core Answer:** The controllers and services only know the latest version (e.g., `v4`). Spring `Filter` or `ResponseBodyAdvice` intercepts the outgoing `v4` JSON tree and runs it through sequential migrator classes (v4→v3→v2) before it hits the client.

### Data & State Management

**Card 5: Database Coupling (The Deadliest Trap)**

* **Question:** If V2 requires splitting a database column (e.g., `name` to `first_name` and `last_name`), how do you handle this in an app that still supports V1?
* **Core Answer:** Never map versioned DTOs directly to the DB. Migrate the actual DB table to the V2 schema. The `V1Mapper` in the app must dynamically compute the old shape (concatenate the names) when old clients read data.

**Card 6: Mapping Layer Complexity**

* **Question:** What is the main maintenance cost of the standard Controller/DTO versioning pattern?
* **Core Answer:** Mapping explosion. You need dedicated mappers (e.g., MapStruct) for Domain-to-V1, Domain-to-V2, etc. These mappers end up containing hidden logic to handle missing/new fields and require strict unit testing.

### Operations & Tooling

**Card 7: Swagger/OpenAPI Pollution**

* **Question:** How must you adjust Swagger/OpenAPI when supporting multiple versions in one Spring app?
* **Core Answer:** You must explicitly group endpoints (e.g., using SpringDoc's `GroupedOpenApi` beans), otherwise clients will see a confusing mix of `V1` and `V2` schemas on a single documentation page.

**Card 8: Deprecation Paralysis**

* **Question:** What operational step is mandatory before writing the code for an API V2?
* **Core Answer:** Establish a deprecation timeline and add metrics to track exactly who is calling V1. If you cannot measure V1 traffic, you will never have the confidence to delete it.

Here are more cards focusing strictly on the technical nuances, traps, and framework-specific behaviors of Spring and Jakarta EE when handling multiple API versions.

### In Spring MVC, how do you route requests to different controller methods based on custom `Accept` or version headers?

Use `@RequestMapping(produces = "application/vnd.company.v1+json")` for standard content negotiation via the `Accept`
header. If you are using custom version headers, use `@RequestMapping(headers = "X-API-Version=1")`. Spring will
automatically route the request to the matching method, keeping your Java code clean.

### In Jakarta EE (JAX-RS), how do you implement version routing via media types?

Use the `@Produces("application/vnd.company.v1+json")` and `@Consumes(...)` annotations directly on your resource
methods or classes. The JAX-RS runtime handles the content negotiation and routes the incoming request to the correct
version of the endpoint automatically without any custom if/else logic in the method body.

### Why is using Jackson's `@JsonView` to hide or show fields for different API versions a bad idea?

It couples multiple API versions directly to a single DTO class. As your schemas diverge over time and fields change
meaning or data types, `@JsonView` becomes an unmaintainable mess of annotations. It is much cleaner and safer to
create separate DTO classes (e.g., `UserDtoV1`, `UserDtoV2`) for each version.

### When using a global `@ControllerAdvice` in Spring, how do you ensure different API versions get correct error formats?

It is very difficult because global advice executes outside the controller's version context. You either have to inspect
the `HttpServletRequest` inside the advice block to check the URI or headers and conditionally format the error, or
adopt an unversioned, standardized error format (like RFC 7807 Problem Details) that applies to all versions.

### How do you handle `@NotNull` validation if a field is required in V2 but did not exist in V1?

By using entirely separate DTO classes for each version, each class gets its own Jakarta Validation annotations. Avoid
trying to use Validation Groups on a single shared DTO to manage version differences, as it quickly leads to high
complexity and hard-to-maintain code.

### What is a major risk when returning hypermedia links (Spring HATEOAS) in a multi-version API?

Hardcoded links can break the API version contract. V1 endpoints must generate links that point back to V1 endpoints,
not V2. You must configure `WebMvcLinkBuilder` very carefully to ensure the dynamically generated URIs respect the
original request's version path or headers, keeping the client in the correct version context.

### If you expose V1 and V2 in the same Spring application, what problem occurs for clients using OpenAPI Generator?

Name collisions. If both versions export a schema named `User`, the generator will fail or overwrite files. You must
configure SpringDoc to append version suffixes to schemas (e.g., `UserV1`, `UserV2`) or serve entirely separate OpenAPI
YAML files per version.

Here are more advanced cards focusing on specific Spring framework mechanics, database migration patterns in Java, and caching traps when versioning APIs.

### How do you test multiple API versions efficiently in a Spring Boot integration test?

Use `@WebMvcTest` (or `@SpringBootTest`) and write parameterized tests. Supply the version headers or URI prefixes
as test parameters, feeding them into `MockMvc`. This ensures both the routing (e.g., `headers = "X-API-Version=..."`)
and the version-specific validation logic are executed properly without duplicating the entire test suite.

### How does API versioning in Spring complicate declarative caching (`@Cacheable`)?

If your cache key is only the resource ID (e.g., `userId`), a V1 request might cache a V1 DTO. A subsequent V2 request
for the same ID will hit the cache and receive the wrong DTO shape. You must manually include the API version
in the cache key (e.g., `@Cacheable(key = "#userId + '-' + #version")`) or cache the domain entity and map it to the
DTO *after* retrieval.

### What happens in Spring MVC if a client sends an `Accept` header version that you do not support?

Spring will throw an `HttpMediaTypeNotAcceptableException`, which by default results in a `406 Not Acceptable` response.
This is the correct REST behavior, signaling to the client that the server cannot produce the requested version format.

### When using Flyway or Liquibase in a Java app supporting both V1 and V2 APIs, what rule governs database migrations?

The migration must be strictly non-destructive. You can add columns or tables, but you cannot drop, rename, or alter
the type of an existing column until you are absolutely certain that V1 code (and any V1 clients) has been completely
removed from the application.

### Why is using Spring's `HandlerInterceptor` to enforce deprecated API usage better than application logs?

An interceptor can actively alter the response. While logs tell *you* a deprecated endpoint was hit, an interceptor
can automatically inject a `Deprecation` and `Link` HTTP header into the response of any controller annotated with
`@Deprecated`, warning the *client* developers directly that they need to migrate.

### How do you implement the "Stripe Model" (Mutation Pipeline) in Spring using `ResponseBodyAdvice`?

Implement `ResponseBodyAdvice<Object>`. Its `beforeBodyWrite` method receives the outgoing payload (usually the latest
DTO version). You intercept this object, check the requested version from the `ServerHttpRequest`, pass the object
through your chain of migrators to downgrade its shape, and return the modified object (or `JsonNode`) to be serialized.

### What is the "Expand/Contract" pattern for Java database entities (`@Entity`) during an API version transition?

It maps to database changes safely.

1. Add new `@Column` to entity (Expand).
2. App writes to both old and new columns.
3. Migrate existing DB rows.
4. App reads from the new column only.
5. Remove old `@Column` from Java entity (Contract).
6. Drop old column in DB.

Here are additional flashcards focusing specifically on Jakarta EE, JAX-RS, and general JVM patterns for API versioning.

### In JAX-RS, how do you handle a client sending an unsupported API version in a custom header?

Unlike `@Consumes`/`@Produces` which automatically throw a `406` or `415`, custom header routing in JAX-RS requires a
`ContainerRequestFilter`. The filter inspects the header; if the version is unsupported, the filter must explicitly
abort the request by calling `requestContext.abortWith(Response.status(400).entity("Unsupported version").build())`
before it ever reaches your resources.

### How can a JAX-RS `ContainerResponseFilter` automate deprecation warnings for old API versions?

You can write a global response filter that inspects the matched resource method for a custom `@DeprecatedApi`
annotation (or simply checks the requested URL/headers). The filter can then automatically append the standard HTTP
`Deprecation` header (e.g., `Deprecation: @114002773`) to the outgoing `ContainerResponseContext` without polluting
your endpoint logic.

### What is the danger of using JPA (Hibernate) `@PrePersist` or `@PreUpdate` to handle data migrations for older API versions?

These lifecycle callbacks execute deep in the persistence layer, far away from the HTTP context. If you try to compute
fallback values for V1 fields inside the entity itself, you tightly couple the database domain to specific API version
requirements. Version mapping logic must stay at the API boundary, not inside JPA entities.

### How do you cleanly implement URL-based versioning (e.g., `/v1/`, `/v2/`) using JAX-RS `@Path` annotations?

Do not put the version in the class-level `@Path` (e.g., `@Path("/v1/users")`). Instead, create a router resource:
`@Path("/api")` with sub-resource locators. Methods annotated with `@Path("/v1")` and `@Path("/v2")` return
instances of `V1UserResource` and `V2UserResource` respectively. This keeps the versioning structure hierarchical
and cleanly isolates the implementations.

### Why is using MapStruct's `@Mapping(target = ..., source = ...)` better than manual getters/setters for version translation?

Manual mapping code is prone to developer error, especially when adding new fields to the domain entity but forgetting
to update the V1 and V2 mappers. MapStruct generates the code at compile-time and can be configured to fail the build
(via `unmappedTargetPolicy = ReportingPolicy.ERROR`) if a field is added to the domain but not explicitly handled
in your version DTOs.

### In a Java microservices environment, how do you manage internal service-to-service communication when an API versions?

Internal services should use the **Tolerant Reader pattern** (e.g., configuring Jackson with
`DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES` set to `false`). If service A sends V2 data with a new field,
Service B (expecting V1) safely ignores the unknown field. This prevents tight coupling and allows services to deploy
independently.

### How does Java's `Record` feature simplify maintaining multiple DTO versions?

Records (`public record UserDtoV1(String name) {}`) are immutable and concise. When defining dozens of DTOs across
V1, V2, and V3, records eliminate all boilerplate (getters, setters, equals, hashcode). This drastically reduces the
noise in your `dto.v1` and `dto.v2` packages, making it easier to spot the actual schema differences between versions.
