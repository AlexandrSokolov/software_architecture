### Modes of dataflow — who encodes, who decodes?
<details><summary>Show answer</summary>

- **Database** — the writer encodes; a later reader decodes, often newer code, years later. 
  During a deploy, old code also reads new records, so both directions are needed.
  [Old code can even drop new fields](#old-code-saves-a-new-record--whats-lost).
- **Service call** (REST, RPC) — the client encodes the request, the server decodes it; for the response, the server
  encodes and the client decodes. [Which direction](#api-calls--which-compatibility-where) each needs depends on who
  was upgraded first.
- **Workflow engine** (durable execution) — the engine encodes each step's input and result into its log, and decodes
  them on retry or replay, possibly with newer code.
- **Async message** — the producer encodes, the consumer decodes, and a broker passes the message between them. They
  deploy separately, so both directions are needed.

</details>

### Database — who encodes, who decodes?
<details><summary>Show answer</summary>

The process that writes a record encodes it; the process that reads it decodes it. Two set-ups:
- **One application** — the reader is a later version of the writer: storing data is sending a message to your
  future self.
- **Several processes** — other services, or several instances of one service, read and write the same data at the
  same time.

</details>

### Database — which compatibility where?
<details><summary>Show answer</summary>

- **Backward** — rows stay for years while the code changes, so today's code reads rows written by old code.
- **Forward** — old and new code run at the same time: during a rolling deploy, a new instance writes a row with a
  new field, and an old instance reads it. The old code must not fail on it, and if it saves the row back, must not
  [drop the field](#old-code-saves-a-new-record--whats-lost).

</details>

### Old code saves a new record — what's lost?
<details><summary>Show answer</summary>

New code adds a field and stores a record with it. Old code reads the record into a model object that has no slot for
that field, changes something, and writes it back. The new field is silently gone.

Fix: decode in a way that keeps fields you don't know and writes them back. Protobuf does this by default; with
Jackson, collect them with `@JsonAnySetter` and write them out with `@JsonAnyGetter`.

</details>

### Service vs shared database — difference?
<details><summary>Show answer</summary>

Both let clients store and query data. The difference is encapsulation — what clients can reach:
- **Shared database** — any query on any table (SQL). The tables become the contract, so changing a column can break
  a client you don't know about.
- **Service** — only the requests its API defines, with answers set by its business logic. The service decides what
  each client may do; its tables stay hidden.

</details>

### Why must a service API stay compatible?
<details><summary>Show answer</summary>

The goal of microservices is independent deploys: each service belongs to one team, and that team ships new versions
often, without waiting for other teams. So old and new clients and servers run at the same time, and they must still
[read each other's requests and responses](#api-calls--which-compatibility-where).

Payoff: as long as the API stays compatible, the team can change anything behind it — code, database, even the whole
system — without asking anyone.

</details>

### API calls — which compatibility where?
<details><summary>Show answer</summary>

Root: look at who reads the message. A newer reader needs
[backward](3.6.1_Evolvability_&_Compatibility.md#backward-vs-forward-compatibility); an older reader needs forward.

- **Old client → new service** — the request needs backward (the new service reads it), and the response needs forward
  (the old client reads it).
- **New client → old service** — the request needs forward, and the response needs backward.

Servers are usually deployed first, so the first case is the common one.

</details>

### Which API changes keep clients working?
<details><summary>Show answer</summary>

An API's compatibility comes from its encoding. gRPC follows the rules of
[Protobuf](3.6.2_Encoding_Formats.md#what-are-protocol-buffers); for REST with JSON:
- **Safe** — add an optional request parameter, or add a field to a response. Old clients must ignore fields they
  don't know — plain Jackson fails on them by default; Spring Boot turns that off.
- **Breaking** — remove or rename a field, make an optional field required, change a field's type or meaning.

</details>

### You need a breaking change to a public API — how?
<details><summary>Show answer</summary>

- **Verdict** — first look for a [safe change](#which-api-changes-keep-clients-working). If the break is real,
  publish a new version and keep the old one running next to it.
- **Reasoning** — the clients belong to other companies, or are apps users don't update. You can't make them upgrade,
  so the old version must keep working for years, maybe forever.
- **Trade-off** — you run and fix two versions until the last client moves. When you control every client (an
  internal API), move them over, then remove the old behavior — no long-lived second version.

</details>

### How does a client choose an API version?
<details><summary>Show answer</summary>

There is no standard. Common ways:
- **In the URL** — `/v2/orders`. Easy to see, test and route; but every version gets new URLs.
- **In the `Accept` header** — `Accept: application/vnd.example.v2+json`. URLs stay the same; but the version is
  hidden, harder to try in a browser, and caches must take the header into account.
- **Stored per API key** — the server remembers each client's version, changed through an admin interface (Stripe
  works this way). Nothing extra in the request; but the request alone doesn't show which version answers it.

</details>

### How is a service API defined?
<details><summary>Show answer</summary>

A client must know each endpoint, what to send and what comes back. 
An IDL (Interface Definition Language) writes this down in one file:
- OpenAPI for JSON/REST, 
- [Protocol Buffers](3.6.2_Encoding_Formats.md#what-are-protocol-buffers) for gRPC. 


From that file, tools make:
- **Docs** built from the file, so they don't go out of date.
- **Client libraries** in many languages, generated instead of hand-written.
- **Compatibility checks** — a changed definition is compared with the old one, so a change that breaks backward or
  forward compatibility is caught before it ships.

</details>

### Code-first vs contract-first — when which?
<details><summary>Show answer</summary>

Root: what is written first — the server code or the [IDL](#how-is-a-service-api-defined) file.

- **Code-first** — write the server; the framework generates the IDL from the code (FastAPI).
    - Prefer for: an internal API where one team owns the server and its clients, and changes are frequent.
    - Cost: the contract is a side effect — a refactoring can change the API without anyone noticing; clients
      wait until the server exists.
- **Contract-first** — write the IDL; generate server stubs and clients from it (gRPC).
    - Prefer for: APIs used by other teams or companies. Teams agree on the file, then build server and clients in
      parallel, and every API change is reviewed as a change to the file.
    - Cost: an extra file and tools to maintain, and the server must fit the generated stubs.

</details>
