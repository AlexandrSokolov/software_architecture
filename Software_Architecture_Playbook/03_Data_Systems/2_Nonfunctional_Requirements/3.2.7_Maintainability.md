## Nonfunctional requirements - Maintainability

### Building vs maintaining — which costs more?
<details><summary>Show answer</summary>

Maintaining, usually — most of a system's cost comes after launch, and it keeps coming as long as the system lives:
- **Bug fixing** — finding and fixing what breaks in production.
- **Keeping it running** — ops, on-call, incidents.
- **Support** — support teams answering customers.
- **Change** — new requirements, upgrades, paying off old shortcuts (field term: *technical debt*).

So every design choice that makes a system easier to run, understand or change pays off for years — that's what the
[maintainability principles](#maintainability--principles) are for.

</details>

### Maintainability — principles?
<details><summary>Show answer</summary>

Every valuable system ends up as legacy, so design for the people who will maintain it:

- [**Operability (Run it)**](#operability--what-supports-it) — easy to **run**, for the ops team day to day: monitoring and
  observability, automation (CI/CD, self-healing) with manual override, docs and predictable behavior, no
  single-machine dependency.
- [**Simplicity (Understand it)**](#simplicity--what-to-reason-about) — easy to **understand**, for new engineers now: well-known
  patterns and consistent abstractions instead of clever hacks — less to keep in your head (field term:
  *cognitive load*).
- [**Evolvability (Change it)**](#what-is-evolvability-and-how-do-you-get-it) — easy to **change**, for future engineers: 
  loose coupling, so requirements nobody expected fit in without a rewrite.

Handle: run it / understand it / change it.

</details>

### Operability — what supports it?
<details><summary>Show answer</summary>

Make routine work easy and incidents fixable, so the ops team spends its time on real problems. Three groups:

- **Know it** — understand what the system is doing and will do:
  - [*Monitoring*](#what-is-monitoring) — key metrics and alerts: is it healthy?
  - [*Observability*](#what-is-observability) — logs, metrics, traces: why is it behaving like this?
  - [*Docs and runbooks*](#how-do-operators-know-what-to-do) — a clear operational model ("if I do X, then Y
    happens") and predictable behavior.
- **Control it** — change its state:
  - [*Automation*](#what-should-be-automated-for-operations) — CI/CD pipelines,
    [infrastructure as code](#what-is-infrastructure-as-code), restarts and self-healing.
  - [*Manual control*](#when-automation-isnt-enough--what-do-you-need) — run, rerun, pause or override by hand when
    the automation gets things wrong.
- **Work on it without downtime** — survive losing a machine:
  - *No single-machine dependency* — take any machine down for maintenance (e.g. a node in a Kubernetes cluster)
    while the rest keeps serving. A single Docker Compose host is one machine: fine if that downtime is acceptable,
    but decide it on purpose.

Handle: know it, control it, work on it without downtime.

</details>

### How do you see what a running system is doing?
<details><summary>Show answer</summary>

Two ways, for two kinds of problems:
- [**Monitoring**](#what-is-monitoring) — for problems you expected: watch chosen metrics, alert when one crosses a
  limit. Answers "is it healthy?"
- [**Observability**](#what-is-observability) — for problems you didn't expect: dig through the system's output to
  find out what happened. Answers "why is it behaving like this?"

Monitoring tells you something is wrong; observability lets you find out what and where.

</details>

### What is monitoring?
<details><summary>Show answer</summary>

Watching a set of metrics chosen in advance — error rate, p99 response time, CPU, queue length — and alerting when one
crosses a limit, e.g. error rate above 1% for 5 minutes.

It answers "is it healthy?" — but only for problems someone thought to check.

</details>

### What is observability?
<details><summary>Show answer</summary>

Being able to understand a system's internal state from what it outputs — so you can answer questions nobody planned
for, like "why are only EU users with large carts slow since 10:15?"

Built on three kinds of output (field term: *three pillars*):
- **Metrics** — numbers over time: how much, how often.
- **Logs** — records of single events: what happened.
- **Traces** — one request's path through all services: where the time went.

</details>

### Logs, metrics, and traces from different tools — how do you unify them?
<details><summary>Show answer</summary>

With **OpenTelemetry** (*OTel*) — one open, vendor-neutral standard instead of three separate vendor libraries that
don't share context.

You instrument the code once. It carries the same trace ID across services and into log lines, 
so a backend can jump from a slow trace to its logs, and it exports to any backend you choose — 
switching vendor is a config change.

It doesn't store or show data: you still need backends (Jaeger, Prometheus, Grafana, Datadog).

</details>

### How do you implement OpenTelemetry in a Java application?
<details><summary>Show answer</summary>

**Automatic instrumentation (the standard approach)** — no code changes. Attach the OpenTelemetry Java agent to the JVM; 
it rewrites the bytecode of popular libraries (Spring, JDBC, HTTP clients, Kafka) as they load and produces
traces, metrics and logs. In a container you don't touch the start command — the JVM reads a standard environment
variable:

```dockerfile
COPY opentelemetry-javaagent.jar /otel/
ENV JAVA_TOOL_OPTIONS="-javaagent:/otel/opentelemetry-javaagent.jar"
```

On Kubernetes, the OpenTelemetry Operator can inject the agent into pods for you.

**Manual instrumentation (your own business logic)** — use the OpenTelemetry API to create a span for your own method
or add business data to the current one:

```java
@WithSpan
void calculatePrice(Order order) {
  Span.current().setAttribute("user_id", order.userId());
}
```

**Exporting** — configure with environment variables: `OTEL_SERVICE_NAME=order-service`,
`OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318` — to a Collector, or straight to a vendor that accepts OTLP.

Spring Boot alternative without an agent: Micrometer Tracing with the OpenTelemetry bridge and an OTLP exporter.

</details>

### Monitoring & observability — mainstream tools?
<details><summary>Show answer</summary>

Popular tools, mapped to what they cover:

- **Prometheus** — open-source metrics collection + alerting; de facto standard for cloud-native / Kubernetes.
- **Grafana** — dashboards and visualization layer; sits on top of Prometheus and many other sources.
- **Datadog** — commercial all-in-one SaaS: metrics, logs, and traces (APM) in one platform.
- **Splunk** — enterprise log search and analytics; strong for large-scale log data and security.
- **New Relic** — commercial all-in-one APM / full-stack observability SaaS.
- **Dynatrace** — commercial enterprise APM, AI-assisted root-cause analysis.

Recall handle: monitoring = is it healthy, observability = why (metrics/logs/traces); 
- one open-source metrics pair (Prometheus + Grafana), 
- three commercial all-in-ones (Datadog, New Relic, Dynatrace), 
- one log giant (Splunk).

</details>

### How do operators know what to do?
<details><summary>Show answer</summary>

- **Docs** — a clear operational model: "if I do X, then Y happens".
- **Runbooks** — step-by-step guides for common incidents, e.g. "DB disk full: check X, clean Y, restart Z".
- **Predictable behavior** — the system does what the docs say; surprises make both useless.

</details>

### What should be automated for operations?
<details><summary>Show answer</summary>

- **Deploys** — CI/CD pipelines: every release the same way.
- **Infrastructure** — servers and config defined in files, recreated identically (*infrastructure as code*).
- **Recovery** — crashed processes restarted on their own (*self-healing*, e.g. Kubernetes).

</details>

### What is infrastructure as code?
<details><summary>Show answer</summary>

Servers, networks and their configuration described in files, kept in Git, and applied by a tool — instead of set up
by hand. Any environment can be recreated the same way, and every change is reviewed like code.

Two jobs:
- **Provisioning** — create the machines, networks, load balancers: Terraform, CloudFormation, Pulumi.
- **Configuration management** — set up what runs on them (packages, config files, services): Ansible, Chef, Puppet.

It only works if:
- **the code is the only way in** — hand edits on servers make them drift from the code (*configuration drift*);
- **re-running is safe** — applying the same code twice gives the same result (*idempotent*).

</details>

### When automation isn't enough — what do you need?
<details><summary>Show answer</summary>

**Manual control** — for when the automation gets things wrong, misses a run, or meets a case it wasn't built for:
- **Run now** — trigger a scheduled job on demand.
- **Rerun** — repeat a failed or past run (e.g. for a date range).
- **Pause** — stop a job, a consumer or a deploy that is going wrong.
- **Override** — change a setting or switch a feature off without redeploying (*feature flag*).

Rule: the manual trigger uses the same code path as the automatic one, and a second run while one is active is refused.

</details>

### A system nobody can understand or change safely — name?
<details><summary>Show answer</summary>

A **big ball of mud** — a system whose complexity grew over time until it is hard to understand, and every change
gets slower and costlier.

</details>

### Simplicity — what to reason about?
<details><summary>Show answer</summary>

Complexity is the main enemy of maintainability, so simplicity is a core design goal. 

To reason about:
1. [Why complexity hurts](#why-does-complexity-hurt) — cost and bug risk.
2. [Why simplicity is hard to define](#why-is-simplicity-hard-to-define) — it's subjective, no clean measure.
3. [The best tool for it](#best-tool-against-complexity) — hide detail behind a clean façade.
4. [How that tool is built](#how-are-abstractions-built) — app-level vs general-purpose infrastructure.

Spine: 
- complexity costs money and breeds bugs → 
- aim for simple → 
- but "simple" is fuzzy → 
- hide detail behind a façade → 
- build those façades app-side or on general-purpose primitives.

</details>

### Why does complexity hurt?
<details><summary>Show answer</summary>

- **Cost** — complexity blows budgets and schedules.
- **Bugs on change** — the harder the system is to reason about, the more a change slips: hidden assumptions,
  unintended consequences, and unexpected interactions get overlooked.

So reducing complexity directly improves maintainability.

</details>

### Why is simplicity hard to define?
<details><summary>Show answer</summary>

There is no objective standard — "simple" is subjective. Example: one system hides a complex implementation
behind a simple interface; another has a simple implementation that exposes internals to users. Which is simpler?
No clear answer.

</details>

### Best tool against complexity?
<details><summary>Show answer</summary>

Hide detail, so people think in a simpler model. Two tools do it together:
- **Abstraction** — the simpler model: what it does, not how. SQL: tables and queries, not disk pages and locks.
  `List`: add and get, not a growing array.
- **Encapsulation** — enforces the hiding, so nobody depends on the internals: `ArrayList`'s array is private; a
  service's database is reachable only through its API.

Both work at every level, from classes to whole systems. Abstraction without encapsulation leaks: callers reach into
the internals, and every internal change breaks them.

A good abstraction serves many uses: reuse beats reimplementing, and one fix in the shared component helps everyone.

</details>

### When does hiding detail not fully work?
<details><summary>Show answer</summary>

A **leaky abstraction** — the details it hides still show through, so you have to learn what's underneath anyway:
- **SQL** — the same query is fast or slow depending on indexes; you must know how the data is stored.
- **ORM (JPA/Hibernate)** — `order.getItems()` looks like plain Java, but in a loop it runs one query per order
  (*N+1 problem*); you must think in SQL.
- **Remote call that looks local** — a Feign client looks like a method call, but it can be slow, time out or fail
  halfway; the network shows through.

Rule of thumb (Joel Spolsky): every non-trivial abstraction leaks somewhere — use it, but know what it hides.

</details>

### How are abstractions built?
<details><summary>Show answer</summary>

They are layered. You cannot build reliable business logic without reliable foundational primitives beneath it:

- **Infrastructure (General-purpose):** Abstracts away hardware, network partitions, and concurrency.
  *Examples:* Database transactions (abstracting crash recovery), indexes, and distributed event logs.
- **Application (Domain-specific):** Abstracts away complex business rules, built entirely on top of the
  infrastructure layer. *Examples:* Domain-Driven Design (DDD) and architectural design patterns.

</details>

### What is evolvability, and how do you get it?
<details><summary>Show answer</summary>

**Evolvability** — how easily a system can change for new requirements. Two things make it easy:
- [**Simplicity**](#simplicity--what-to-reason-about) **and good [abstractions](#best-tool-against-complexity)** —
  you can only change safely what you understand.
- **Loose coupling** — parts that depend little on each other can change one at a time, without breaking the rest.

</details>
