### How do you raise maximum throughput?
<details><summary>Show answer</summary>

To raise the [maximum throughput](3.2.1_Performance.md#what-is-maximum-throughput), fix the software or
[scale](3.2.6_Scalability.md):
- **Fix the software limit** — bigger pool, faster code. 
  Per [Little's law](3.2.1_Performance.md#what-is-littles-law) the maximum is N / d, so raise N or cut d.
- **Bigger machine** — scale up: move to a machine with more CPU cores, memory and faster disks. No code changes, but
  everything still runs on one machine.
- **More machines** — scale out. Once the biggest machine is not enough, this is the only way left.

</details>

### What happens when a system nears overload?
<details><summary>Show answer</summary>

Near the [maximum throughput](3.2.1_Performance.md#what-is-maximum-throughput), the queue grows and
[response times rise sharply](3.2.1_Performance.md#how-do-throughput-and-response-time-relate). From there it can fall into a
**vicious cycle** — each bad step causes the next, so it keeps getting worse:
- [**Retry storm**](#what-is-a-retry-storm) — it feeds itself: clients time out and resend, adding even more load.
- [**Metastable failure**](#what-is-a-metastable-failure) — it gets stuck: the overload stays even after traffic drops.

Both are [stopped from two sides](#how-do-you-prevent-overload-from-feeding-itself): clients retry less, servers drop
extra work.

</details>

### What is a retry storm?
<details><summary>Show answer</summary>

A loop that starts when a system gets slow:
- Near the [maximum throughput](#what-is-maximum-throughput), the queue grows and response times rise.
- Clients time out and **resend** their requests.
- The server now handles the old requests *plus* the resends, so the load jumps and the queue grows further.

Each step feeds the next — the system gets slower *because* it is slow.

</details>

### What is a metastable failure?
<details><summary>Show answer</summary>

A traffic spike ends, but the system stays overloaded and can't get out on its own. **Metastable** — once pushed into
the bad state, it stays there without the push.

Why it stays stuck:
- **Retries keep the load high.** A [retry storm](#what-is-a-retry-storm) keeps the request rate above the
  [maximum throughput](3.2.1_Performance.md#what-is-maximum-throughput) even after real traffic falls.
- **The server works for nobody.** It is still processing old requests whose clients already gave up and resent.
  That work helps no one, so the queue never shrinks.

It recovers only when something breaks the loop: a restart that empties the queue, or
[cutting retries and dropping extra requests](#how-do-you-prevent-overload-from-feeding-itself).

</details>

### How do you prevent overload from feeding itself?
<details><summary>Show answer</summary>

Break the [vicious cycle](#what-happens-when-a-system-nears-overload) from both ends:
- [**Client side**](#how-does-the-client-stop-overload-feeding-itself)
- [**Server side**](#how-does-the-server-stop-overload-feeding-itself)

</details>

### How does the client stop overload feeding itself?
<details><summary>Show answer</summary>

Each client stops its [retries](#what-is-a-retry-storm) from adding more load:
- [**Exponential backoff with jitter**](#what-is-exponential-backoff-with-jitter) — wait longer after each failed
  try, plus a random delay so clients don't all retry at the same moment.
- [**Circuit breaker**](#what-is-a-circuit-breaker) — after too many failures, stop calling the service for a while.
- [**Retry budget**](#what-is-a-retry-budget) — cap how many retries are allowed, e.g. at most 10% of requests.

Handle: spread retries out, pause them, cap them.

</details>

### What is exponential backoff with jitter?
<details><summary>Show answer</summary>

A retry rule with two parts:
- **Exponential backoff** — double the wait after each failed try: 1 s, 2 s, 4 s, 8 s… Retries get rarer instead of
  hitting the overloaded service at full speed.
- **Jitter** — add a random amount to each wait. Without it, clients that failed together retry together, and every
  retry wave hits the server at the same moment (field term: *thundering herd*).

</details>

### What is a circuit breaker?
<details><summary>Show answer</summary>

A small object in the caller's client code that wraps every call to another service, watches the results, and
decides whether to call that service at all.

Problem it solves: service A calls B; B starts timing out. Without a breaker, every request in A waits for the timeout,
threads run out, and A goes down too — while B keeps getting hit and can't recover.

Three states, named after an electric circuit (**closed** = wire connected, current flows; **open** = wire cut):
- **Closed** — normal: calls go to B; the breaker counts failures and timeouts.
- **Open** — failures pass a limit (e.g. 50% of recent calls): the breaker returns an error or a fallback right away,
  without calling B.
- **Half-open** — after a wait (e.g. 30 s), a few test calls go through. Success → closed; failure → open again.

Both sides win: A fails fast instead of tying up threads, and B gets no traffic while it recovers.
In Java: Resilience4j `CircuitBreaker`.

</details>

### What is a retry budget?
<details><summary>Show answer</summary>

A limit on how many **retries** a client may send, measured against its normal traffic — e.g. retries may be at most
10% of requests. First attempts always go through; only the extra attempts are limited.

Why: when a service is half broken, unlimited retries multiply the load. Example: 1,000 requests/s, 50% fail, up to 3
retries each → 1,000 + 500 + 250 + 125 ≈ 1,875 requests/s — almost double, on a service that is already struggling.
With a 10% budget: at most 100 retries/s → about 1,100 requests/s.

How it works — a **token bucket** tied to traffic:
- each normal request adds a fraction of a token (0.1 for a 10% budget);
- each retry spends one token;
- no token → no retry: the failed request just fails.

Result: retries still help with short blips (some failed requests get one more try), but even if every request fails,
retries add at most 10% extra load.

</details>

### Retry budget vs per-call retry?
<details><summary>Show answer</summary>

Same goal — retry failed calls — but a different scope:
- **Per-call retry** — each call decides alone: "I failed, I may try again, up to N times." It knows nothing about
  other calls. Java: Resilience4j `Retry` (`maxAttempts = 3`), Spring Retry `@Retryable(maxAttempts = 3)` — both
  count the first call, so 3 attempts = up to 2 retries.
- [**Retry budget**](#what-is-a-retry-budget) — one limit for **all traffic** to a service: "retries may be at most
  10% of requests", shared by every call.

Example — 1,000 requests fail at once:
- per-call retry, max 3 attempts: every one of them retries → up to **2,000 extra calls**, on a service already failing;
- retry budget of 10%: at most **100 retries**, then failed requests just fail.

Use both: per-call retry sets how often one call may try; the budget stops all calls together from multiplying the load.

</details>

### Circuit breaker vs retry budget?
<details><summary>Show answer</summary>

They both protect a struggling service, but they limit different things:
- A [**circuit breaker**](#what-is-a-circuit-breaker) decides whether to call the service **at all**. When it's open,
  nothing goes through, not even first attempts. It's an on/off switch.
- A [**retry budget**](#what-is-a-retry-budget) never touches first attempts. It only limits the **extra** attempts —
  the retries — so they can't add extra load on top of normal traffic. It's a cap, not a switch.

Same example — 1,000 requests/s, 50% failing: 
- no limits ≈ 1,875/s reach the service; 
- retry budget ≈ 1,100/s; 
- open breaker 0/s.


Use both: 
- the budget handles partial or short failures, where some retries still help; 
- the breaker handles a service that is clearly down, where even first tries are wasted.

</details>

### How does the server stop overload feeding itself?
<details><summary>Show answer</summary>

The server keeps its load under the [maximum throughput](#what-is-maximum-throughput), so it can't
[get stuck](#what-is-a-metastable-failure):
- [**Load shedding**](#what-is-load-shedding) — near the limit, reject some requests right away (e.g. `503`).
- [**Backpressure**](#what-is-backpressure) — tell senders to slow down (e.g. `429` with a `Retry-After` header).
- [**Queue timeouts**](#what-is-a-queue-timeout) — drop queued requests that already waited longer than the client's
  timeout; nobody is waiting for the answer.

Handle: reject early, slow the senders, skip dead work.

</details>

### What is load shedding?
<details><summary>Show answer</summary>

The server rejects some requests on purpose when it is near its 
[maximum throughput](3.2.1_Performance.md#what-is-maximum-throughput) —
right away, with a cheap error (e.g. `503 Service Unavailable`), instead of putting them in a queue.

Rejecting costs almost nothing. A queued request would only wait, time out at the client and come back as a retry.
So the server answers the requests it keeps at normal speed, instead of answering all of them too late.

</details>

### What is backpressure?
<details><summary>Show answer</summary>

The receiver controls how fast the sender may send. When the receiver falls behind, the sender has to slow down —
instead of the receiver's queue growing without end.

Examples:
- **Bounded queue** — when it is full, the producer blocks until there is room (Java `ArrayBlockingQueue.put()`).
- **Reactive Streams** — the consumer asks for the next N items with `request(n)`; the producer sends no more than
  that.
- **HTTP** — `429 Too Many Requests` with a `Retry-After` header tells the client when to come back.

</details>

### What is a queue timeout?
<details><summary>Show answer</summary>

The server drops a queued request if it has waited in line longer than the client's timeout limit.
The client has already given up — and likely resent the request — so processing the original one is wasted work.

**How it works (HTTP example):**
- The client sends its maximum wait time in a custom header (e.g. `X-Timeout-Ms: 2000`).
- The server attaches the arrival timestamp to the request and puts it in a normal queue.
- When a worker thread pulls the request, it checks the clock: `now − arrival timestamp`.
- If the wait exceeded 2000 ms, the worker skips the work and drops the request — answers `503`, or just discards it
  if the client is already gone.

This stops the server from [working for nobody](#what-is-a-metastable-failure) — one of the two reasons an overloaded
system stays stuck.

</details>
