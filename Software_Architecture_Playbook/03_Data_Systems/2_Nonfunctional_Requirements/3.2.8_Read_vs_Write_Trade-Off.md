### Latest posts from everyone you follow — two ways?
<details><summary>Show answer</summary>

Field terms for this feed: *home timeline*, *news feed*.

- **Pull — compute on read:** query the posts of everyone the user follows, merge, sort by time. Cheap to post,
  [expensive to read](#read-time-timelines--what-do-they-cost). (*fan-out on read*)
- **Push — precompute on write:** when someone posts, copy the post into every follower's timeline cache (their
  "mailbox"). Cheap to read, [expensive to post](#precomputed-timelines--what-do-they-cost). (*fan-out on write*)

*Fan-out* — one post spreading out to many followers.

</details>

### Read-time timelines — what do they cost?
<details><summary>Show answer</summary>

Every app open runs this join:

```sql
SELECT p.* 
FROM posts p JOIN follows f ON p.author_id = f.followee_id
WHERE f.follower_id = ?
ORDER BY p.created_at DESC LIMIT 50;
```

- **Most frequent action = most expensive** — users open the app far more often than they post, so the heaviest
  query runs most often; at scale it overloads the database.
- **Grows with follows** — a user following 2,000 accounts makes the database gather and sort posts from 2,000 authors
  on every open; these users set your p99.
- **Hard to cache** — every user's result is different, and it changes with every new post from anyone they follow.

What you get in return: posting stays cheap — one insert.

</details>

### Precomputed timelines — what do they cost?
<details><summary>Show answer</summary>

Pushing each post into every follower's mailbox makes reads instant, but you pay for it:
- **One post = many writes** — 300 followers → 300 mailbox writes per post; a user with millions causes
  [millions](#one-user-30-million-followers--what-breaks). (field term: *write amplification*)
- **Storage** — every user keeps their own timeline, so one post is copied into every follower's mailbox.
- **Delay** — followers see the post only after background workers finish the push: seconds normally, longer when a
  big account posts.
- **Wasted work** — mailboxes of users who never log in get filled too.

</details>

### Which load numbers decide the timeline design?
<details><summary>Show answer</summary>

Requests per second alone can't decide it. 
Two [load parameters](3.2.6_Scalability.md#how-do-you-describe-a-systems-load) do:
- **Read/write ratio** — how often users open the timeline vs how often they post. 
  Reads far outnumber posts, so you make reads cheap → push.
- **Follower distribution - followers per user** — most users have a few hundred followers, a few have millions. 
  The average makes push look cheap; the [extremes](#one-user-30-million-followers--what-breaks) break it.

</details>

### One user, 30 million followers — what breaks?
<details><summary>Show answer</summary>

With push, one post from that user means **30 million mailbox writes**, where a normal post needs a few hundred.
This **write storm** fills the push queue:
- The push workers can be busy with that one post for minutes.
- Posts from everyone else wait in the queue behind it — a lag spike for **all** users.
- The celebrity's own followers get the post at very different times, from seconds to minutes.

Field term: *celebrity problem*. The fix: [don't push for these users](#celebrities-and-normal-users--one-approach-for-both).

</details>

### Celebrities and normal users — one approach for both?
<details><summary>Show answer</summary>

No — pick the approach per user, by follower count, the
[load number](#which-load-numbers-decide-the-timeline-design) that decides it (field term: *hybrid approach*):
- **Normal users → push.** Their posts are copied into followers' mailboxes (*fan-out on write*).
- **Celebrities (above a threshold, e.g. 100,000 followers) → pull.** Their posts are *not* pushed; they are stored
  once and fetched at read time.

On every timeline read: take the user's mailbox, add recent posts from the few celebrities they follow, merge by time.

Why both sides stay cheap: no post causes millions of writes, and celebrity posts are the same for every reader, so
they cache well — unlike [per-user pull results](#read-time-timelines--what-do-they-cost).

Cost: two code paths, a merge on every read, and a threshold to tune.

</details>

### In a system-design context, what exactly is a precomputed timeline?
<details><summary>Show answer</summary>

A **materialized view** — derived data computed in advance and stored, so the system doesn't run the expensive
timeline query on every request. It is updated whenever its source data changes:
- **Source data** (system of record): the posts and follows tables.
- **Stored result**: each user's mailbox — the query's answer, ready to read.
- **Kept up to date**: every new post updates the mailboxes of its author's followers.

Because it is derived data, a lost mailbox can be rebuilt from posts and follows.

General rule: a materialized view moves work from read time to write time — the same trade-off as
[pull vs push](#latest-posts-from-everyone-you-follow--two-ways).

</details>

### Where else is a materialized view used?
<details><summary>Show answer</summary>

Anywhere a stored, kept-up-to-date answer replaces recomputing it on every read:
- **Counters** — a `follower_count` column, +1 on follow, −1 on unfollow — instead of `COUNT(*)` on every profile
  view.
- **Dashboards** — totals per day computed ahead of time, instead of summing raw rows on every page load.
- **Search indexes** — a query-ready copy of the data, updated on every change.
- **CQRS read models** — tables shaped for reading, updated from events.
- **Inside the database** — PostgreSQL `CREATE MATERIALIZED VIEW`, refreshed when you run `REFRESH MATERIALIZED VIEW`.

The [timeline mailbox](#in-a-system-design-context-what-exactly-is-a-precomputed-timeline) is the same trick.

</details>

### When is a materialized view worth it?
<details><summary>Show answer</summary>

When a read is slow because it recomputes the same expensive result over and over — a heavy join, an aggregation, a
count — and reads far outnumber the writes that change it.

You always pay three costs, the same as [push](#precomputed-timelines--what-do-they-cost):
- **Writes do more** — every change also updates the stored result.
- **Slightly stale** — readers may see the result before the latest change lands.
- **Storage** — the result is a second copy of the data.

Interview form: "reads are slow because of a heavy join" → materialize the result and update it on write, then name
the three costs.

</details>

### Building a push feed — which traps?
<details><summary>Show answer</summary>

Five places where the obvious way breaks at scale:
- [**Pushing inside the post request**](#push-a-new-post-to-all-followers--how) — timeouts, duplicate posts on retry;
  push in background workers instead.
- [**Pushing to every follower**](#which-followers-should-get-a-pushed-post) — writes for users who never log in;
  push only to active ones.
- [**Keeping every post**](#how-many-posts-should-a-mailbox-keep) — mailboxes grow forever; cap them, load older pages
  from the database.
- [**Deleting from the posts table only**](#delete-a-post--how) — copies keep showing; mark it deleted and filter at
  read time.
- [**Reading celebrity posts from the database**](#fetch-celebrity-posts-at-read-time--how) — one hot key; serve them
  from a cache.

Handle: when, to whom, how much, how to remove, where to read.

</details>

### Push a new post to all followers — how?
<details><summary>Show answer</summary>

**Trap:** loop over all followers inside the post request and write each mailbox before answering:
- request time grows with followers — fine for 300, minutes for 30 million; the client times out first;
- the client resends; nothing marks it as the same request, so each retry saves a new post and pushes it again →
  a [retry storm](3.2.2_Managing_Throughput.md#what-is-a-retry-storm);
- if the cache fails mid-loop, some followers have the post, the client retries, and the first half get it twice;
- all 30 million follower IDs are loaded into memory at once.

**Right way:**
- save the post, put one push job on a queue, answer right away; background workers push in batches;
- skip the push for authors above a follower threshold —
  [their posts are pulled at read time](#celebrities-and-normal-users--one-approach-for-both);
- accept an idempotency key, so a retried post doesn't create a second one.

</details>

### Which followers should get a pushed post?
<details><summary>Show answer</summary>

**Trap:** all of them. Many followers haven't logged in for months; filling their mailboxes costs writes and storage
for timelines nobody reads.

**Right way:** push only to **active** users — the push worker checks each follower's last-login time (e.g. within
30 days). When an inactive user comes back, build their timeline once at read time
([pull](#latest-posts-from-everyone-you-follow--two-ways)), store it as their mailbox, and push to them again from
then on. Their first open is slower — a fair price for skipping millions of unread writes.

</details>

### How many posts should a mailbox keep?
<details><summary>Show answer</summary>

**Trap:** all of them. Every pushed post stays forever, so each mailbox grows without end — memory for millions of
users, mostly holding old posts. Users rarely scroll past the first few pages.

**Right way:** cap the mailbox — the latest N post IDs (e.g. a few hundred) or the last two weeks — and drop the
oldest on each push. Store IDs, not full posts: the text lives once in the posts table. If a user scrolls past the
cap, load older pages from the database ([pull](#latest-posts-from-everyone-you-follow--two-ways)) — rare, so the
slower read is fine.

</details>

### Delete a post — how?
<details><summary>Show answer</summary>

**Trap:** delete the row from the posts table only. Copies are already spread out — the post ID sits in thousands of
follower mailboxes, the post itself in caches — so the post can keep showing, or timelines break on an ID that no
longer exists.

**Right way:**
- **Mark it deleted** instead of only removing the row (field term: *tombstone*), and drop it from the post cache.
- **Filter at read time** — when building a timeline, skip posts marked deleted. The post disappears at once.
- **Clean mailboxes in the background** — optional: a worker removes the ID from followers' mailboxes. For a celebrity
  that's millions of writes, so you can skip it; [capped mailboxes](#how-many-posts-should-a-mailbox-keep) drop the ID
  on their own soon.

</details>

### Fetch celebrity posts at read time — how?
<details><summary>Show answer</summary>

**Trap:** query the database for each followed celebrity's latest posts on every timeline load. Millions of users
follow the same celebrity, so the same few rows are read millions of times — one hot spot on one database server
(field term: *hot key*).

**Right way:** keep each celebrity's latest posts in an in-memory store (Redis, Memcached), updated when they post —
the read-time merge then reads from memory, not disk. Every reader gets the same list, so one cached copy serves them
all — that's why the [hybrid approach](#celebrities-and-normal-users--one-approach-for-both) works. Keep copies of the
hottest entries on several cache nodes, so one node doesn't become the new hot spot.

</details>
