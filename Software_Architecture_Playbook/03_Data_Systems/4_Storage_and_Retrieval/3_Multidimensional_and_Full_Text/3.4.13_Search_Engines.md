## 3.4.13 Search Engines

Book: no section of its own. DDIA uses Lucene / Elasticsearch only as examples (from the 1st ed. and the 2nd-ed. table
of contents; the exact 2nd-ed. mentions are not checked):
- Log-Structured Storage (118) — Lucene stores its word index the way an LSM-tree stores data.
- Full-Text Search (146) — the inverted index (word → documents), fuzzy search. Mechanics go to `3.4.11`.
- Local Secondary Indexes (268) — Elasticsearch shards by document; every search asks every shard.
- Systems of Record and Derived Data (10), Keeping Systems in Sync (501), Change Data Capture (503) — the search index
  is a copy built from the database.

**Purpose.** Why a search engine runs next to the database: what a database index can't do for search, what the search
engine adds, and what running a second system costs.

Holds:
- Why a database index fails at search:
  - A B-tree is sorted by the whole value: it finds `title = '...'` and titles that start with a word.
  - It can't find a word in the middle: `WHERE title LIKE '%laptop%'` reads every row.
- What a search engine adds:
  - Inverted index — for each word, the list of documents that contain it (details in `3.4.11`).
  - Text processing — split into words, lowercase, "running" → "run", synonyms ("notebook" → "laptop").
  - Typo tolerance — "lapotp" still finds "laptop".
  - Ranking — each match gets a score (the word is frequent in this document, rare across all documents), not just
    "matches or not".
  - Search-page features — counts per category, highlighting matched words, autocomplete.
- Why a separate tool, not one more database index:
  - Storage built for reads and text; new data shows up after a short delay (~1 s); no transactions.
  - The database stays the source of truth; the search engine holds a copy, grows to more machines on its own, and
    keeps search traffic off the main database.
  - Price: keeping the copy in sync — dual write (`06_Architecture_Traps/`), fixed by change data capture
    (`05_Integration_and_Event_Driven/4_Microservices_and_Sagas/`).
- The line is not absolute:
  - Postgres has built-in full-text search (`tsvector` + GIN index); MySQL has `FULLTEXT` indexes.
  - Enough for simple search on a modest dataset — and no second system to keep in sync.
  - A search engine wins when ranking quality, typo tolerance, search-page features, or scale matter.
- Scenario candidates:
  - Product search with `LIKE '%term%'` is slow.
  - Postgres full-text search or Elasticsearch?
  - Search still shows a product deleted minutes ago.
