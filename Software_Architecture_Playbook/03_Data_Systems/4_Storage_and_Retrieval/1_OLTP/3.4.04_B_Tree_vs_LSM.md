### B-tree vs LSM-tree — trade-offs?
<details><summary>Show answer</summary>

- [How they store](#b-tree-vs-lsm-tree--how-they-store) — LSM-tree appends, B-tree overwrites in place.
- [Write speed](#b-tree-vs-lsm-tree--write-speed) — LSM-tree usually faster.
- [Read speed](#b-tree-vs-lsm-tree--read-speed) — B-tree usually faster.
- [Disk space](#b-tree-vs-lsm-tree--disk-space) — LSM-tree usually smaller.
- [Response times](#b-tree-vs-lsm-tree--response-times) — B-tree steadier.
- [Heavy write load](#b-tree-vs-lsm-tree--heavy-write-load) — B-tree slows down; LSM-tree can fall behind.
- [Locking key ranges](#b-tree-vs-lsm-tree--locking-key-ranges) — B-tree easier.
- **Scenarios:**
    - [sensor readings](#100k-sensor-readings-per-second--which-engine);
    - [account balances](#balances-transactions-strict-p99--which-engine);
    - [reads slowing, disk filling](#lsm-store-reads-slowing-disk-filling--why).

Every row follows from the first one: appending makes writes cheap and reads costlier; overwriting does the opposite.
No rule settles it in general — test both with your own workload.

</details>

### B-tree vs LSM-tree — how they store?
<details><summary>Show answer</summary>

- **LSM-tree** — only appends: writes collect in memory, reach disk as new sorted files, and old files are merged in
  the background; nothing on disk is changed in place.
- **B-tree** — keeps each key in one fixed-size page and overwrites that page in place.

</details>

### B-tree vs LSM-tree — write speed?
<details><summary>Show answer</summary>

LSM-tree usually writes faster:

- **LSM-tree:**
    - a write goes to memory; disk sees it later inside a whole sorted file written in one go — a
      [sequential write](#sequential-vs-random-disk-writes--why-care);
    - files are rewritten again each time they merge.
- **B-tree:**
    - a small change rewrites a whole page at its own place on disk — a random write;
    - the change also goes to the WAL first.
- **Both** pay [write amplification](#what-is-write-amplification) — LSM-tree through merging, B-tree through the WAL
  and whole pages; which pays more depends on the workload and settings.

</details>

### What is write amplification?
<details><summary>Show answer</summary>

**Write amplification** — one write from the app turns into several writes to disk:

- **B-tree:** change 100 bytes → a WAL record plus the whole page (e.g. 8 KB).
- **LSM-tree:** a value goes to the WAL, then into the flushed file, then again each time merging rewrites it.
- **Why it matters:**
    - disk bandwidth spent on rewrites is not left for new writes → it caps how fast a write-heavy app can go;
    - SSDs wear out after a limited number of writes.

</details>

### Sequential vs random disk writes — why care?
<details><summary>Show answer</summary>

- **Sequential** — one long run of bytes written in order (a whole new file).
- **Random** — small pieces written at scattered places (one page here, one there).
- **Hard disk:** each random write first moves the disk head into place — milliseconds each; sequential writes skip
  that, so they are far faster.
- **SSD:** no head, but data is erased and rewritten in large blocks; scattered small writes force extra copying
  inside the drive → sequential is still faster, the gap is smaller.

LSM-trees turn the app's random writes into sequential disk writes; B-trees write each page where it lives.

</details>

### B-tree vs LSM-tree — read speed?
<details><summary>Show answer</summary>

B-tree usually reads faster:

- **B-tree** — one path from root to leaf: the same few page reads every time.
- **LSM-tree:**
    - one key may be in the memtable or in any of several files — checked newest to oldest;
    - Bloom filters skip files that don't hold the key;
    - a range read must combine results from every file — Bloom filters don't help there.

</details>

### B-tree vs LSM-tree — disk space?
<details><summary>Show answer</summary>

LSM-tree usually takes less space:

- **LSM-tree:**
    - merging drops old and deleted values and writes files packed full;
    - sorted files compress well;
    - until files merge, old values still take space.
- **B-tree:**
    - page splits leave pages partly empty;
    - space freed by deletes is reused only by keys in the same range.

</details>

### B-tree vs LSM-tree — response times?
<details><summary>Show answer</summary>

B-tree is steadier:

- **LSM-tree** — background merging uses the same disk as live requests; a request that waits behind it is slow →
  spikes in the slowest responses (high p99).
- **B-tree** — no background merging; each request does about the same work.

</details>

### B-tree vs LSM-tree — heavy write load?
<details><summary>Show answer</summary>

- **LSM-tree** — merging must keep up with incoming writes; when it can't:
    - files pile up;
    - reads check more and more files and slow down;
    - the disk fills up;
    - some engines then slow down or stop new writes (RocksDB), others keep accepting them — so watch the backlog.
- **B-tree** — no backlog builds up; writes simply get slower as the disk gets busier.

</details>

### B-tree vs LSM-tree — locking key ranges?
<details><summary>Show answer</summary>

B-tree makes it easier:

- **B-tree** — each key lives in exactly one page, so a lock on a key or a range of keys can sit right there in the
  tree.
- **LSM-tree** — the same key may sit in the memtable and several files at once; there is no single place to attach
  the lock.

</details>

### 100k sensor readings per second — which engine?
<details><summary>Show answer</summary>

- **Verdict:** an LSM-tree engine (e.g. Cassandra, ScyllaDB).
- **Reasoning:**
    - writes far outnumber reads, and readings are never changed → appending fits;
    - writes reach disk as sequential batches, and sorted files compress well;
    - reads ask for a recent time range per sensor → one forward read through sorted files.
- **Trade-off:**
    - background merging causes p99 spikes, and its backlog must be watched;
    - if the data were read far more than written, or needed steady response times, a B-tree would win.

</details>

### Balances, transactions, strict p99 — which engine?
<details><summary>Show answer</summary>

- **Verdict:** a B-tree engine — a relational database such as PostgreSQL.
- **Reasoning:**
    - balances are read and updated by key, inside transactions;
    - each key lives in one page → locks on rows and key ranges sit right in the tree;
    - no background merging → steady response times.
- **Trade-off:**
    - every update rewrites a whole page plus the WAL;
    - a part that is mostly writes (e.g. a log of every payment event) can go to an LSM store instead.

</details>

### LSM store: reads slowing, disk filling — why?
<details><summary>Show answer</summary>

- **Verdict:** merging can't keep up with incoming writes.
- **Reasoning:**
    - every flush adds a file; only merging removes files;
    - when writes arrive faster than merging, files pile up → reads check more files, old values stay on disk.
- **Trade-off — each fix has a cost:**
    - give merging more disk bandwidth or threads → less is left for live requests;
    - slow down incoming writes → the app waits;
    - add machines to share the writes → more to run and pay for.

</details>
