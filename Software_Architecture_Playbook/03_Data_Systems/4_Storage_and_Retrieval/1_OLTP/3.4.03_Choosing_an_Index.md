# Choosing an Index

**Purpose.** For each query: does it need an index, and of which type.

**Covers:**
- What you control when you create an index.
- Index or not.
- Index type per column.

## What you control

### Creating an index — what can you choose?
<details><summary>Show answer</summary>

- **Whether** — each index speeds some reads and slows every write.
- **Which columns, in what order** → [index design](3.4.04_Index_Design.md).
- **Unique or not** — unique also blocks duplicate values.
- **Which rows** — a partial index covers only rows that match a `WHERE` (Postgres; SQL Server calls it a filtered
  index).
- **Expression** — index `LOWER(email)` instead of `email`.
- **Extra columns stored with the key** — [covering index](3.4.04_Index_Design.md#what-is-a-covering-index).
- **Type — only if the database offers a choice:**
  - Postgres: `CREATE INDEX ... USING btree | hash | gin | gist | brin` — `btree` is the default;
  - MySQL InnoDB: B-tree for normal indexes; `FULLTEXT` and `SPATIAL` as separate kinds.
- **Later** — drop it, rebuild it, or create it without blocking writes (`CREATE INDEX CONCURRENTLY`, Postgres).

Not chosen here: B-tree vs LSM-tree — it came with the database
([where that choice is made](3.4.02_Choosing_an_Engine.md#b-tree-or-lsm--where-is-that-choice-made)).

</details>

## Index or not

### Column appears in a WHERE — index it or not?
<details><summary>Show answer</summary>

Index it when all three hold:

- **The query runs often, or must be fast** — a rare report can afford a full read.
- **It returns a small share of the rows** — a few out of millions; for a large share the database
  [reads the whole table instead](#index-on-a-status-column-is-ignored--why).
- **The table is big** — a few thousand rows fit in a few pages; reading them all is already fast.

Against: every index [slows every write](#table-with-10-indexes-inserts-slow--why) and takes disk.

Check with `EXPLAIN`: is the index used, and how many rows are read?

</details>

### Index on a status column is ignored — why?
<details><summary>Show answer</summary>

**Verdict:** the searched value matches a large share of the rows, so the database judges a full table read cheaper
than the index.

**Reasoning:** say `status = 'PAID'` on 90% of 1 million orders. Through the index, each match costs a separate jump to
its row — 900,000 jumps to scattered spots. Reading the table start to end is faster.

**Trade-off:** the same index wins for a rare value — `status = 'FAILED'` on 0.1% of rows. Ways to keep that win:
- Index only the rare rows: a partial index, `CREATE INDEX ... WHERE status = 'FAILED'` (Postgres; SQL Server calls it
  a filtered index).
- Search `status` together with a column that narrows well, in one
  [composite index](3.4.04_Index_Design.md#what-is-a-composite-index).

</details>

### Table with 10 indexes, inserts slow — why?
<details><summary>Show answer</summary>

**Verdict:** every insert writes the row and a new entry into each of the 10 indexes. Drop the indexes no query uses
(Postgres: `idx_scan = 0` in `pg_stat_user_indexes`; MySQL: `sys.schema_unused_indexes`).

**Reasoning:**
- each index is its own B-tree: the new key goes into its own leaf page, plus a WAL record → one insert, 11 writes;
- for columns with scattered values (`user_id`, `email`), the right leaf page is often not in memory → a disk read
  before each write;
- updates pay too, whenever they change an indexed column.

**Trade-off:** dropping an index that a rare query needs makes that query read the whole table. Such a query can run
on a read replica instead.

</details>

### Indexed column updated all the time — what's the cost?
<details><summary>Show answer</summary>

**Verdict:** take `last_seen_at`, set on every request, with an index on it. Each update also moves the entry inside
that index — removed from one leaf page, added to another — plus WAL records.

**Reasoning:**
- the index is sorted by that column, so the new value belongs in a different place in the tree;
- Postgres: an update that changes an indexed column can't be a **HOT update** (one that leaves the indexes alone) —
  every index on the table gets a new entry, not only this one.

**Trade-off:**
- no frequent query filters on that column → drop the index;
- or write the column less often — once a minute instead of every request;
- a frequent query needs it → keep it and pay the write cost.

</details>

## Index type per column

### Price range search — which index type?
<details><summary>Show answer</summary>

**Verdict:** a plain B-tree index — the default.

**Reasoning:** keys sit sorted, so `price BETWEEN 50 AND 100` = find 50, then read forward to 100. The same order
serves `<`, `>` and `ORDER BY price`.

**Trade-off:** a hash index (Postgres `USING hash`) serves only `=`: hashing scatters 50 and 51 to unrelated places.
A B-tree handles `=` as well, so a hash index rarely pays off.

</details>

### Match inside a JSON field — which index?
<details><summary>Show answer</summary>

**Verdict:** a GIN index on the `jsonb` column (Postgres).

**Reasoning:** take `WHERE data @> '{"color": "red"}'`. A B-tree on `data` sorts whole documents as one value — that
order says nothing about the `color` inside them. GIN works like the index at the back of a book: it lists every key
and value found inside the documents, each pointing to the rows that contain it.

**Trade-off:**
- slower writes — every insert adds an entry for each key and value in the document;
- queries always on one known field → a B-tree on just that field, `((data->>'color'))`, is smaller and also serves
  ranges and sorting;
- MySQL has no GIN: index one field through a generated column.

</details>

### Huge time-ordered table, queried by time range — which index?
<details><summary>Show answer</summary>

**Verdict:** a BRIN index on the time column (Postgres), or partition the table by time.

**Reasoning:** take 2 billion log rows, inserted in time order, queried for "the last 24 hours".
- rows arrive in time order, so each run of pages holds a narrow time range;
- BRIN stores only the min and max time per run of pages (128 by default) → megabytes, where a B-tree takes
  gigabytes; a query skips every run whose range can't match;
- partitioning by day or month: the query touches only the partitions in range, and
  [old ones are dropped whole](3.4.04_Index_Design.md#old-data-must-expire--how-do-you-remove-it).

**Trade-off:**
- BRIN works only while disk order follows time; updates or late-arriving old rows mix the order and it stops
  skipping;
- it narrows to runs of pages, not rows — every page in a matching run is read; a B-tree finds the exact rows.

</details>
