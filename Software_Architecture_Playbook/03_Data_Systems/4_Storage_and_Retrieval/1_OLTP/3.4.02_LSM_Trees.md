## 3.4.2 LSM-Trees

Book: Log-Structured Storage (118–124).

Holds one chain, in order — each step fixes the problem of the step before:
- Hash index over the log: key → byte position in the file, kept in memory.
- Segments and compaction: cut the file into pieces, merge them in the background, keep the latest value per key.
  Deleting a key: a tombstone — a special record meaning "this key is deleted".
- SSTable: segments sorted by key. Only some keys in memory, range queries work, merging is cheap.
- Memtable: a sorted tree in memory; when it gets big, written to disk as one SSTable.
- WAL: the concept card lives here (first place you meet it). Here it protects the memtable from a crash.
- LSM-tree: the name for the whole design — memtable + SSTables on disk + background merging.
- Bloom filter: skips files that cannot hold the key.
- Compaction strategies: size-tiered vs leveled.

Not here: write amplification (3.4.4).

1. Log-structured: the LSM-tree

The rule here is never overwrite anything, only append. Old values are cleaned up later in the background. The book builds this up step by step, and each step fixes the problem left by the previous one:

Hash index. Keep a map in memory from each key to its byte position in the file. Problem: all keys must fit in memory, and you can't ask for a range of keys.
Segments + compaction. The file grows forever, so cut it into smaller files (segments). A background job merges them and keeps only the latest value per key.
SSTable (Sorted String Table). Keep each segment sorted by key. Now you only need some keys in memory (one every few KB, then scan a little), range queries work, and merging files is cheap.
Memtable. Writes arrive in random order, so how do you get a sorted file? Collect writes in a sorted tree in memory, and when it gets big, write it out as one sorted file.
WAL (write-ahead log). The memtable lives in memory, so a crash loses it. To prevent that, every write is also appended to a plain file on disk first. After a crash, the database replays that file to rebuild the memtable.
LSM-tree (Log-Structured Merge-tree). This is the name for the whole design above: memtable, sorted files on disk, and background merging. Cassandra, RocksDB, and LevelDB use it.
Bloom filter. Looking up a key that doesn't exist means checking every file. A Bloom filter is a small structure in memory that answers "definitely not here" or "maybe here", so most files get skipped.
Compaction strategies. These decide how files get merged (size-tiered vs. leveled). The choice trades write cost against read cost and disk space.
