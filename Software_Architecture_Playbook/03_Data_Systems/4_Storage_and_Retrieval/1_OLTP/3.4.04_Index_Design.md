### Index design — what are the choices?
<details><summary>Show answer</summary>

Take an index on `users(email)`. One entry: the key is `alice@example.com`, and next to it sits something that leads
to Alice's row. Every entry has this shape, so an index is a sorted map from key to value, and its design is two
choices:

- **The key** — what queries search by.
  - Is it the primary key? [Primary vs secondary index](#primary-vs-secondary-index--the-difference).
  - Can one key match many rows? [How repeats are stored](#how-does-an-index-store-a-key-that-repeats).
  - One column or several? [Composite index](#what-is-a-composite-index): [which searches it serves](#index-on-a-b--which-searches-can-use-it),
    [how to order its columns](#composite-index--how-do-you-pick-column-order).
- **The value** — [what sits next to the key](#what-can-an-index-entry-hold), from least to most:
  - a reference to the row;
  - plus a few columns: [covering index](#what-is-a-covering-index);
  - the whole row: [clustered index](#what-is-a-clustered-index).

**Trigger:** the key decides which queries the index can help (wrong key → the database reads too many entries); the
value decides how much work is left once an entry is found (wrong value → one extra jump per match).

</details>

### Primary vs secondary index — the difference?
<details><summary>Show answer</summary>

- **Primary key index** — built on the primary key: unique by definition, one key → one row. It is the row's identity:
  other tables point to the row by this key (foreign key `orders.user_id = 42` → `users.id = 42`).
- **Secondary index** — built on any other column(s), added with `CREATE INDEX`. Its key may repeat (one key → many rows,
  e.g. an index on `orders.user_id`) or be unique (`CREATE UNIQUE INDEX` on `users.email`), and it is still secondary.

Whether they also differ in the [value](#what-can-an-index-entry-hold) depends on the database:
- **MySQL InnoDB** — the primary index holds the row itself; a secondary index holds the primary key, so reading the
  row takes a second lookup through the primary index.
- **PostgreSQL** — both hold a pointer to the row in the table; no difference in the value.

**Trigger:** the primary key is the row's identity; a secondary index is any other way to search.

</details>

### How does an index store a key that repeats?
<details><summary>Show answer</summary>

`user_id = 42` matches 300 orders. Two ways to store one key with many rows:

- **One entry per key** — the value is a list of all matching row IDs: `42 → [r7, r19, r311, ...]`.
  Used by full-text search (inverted indexes), where the list is called a *postings list*.
- **One entry per row** — add the row ID to the key, so each key is unique again: `(42, r7)`, `(42, r19)`, ...
  All entries for 42 still sit side by side, because the index is sorted by `user_id` first.
  Used by MySQL InnoDB secondary indexes, where the row ID is the primary key.

</details>

### What is a composite index?
<details><summary>Show answer</summary>

One key built from several columns, in a fixed order:

```sql
CREATE INDEX idx_people_name ON people (last_name, first_name);
```

Entries are sorted by `last_name`; rows with the same last name are sorted by `first_name`. 

Other names: multicolumn index, concatenated index.

</details>

### Index on (A, B) — which searches can use it?
<details><summary>Show answer</summary>

Phone book sorted by `(last_name, first_name)`:
- `last_name = 'Smith'` — yes: all Smiths sit together.
- `last_name = 'Smith' AND first_name = 'Alice'` — yes: one spot inside the Smiths.
- `last_name = 'Smith' AND first_name > 'M'` — yes: one stretch inside the Smiths.
- `first_name = 'Alice'` alone — no: the Alices are spread across every last name, so the database reads everything.

**Leftmost-prefix rule:** columns are used from the left, without gaps. With `(A, B, C)`:
- A, A + B, A + B + C — the index **seeks** on all of them: it jumps straight to the matching stretch.
- A + C — seeks on A only; C is **filtered**: checked entry by entry inside that stretch.
- A range on A stops the prefix: `A > x AND B = y` seeks on A only; B is filtered.

**Exception — skip scan:** MySQL 8, Oracle and PostgreSQL 18 can skip the first column, running one small search for
`first_name = 'Alice'` under each distinct `last_name`. It pays off only when the skipped column has few distinct
values (low cardinality); `last_name` has many.

</details>

### Composite index — how do you pick column order?
<details><summary>Show answer</summary>

Query: `WHERE country = 'DE' AND age > 60`.
- `(country, age)` — all German rows sit together, sorted by age: jump to DE, find the first age above 60, read to the
  end of DE.
- `(age, country)` — `age > 60` covers every country; the index reads all those entries and checks `country` one by
  one.

Inside a range of the first column, the second column is not sorted, so it is only filtered, never used to seek.
Rules:
- **Equality before range** — columns compared with `=` or `IN` go first; the column with `>`, `<` or `BETWEEN`
  goes last.
- **Solo queries go first** — a column that some query filters on alone goes first, or that query can't use the index
  ([leftmost-prefix rule](#index-on-a-b--which-searches-can-use-it)).
- **Not "most selective first"** — with `=` on both columns, either order jumps to the same entries.

</details>

### What can an index entry hold?
<details><summary>Show answer</summary>

How much of the row sits next to the key, from least to most:
- **Only a reference** — the row lives elsewhere, in a heap file (the table's rows in no particular order); the entry
  says [where to find it](#secondary-index--how-does-it-point-to-the-row).
- **A reference plus a few columns** — copied in with `INCLUDE` (PostgreSQL, SQL Server), so some queries are answered
  from the index alone: [covering index](#what-is-a-covering-index).
- **The whole row** — the table is stored inside the index: [clustered index](#what-is-a-clustered-index).

**Trigger:** the more of the row sits in the index, the fewer jumps a read needs, but the more space it takes and the
more every write must update.

</details>

### What is a clustered index?
<details><summary>Show answer</summary>

The rows themselves are stored inside the index, sorted by its key: the index is the table. A search by the key lands
directly on the full row, and rows with nearby keys sit together, so range reads are cheap.

A row can be stored in only one place, so a table has at most one clustered index:
- **MySQL InnoDB** — always the primary key.
- **SQL Server** — you choose which index; by default, the primary key.
- **PostgreSQL** — none: tables are heaps, and every index [points into the heap](#secondary-index--how-does-it-point-to-the-row).
  `CLUSTER` sorts a table once, but later writes don't keep the order.

</details>

### Why only one clustered index per table?
<details><summary>Show answer</summary>

A clustered index stores the rows themselves, sorted by its key. A row can be stored in only one place: if the table
is sorted by `id`, it can't also be sorted by `email`, because that would need a second full copy of the table.
Any other order comes from a [secondary index](#primary-vs-secondary-index--the-difference) that points back to the rows.

</details>

### What is a covering index?
<details><summary>Show answer</summary>

An index that also stores, next to the key, a few extra columns that a query needs. The full row still lives in the
table.

```sql
CREATE INDEX idx_orders_customer ON orders (customer_id) INCLUDE (status, total);

SELECT status, total FROM orders WHERE customer_id = ?;  -- answered from the index alone
```

The query reads only the index and never touches the row: the index **covers** the query. 
Also called **index with included columns**. In `EXPLAIN`: Postgres shows *Index Only Scan*, MySQL shows *Using index*.

- **Postgres, SQL Server** — extra columns go in `INCLUDE`. They are only stored, not part of the sort: you can't search
  by them, but the key stays small, and a `UNIQUE` index stays unique on the key alone.
- **MySQL** — no `INCLUDE`: put the extra columns at the end of the key, `(customer_id, status, total)`. InnoDB also
  stores the primary key in every secondary index, so `SELECT id ... WHERE email = ?` is covered for free.

</details>

### Covering index — what does it cost?
<details><summary>Show answer</summary>

The extra columns are a second copy of data that already lives in the row. Two costs follow:

- **More disk** — every entry grows by the size of the copied columns.
- **Slower writes** — every insert, and every update of a copied column, must change the index too.

</details>
