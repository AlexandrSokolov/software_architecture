## Choosing an Engine

**Purpose.** Pick the storage engine — B-tree or LSM-tree — and with it the database, from what the data is and how
it is read and written.

### What is a B-tree?
<details><summary>Show answer</summary>

**B-tree** — data split into fixed-size blocks on disk called **pages** (usually 4–16 KB), linked into a tree:
one page points to another by its page number.

- **Root page** — the top inner page; every lookup starts here.
- **Inner pages** — highway signs: keys mark the boundaries, and pointers to child pages tell which exit to take.
  No data. The pointer between keys 300 and 600 leads to the page for keys 300–599.
- **Leaf pages** — the destination: the rows themselves, or a reference to where each row is stored.
  No child pointers; the path ends here.

Example — table `users`, B-tree on `user_id`:

```text
==================================================
PAGE 1 (Root / Inner Page)
Role: Navigation (highway signs)
Size: 4 KB block on disk
==================================================
[Pointer to Page 2]  <-- IDs below 1000
[Key: 1000]
[Pointer to Page 3]  <-- IDs 1000–1999
[Key: 2000]
[Pointer to Page 4]  <-- IDs 2000 and above
==================================================

==================================================
PAGE 2 (Inner Page)
Role: Navigation (highway signs)
Size: 4 KB block on disk
==================================================
[Pointer to Page 5]  <-- IDs below 300
[Key: 300]
[Pointer to Page 6]  <-- IDs 300–599
[Key: 600]
[Pointer to Page 7]  <-- IDs 600–999
==================================================

==================================================
PAGE 6 (Leaf Page)
Role: Data (destination)
Size: 4 KB block on disk
==================================================
[Key: 312] | [Value: {"name": "Alice", "age": 28}]
[Key: 450] | [Value: {"name": "Bob", "age": 34}]
[Key: 587] | [Value: {"name": "Diana", "age": 41}]
-- No child pointers here. Just data. --
==================================================
```

Pages 3–4 are inner pages like page 2; pages 5 and 7 are leaves like page 6. Same shape, other ID ranges.

</details>

### What is an LSM-tree?
<details><summary>Show answer</summary>

**LSM-tree** (Log-Structured Merge-tree) — a storage engine that never changes data on disk; it only adds new files:

- **Write** — goes into a sorted map in memory (the **memtable**) and into an append-only file on disk (the **WAL**),
  so a crash loses nothing.
- **Flush** — when the memtable reaches a few MB, it is written to disk in key order as a new sorted file (an
  **SSTable**): one whole file in one go.
- **Merge** — in the background, files are merged into bigger ones; old values and deleted keys are dropped
  (**compaction**).
- **Read** — the memtable first, then each file from newest to oldest; the first hit wins. A small filter per file
  (**Bloom filter**) skips files that surely don't hold the key.

</details>

### B-tree vs LSM-tree — trade-offs?
<details><summary>Show answer</summary>

- Mostly reads → B-tree: one path from root to leaf; an LSM-tree may check several files.
- Heavy writes → LSM-tree: writes reach disk as whole sorted files; a B-tree rewrites pages at scattered spots.
- Strict p99, writes not heavy → B-tree: no background merging, so no merge spikes.
- Huge data, disk cost **dominates** → LSM-tree: merged files are packed full and compress well. Rare — Facebook moved
  from InnoDB to MyRocks for this.

**Trigger:** appending makes writes cheap and reads costlier; overwriting does the opposite.

</details>

### Transactions — B-tree vs LSM-tree?
<details><summary>Show answer</summary>

Both engines support transactions and fit money operations (e.g. CockroachDB, YugabyteDB on LSM), 
so transactions are not a reason to choose one.

One detail differs: locking a key range (blocks phantoms: new rows inside a range already read) is easier in a B-tree.
Each key lives in one leaf page, so the gap between two keys is one fixed spot in the tree. An LSM-tree has no such
spot (a key can sit in the memtable and several files), so it keeps a separate range lock table, or skips locks and
retries one transaction on conflict.

</details>

### Which databases are B-tree, which LSM?
<details><summary>Show answer</summary>

- **B-tree:** PostgreSQL, MySQL InnoDB, Oracle, SQL Server, SQLite, MongoDB.
- **LSM-tree:** Cassandra, ScyllaDB, HBase, CockroachDB, YugabyteDB, TiKV, MyRocks; RocksDB as a library.

</details>

### 100k sensor readings per second — which engine?
<details><summary>Show answer</summary>

- **Verdict:** an LSM-tree engine (e.g. Cassandra, ScyllaDB).
- **Reasoning:**
    - writes far outnumber reads, and readings are never changed → appending fits;
    - writes reach disk as sequential batches, and sorted files compress well;
    - reads ask for a recent time range per sensor → one forward read through sorted files.
- **Trade-off:**
  - merging causes p99 spikes and can [fall behind](#lsm-store-reads-slowing-disk-filling--why) — watch its backlog;
  - a B-tree would win only if writes were light enough for it to keep up — then no merge spikes.

</details>

### Balances, transactions, strict p99 — which engine?
<details><summary>Show answer</summary>

- **Verdict:** a B-tree engine — e.g. PostgreSQL.
- **Reasoning:**
  - balances are read often and updated in place, by key — not a heavy-write load, so a B-tree keeps up;
  - no background merging → no merge spikes → steady p99;
  - transactions don't decide the engine: [both engines have them](#transactions--b-tree-vs-lsm-tree); they narrow
    the database.
- **Trade-off:**
  - each update rewrites a whole page at its own spot on disk;
  - writes too heavy for a B-tree to keep up → an LSM database with transactions (e.g. CockroachDB) wins, and you
    accept merge spikes.

</details>

### Product catalog, read 100× more than written — which engine?
<details><summary>Show answer</summary>

- **Verdict:** a B-tree database — PostgreSQL or MySQL.
- **Reasoning:**
    - reads far outnumber writes → B-tree's cheap, steady reads matter; its costlier writes don't;
    - reads are by key or by range ("this category, sorted by price") → one walk down the tree, then leaves in order;
    - price and stock changes update existing rows in place.
- **Trade-off:**
    - each change rewrites a whole page plus the WAL — fine at this ratio;
    - data in the same shop that is written all the time (view counters, click logs) doesn't belong in this table.

</details>

### Chat message history — which engine?
<details><summary>Show answer</summary>

- **Verdict:** a B-tree database (e.g. PostgreSQL) at normal volume; an LSM-tree database (Cassandra, ScyllaDB) at
  very large volume.
- **Reasoning:**
  - a read loads the latest messages of one chat → key `(chat_id, sent_at)` keeps one chat's messages together,
    sorted by time — a B-tree index serves this well;
  - at very large volume, new messages land on the pages of thousands of different chats at once → scattered page
    writes; an LSM-tree writes them as whole sorted files.
- **Trade-off:** the LSM database is a second system next to your main one, and messages no longer commit in one
  transaction with the rest of your data (e.g. unread counters).

</details>

### Audit log, written once, rarely read — where do you keep it?
<details><summary>Show answer</summary>

- **Verdict:** recent records in an append-only table in the main database, written in the same transaction as the
  change; old records moved to files in cheap object storage (e.g. S3).
- **Reasoning:**
  - **Shared transaction** — no change is saved without its audit record;
  - **Cheap storage** — old records are never changed and rarely read, so they need no index and no fast lookup;
  - **Partition by month** — a whole old month is copied out and
    [dropped at once](3.4.04_Index_Design.md#old-data-must-expire--how-do-you-remove-it).
- **Trade-off:**
  - every change pays one more insert;
  - reading old records scans files for the time range — slow, but rare;
  - audit records far outnumber everything else → an LSM store or Kafka wins, and the shared transaction is lost.

</details>

### Orders plus order events — where do events live?
<details><summary>Show answer</summary>

- **Verdict:** keep the events in the orders database until their volume forces a split.
- **Reasoning:**
  - the order and its event commit in one transaction → both or neither. With two databases, one write can fail
    while the other succeeds;
  - events go into an append-only table with a time-ordered key → each insert lands on the last page of the index,
    which stays in memory — the cheapest kind of B-tree insert.
- **Trade-off:**
  - every order pays one more insert, and the events table grows the orders database;
  - events far outnumber orders → they move to an LSM store or Kafka; the order and its event no longer commit
    together → an outbox table or change data capture is needed to send events reliably.

</details>

### Disk cost matters most, huge table — which engine?
<details><summary>Show answer</summary>

- **Verdict:** an LSM-tree engine — e.g. MyRocks in place of InnoDB.
- **Reasoning:**
    - merging writes files packed full and drops old values; B-tree splits leave pages partly empty;
    - sorted files compress well — similar keys sit next to each other;
    - Facebook built MyRocks for exactly this: less disk for its MySQL data.
- **Trade-off:**
    - reads are slower and less steady;
    - merging needs spare disk while it runs;
    - if the table is mostly read by reports (few columns, many rows), column storage compresses even better.

</details>

### Need a database without running a server — what do you use?
<details><summary>Show answer</summary>

An **embedded database** — a library inside your program: plain function calls, no network, data in local files.

- **Engine** — picked like any database: SQLite → B-tree, RocksDB → LSM-tree, DuckDB → column storage (analytics).
- **Fits** — data kept on a phone; a stream processor's running totals (Kafka Streams uses RocksDB by default); one
  small database file per tenant.
- **Limit** — only the program that holds it can reach the data.

</details>

### LSM store: reads slowing, disk filling — why?
<details><summary>Show answer</summary>

- **Verdict:** merging can't keep up with incoming writes.
- **Reasoning:**
  - every flush adds a file; only merging removes files;
  - when writes arrive faster than merging, files pile up → reads check more files, old values stay on disk.
- **Trade-off — each fix has a cost:**
  - give merging more disk bandwidth or threads → less is left for live requests;
  - slow down incoming writes → the app waits;
  - add machines to share the writes → more to run and pay for;
  - switch to a B-tree → worse under the same heavy writes; it helps only if writes are light enough for it.

</details>
