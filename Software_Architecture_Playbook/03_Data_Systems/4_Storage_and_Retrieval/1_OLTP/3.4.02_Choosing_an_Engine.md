# Choosing an Engine

**Purpose.** Pick the storage engine — B-tree or LSM-tree — and with it the database, from what the data is and how
it is read and written.

**Covers:**
- Engine shapes — only enough structure to see why each one is good at what.
- Data and load → engine — scenarios.
- When it goes wrong.

## Engine shapes

### What is a B-tree?
<details><summary>Show answer</summary>

**B-tree** — data split into fixed-size blocks on disk called **pages** (usually 4–16 KB), linked into a tree:
one page points to another by its page number.

- **Root page** — the top inner page; every lookup starts here.
- **Inner pages** — highway signs: keys mark the boundaries, and pointers to child pages tell which exit to take.
  No data. The pointer between keys 300 and 600 leads to the page for keys 300–599.
- **Leaf pages** — the destination: the rows themselves, or a reference to where each row is stored.
  No child pointers; the path ends here.

Example — table `users`, B-tree on `user_id`:

```text
==================================================
PAGE 1 (Root / Inner Page)
Role: Navigation (highway signs)
Size: 4 KB block on disk
==================================================
[Pointer to Page 2]  <-- IDs below 1000
[Key: 1000]
[Pointer to Page 3]  <-- IDs 1000–1999
[Key: 2000]
[Pointer to Page 4]  <-- IDs 2000 and above
==================================================

==================================================
PAGE 2 (Inner Page)
Role: Navigation (highway signs)
Size: 4 KB block on disk
==================================================
[Pointer to Page 5]  <-- IDs below 300
[Key: 300]
[Pointer to Page 6]  <-- IDs 300–599
[Key: 600]
[Pointer to Page 7]  <-- IDs 600–999
==================================================

==================================================
PAGE 6 (Leaf Page)
Role: Data (destination)
Size: 4 KB block on disk
==================================================
[Key: 312] | [Value: {"name": "Alice", "age": 28}]
[Key: 450] | [Value: {"name": "Bob", "age": 34}]
[Key: 587] | [Value: {"name": "Diana", "age": 41}]
-- No child pointers here. Just data. --
==================================================
```

Pages 3–4 are inner pages like page 2; pages 5 and 7 are leaves like page 6. Same shape, other ID ranges.

</details>

### What is an LSM-tree?
<details><summary>Show answer</summary>

**LSM-tree** (Log-Structured Merge-tree) — a storage engine that never changes data on disk; it only adds new files:

- **Write** — goes into a sorted map in memory (the **memtable**) and into an append-only file on disk (the **WAL**),
  so a crash loses nothing.
- **Flush** — when the memtable reaches a few MB, it is written to disk in key order as a new sorted file (an
  **SSTable**): one whole file in one go.
- **Merge** — in the background, files are merged into bigger ones; old values and deleted keys are dropped
  (**compaction**).
- **Read** — the memtable first, then each file from newest to oldest; the first hit wins. A small filter per file
  (**Bloom filter**) skips files that surely don't hold the key.

</details>

### B-tree vs LSM-tree — trade-offs?
<details><summary>Show answer</summary>

- **How they store** — LSM-tree only appends and merges files in the background; B-tree overwrites fixed-size pages
  in place.
- **Writes** — LSM-tree usually faster: a write reaches disk inside a whole sorted file, written in one go. B-tree
  rewrites a whole page at its own place on disk, plus the WAL.
- **Reads** — B-tree usually faster: one path from root to leaf. LSM-tree may check the memtable and several files.
- **Disk space** — LSM-tree usually smaller: merging drops old values, sorted files compress well. B-tree splits leave
  pages partly empty.
- **Response times** — B-tree steadier: no background merging competing with requests for the disk.
- **Heavy write load** — B-tree gets slower; LSM-tree merging can
  [fall behind](#lsm-store-reads-slowing-disk-filling--why).
- **Locking key ranges** — B-tree easier: each key lives in exactly one page.

**Trigger:** appending makes writes cheap and reads costlier; overwriting does the opposite. No rule settles it in
general — test both with your own workload.

</details>

## Data and load → engine

### B-tree or LSM — where is that choice made?
<details><summary>Show answer</summary>

When you pick the database — the engine comes with it:

- **B-tree:** PostgreSQL, MySQL InnoDB, Oracle, SQL Server, SQLite, MongoDB.
- **LSM-tree:** Cassandra, ScyllaDB, HBase, CockroachDB, YugabyteDB, TiKV; RocksDB as a library.
- **Exception:** MySQL sets the engine per table (`ENGINE=InnoDB`); MariaDB and Percona Server also ship MyRocks, an
  LSM engine. In practice almost everyone stays on InnoDB.

So for a new system, "B-tree or LSM" and "which database" are one decision. Index types are chosen later, per index:
[choosing an index](3.4.03_Choosing_an_Index.md).

</details>

### 100k sensor readings per second — which engine?
<details><summary>Show answer</summary>

- **Verdict:** an LSM-tree engine (e.g. Cassandra, ScyllaDB).
- **Reasoning:**
    - writes far outnumber reads, and readings are never changed → appending fits;
    - writes reach disk as sequential batches, and sorted files compress well;
    - reads ask for a recent time range per sensor → one forward read through sorted files.
- **Trade-off:**
    - background merging causes p99 spikes, and its backlog must be watched;
    - if the data were read far more than written, or needed steady response times, a B-tree would win.

</details>

### Balances, transactions, strict p99 — which engine?
<details><summary>Show answer</summary>

- **Verdict:** a B-tree engine — a relational database such as PostgreSQL.
- **Reasoning:**
    - balances are read and updated by key, inside transactions;
    - each key lives in one page → locks on rows and key ranges sit right in the tree;
    - no background merging → steady response times.
- **Trade-off:**
    - every update rewrites a whole page plus the WAL;
    - a part that is mostly writes (e.g. a log of every payment event) can go to an LSM store instead.

</details>

### Product catalog, read 100× more than written — which engine?
<details><summary>Show answer</summary>

- **Verdict:** a B-tree database — PostgreSQL or MySQL.
- **Reasoning:**
    - reads far outnumber writes → B-tree's cheap, steady reads matter; its costlier writes don't;
    - reads are by key or by range ("this category, sorted by price") → one walk down the tree, then leaves in order;
    - price and stock changes update existing rows in place.
- **Trade-off:**
    - each change rewrites a whole page plus the WAL — fine at this ratio;
    - data in the same shop that is written all the time (view counters, click logs) doesn't belong in this table.

</details>

### Chat message history — which engine?
<details><summary>Show answer</summary>

- **Verdict:** at normal volume, the database you already run (e.g. PostgreSQL); at very large volume, an LSM-tree
  database (Cassandra, ScyllaDB).
- **Reasoning:**
    - every message is a new write and is never changed → appending fits;
    - a read loads the latest messages of one chat → key `(chat_id, sent_at)`: one chat's messages sit together,
      sorted by time;
    - in a B-tree, new messages land on the pages of thousands of different chats at once → random page writes; an
      LSM-tree turns them into sequential file writes.
- **Trade-off:**
    - an LSM database is usually a second, distributed system: more to run, weaker transactions;
    - below that volume, a B-tree index on `(chat_id, sent_at)` serves the same read just as well.

</details>

### Audit log, written once, rarely read — where do you keep it?
<details><summary>Show answer</summary>

- **Verdict:** recent records in an append-only table in the main database, written in the same transaction as the
  change; old records moved out to files in cheap object storage (e.g. S3).
- **Reasoning:**
    - same transaction → no change is saved without its audit record;
    - records are never changed and rarely read → old ones need no index and no fast lookup; cheapest storage wins;
    - partition the table by month → a whole old month is copied out and dropped at once.
- **Trade-off:**
    - every change pays one more insert;
    - reading old records means scanning files for the time range — slow, but rare;
    - if audit records far outnumber everything else, they go to an LSM store or Kafka instead — and lose the shared
      transaction.

</details>

### Orders plus a stream of order events — one database or two?
<details><summary>Show answer</summary>

- **Verdict:** one — keep the events in the orders database until their volume forces a split.
- **Reasoning:**
    - the order and its event are saved in one transaction → both or neither, no lost events;
    - an append-only events table with a time-ordered key is the cheapest kind of B-tree insert;
    - two databases mean two writes per change; one can succeed while the other fails.
- **Trade-off:**
    - when events far outnumber orders, they move to an LSM store or Kafka; the order and its event then no longer
      commit together → you need an outbox table or change data capture to send events reliably.

</details>

### Disk cost matters most, huge table — which engine?
<details><summary>Show answer</summary>

- **Verdict:** an LSM-tree engine — e.g. MyRocks in place of InnoDB.
- **Reasoning:**
    - merging writes files packed full and drops old values; B-tree splits leave pages partly empty;
    - sorted files compress well — similar keys sit next to each other;
    - Facebook built MyRocks for exactly this: less disk for its MySQL data.
- **Trade-off:**
    - reads are slower and less steady;
    - merging needs spare disk while it runs;
    - if the table is mostly read by reports (few columns, many rows), column storage compresses even better.

</details>

### Need a database without running a server — what do you use?
<details><summary>Show answer</summary>

An **embedded database** — a library inside your program, not a separate server:

- **How it runs** — in the same process as your code: normal function calls, no network; data lives in local files.
- **Pick it by engine, like any database:**
    - SQLite, LMDB — B-tree;
    - RocksDB — LSM-tree;
    - DuckDB — column storage, for analytics.
- **Fits when:**
    - a mobile app keeps the user's own data on the phone;
    - a stream processor keeps its running totals next to the code (Kafka Streams uses RocksDB by default);
    - each tenant is small and fully separate — one database file per tenant.
- **Limit:** only the program that holds it can reach the data; sharing it with other machines is your job.

</details>

## When it goes wrong

### LSM store: reads slowing, disk filling — why?
<details><summary>Show answer</summary>

- **Verdict:** merging can't keep up with incoming writes.
- **Reasoning:**
    - every flush adds a file; only merging removes files;
    - when writes arrive faster than merging, files pile up → reads check more files, old values stay on disk.
- **Trade-off — each fix has a cost:**
    - give merging more disk bandwidth or threads → less is left for live requests;
    - slow down incoming writes → the app waits;
    - add machines to share the writes → more to run and pay for.

</details>
