# Index Design

**Purpose.** Every index entry is a key and a value, and both are design choices. This file trains the two choices,
then uses them on the most common index question: why is this query slow?

**Covers:**
- The key — what queries search by: which columns, in what order.
- The value — what is stored next to the key.
- Scenarios — slow queries, each traced back to one of the two choices.

### Index design — what are the two choices?
<details><summary>Show answer</summary>

Take an index on `users(email)`. One entry: the key is `alice@example.com`, and next to it sits something that leads
to Alice's row. Every index entry has this shape, so an index design is two choices:

- **The key** — what queries search by.
  - Is it unique? [Primary vs secondary index](#primary-vs-secondary-index--the-difference).
  - One column or several? [Composite index](#what-is-a-composite-index).
- **The value** — [what is stored next to the key](#what-can-an-index-entry-hold).

**Trigger:** the key is how you find the entry; the value is what you get once you find it.

</details>

## A1. The key — primary vs secondary

### Primary vs secondary index — the difference?
<details><summary>Show answer</summary>

- **Primary key index** — the key is the primary key: unique, one key → one row. Example: `users.id = 42` → exactly
  one user. Other records refer to the row by this key, and the index finds the row they point to.
- **Secondary index** — the key is any other column, added with `CREATE INDEX`. Not unique: one key → many rows.
  Example: an index on `orders.user_id` finds all orders of one user.

</details>

### How does an index store a key that repeats?
<details><summary>Show answer</summary>

`user_id = 42` matches 300 orders. Two ways to store one key with many rows:

- **One entry per key** — the value is a list of all matching row IDs: `42 → [r7, r19, r311, ...]`.
- **One entry per row** — add the row ID to the key, so each key is unique again: `(42, r7)`, `(42, r19)`, ...
  All entries for 42 still sit side by side, because the index is sorted by `user_id` first.

</details>

## A2. The key — composite index

### What is a composite index?
<details><summary>Show answer</summary>

One key built from several columns, in a fixed order:

```sql
CREATE INDEX idx_people_name ON people (last_name, first_name);
```

Entries are sorted by `last_name`; rows with the same last name are sorted by `first_name`. This is an old paper phone
book: every Jones comes before every Smith, and Smith, Alice comes before Smith, Bob.

Other names: multicolumn index, concatenated index.

</details>

### Index on (A, B) — which searches can use it?
<details><summary>Show answer</summary>

Phone book sorted by `(last_name, first_name)`:

- `last_name = 'Smith'` — yes: all Smiths sit together.
- `last_name = 'Smith' AND first_name = 'Alice'` — yes: one spot inside the Smiths.
- `last_name = 'Smith' AND first_name > 'M'` — yes: one stretch inside the Smiths.
- `first_name = 'Alice'` alone — no: the Alices are spread across every last name, so the database reads everything.

With three columns `(A, B, C)`, a search can use:
- A
- A + B
- A + B + C

A + C narrows by A only; C is checked entry by entry. The rule: columns are used from the left, without gaps — the
**leftmost-prefix rule**.

Not absolute: some databases (MySQL 8, Oracle, Postgres 18) can **skip scan** — run one small search per distinct value
of the first column. It pays off only when that column has few distinct values; `last_name` has many.

</details>

### Composite index — how do you pick column order?
<details><summary>Show answer</summary>

Query: `WHERE country = 'DE' AND age > 60`.

- `(country, age)` — all German rows sit together, sorted by age: jump to DE, find the first age above 60, read to the
  end of DE.
- `(age, country)` — `age > 60` covers every country; the index reads all those entries and checks `country` one by
  one.

Inside a range of the first column, the second column is not sorted, so it can't narrow the search any more. Two rules
follow:

- Columns compared with `=` go first; the range column goes last.
- A column that some query filters on alone goes first, or that query can't use the index
  ([leftmost-prefix rule](#index-on-a-b--which-searches-can-use-it)).

</details>

## B. The value — what an index entry holds

### What can an index entry hold?
<details><summary>Show answer</summary>

How much of the row sits in the index:

- **The whole row** — the table is stored inside the index: [clustered index](#what-is-a-clustered-index).
- **Only a reference** — the row lives elsewhere; the entry says
  [where to find it](#secondary-index--how-does-it-point-to-the-row).
- **In between** — a reference plus a few columns, so some queries never need the row:
  [covering index](#what-is-a-covering-index).

**Trigger:** the more of the row sits in the index, the fewer jumps a read needs.

</details>

## B1. The value — clustered index

### What is a clustered index?
<details><summary>Show answer</summary>

The rows themselves are stored inside the index, sorted by its key. There is no separate place for the table: the
index is the table. A search by the key lands directly on the row.

- MySQL InnoDB: the primary key is always the clustered index.
- SQL Server: you choose which index is clustered — one per table.

</details>

### Why only one clustered index per table?
<details><summary>Show answer</summary>

A clustered index stores the rows themselves, sorted by its key. Rows can sit on disk in only one order — a second
clustered index would need a second full copy of the table. Any other order comes from a
[secondary index](#primary-vs-secondary-index--the-difference) that points back to the rows.

</details>

## B2. The value — reference to the row

### Secondary index — how does it point to the row?
<details><summary>Show answer</summary>

Two kinds of reference:

- **The row's disk location** — jump straight to the row in the [heap file](#what-is-a-heap-file). Postgres works
  this way.
- **The row's primary key** — then search the [clustered index](#what-is-a-clustered-index) by that key: two searches
  per row. MySQL InnoDB works this way.

</details>

### What is a heap file?
<details><summary>Show answer</summary>

The place where a table's rows are stored when the table is not a [clustered index](#what-is-a-clustered-index). Rows
sit in no particular order: a new row goes at the end, or into the space a deleted row left behind. Indexes point into
it by disk location. Postgres stores tables this way.

</details>

### An updated row no longer fits in place — what happens?
<details><summary>Show answer</summary>

In a [heap file](#what-is-a-heap-file), an updated row that is not bigger than before is overwritten in place, and the
indexes don't change. A row that grew (a longer text, say) must move to a new spot with enough room. Then one of two:

- **Update every index** to the new location — the update gets slower; reads still take one jump.
- **Leave a forwarding pointer** at the old spot — indexes stay as they are, but every read through an index lands on
  the old spot and makes one extra jump.

Postgres does neither: it never overwrites a row. Every `UPDATE` writes a new version of the row; the old one stays
until `VACUUM` removes it. If no indexed column changed and the page has room, the indexes are not touched (a
**HOT update**); otherwise every index gets a new entry.

</details>

## B3. The value — covering index

### What is a covering index?
<details><summary>Show answer</summary>

An index that stores, next to the key, a few extra columns that a query needs. The full row still lives in the heap
file or the clustered index.

```sql
CREATE INDEX idx_orders_customer ON orders (customer_id) INCLUDE (status, total);

SELECT status, total FROM orders WHERE customer_id = ?;  -- answered from the index alone
```

The query reads only the key and the extra columns, so it never touches the row: the index **covers** the query. The
book also calls it an **index with included columns**.

`INCLUDE` exists in Postgres and SQL Server. MySQL has none: put the extra columns at the end of the key instead —
`(customer_id, status, total)`.

</details>

### Covering index — what does it cost?
<details><summary>Show answer</summary>

The extra columns are a second copy of data that already lives in the row. Two costs follow:

- **More disk** — every entry grows by the size of the copied columns.
- **Slower writes** — every insert, and every update of a copied column, must change the index too.

</details>

## Scenarios — why is this query slow?

### Index on a status column is ignored — why?
<details><summary>Show answer</summary>

**Verdict:** the searched value matches a large share of the rows, so the database judges a full table read cheaper
than the index.

**Reasoning:** say `status = 'PAID'` on 90% of 1 million orders. Through the index, each match costs a separate jump to
its row — 900,000 jumps to scattered spots. Reading the table start to end is faster. This is a
[key that repeats](#how-does-an-index-store-a-key-that-repeats) too often for the index to pay off.

**Trade-off:** the same index wins for a rare value — `status = 'FAILED'` on 0.1% of rows. Ways to keep that win:
- Index only the rare rows: a partial index, `CREATE INDEX ... WHERE status = 'FAILED'` (Postgres; SQL Server calls it
  a filtered index).
- Search `status` together with a column that narrows well, in one [composite index](#what-is-a-composite-index).

</details>

### `WHERE LOWER(email) = ?` ignores the index on email — why?
<details><summary>Show answer</summary>

**Verdict:** the index holds `email`, not `LOWER(email)`. Index the expression itself.

**Reasoning:** the database uses an index only when the query asks about the same column or expression the index was
built on. `LOWER(email)` is a new value the index has never seen, so the database reads every row and runs `LOWER()`
on each. An index on the expression makes the lowercase value the [key](#index-design--what-are-the-two-choices):

```sql
CREATE INDEX idx_users_email_lower ON users (LOWER(email));  -- Postgres
```

**Trade-off:**
- That index serves only queries that use exactly `LOWER(email)`.
- Other way: store emails already lowercased; then a plain index on `email` works — but every write must lowercase,
  and the original spelling is lost.
- MySQL: the default collation ignores case, so plain `email = ?` already matches any case and uses the index.

</details>

### Index on (last_name, first_name); search by first name reads the whole table — why?
<details><summary>Show answer</summary>

**Verdict:** the index is sorted by last name first, so it can't find first names. Add an index that starts with
`first_name`.

**Reasoning:** as in a phone book, the Alices are spread across every last name — there is no single stretch to read.
A [composite index](#what-is-a-composite-index) serves a search only
[from its first column](#index-on-a-b--which-searches-can-use-it).

**Trade-off:**
- A second index costs disk and slows every write.
- Swapping the order to `(first_name, last_name)` avoids a second index, but breaks last-name-only search.
- If first-name search is rare, the full read may be the cheaper choice.

</details>

### Orders filtered by customer and a date range — which index?
<details><summary>Show answer</summary>

**Verdict:** `(customer_id, created_at)`.

**Reasoning:** one customer's orders sit together, sorted by date — jump to the customer, read one stretch. With
`(created_at, customer_id)`, the date range spans every customer's orders, and `customer_id` is checked one entry at a
time ([column order](#composite-index--how-do-you-pick-column-order)).

**Trade-off:** this index does nothing for "all orders in a date range" across customers — that query needs its own
index that starts with `created_at`.

</details>

### Rows grew after updates; reading them got slower — why?
<details><summary>Show answer</summary>

**Verdict:** the grown rows were moved, and each left a forwarding pointer at its old spot. Every read through an index
now takes two jumps instead of one. Rebuild the table so the indexes point straight at the rows again.

**Reasoning:** in a [heap file](#what-is-a-heap-file), a row that no longer fits must
[move](#an-updated-row-no-longer-fits-in-place--what-happens). The indexes still hold the old location, and the old
spot holds only a pointer to the new one. SQL Server tables without a clustered index work this way ("forwarded
records"); the rebuild is `ALTER TABLE ... REBUILD`.

**Trade-off:** the other design — update every index when a row moves — keeps reads at one jump, but makes each such
update slower.

</details>

### InnoDB, UUID primary key; secondary indexes much bigger than expected — why?
<details><summary>Show answer</summary>

**Verdict:** every secondary index entry stores the primary key, so a long key is copied into every entry of every
secondary index.

**Reasoning:** InnoDB secondary indexes
[point to the row by its primary key](#secondary-index--how-does-it-point-to-the-row). A UUID as text (`CHAR(36)`)
takes 36 bytes; a `BIGINT` takes 8. With 10 million rows and 5 secondary indexes, the 28-byte difference is copied
50 million times — about 1.4 GB.

**Trade-off:**
- A `BIGINT` key keeps indexes small, but the IDs come from one counter and are easy to guess.
- Keeping UUIDs: store them as `BINARY(16)` — 16 bytes instead of 36.
- Postgres doesn't have this problem: its indexes store the row's disk location, whatever the primary key's size.

</details>

### A frequent query uses an index on its filter column but is still slow — what's missing?
<details><summary>Show answer</summary>

**Verdict:** the columns the query returns are not in the index. Add them — make it a
[covering index](#what-is-a-covering-index).

**Reasoning:** take `SELECT name, price FROM products WHERE category_id = ?` with an index on `category_id`. The index
finds the matching entries fast, but for each one the database must jump to the row to read `name` and `price` — into
the heap, or (InnoDB) a second search in the clustered index. 200 matches = 200 extra jumps, on every call. With
`(category_id) INCLUDE (name, price)`, the answer comes from the index alone.

**Trade-off:**
- The index grows, and every write to `name` or `price` updates it too ([cost](#covering-index--what-does-it-cost)).
- Worth it for a frequent query that reads few columns. For `SELECT *` it would be a second copy of the table.
- Postgres: an index-only read still checks the table for rows on recently changed pages; `VACUUM` marks pages as
  safe to skip. A table that changes all the time gains less.

</details>
