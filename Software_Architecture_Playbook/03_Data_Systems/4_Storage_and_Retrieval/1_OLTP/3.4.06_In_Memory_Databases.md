# In-Memory Databases

**Purpose.** Some databases keep all their data in RAM. This file trains what follows from that one choice — how they
get their data back after a restart, why they are fast, what they make easy — and the Redis questions interviews ask.

**Covers:**
- What an in-memory database is, and how it survives a restart.
- Why it is fast: the book's answer and the interview answer.
- Scenarios — data lost in a Redis crash, a frozen server, a leaderboard, memory running out.

### In-memory database — what are the main questions?

Everything follows from one choice: [all data lives in RAM](#what-is-an-in-memory-database). That has three results:

- **RAM is wiped when the power goes** — the data must come back from somewhere.

- **No disk format to maintain** — faster, and free to use any data structure.
  - [Why faster than a disk database with enough RAM](#disk-database-with-enough-ram--why-still-slower)
  - [Why Redis is fast](#why-is-redis-fast) — and [the price of its one thread](#keys--in-production-froze-every-redis-client--why)

**Trigger:** all in RAM — it vanishes on power-off, it skips the disk format, it must fit.

### What is an in-memory database?
<details><summary>Show answer</summary>

A database that keeps all its data in RAM and answers every read from memory. Examples: Redis (key-value), VoltDB
(relational).

It may still write to disk — a log of changes or snapshots — but only to rebuild memory after a restart. During normal
work, it never reads from disk. That is what makes it in-memory: not that it has no disk, but that reads never use it.

</details>

### How does an in-memory database survive a restart?
<details><summary>Show answer</summary>

After a power loss, RAM is empty. The database rebuilds its memory from a copy kept somewhere else:

- **A log of changes on disk** — every write is appended; on restart, replay the log.
- **Snapshots on disk** — the whole memory written out now and then; on restart, load the latest one.
- **Replicas on other machines** — copy the state back over the network.
- **Battery-backed RAM** — special hardware keeps memory powered. Rare.

</details>

### Disk database with enough RAM — why still slower?
<details><summary>Show answer</summary>

Give Postgres enough RAM and every page it reads is already in memory — the OS (and the database's own cache) keeps
recently used disk blocks there. So it doesn't read from disk either.

The difference is the format. A disk database keeps data in memory in its disk layout — pages, B-tree nodes, rows as
encoded bytes — and translates on every read and write. An in-memory database keeps data as plain in-memory structures
(hash tables, lists), with nothing to translate.

The gain is skipping the disk format, not skipping the disk.

</details>

### Why is Redis fast?
<details><summary>Show answer</summary>

- **Data in RAM** — no request ever waits for a disk read.
- **One thread runs every command** — no locks, no waiting for other threads. Commands run one after another.
- **One loop serves all connections** — the thread watches thousands of sockets at once and handles whichever is
  ready (I/O multiplexing), instead of one thread per client.
- **Simple data structures** — hash tables, lists, sorted sets kept in memory; most operations are O(1) or O(log N),
  with no disk format to maintain ([the book's reason](#disk-database-with-enough-ram--why-still-slower)).

Since Redis 6, extra threads can read and write network data; the commands themselves still run on one thread.

</details>

### Memcached vs Redis — when do you pick which?
<details><summary>Show answer</summary>

- **Memcached** — a plain cache: string values, nothing on disk; a restart empties it. It runs on many threads, so one
  process uses all CPU cores. Pick it when the data is a copy you can rebuild and get/set is all you need.
- **Redis** — pick it when you need either:
  - data structures beyond plain values — sets, sorted sets, lists;
  - data that survives a restart — saving to disk, replicas.

Memcached holds a copy you can throw away; Redis can also be the place the data lives.

</details>

## Scenarios

### Redis server crashes — how much data is lost?
<details><summary>Show answer</summary>

**Verdict:** it depends on the disk setting — from minutes of writes with the default, to almost nothing with a sync on
every write.

**Reasoning:** Redis confirms a write once it is in memory; the disk gets it later. That is how it
[survives a restart](#how-does-an-in-memory-database-survive-a-restart), and the delay is what a crash loses:
- **RDB snapshots only** (the default) — everything since the last snapshot. With the default rules, minutes or more.
- **AOF log, `appendfsync everysec`** (the AOF default) — about one second of writes.
- **AOF log, `appendfsync always`** — almost nothing: every write is synced to disk.

**Trade-off:**
- `always` makes every write wait for the disk — much lower throughput.
- An RDB file is compact and loads fast; an AOF file is bigger and replays slower. Both can be on; Redis then restores
  from AOF.

</details>

### `KEYS *` in production froze every Redis client — why?
<details><summary>Show answer</summary>

**Verdict:** Redis runs every command on [one thread](#why-is-redis-fast). `KEYS *` walks every key, and all other
clients wait until it ends. Use `SCAN` instead.

**Reasoning:** with millions of keys, `KEYS *` can run for seconds. During that time no other command runs, so every
session read in the app waits and times out. `SCAN` returns keys in small batches with a cursor; other commands run
between the batches.

**Trade-off:** `SCAN` takes many round trips, and its result is weaker: a key may come back twice, and keys added or
removed during the scan may be missed.

</details>

### Live leaderboard: top 100 and any player's rank — which store?
<details><summary>Show answer</summary>

**Verdict:** a Redis sorted set.

**Reasoning:** a sorted set keeps members ordered by score; each operation costs O(log N), plus the entries returned:

```text
ZADD board 4200 player:7            # set or update a score
ZRANGE board 0 99 REV WITHSCORES    # top 100
ZREVRANK board player:7             # one player's rank
```

In SQL, the top 100 is easy with an index on score. A player's rank is not: it means counting everyone above them, on
every request, while scores change all the time. Redis can offer such a structure simply because it never has to lay
it out on disk — the [in-memory](#what-is-an-in-memory-database) advantage beyond speed.

**Trade-off:** the whole board sits in RAM, and Redis can lose recent writes. Keep the scores in the main database and
rebuild the set after a loss. For a small board, or ranks checked rarely, SQL is enough.

</details>

### Redis as the main store runs out of RAM — what happens to writes?
<details><summary>Show answer</summary>

**Verdict:** with a memory limit set, writes fail with an out-of-memory error, reads still work, and nothing is
deleted. Without a limit, it is worse.

**Reasoning:** an [in-memory database](#what-is-an-in-memory-database) must fit in RAM — it has nowhere else to put
data.
- **No limit** (`maxmemory 0`, the default on 64-bit systems) — Redis grows until the machine swaps to disk and
  everything slows, or the OS kills it and the data since the last save is lost.
- **Limit with the default policy `noeviction`** — Redis refuses writes that need more memory and keeps every key.
- **Other policies** — delete keys to make room: fine for a cache, silent data loss for a main store.

**Trade-off:** `noeviction` keeps every key, but the app gets write errors and must handle them. The real fix is more
RAM, or splitting the data across machines — so alert well before the limit.

</details>
