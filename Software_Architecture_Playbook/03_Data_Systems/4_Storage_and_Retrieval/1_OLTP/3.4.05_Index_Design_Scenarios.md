## Scenarios — why is this query slow?

### `WHERE LOWER(email) = ?` ignores the index on email — why?
<details><summary>Show answer</summary>

**Verdict:** the index holds `email`, not `LOWER(email)`. Index the expression itself.

**Reasoning:** the database uses an index only when the query asks about the same column or expression the index was
built on. `LOWER(email)` is a new value the index has never seen, so the database reads every row and runs `LOWER()`
on each. An index on the expression makes the lowercase value the [key](#index-design--what-are-the-two-choices):

```sql
CREATE INDEX idx_users_email_lower ON users (LOWER(email));  -- Postgres
```

**Trade-off:**
- That index serves only queries that use exactly `LOWER(email)`.
- Other way: store emails already lowercased; then a plain index on `email` works — but every write must lowercase,
  and the original spelling is lost.
- MySQL: the default collation ignores case, so plain `email = ?` already matches any case and uses the index.

</details>

### Prefix search `'john%'` — does an index help?
<details><summary>Show answer</summary>

**Verdict:** yes — a B-tree on the column serves `LIKE 'john%'`.

**Reasoning:** like a phone book: every value starting with "john" sits in one stretch — find the first, read until
the prefix changes. `LIKE '%john'` and `LIKE '%john%'` have no fixed start, so the whole index or table is read.

**Trade-off:**
- Postgres with a non-C collation: a plain B-tree can't serve `LIKE` — create it with `text_pattern_ops`
  (`CREATE INDEX ... (email text_pattern_ops)`) or use the C collation;
- search that ignores case → needs an
  [index on the expression](#where-loweremail---ignores-the-index-on-email--why);
- search in the middle of the text → a different index type (in Postgres, a trigram index).

</details>

### Two users must never share an email — what enforces it?
<details><summary>Show answer</summary>

**Verdict:** a unique constraint on `email` in the database, not a check in application code.

**Reasoning:**
- a check in code — select, then insert if nothing was found — has a gap: two requests both find nothing, both insert;
- the database checks its unique index on every insert; of two inserts of the same email, the second waits for the
  first to commit, then fails;
- the unique index is a B-tree, so the check is one lookup.

**Trade-off:**
- the app must catch the error and turn it into "email already taken";
- `Alice@x.com` and `alice@x.com` count as different → in Postgres, put the unique index on `LOWER(email)`; MySQL's
  default collation already ignores case.

</details>

### Deleting a user is slow, orders table is big — why?
<details><summary>Show answer</summary>

**Verdict:** `orders.user_id` has no index. For every deleted user, the database reads the whole orders table to check
for orders that still point to it. Index the foreign key column.

**Reasoning:**
- a foreign key from `orders.user_id` to `users.id` means: before a user goes, the database checks that no order
  points to it — or deletes those orders too, with `ON DELETE CASCADE`;
- that check is a search by `user_id` in `orders`; without an index, it reads every row;
- PostgreSQL never creates this index on its own; MySQL InnoDB does.

**Trade-off:** one more index to update on every order insert — rarely a problem, since the app usually searches
orders by user anyway.

</details>

### Index on (last_name, first_name); search by first name reads the whole table — why?
<details><summary>Show answer</summary>

**Verdict:** the index is sorted by last name first, so it can't find first names. Add an index that starts with
`first_name`.

**Reasoning:** as in a phone book, the Alices are spread across every last name — there is no single stretch to read.
A [composite index](#what-is-a-composite-index) serves a search only
[from its first column](#index-on-a-b--which-searches-can-use-it).

**Trade-off:**
- A second index costs disk and slows every write.
- Swapping the order to `(first_name, last_name)` avoids a second index, but breaks last-name-only search.
- If first-name search is rare, the full read may be the cheaper choice.

</details>

### Orders filtered by customer and a date range — which index?
<details><summary>Show answer</summary>

**Verdict:** `(customer_id, created_at)`.

**Reasoning:** one customer's orders sit together, sorted by date — jump to the customer, read one stretch. With
`(created_at, customer_id)`, the date range spans every customer's orders, and `customer_id` is checked one entry at a
time ([column order](#composite-index--how-do-you-pick-column-order)).

**Trade-off:** this index does nothing for "all orders in a date range" across customers — that query needs its own
index that starts with `created_at`.

</details>

### Search form with 6 optional filters — which indexes?
<details><summary>Show answer</summary>

**Verdict:** a few indexes for the most used filters, not one per combination; let the database combine them.

**Reasoning:** product search with filters on category, brand, price, color, size and rating, in any mix — 63
combinations.
- a composite index serves a search only [from its first column](#index-on-a-b--which-searches-can-use-it), so no
  small set of composite indexes covers them all;
- start with the filters that are used most and cut the most rows (e.g. `category_id`);
- Postgres and MySQL can combine several single-column indexes in one query (Postgres: bitmap scan; MySQL: index
  merge);
- the slow-query log shows which combinations really matter → add a composite index for those.

**Trade-off:**
- each extra index slows writes;
- combining indexes is slower than one exact composite index;
- many free filters plus text search → a search engine fits better.

</details>

### Rows grew after updates; reading them got slower — why?
<details><summary>Show answer</summary>

**Verdict:** the grown rows were moved, and each left a forwarding pointer at its old spot. Every read through an index
now takes two jumps instead of one. Rebuild the table so the indexes point straight at the rows again.

**Reasoning:** in a [heap file](#what-is-a-heap-file), a row that no longer fits must
[move](#an-updated-row-no-longer-fits-in-place--what-happens). The indexes still hold the old location, and the old
spot holds only a pointer to the new one. SQL Server tables without a clustered index work this way ("forwarded
records"); the rebuild is `ALTER TABLE ... REBUILD`.

**Trade-off:** the other design — update every index when a row moves — keeps reads at one jump, but makes each such
update slower.

</details>

### A frequent query uses an index on its filter column but is still slow — what's missing?
<details><summary>Show answer</summary>

**Verdict:** the columns the query returns are not in the index. Add them — make it a
[covering index](#what-is-a-covering-index).

**Reasoning:** take `SELECT name, price FROM products WHERE category_id = ?` with an index on `category_id`. The index
finds the matching entries fast, but for each one the database must jump to the row to read `name` and `price` — into
the heap, or (InnoDB) a second search in the clustered index. 200 matches = 200 extra jumps, on every call. With
`(category_id) INCLUDE (name, price)`, the answer comes from the index alone.

**Trade-off:**
- The index grows, and every write to `name` or `price` updates it too ([cost](#covering-index--what-does-it-cost)).
- Worth it for a frequent query that reads few columns. For `SELECT *` it would be a second copy of the table.
- Postgres: an index-only read still checks the table for rows on recently changed pages; `VACUUM` marks pages as
  safe to skip. A table that changes all the time gains less.

</details>

### Primary key — auto-increment or UUID?
<details><summary>Show answer</summary>

**Verdict:** auto-increment `BIGINT` by default; UUID v7 when IDs must be created outside the database. Avoid UUID v4.

**Reasoning:**
- `BIGINT` — 8 bytes; new keys go to the end of the index, so [inserts stay cheap](#random-primary-keys-slow-inserts--why).
  But only the database hands out IDs, and `/orders/1001` tells everyone that 1002 exists.
- UUID — any service or client creates one without asking the database; IDs from different systems never clash.
  16 bytes.
- UUID v4 is fully random → inserts land all over the index. UUID v7 starts with a timestamp → inserts stay near the
  end, like auto-increment.

**Trade-off:**
- a bigger key makes every index that holds it bigger —
  [worst in InnoDB](#innodb-uuid-primary-key-secondary-indexes-much-bigger-than-expected--why);
- store UUIDs in a binary type (`uuid` in Postgres, `BINARY(16)` in MySQL), never as text;
- a UUID v7 shows when the row was created.

</details>

### Random primary keys slow inserts — why?
<details><summary>Show answer</summary>

- **Sequential keys** (auto-increment) — every insert goes to the rightmost leaf page; that page stays in memory,
  fills up, splits once, and the next page takes over.
- **Random keys** (UUID v4) — every insert hits a random leaf page:
    - that page is often not in memory → a disk read before the write;
    - splits happen all over the tree and leave many pages half empty → the index grows bigger and slower.
- **Fix:** time-ordered IDs — **UUID v7** (RFC 9562, 2024) starts with a timestamp, so new keys land near the end like
  auto-increment and stay unique across machines.
- **Worst on:** databases where the table itself is sorted by primary key (MySQL InnoDB) — whole rows move with the
  splits.

</details>

### InnoDB, UUID primary key; secondary indexes much bigger than expected — why?
<details><summary>Show answer</summary>

**Verdict:** every secondary index entry stores the primary key, so a long key is copied into every entry of every
secondary index.

**Reasoning:** InnoDB secondary indexes
[point to the row by its primary key](#secondary-index--how-does-it-point-to-the-row). A UUID as text (`CHAR(36)`)
takes 36 bytes; a `BIGINT` takes 8. With 10 million rows and 5 secondary indexes, the 28-byte difference is copied
50 million times — about 1.4 GB.

**Trade-off:**
- A `BIGINT` key keeps indexes small, but the IDs come from one counter and are easy to guess.
- Keeping UUIDs: store them as `BINARY(16)` — 16 bytes instead of 36.
- Postgres doesn't have this problem: its indexes store the row's disk location, whatever the primary key's size.

</details>

### Rows deleted, index didn't shrink — why?
<details><summary>Show answer</summary>

Deleting rows removes their keys, but the pages stay — partly empty pages remain part of the index.

- **PostgreSQL:**
    - VACUUM removes dead entries but doesn't merge half-empty pages, so the index file doesn't get smaller;
    - freed space is reused only by keys in the same key range — delete old timestamps, insert ever-higher new ones,
      and the index keeps growing;
    - fix: rebuild it with `REINDEX` (`REINDEX ... CONCURRENTLY` to avoid blocking writes).
- **MySQL InnoDB:** merges a page with its neighbour when it drops below half full (`MERGE_THRESHOLD`, default 50%).

A B-tree grows on its own through splits; shrinking needs page merging or a rebuild.

</details>

### Old data must expire — how do you remove it?
<details><summary>Show answer</summary>

**Verdict:** partition the table by time (one partition per day or month) and drop old partitions, instead of `DELETE`.

**Reasoning:** take an events table that keeps 90 days and gets 10 million rows a day.
- `DELETE ... WHERE created_at < now() - interval '90 days'` removes rows one by one: an index entry and a WAL record
  for each, and [the index doesn't shrink](#rows-deleted-index-didnt-shrink--why) afterwards;
- dropping a partition removes its files and its indexes at once — near instant, nothing left behind;
- queries by time read only the partitions in range.

**Trade-off:**
- a query without a time filter reads every partition;
- Postgres: a unique index on a partitioned table must include the time column;
- new partitions must be created ahead of time, by a scheduled job or an extension (e.g. `pg_partman`).

</details>
