## 3.4.1 Why Indexes

Book: Ch. 4 — Storage and Indexing for OLTP (116), start of Log-Structured Storage (118).

- The simplest database: append every write to the end of one file. Fastest write; a read scans the whole file.
- What an index is: an extra structure, built from the data, that tells you where a key is.
- The cost: every write must also update the index, so the database doesn't index everything — you choose.

Not here: how indexes are built (3.4.2, 3.4.3), which columns to index (3.4.5).


The chapter answers one question: how does a database store data on disk so it can find it again fast?
Start with the simplest possible database: every write goes to the end of one file. Adding to the end of a file is the fastest write there is. But to read a key, you have to scan the whole file. An index fixes the read side. It is an extra structure that tells you where a key is. The cost is that every write now also has to update the index. That trade-off is file 4.1.
A storage engine is the part of the database that writes to disk and reads back. There are two main ways to build one with an index.

In particular, there is a big difference between storage engines that are optimized for
transactional workloads (OLTP) and those that are optimized for analytics (we intro‐
duced this distinction in “Operational Versus Analytical Systems” on page 3)

### Why care how storage engines work?
<details><summary>Show answer</summary>

You won't write a storage engine (the part of the database that writes data to disk and reads it back), but you will
pick one and configure it. Both need a rough picture of what it does on disk:

- **Pick** — each engine is built for a different kind of load (mostly writes vs mostly reads); you match it to yours.
- **Configure** — a setting only makes sense if you know what it changes inside the engine.
