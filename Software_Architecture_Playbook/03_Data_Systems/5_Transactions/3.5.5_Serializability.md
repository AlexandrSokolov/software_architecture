### Serializable isolation — how is it built?
<details><summary>Show answer</summary>

Three ways, placed on one axis — what happens when two transactions want the same data:

- Never overlap → [actual serial execution](#what-is-actual-serial-execution): one thread runs transactions one at a
  time.
- Wait → [two-phase locking](#what-is-two-phase-locking): a transaction waits for rows another one has locked.
  Pessimistic.
- Abort later → [serializable snapshot isolation](#what-is-serializable-snapshot-isolation): nobody waits; at commit
  the database checks for a conflict and aborts the loser. Optimistic.

Trigger: never overlap → wait → abort at commit.

Each one costs something (waiting, aborts, retry code), so in practice you often
[fix the one race instead](#race-condition--serializable-or-targeted-fix).

</details>

### What is actual serial execution?
<details><summary>Show answer</summary>

The database runs all transactions on one thread, one after another. Two transactions never overlap, so there is
nothing to lock and nothing to check: the order they ran in is the serial order.

One thread is fast enough only if:

- Data fits in memory — a transaction never waits for disk.
- The app sends the whole transaction as one stored procedure or script. With the usual back-and-forth (query, app
  thinks, next query) the single thread would sit idle on every network round trip.
- Each transaction stays in one partition. More CPU cores = more partitions, one thread each. A transaction across
  partitions must run in step on all of them and is far slower.

Cost: one slow transaction stops every transaction behind it. Used by VoltDB and Redis (Lua scripts).

</details>

### What is two-phase locking?
<details><summary>Show answer</summary>

A transaction locks every row it touches and keeps all locks until it commits or aborts:

- Read a row → shared lock. Other readers may share it; a writer must wait.
- Write a row → exclusive lock. Every other reader and writer must wait.
- Search a range ("bookings for room 12 at 2 pm") → lock the range itself, in practice a range of an index. Nobody can
  insert a new matching row (a phantom) until commit. Called an index-range lock.

The two phases: while running, the transaction only takes locks; at the end it releases them all. Nothing to do with
[two-phase commit](#two-phase-locking-vs-two-phase-commit).

Readers block writers and writers block readers — the opposite of snapshot isolation. That waiting is the cost: lower
throughput, unpredictable slow responses (bad p99), and deadlocks (A waits for B, B waits for A), where the database
aborts one and the app must [retry](#serialization-failure--what-must-the-app-do).

Pessimistic: assume conflicts, block up front. MySQL InnoDB and SQL Server build `SERIALIZABLE` this way.

</details>

### What is serializable snapshot isolation?
<details><summary>Show answer</summary>

Example: two doctors are on call. Each opens a transaction, reads "2 on call", and removes their own name. Under plain
snapshot isolation both commit and nobody is on call (write skew).

SSI runs transactions the same way — each reads its own snapshot, nobody waits — but it also records what each one
read. At commit it checks: did a transaction that committed after my snapshot change data I read? If yes, my decision
rests on stale data → abort. In the example, the second doctor's commit fails.

- Optimistic: let everyone run, check only at commit.
- Postgres `SERIALIZABLE` is SSI. The abort arrives as a
  [serialization failure](#serialization-failure--what-must-the-app-do).
- Cost: when many transactions hit the same rows, many abort and redo their work. Long read-write transactions abort
  most often.
- Gain over 2PL: reads never wait for locks, so response times stay predictable.

</details>

### Race condition — serializable or targeted fix?
<details><summary>Show answer</summary>

Verdict: fix the one race with a targeted tool. Turn on `SERIALIZABLE` only in the two cases below.

Targeted tools, by shape of the race:

- Read, change, write one value (stock, balance) → atomic `UPDATE stock SET qty = qty - 1 WHERE qty > 0`.
- Read, change, write an entity through an ORM → version column (`@Version`): the losing save fails, retry it.
- Check, then write, others must wait (the on-call doctors) → row lock (`SELECT ... FOR UPDATE`).
- No duplicates (email, seat) → unique constraint.

Serializable is worth it when:

- the check reads rows that don't exist yet, so there is no row to lock (two bookings for the same room and hour);
- the rule spans many rows and many code paths, so a fix on one path leaves the others open.

Trade-off:

- Serializable: any transaction can abort ([SSI](#what-is-serializable-snapshot-isolation)) or wait and deadlock
  ([2PL](#what-is-two-phase-locking)); the app needs [retry code](#serialization-failure--what-must-the-app-do);
  throughput drops when many transactions hit the same rows. In return it also covers races nobody has found yet.
- Targeted fix: cheap and limited to the hot spot, but each race is fixed by hand, and a new code path can silently
  bring the race back.

</details>

### Serialization failure — what must the app do?
<details><summary>Show answer</summary>

Retry the whole transaction from the start, as a new transaction — not just the failed statement. After the error the
old transaction is dead: Postgres rejects every further command in it until rollback.

- Rerun the code, don't replay saved values. The retry must read the new data — that is why the database aborted.
- Retry only conflict errors: SQLSTATE `40001` (serialization failure) and `40P01` (deadlock). A constraint violation
  or a bug fails again on every attempt.
- Cap the attempts and wait a short random time between them, or two retries can collide again.
- No email, HTTP call, or message send inside the transaction — the retry would do it twice. Do it after commit.
- Spring: the retry must sit outside the `@Transactional` method. A retry inside it keeps using the dead transaction.

</details>

### Two-phase locking vs two-phase commit?
<details><summary>Show answer</summary>

Same words in the name, different problems:

- [Two-phase locking](#what-is-two-phase-locking) — isolation: stops concurrent transactions from seeing or
  overwriting each other's work. Phases: take locks while running, release all at the end.
- Two-phase commit — atomicity across several nodes or databases: all commit or all abort. Phases: the coordinator
  asks every node "can you commit?", then tells all of them to commit (or all to abort).

Short form: 2PL serves the I in ACID, 2PC serves the A across machines.

</details>

As an application developer, you will almost never implement Two-Phase Locking, write a concurrency control algorithm, or build a transaction manager from scratch. That is the job of the database engine developers (at Oracle, PostgreSQL, Microsoft, etc.).

However, understanding these internal implementations is critical for you for three practical reasons that directly affect your daily work:

**1. Choosing the right database**
Different databases are built on different philosophies. If your application has massive write-contention (everyone updating the same few rows), an optimistic database (SSI) will constantly abort transactions and perform terribly. You would need to know to choose a database better suited for pessimistic locking or serial execution.

**2. Configuring the isolation level**
Most databases do **not** default to Serializable. PostgreSQL, SQL Server, and Oracle default to `Read Committed`. MySQL/InnoDB defaults to `Repeatable Read`. If your business logic requires absolute correctness (like financial accounting), you must know to explicitly execute `SET TRANSACTION ISOLATION LEVEL SERIALIZABLE`, and you need to understand what performance penalty you are accepting by doing so.

**3. Shaping your application code**
This is the most important part. The database's implementation dictates how you write your code:

* **If the DB uses Actual Serial Execution (e.g., Redis, VoltDB):** You must write your logic as stored procedures so the database can execute them instantly without waiting for network round-trips from your application.
* **If the DB uses Two-Phase Locking (Pessimistic):** You must keep your transactions incredibly short. If you fetch a record, run a slow API call to a third party, and then write the record back, you will lock the database row and freeze out other users the entire time. You also have to write code to handle deadlocks.
* **If the DB uses Serializable Snapshot Isolation (Optimistic):** The database will let conflicts happen, but abort one of the transactions right before it commits. This means your application code **must** include `try/catch` loops to automatically retry transactions when the database throws a serialization error.

You don't build the engine, but you are the driver. Knowing whether you have a manual, automatic, or electric transmission changes how you drive the car.
