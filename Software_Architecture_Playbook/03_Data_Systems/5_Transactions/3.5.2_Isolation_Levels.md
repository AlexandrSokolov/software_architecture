### Concurrent transactions — problem and fix?
<details><summary>Show answer</summary>

**Problem:** **race conditions** — one transaction reads data another is changing, or both write the same data. 
The result depends on timing: rare, hard to reproduce or catch in tests.

**Fix:** **isolation** (the "I" in ACID) — the database makes each transaction act as if it ran alone, so the developer
does not handle the timing. Strict form: **serializable**; databases usually run weaker, faster levels.

</details>

### Isolation — what does it cost?
<details><summary>Show answer</summary>

Full isolation (**serializable**) — same result as if transactions ran one at a time — costs performance.

So databases usually run **weaker isolation levels**: faster, but they block only some race conditions. 
Harder to understand, and subtle bugs get through.

</details>

### Financial data — use an ACID database?
<details><summary>Show answer</summary>

**Not enough on its own — trap.** ACID does not fix the isolation level. Most popular relational databases default
to weak isolation for speed, so race conditions still get through.

Because of this, simply choosing an ACID database will not automatically prevent complex concurrency bugs. 
You must explicitly configure stricter isolation (up to **serializable**) to fully protect against data inconsistencies.

</details>

### No isolation — what can go wrong?
<details><summary>Show answer</summary>

Every race condition:

- Uncommitted data:
  - [Dirty read](#what-is-a-dirty-read)
  - [Dirty write](#what-is-a-dirty-write)
- Committed data, bad timing:
  - [Read skew](#what-is-read-skew)
  - [Lost update](3.5.3_Lost_Updates_and_Write_Skew.md#what-is-a-lost-update)
  - [Write skew](3.5.3_Lost_Updates_and_Write_Skew.md#what-is-write-skew) 
  - [Phantom](3.5.3_Lost_Updates_and_Write_Skew.md#what-is-a-phantom)

</details>

### What is a dirty read?
<details><summary>Show answer</summary>

A transaction reads data another transaction has written but not yet committed.


**Example:**
- Transaction A updates an invoice amount but hasn't committed. 
- Transaction B reads this new amount to calculate a daily total. 
- If A rolls back, B's total is now based on data that never officially existed in the database.

</details>

### What is a dirty write?
<details><summary>Show answer</summary>

A transaction overwrites data another transaction has written but not yet committed.


**Example:**
Alice and Bob concurrently try to buy the same car. 
- Alice updates the car's title to "Alice". 
- Before she commits, Bob overwrites the title with "Bob".
- Bob's write silently destroys Alice's uncommitted write.

</details>

### Lowest isolation level that blocks dirty writes?
<details><summary>Show answer</summary>

**Read uncommitted** — blocks [dirty writes](#what-is-a-dirty-write).

</details>

### Blocking dirty writes — implementation?
<details><summary>Show answer</summary>

**Row-level locks.** Before writing a row, a transaction locks it and holds the lock until commit or abort. 
Another transaction that wants to write the same row waits. The database does this automatically.

</details>

### Read uncommitted — when to use it?
<details><summary>Show answer</summary>

Too weak for most work. It blocks [dirty writes](#what-is-a-dirty-write) but lets [dirty reads](#what-is-a-dirty-read)
and every other race condition through: a transaction can act on data that is later rolled back.

So it is rarely used in practice — at most for rough reports where an approximate number is fine.

</details>

### Lowest isolation level that blocks dirty reads?
<details><summary>Show answer</summary>

**[Read committed](#read-committed--what-does-it-guarantee)** — blocks [dirty reads](#what-is-a-dirty-read).

</details>

### Read committed — what does it guarantee?
<details><summary>Show answer</summary>

- No [dirty reads](#what-is-a-dirty-read): you read only committed data.
- No [dirty writes](#what-is-a-dirty-write): you overwrite only committed data.

Default level in many databases, e.g. PostgreSQL, Oracle, SQL Server.

</details>

### Blocking dirty reads — implementation?
<details><summary>Show answer</summary>

- **[Read locks](#how-do-read-locks-work)** (some databases): a reader waits until the row's writer commits or aborts.
  Problem: one long write makes every reader of that row wait — reads slow down, and a slowdown in one part of the
  app spreads to unrelated parts.
- **Keep the old value** (most databases): Also known as 
  [Multi-Version Concurrency Control (MVCC).](#how-does-mvcc-work) 
  For each row being written, the database keeps the last committed value next to the new one. 
  Other transactions read the old value until the writer commits, then switch to the new one.
  Readers never wait for writers, and writers never wait for readers.

</details>

### How do read locks work?
<details><summary>Show answer</summary>

Each row uses a Read-Write Lock (Shared/Exclusive) system.

- **Read** — shared mode. The transaction takes the lock, reads the row, and releases it at once. 
  Readers don't block each other; a writer waits for a reader only until that single read ends.
- **Write** — exclusive mode, held until commit or abort. 
  It blocks new readers and other writers, 
  so a reader waits until the writer commits or aborts and never sees the uncommitted value.

</details>

### Reading rows only, another commit between — what breaks?
<details><summary>Show answer</summary>

Cause: under [read committed](#read-committed--what-does-it-guarantee), each query sees the latest committed data at
the moment it runs. If another transaction commits between two queries of one transaction, the two queries see two
different moments.

What breaks depends on what the two queries read:

- **The same row** → [nonrepeatable read](#what-is-a-nonrepeatable-read): the second read returns a different value.
- **Different, related rows** → [read skew](#what-is-read-skew): each value is right, but together they don't fit.

</details>

### What is a nonrepeatable read?
<details><summary>Show answer</summary>

A transaction reads the same row twice and gets two different values, because another transaction changed the row and
committed in between. Both values were committed — the change between the two reads is what's wrong.

**Example:**
Alice has $500 in Account 1.
- Transaction A reads Account 1 ($500).
- Transaction B transfers $100 from Account 1 to 2 and commits.
- Transaction A reads Account 1 again ($400). To A, the same balance is both $500 and $400.

</details>

### What is read skew?
<details><summary>Show answer</summary>

A transaction reads different parts of the data at different moments, so it sees a mix of before and after another
transaction's change. Every value it reads was committed — the mix is what's wrong.


**Example:**
Alice has $500 in Account 1 and $500 in Account 2. 
- Transaction A reads Account 1 ($500). 
- Transaction B transfers $100 from Account 1 to 2 and commits. 
- Transaction A then reads Account 2 ($600). To A, Alice has $1100.

</details>

### Which isolation level blocks both nonrepeatable reads and read skew?
<details><summary>Show answer</summary>

**Snapshot isolation** — blocks both [nonrepeatable reads](#what-is-a-nonrepeatable-read) and
[read skew](#what-is-read-skew).
Some databases (PostgreSQL, MySQL) call it **repeatable read**.

</details>

### Snapshot isolation — what does it guarantee?
<details><summary>Show answer</summary>

Each transaction reads from a **snapshot**: the data as it was committed when the transaction started. 
Changes that other transactions commit later stay invisible to it.

Blocks:
- [nonrepeatable reads](#what-is-a-nonrepeatable-read): reading the same row again gives the same value.
- [read skew](#what-is-read-skew): all reads come from the same moment, so they fit together.
- [dirty reads](#what-is-a-dirty-read) 
- [dirty writes](#what-is-a-dirty-write)

Also called **repeatable read** (PostgreSQL, MySQL).

</details>

### Read committed vs snapshot isolation — how to choose?
<details><summary>Show answer</summary>

The difference is when the view of the data is taken:

- **Read committed** — each query sees the latest committed data, so two queries in one transaction can see two
  different moments.
  - Fits: most quick user operations, e.g., a bank web page. A mismatch is temporary: reload, and the numbers fit.
    Default in many databases.
- **Snapshot isolation** (repeatable read) — the whole transaction sees the data frozen at its start.
  - Fits: long, read-only operations whose result must be consistent:
    - **Backups** — copying takes hours while writes go on; a mix of old and new parts becomes permanent once you
      restore (e.g., money disappears).
    - **Analytics and integrity checks** — a scan over large parts of the data gives nonsense if the data changes
      mid-scan.

Rule: short read you can repeat → read committed; long read whose result you keep or act on → snapshot.

</details>

### Snapshot isolation — implementation?
<details><summary>Show answer</summary>

**[MVCC](#how-does-mvcc-work)**, with one fixed moment for the whole transaction. Transactions that started at
different moments each need their own committed version of a row, so the database keeps many versions per row — not
just the two that [read committed alone would need](#blocking-dirty-reads--implementation).

</details>

### How does MVCC work?
<details><summary>Show answer</summary>

**MVCC** (multi-version concurrency control) — a write never changes a row in place.
It adds a new version of the row and leaves the old one as it is.

- **Write** — adds a new, uncommitted version and [locks the row](#blocking-dirty-writes--implementation) against
  other writers until commit or abort. The last committed version stays readable.
- **Read** — no lock. The reader takes the newest version committed at a fixed moment and skips anything newer:
  - **read committed** — the moment each query starts;
  - **[snapshot isolation](#snapshot-isolation--what-does-it-guarantee)** — the moment the transaction starts.
- **Commit** — the new version becomes visible to reads that start after it. **Abort** — it never becomes visible.
- **Cleanup** — garbage collection later removes versions that no running transaction can see.

Result: readers never wait for writers, and writers never wait for readers.

</details>

### Snapshot isolation — how do indexes work?
<details><summary>Show answer</summary>

Two ways:

- **Version-linked index** (most common): each index entry points to one version of the row (oldest or newest), and
  the versions link to each other. A query follows the links until it finds a version that its snapshot can see and
  that still matches. When GC removes old versions, it removes their index entries too.
- **Copy-on-write (immutable) B-tree** (CouchDB, Datomic, LMDB): pages are never changed in place. A write copies
  each page it changes, plus every parent up to a new root; untouched pages are shared. Each root is a frozen
  snapshot, so no filtering by txid is needed. Old pages need background GC.

</details>

### Isolation level names — across databases?
<details><summary>Show answer</summary>

Not consistent. Two kinds of mix-up:

- **Same level, different names** — snapshot isolation is called:
    - "repeatable read" in PostgreSQL
    - "serializable" in Oracle
- **Same name, different levels** — "repeatable read" means:
    - snapshot isolation in PostgreSQL
    - a weaker MVCC variant in MySQL
    - serializable in IBM Db2

So the name alone tells you little — check what the database really does.

</details>
