### Writes fail halfway — how to avoid partial data?
<details><summary>Show answer</summary>

A **transaction**: group the reads and writes into one unit that runs as a single operation.
- All succeed → **commit**.
- Any fails → **abort** (**rollback**): nothing is left half-written, so the app can safely retry.

</details>

### Transactions — main gain for the app?
<details><summary>Show answer</summary>

Any failure undoes the whole unit, so the app never has to find and clean up half-done changes.
Result: **simple error handling** — on failure, just retry or report the error.

</details>

### Transactions — what do they cost?
<details><summary>Show answer</summary>

**Performance** and **availability**. So not every app needs full transactions: some weaken the guarantees,
some drop them entirely.

</details>

### Transactions or not — which default?
<details><summary>Show answer</summary>

**Keep transactions by default.** 
- With them, some spots get slow, and you fix those bottlenecks when they show up. You pay in a few places, later.
- Without them, all app code must handle half-done writes itself. You pay everywhere, always.

Exception: some systems need [speed or availability more than these guarantees](#transactions--what-do-they-cost).

</details>

### Does NoSQL support transactions?
<details><summary>Show answer</summary>

Early NoSQL (late 2000s) dropped transactions or weakened what the word meant, believing transactions can't scale.
That belief turned out wrong: **NewSQL** databases (e.g., Spanner, CockroachDB, TiDB) scale with full transactions.
Many NoSQL stores have since added transactions back, often with limits.

</details>

### Transactions — what safety do they guarantee?
<details><summary>Show answer</summary>

Transactions provide **ACID** guarantees to ensure data integrity:
- **Atomicity** (all or nothing): if any step fails, the whole transaction is rolled back.
  [No partial updates](#writes-fail-halfway--how-to-avoid-partial-data).
- **Consistency** (valid state): data moves from one valid state to another, obeying the app's rules.
- **Isolation** (independent): concurrent transactions do not interfere; they act as if run one after the other.
- **Durability** (permanent): once committed, changes are saved to disk (or copied to other nodes) and survive a crash.

</details>

### ACID consistency — what can the database enforce?
<details><summary>Show answer</summary>

To enforce consistency and ensure the database only moves between valid states, you declare invariants as part of the
schema. These are implemented as constraints, such as:
- Foreign-key constraints
- Uniqueness constraints
- Check constraints

</details>

### What does Isolation (in ACID) guarantee, and how is it implemented in practice?
<details><summary>Show answer</summary>

- **Ideal — serializability**: 
  ensuring concurrent transactions don't interfere and the result is as if they ran one after another.
- **Practice — weaker levels** (e.g., snapshot isolation): serializability costs performance, so most databases use
  weaker levels by default, and some race conditions remain. Oracle's "serializable" is really snapshot isolation.

</details>

### No isolation — what can a reader see?
<details><summary>Show answer</summary>

Another transaction's writes before they are committed: a **dirty read**. 
E.g., a new email is inserted but the unread counter isn't updated yet, so the user sees the email with a counter of 0.

</details>

### Atomicity vs. Isolation: Why is the un-updated email counter an Isolation issue?
<details><summary>Show answer</summary>

Same transaction: (1) insert an email, (2) increase the unread counter.
- **Atomicity (deals with failures)**: if the database crashes after step 1, the insert is rolled back. 
  It gives all or nothing in the end, but it doesn't hide work in progress.
- **Isolation (deals with concurrency)**: while the transaction is between steps 1 and 2, no other query can see the
  half-done state.

The user sees the email with a counter of 0 and nothing has failed, so their read wasn't isolated from the in-progress
write. Atomicity steps in only if the write fails and must be undone.

</details>

### Atomic — Java vs ACID meaning?
<details><summary>Show answer</summary>

- **Java**: other threads can't see a half-done state (`incrementAndGet()`, `synchronized`). In ACID terms this is
  [isolation](#what-does-isolation-in-acid-guarantee-and-how-is-it-implemented-in-practice).
- **ACID**: if the work fails halfway, [everything is undone](#writes-fail-halfway--how-to-avoid-partial-data). 
  It's about failure, not other threads. Plain Java has no such undo: 
  a `synchronized` block that updates one of two fields and then throws keeps that first update.

A better name for the ACID kind would be **abortability**.

</details>

### Durability on a single node — how?
<details><summary>Show answer</summary>

Durable on one node means written to disk (HDD/SSD), not just to memory. Each fix closes a hole the step before leaves:
- Writes wait in an OS memory buffer and are lost on power failure → **fsync** forces them onto disk.
- A crash in the middle of a write leaves data half-written → **write-ahead log (WAL)**: replay it to recover.
- A log entry itself can be half-written or corrupted → **checksums** detect bad entries, so recovery restores the
  last good state.

</details>

### Durability on a replicated database — how?
<details><summary>Show answer</summary>

When the data has been copied to a set number of nodes.
The database waits for those copies to finish before it reports the transaction as committed.

</details>

### Durability — how to guarantee it?
<details><summary>Show answer</summary>

You can't fully guarantee it, because each approach has gaps:
- **Disk**: a dead machine makes the data unreachable, firmware has bugs, `fsync` is hard to use correctly, worn SSDs
  lose data when unpowered, and data can silently become corrupted.
- **Replication**: with async replication, recent writes are lost if the leader dies before copying them, and one power
  outage or bug can crash all replicas at once, losing any data held only in memory.

**No technique gives a full guarantee; each only lowers the risk.** So combine them: disk, replication, and backups.

</details>

### Transaction aborted — what should the app do?
<details><summary>Show answer</summary>

**Retry it.** Simple and effective, but [not perfect](#retry--when-does-it-go-wrong).

</details>

### Which errors are not worth retrying?
<details><summary>Show answer</summary>

**Permanent** errors, e.g., a constraint violation: a retry fails the same way.
[Retry](#transaction-aborted--what-should-the-app-do) only **transient** ones: deadlock, isolation violation, short
network outage, failover.

</details>

### Retry — when does it go wrong?
<details><summary>Show answer</summary>

- The commit succeeded and only the reply was lost → it runs twice.
- Overload or heavy contention → retries add load and make it worse.
- Side effects outside the database (e.g., an email) → they repeat on every retry.
- The client crashes while retrying → the data it was writing is lost.

</details>
