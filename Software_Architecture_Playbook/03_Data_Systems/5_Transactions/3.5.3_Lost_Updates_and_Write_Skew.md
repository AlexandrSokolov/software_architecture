
### What is a lost update?
<details><summary>Show answer</summary>

Two transactions read the same value, change it, and write it back. The second write overwrites the first, so one
change is lost.


E.g., a counter is 42. Both transactions read 42 and write 43. Two increments happened; the counter shows one.

</details>

### Dirty write vs lost update — difference?
<details><summary>Show answer</summary>

- [**Dirty write**](3.5.2_Isolation_Levels.md#what-is-a-dirty-write) — the second write lands on a value the first transaction has not
  committed yet. No read is needed. It is a pure Write -> Write conflict.
- [**Lost update**](#what-is-a-lost-update) — the second write is based on a read that is now old. 
  The value it overwrites may already be committed. It requires a Read -> Modify -> Write cycle on committed data.

Two separate checks on the second write:
- "was the old value uncommitted?" 
- "was the new value based on an old read?" 

</details>

### Lost update — common scenarios?
<details><summary>Show answer</summary>

- Counter or account balance: read the value, compute the new one, write it back.
- Change inside a JSON document, e.g. add an item to a list: parse it, change it, write the whole document back.
- Two users edit a wiki page at once: each save sends the whole page and overwrites the other's changes.

</details>

### Lost update — how to fix?
<details><summary>Show answer</summary>

- **One after another:**
    - [Atomic write](#atomic-write-operations---how) — the database does the whole cycle in one statement.
    - [Explicit lock](#explicit-locking--how) — lock the rows on read, when app logic sits between read and write.
- **In parallel, catch the conflict, retry (optimistic):**
    - [Automatic detection](#automatic-lost-update-detection--how) — the database spots the lost update and aborts.
    - [Compare-and-set](#compare-and-set--how) — the app puts the check into the `UPDATE`.
- **Across replicas:** there is no single up-to-date copy, so none of the above works —
  [merge the conflicting versions](#lost-updates-across-replicas--fix).

Either stop the read → modify → write cycles from overlapping, or let them overlap and catch the conflict.

</details>

### Pessimistic vs optimistic locking — which to choose?
<details><summary>Show answer</summary>

- **Pessimistic** ([lock on read](#explicit-locking--how)): the second transaction waits.
- **Optimistic** ([version check](#compare-and-set--how) or
  [database detection](#automatic-lost-update-detection--how)): the second transaction fails and retries.

Two questions decide:
- **Does the read → write cycle span user think time?** Read in one request, save in another (wiki page edit) →
  optimistic. A lock lives only inside an open transaction, so it can't wait for the user.
- **Otherwise, how often do conflicts happen?**
    - Often, or redoing the work is costly (last seats in a ticket sale) → pessimistic. Waiting beats failing and
      redoing the work again and again.
    - Rarely (a user editing their own profile) → optimistic. No locks and no waiting; the rare retry is cheap.

What each costs:
- Pessimistic: waiting, plus [deadlocks and forgotten locks](#explicit-locking--what-can-go-wrong).
- Optimistic: retry code, and for user edits the version must go to the client and come back.

Pessimistic waits, optimistic retries: pick by how long the cycle is and how often it conflicts.

</details>

### Atomic write operations - how?
<details><summary>Show answer</summary>

Let the database do read → modify → write in one statement, instead of in app code:

`UPDATE counters SET value = value + 1 WHERE key = 'foo'`

How the database keeps it safe:
- It holds an exclusive lock on the row from read until write, so no other transaction reads it in between.
- Or it runs all such operations on a single thread.

Use it whenever the change fits the database's built-in operations (increment, append to a list in a document).
It does not fit logic computed in the app, e.g. saving an edited wiki page.

</details>

### Atomic write operations — when not enough?
<details><summary>Show answer</summary>

[Atomic writes](#atomic-write-operations---how) don't help in two cases:

- **Logic computed in the app** — the change can't be expressed as one database operation. Example: a wiki page
  edited by the user and saved as a whole.
- **[ORM trap](#orm-trap--how-do-updates-get-lost)** — the operation exists, but the code never uses it. The ORM loads the object, the change
  happens in Java, and the ORM writes the result back: read → modify → write in app code again.

</details>

### Explicit locking — how?
<details><summary>Show answer</summary>

Use it when the change needs [logic computed in the app](#atomic-write-operations--when-not-enough), e.g. checking
that a game move follows the rules. Lock the rows when you read them, then do read → modify → write in app code:

```sql
BEGIN;
SELECT * FROM figures WHERE name = 'robot' AND game_id = 222 FOR UPDATE; -- locks the returned rows
-- app checks that the move is valid
UPDATE figures SET position = 'c4' WHERE id = 1234;
COMMIT;                                                                  -- lock released
```

Another transaction that tries to update or lock the same rows waits until this one commits.

Risk: every code path that changes these rows must lock them. 
A path that reads without `FOR UPDATE` does not wait, so it can lose an update again, and nothing warns you.

</details>

### Explicit locking — what can go wrong?
<details><summary>Show answer</summary>

- **A forgotten lock** — every code path that changes these rows must lock them. A path that reads without
  `FOR UPDATE` does not wait, so it can lose an update again, and nothing warns you.
- **Deadlock** — T1 locks row A and waits for row B; T2 locks row B and waits for row A. Neither can go on. 
  Many databases detect this and abort one transaction, so the app must be ready to retry it.

</details>

### Automatic lost update detection — how?
<details><summary>Show answer</summary>

Atomic writes and locks make read → modify → write cycles run one after another. Detection is **optimistic**: it lets
them run in parallel, and if the database sees that a transaction would lose an update, it aborts that transaction
and the app retries it.

```sql
-- PostgreSQL, REPEATABLE READ; counter is 42
T1: SELECT value FROM counters WHERE key = 'foo';      -- 42
T2: SELECT value FROM counters WHERE key = 'foo';      -- 42
T1: UPDATE counters SET value = 43 WHERE key = 'foo';  COMMIT;
T2: UPDATE counters SET value = 43 WHERE key = 'foo';  -- ERROR: could not serialize access due to concurrent update
T2: retry: reads 43, writes 44
```

- **Plus:** no special code, so there is no [lock or atomic write to forget](#explicit-locking--what-can-go-wrong).
- **Minus:** the app must catch the abort and retry.
- **Where:** it is built on snapshot isolation, so the check is cheap. 

</details>

### Automatic lost update detection — which databases?
<details><summary>Show answer</summary>

- **Detect and abort:** PostgreSQL at repeatable read, Oracle at serializable, SQL Server at snapshot.
- **Do not detect:** MySQL/InnoDB at repeatable read.

Some authors say a database must prevent lost updates to count as snapshot isolation. 
By that rule, MySQL's repeatable read is not snapshot isolation.

</details>

### Compare-and-set — how?
<details><summary>Show answer</summary>

Write only if the value has not changed since you read it. 
If it has, the update matches 0 rows, so the app checks the row count and retries the read → modify → write. 
It is optimistic, like [automatic detection](#automatic-lost-update-detection--how), 
but here the app writes the check, not the database.

**Compare the value itself** — needs no extra column, but compares the whole content:

```sql
UPDATE wiki_pages SET content = 'new content' WHERE id = 1234 AND content = 'old content';
```

**Compare a version number** (also called optimistic locking) — a small column that every write must increment:

```sql
UPDATE wiki_pages SET content = 'new content', version = 6 WHERE id = 1234 AND version = 5;
```

</details>

### Compare-and-set — when is it unsafe?
<details><summary>Show answer</summary>

Under MVCC, a transaction reads from its snapshot: the data as it was at an earlier moment. If another transaction
changed the page after that, the snapshot still shows the old content. A `WHERE content = 'old content'` checked
against that snapshot passes, the update goes through, and the other change is lost.

Many MVCC databases make an exception for this case: the `WHERE` of `UPDATE` and `DELETE` sees the latest committed
values, even ones the rest of the snapshot hides. [Compare-and-set](#compare-and-set--how) is safe only on a database
that does this.

</details>

### Lost updates across replicas — fix?
<details><summary>Show answer</summary>

[Locks](#explicit-locking--how) and [conditional writes](#compare-and-set--how) don't work: multi-leader and
leaderless databases accept writes on several nodes at once and copy them later, so there is no single up-to-date
copy. Instead, concurrent writes create conflicting versions (**siblings**), which are resolved after the fact in one
of two ways:

- **Merge**: combine the siblings into one value.
    - **Commutative Operations**: updates that give the same result in any order (counters, set additions). Merging
      loses nothing only for these. Conditional writes can't be made commutative.
    - **CRDTs (Conflict-free Replicated Datatypes)**: data types built on this idea.
- **LWW (Last Write Wins)**: the default resolution method in many replicated databases. It keeps one write and drops
  the others, so it loses updates.

</details>

### What is write skew?
<details><summary>Show answer</summary>

Two transactions read the same data, decide based on it, then each writes a different row.
Neither write overwrites the other, but together they break a rule that each one checked.


**Example:**
A hospital requires at least 1 doctor on call.
- Alice and Bob are both on call.
- They concurrently check the schedule, see 2 doctors, and both update their own status to "off".
- Result: 0 doctors on call.

</details>

### Write skew vs lost update — difference?
<details><summary>Show answer</summary>

- [**Lost update**](#what-is-a-lost-update) — both transactions write the same object. The second write is based on
  an old read and overwrites the first.
- [**Write skew**](#what-is-write-skew) — both read the same data, check a rule against it, then each writes a
  different object. Nothing is overwritten and both writes survive. Each is fine alone, but together they break the
  rule they checked.

It is not a [dirty write](#dirty-write-vs-lost-update--difference) either: neither transaction writes over
uncommitted data.

Same pattern — read, decide, write — but the writes land on different objects. When they land on the same object,
you get a lost update or a dirty write, depending on timing.

</details>

### Write skew — how to fix?
<details><summary>Show answer</summary>

[Lost-update fixes](#lost-update--how-to-fix) guard the row being written, so they miss write skew, where the conflict
is in the rows that were read. [Atomic writes](#atomic-write-operations---how) and
[automatic detection](#automatic-lost-update-detection--how) don't catch it.

- **Serializable isolation** — the database makes transactions behave as if they ran one after another. The best fix.
- **Lock the rows you read** — the second-best fix, when serializable is not an option:

```sql
  BEGIN;
  SELECT * FROM doctors WHERE on_call = true AND shift_id = 1234 FOR UPDATE; -- locks every row the check reads
  -- app checks: at least 2 on call?
  UPDATE doctors SET on_call = false WHERE name = 'Alice' AND shift_id = 1234;
  COMMIT;
```

Bob's transaction now waits at its own locked read, then counts 1 and is refused.

</details>

### Write skew — common scenarios?
<details><summary>Show answer</summary>

- Meeting room booking: check that no booking overlaps the time slot, then insert one. 
  Two bookings for the same room and time.
- Multiplayer game: a lock stops two players moving the same figure, but not moving two different figures to the
  same square.
- Claiming a username: check the name is free, then create the account. Two accounts with the same name (a unique
  constraint fixes this one).
- Double-spending: insert a spending item, sum all items, check the balance stays positive. Two spendings together go
  negative, and neither sees the other.

</details>

### Write skew — what causes it?
<details><summary>Show answer</summary>

Every write skew follows the same three steps:
- **Check:** a `SELECT` tests a rule by searching for rows that match a condition: at least two doctors on call, no
  booking for this room and time, the square is empty, the username is free, money is left.
- **Decide:** the app looks at the result and decides to go ahead or to abort with an error.
- **Write:** if it goes ahead, it makes an `INSERT`, `UPDATE` or `DELETE` and commits.

The write changes the answer to the check. Run the same `SELECT` after the commit and you get a different result: one
doctor fewer on call, the room booked, the square taken, the name taken, less money. So when two transactions run
these steps at the same time, both check the old state, both pass, and both write. Together the writes break the rule
each one checked.

The order can differ: write first, then `SELECT`, then commit or abort based on the result. Same problem.

There are two kinds of check, and the kind decides how hard the fix is:
- **The write changes a row the check returned** (doctors on call). 
  [Lock the rows the check finds](#write-skew--how-to-fix) with `SELECT ... FOR UPDATE`.
- **The write makes a new row match the search** (a new booking, a figure moved onto the square, a new account with
  that name, a new spending item). The check never returned that row, and often returned no rows at all, so
  `FOR UPDATE` has nothing to lock. A write in one transaction that changes the result of another transaction's
  search is a [phantom](#what-is-a-phantom).

Check, decide, write — and the write changes what the check saw.

</details>

### What is a phantom?
<details><summary>Show answer</summary>

A transaction searches for rows that match a condition. Another transaction then inserts, updates, or deletes a
row matching that condition, so the first transaction's search result is already out of date.


**Example:**
E.g., two users book room 101 for 12:00. Each checks "any booking for room 101 at 12:00?", sees none, and inserts one.
Result: double booking.

Also called **phantom read**.

</details>

### Phantoms — how to fix?
<details><summary>Show answer</summary>

A [phantom](#what-is-a-phantom) is a row the check never saw: another transaction adds it after the check ran. Each
option has a limited scope:

- **Snapshot isolation** — read-only transactions only. The same search run twice returns the same rows. In a
  read/write transaction the snapshot hides the other's new row, so both checks pass on old data: both see room 1
  free at 12:00, and both insert a booking.
- **Lock the rows you read** (`FOR UPDATE`) — does not work: the new row is not in the result, so there is nothing
  to lock.
- **Unique constraint** — only rules of the form "no two rows with the same value" (username). It can't cover
  overlapping time ranges or sums.
- **Materializing conflicts** — create rows that stand for the thing being checked (one row per room per time slot),
  then lock those. Works with any database, but it mixes locking into the data model, so it's a last resort.
- **Serializable isolation** — all cases. The database tracks what each search depended on, not just the rows it
  returned.

Locks need a row, and a phantom has none: make the row, or let the database guard the search.

</details>

### Write skew vs phantom — difference?
<details><summary>Show answer</summary>

- [**Write skew**](#what-is-write-skew) — the problem: two transactions
  [check, decide and write](#write-skew--what-causes-it), and each write changes what the other's check saw. Together
  they break the rule.
- [**Phantom**](#what-is-a-phantom) — an effect: a write in one transaction adds a row that another transaction's
  search never returned. In read/write transactions it causes the harder kind of write skew.

Two kinds of write skew, depending on whether the changed row was in the check's result:
- **Yes** (doctors on call): the row exists and the check returned it, so you can lock it with `FOR UPDATE`.
- **No** (booking, username): the write adds a row the check never returned. That is a phantom, and there is nothing
  to lock.

Fixes:
- Serializable isolation fixes both kinds.
- [Locking the rows you read](#write-skew--how-to-fix) fixes only the first kind.
- [The phantom kind](#phantoms--how-to-fix) needs serializable or materializing conflicts. Simple cases like the
  username can use a unique constraint.

Write skew is the problem; a phantom is the hard version of it, where the row to lock doesn't exist yet.

</details>

### Materializing conflicts — how?
<details><summary>Show answer</summary>

A [phantom](#what-is-a-phantom) has no row to lock, so you create rows whose only job is to be locked.

Room booking: a `room_slots` table with one row per room per 15 minutes, created ahead of time (say, for the next
six months). It stores nothing about bookings; it is purely a set of locks.

```sql
BEGIN;
SELECT * FROM room_slots
WHERE room_id = 1 AND slot_start >= '12:00' AND slot_start < '13:00'
FOR UPDATE;                                                            -- locks the 4 slots of 12:00–13:00
SELECT COUNT(*) FROM bookings
WHERE room_id = 1 AND start_time < '13:00' AND end_time > '12:00';     -- 0: no overlap
INSERT INTO bookings (room_id, start_time, end_time) VALUES (1, '12:00', '13:00');
COMMIT;                                                                -- locks released
```

A second booking for 12:30–13:30 needs the 12:30 and 12:45 slots too, so it waits until the first commits. Then,
under read committed, its check sees the new booking and it is refused. The phantom has turned into a lock conflict on
rows that exist, which is where the name comes from.

Why it's a last resort:
- Hard and error-prone: you must pick the slot size, create the rows ahead, and make
  [every write path lock them](#explicit-locking--what-can-go-wrong).
- Locking leaks into the data model: the table exists only for concurrency control.

Prefer [serializable isolation](#phantoms--how-to-fix). Use this only when nothing else is available.

</details>
