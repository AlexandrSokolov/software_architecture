### Why duplicates exist

### Where can a message get lost?
<details><summary>Show answer</summary>

At every hop of its way:

- **[Sender](#sender)** — the DB change is saved, but the message never reaches the broker, and nobody notices.
- **[Broker](../6_Message_Brokers/)** — it confirmed, but the message sat on too few disks or copies when a node died;
  or the broker never kept it for you, or deleted it before you read it.
- **[Receiver](3_Lost_on_Receive.md)** — it confirmed (ack, saved offset, `200 OK`) before the work was done, or caught
  an error and confirmed anyway. A poller can also [skip rows](Polling_for_Changes.md) and never see them.

Trigger: each hop loses the message the same way — it says "done" before the message is safe at the next step.

</details>

### When is losing a message fine?
<details><summary>Show answer</summary>

When the next message makes it useless anyway. It is fine only when two conditions are met simultaneously:

- **Absolute state, not a delta**: The message carries the full current value (e.g., "balance is 50"), not a change
  ("add 10").
- **Continuous stream**: Messages arrive periodically (e.g., GPS pings, live metrics).

Because the state is absolute and the stream is continuous, a lost message is harmlessly replaced by the next one.
This enables **at-most-once delivery**: send once, no retries, no waiting for acks, no duplicate handling.

</details>


### Fire and forget — what's the trade-off?
<details><summary>Show answer</summary>

**Fire and forget:** the sender sends the message and moves on. It does not wait for the broker's ACK, so it never
learns about a failure and never retries. Examples: Kafka with `acks=0`; RabbitMQ without publisher confirms.

This is **at-most-once delivery**: each message arrives once or not at all.

- **Gain:** highest throughput, lowest latency. There is no waiting for the ACK.
- **Loss:** a message can be lost, and nobody knows: the network drops it, the broker is down (restart, leader
  change), or the broker rejects it (disk full, message too large).

Use only for data [you can afford to lose](#when-is-losing-a-message-fine), like click tracking.


**Fix:** don't send from the business method. Save the message to an
[outbox](#how-do-you-fix-the-dual-write-problem) table in the same transaction as the business change.
A relay reads the table and sends:

- Waits for the ACK. No ACK → retries.
- Marks the row sent only after the ACK. A crash before that leaves the row, so the relay sends it again on restart.

This is **at-least-once**. Cost: duplicates, from a lost ACK or a crash before the row is marked. Receivers must
handle them.

</details>
