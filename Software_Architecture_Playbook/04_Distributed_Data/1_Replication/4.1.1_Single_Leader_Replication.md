## cards

### What is replication?
<details><summary>Show answer</summary>

Keeping a copy of the same data on several machines connected by a network.

</details>

### Why replicate data?
<details><summary>Show answer</summary>

- **Availability and durability** — if a machine fails, the others keep serving and the data isn't lost.
- **Scalability and Read throughput** — more copies can serve more reads.
- **Lower latency** — a copy close geographically to the users answers faster.

</details>

### Replication — what are the approaches?
<details><summary>Show answer</summary>

- **Single-leader** — one node takes all writes; the others copy from it.
- **Multi-leader** — several nodes take writes and copy changes to each other.
- **Leaderless** — any node takes writes; the client writes to several nodes at once.

</details>

### Backups with replication
<details><summary>Show answer</summary>

They serve entirely different purposes.

- **Replication** provides high availability. 
  It copies every write fast across nodes — mistakes too: an accidental delete reaches every replica.
- **Backups** provide historical recovery, 
  so you can go back in time and restore data after accidental deletions or logical corruptions.

</details>

### Node holding a database copy — name?
<details><summary>Show answer</summary>

A **replica**.

</details>

### How does leader–follower replication work?
<details><summary>Show answer</summary>

Also called single-leader, leader-based, primary-backup, or active/passive replication.
- **Writes go only to the leader** (primary, source). It writes the change to its own storage first.
- **The leader sends each change to the followers** (read replicas, secondaries, hot standbys) through a replication log.
- **Followers apply the changes in the same order** as the leader did.
- **Reads go to the leader or any follower.** Followers are read-only for clients.

</details>

### How do changes reach the followers?
<details><summary>Show answer</summary>

The follower starts the connection, not the leader.

- **The follower connects to the leader.** It knows the leader's address and opens one long-lived connection.
- **It says where it is:** "I have everything up to position X." The position is a point in the leader's log.
- **The leader pushes each new change down that open connection** as it happens. There is no request per change:
  the follower reads the log like a file that keeps growing.
- **The follower reports back how far it got.** This is how the leader knows each follower's position. The
  follower sends it in both modes: 
  - in sync mode the leader waits for it before telling the client "done", 
  - in async mode it does not.

The leader needs no list of follower addresses. It learns about a follower when the follower connects.

</details>

### Leader-follower replication with a sharded database?
<details><summary>Show answer</summary>

In a sharded database, replication happens at the shard level. One leader per shard.
Leaders of different shards can sit on different nodes, so one node may lead some shards and follow for others.

</details>

### Where is single-leader replication used?
<details><summary>Show answer</summary>

- **Relational databases** — PostgreSQL, MySQL, Oracle Data Guard, SQL Server Always On.
- **Document databases** — MongoDB, DynamoDB.
- **Message brokers** — Kafka.

</details>

### Replication timing — two modes?
<details><summary>Show answer</summary>

- **Synchronous** — the leader waits for the follower to confirm before reporting the write as done.
- **Asynchronous** — the leader reports the write as done without waiting for the follower.

Both modes use the [same connection and the same stream](#how-do-changes-reach-the-followers). Sync is not a
remote call that waits for a reply, and async is not sending an event: the changes reach the followers the same
way in both modes. The only difference is when the leader tells the client the write is done.

</details>

### Sync vs async replication — trade-off?
<details><summary>Show answer</summary>

- **Synchronous** — the follower is always up to date, so if the leader fails no write is lost. 
  Cost: if the follower crashes or is slow, the leader must block all writes until it's back.
- **Asynchronous** — writes never wait. Costs: 
  - if the leader fails, writes not yet copied are lost.
  - inconsistencies in the database; if you run the same query on the leader and a follower at the same time, 
    you may get different results.

All followers synchronous is impractical: one node outage stops every write.

</details>

### What are the common configurations for managing replication timing?
<details><summary>Show answer</summary>

Not all followers should be synchronous: then one node outage stops every write. Common setups:
- **One follower** — [semi-synchronous](#what-is-semisynchronous-replication).
- **A majority of followers** — [majority quorum](#what-is-majority-quorum-replication).
- **None** — [fully asynchronous](#what-is-fully-asynchronous-replication).

</details>

### What is semisynchronous replication?
<details><summary>Show answer</summary>

One follower is synchronous, the rest asynchronous. 
If the synchronous one fails or slows down, an asynchronous one takes its place. 
The latest data is always on at least two nodes: the leader and that follower.

</details>

### What is majority-quorum replication?
<details><summary>Show answer</summary>

A majority of replicas, leader included (e.g. 3 of 5), is updated synchronously; the rest asynchronously. 
Used in systems that elect the leader automatically through consensus, and in eventually consistent systems.

</details>

### What is fully asynchronous replication?
<details><summary>Show answer</summary>

The leader confirms writes without waiting for any follower.
- Gain: the leader keeps accepting writes even if every follower falls behind.
- Cost: if the leader is lost for good, writes not yet copied are lost — even ones already confirmed to the client.

Still widely used, especially with many followers or followers in other regions.

</details>

### Setting up a new follower — options?
<details><summary>Show answer</summary>

Both start from a snapshot and then catch up from the leader's log. They differ in where the snapshot comes from:
- **From the leader** — [snapshot the leader, copy it, catch up](#new-follower--how-to-get-a-correct-copy).
- **From an object store** — [download the archived snapshot and log](#new-follower--how-to-spare-the-leader), then
  catch up with the leader.

</details>

### New follower — how to get a correct copy from the leader?
<details><summary>Show answer</summary>

Fails:
- **Copy the leader's data files** (the tables on disk) while it runs — writes keep coming, so the copy mixes
  parts from different moments. Locking the database for the copy fixes this but means downtime.
- **Rebuild from the logs alone** — neither the replication log nor the
  [recovery log](#recovery-log-vs-replication-log--what-for) keeps the full history: old parts get deleted.

Works — a snapshot plus the replication log after it:
- **Snapshot** — a full copy of the leader's data as of one moment, taken without locking it. In effect a full
  backup, with one required extra: the exact replication log position at that moment — the log sequence number
  in PostgreSQL, binlog coordinates or GTIDs in MySQL.
- **Copy** — move the snapshot to the new follower.
- **Catch up** — the follower asks the leader for all changes after that position and applies them.
- **Follow** — once caught up, it applies new changes as they happen.

</details>

### New follower — how to spare the leader?
<details><summary>Show answer</summary>

Load the starting copy from an object store (e.g. S3) instead of the leader. 
If the database already archives periodic snapshots and its replication log there for backups, 
the new follower downloads the latest snapshot and the log from it. 
It connects to the leader only for the last few changes, so the leader doesn't have to build and send a big snapshot.

</details>

### Replication log — what can it contain?
<details><summary>Show answer</summary>

Three levels, from high to low:
- **SQL statements** — the leader sends each `INSERT`/`UPDATE`/`DELETE`; followers run it again.
  [Fragile](#statement-based-replication--what-breaks).
- **Rows (logical log)** — which rows were inserted, updated or deleted, independent of storage internals.
  [Usually preferred](#logical-log--why-is-it-preferred).
- **Write-ahead log (WAL) shipping** — the leader's sends its exact physical disk modifications (byte-by-byte changes).
  [Tied to the version](#wal-shipping--whats-the-drawback).

</details>

### Statement-based replication — what breaks?
<details><summary>Show answer</summary>

Replaying the same SQL on a follower can give a different result:
- **Nondeterministic functions** — `NOW()`, `RAND()` give a different value on each replica.
- **Order dependence** — auto-increment and `UPDATE … WHERE` need the exact same order on every replica, which is hard
  with concurrent transactions.
- **Side effects** — triggers, stored procedures and functions may act differently on each replica.

Fix: the leader writes fixed values into the log, or the database requires deterministic transactions (VoltDB).
MySQL used it before 5.1; today it switches to row-based when a statement isn't deterministic.

</details>

### WAL shipping — what's the drawback?
<details><summary>Show answer</summary>

The leader sends its write-ahead log, and followers build exactly the same files (PostgreSQL, Oracle). 
But the log describes bytes in disk blocks, so it's tied to the storage format: 
leader and followers must usually run the same database version, and a version upgrade needs downtime.

</details>

### Logical log — why is it preferred?
<details><summary>Show answer</summary>

It decouples the replication log from the underlying storage engine internals.
Because it just describes changes to rows (e.g., "Row ID 5 changed column X to Y"), it allows:
- **Zero-downtime upgrades** — leader and followers can run different versions: upgrade the followers, then fail over
  to one of them.
- **Change Data Capture** — outside systems (a data warehouse, a search index) can read it to get every change.

</details>

### Recovery log vs replication log — what for?
<details><summary>Show answer</summary>

- **Recovery log** — on every machine, leader and followers, each its own. Purpose: after a crash, finish the changes
  that never reached the tables. A change is safe once it is in this log; only the table update is pending. Names:
  - WAL — PostgreSQL
  - redo log — MySQL (InnoDB), Oracle
  - transaction log — SQL Server
- **Replication log** — the leader's list of changes, in order. Each follower keeps a copy and applies from it.
  Purpose: keep followers in sync.

One file or two:

- **PostgreSQL — one file, both jobs:**
  - the WAL is the recovery log on every machine
  - the leader sends its WAL to followers, so the WAL is also the replication log
  - a follower writes what it receives into its own WAL — its copy and its recovery log are the same file
- **MySQL — separate files:**
  - redo log — recovery, on every machine
  - binlog — the replication log, on the leader
  - relay log — the follower's copy of the binlog, waiting to be applied; applied changes go through the follower's
    own redo log

**Handle:** Recovery log saves pending writes from a crash; replication log syncs followers.

</details>
