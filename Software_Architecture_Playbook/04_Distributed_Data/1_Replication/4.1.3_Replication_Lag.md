### What is replication lag?
<details><summary>Show answer</summary>

Replication lag is the delay between a successful write on the leader and that exact write being applied on an
asynchronous follower.

- **Normally:** The lag is just milliseconds, so the data appears consistent to the user.
- **Under load or failure:** The lag grows. A client reading from the follower will see outdated data compared to the
  leader (e.g., a user updates their profile but sees the old version on refresh).

</details>

### Replication lag — how to measure it?
<details><summary>Show answer</summary>

- **By position** — the leader's current log position minus the position the follower has applied.
  Exact: it shows how much of the log the follower is missing.
- **By time** — how many seconds the follower is behind the leader. Easier to alert on, but it depends on clocks, and
  with no new writes some databases show it growing even though the follower is caught up.

Leaderless replication has no single order of writes, so there is no position to compare and lag is harder to measure.

</details>

### What is eventual consistency?
<details><summary>Show answer</summary>

It is the fundamental nature of asynchronous replication. Every async follower is a little behind the leader.
There is always a delay ([replication lag](#what-is-replication-lag))
between a write on the leader and its arrival at the follower.

It is called "eventual" because this inconsistency is temporary. If you stop all new writes to the system,
the follower will process its backlog and eventually catch up to perfectly match the leader's state.

</details>

### Reading your own writes — what breaks?
<details><summary>Show answer</summary>

Writes go to the leader, reads go to a follower.
A user saves a comment and reloads the page right away, and the read hits an async follower that is still
[behind](#what-is-replication-lag). The comment is missing, so the user thinks it was lost.

</details>

### Which guarantee fixes missing own writes?
<details><summary>Show answer</summary>

**Read-after-write consistency** (also **read-your-writes consistency**): after a reload, the user always sees the
updates they made themselves, which fixes [missing own writes](#reading-your-own-writes--what-breaks).
It promises nothing about other users' updates; those may show up later.

</details>

### Read-after-write consistency — how to get it?
<details><summary>Show answer</summary>

Choose by how much is known about the user's writes, from coarse to precise:

- **Which data they can edit** (e.g. own profile) → [route by data ownership](#only-the-owner-edits-it--where-to-read)
- **When they last wrote** (e.g. collaborative apps) → [route by time](#user-can-edit-almost-everything--how-to-read)
- **Which write they made last** (client sends it) → [route by write position](#reads-must-stay-off-the-leader--how)

With replicas in several regions, every read that must go to the leader crosses to the leader's region: extra latency.

</details>

### Only the owner edits it — where to read?
<details><summary>Show answer</summary>

**Route by data ownership.** You know what the user can change without querying, so the rule is fixed in code:
- the user's own data (their profile) → from the leader (or a sync follower);
- other users' data → from an async follower.

The leader gets little load: most reads are of other people's data and stay on followers.

</details>

### User can edit almost everything — how to read?
<details><summary>Show answer</summary>

**Route by time.** Reading all editable data from the leader would send almost every read there, and followers would
stop helping. Decide by how recent the write is instead:
- **Per user** — for a short time after the user's last write (e.g. one minute), send all their reads to the leader.
- **Per follower** — track each follower's lag, and send no reads to a follower more than a minute behind.

</details>

### Reads must stay off the leader — how?
<details><summary>Show answer</summary>

**Route by write position.** The server tracks nothing; the client does:
- the client remembers the position of its last write and sends it with each read;
- a replica serves the read only if it has applied the log up to that position; if not, another replica serves it,
  or the read waits until this one catches up.

The position can be a log sequence number (orders writes) or a clock time — then the machines' clocks must be in sync.

</details>

### How do multiple devices complicate read-after-write consistency?
<details><summary>Show answer</summary>

Users expect **cross-device read-after-write consistency**: if they update data on their phone, they expect to see it
immediately when opening their laptop. This introduces two major complications:

- **[Client-tracked timestamps](#reads-must-stay-off-the-leader--how) fail:** The laptop does not know the timestamp of
  the write made by the phone.
  **Fix:** The metadata (timestamp of the user's last global update) must be centralized on the server, not the client.
- **Multi-region routing mismatches:** Devices on different networks (e.g., home WiFi vs. cellular) might be routed to
  completely different geographical datacenters. **Fix:** If your consistency strategy requires
  [reading from the leader](#read-after-write-consistency--how-to-get-it), you must explicitly route all traffic for a
  specific user's devices to the exact same region.

</details>

### Region vs zone — what is each?
<details><summary>Show answer</summary>

- **Availability zone (zone):** a single datacenter in its own building, with its own power and cooling.
- **Region:** one geographic location with several zones, joined by a very fast network.

</details>

### Multi-zone vs multi-region — what does each survive?
<details><summary>Show answer</summary>

- **Zonal outage (one datacenter fails):** survived by spreading the system across several zones in one region.
- **Regional outage (all zones in a region fail):** multi-zone can't survive this; the system must be spread across
  [several regions](#multi-region--what-does-it-cost).

</details>

### Multi-region — what does it cost?
<details><summary>Show answer</summary>

Higher latency, lower throughput, and much higher cloud network bills.

Multi-zone costs almost nothing in comparison: zones in one region are so close that the system can treat them as one
location.

</details>

### One city's datacenters all fail — how to stay up?
<details><summary>Show answer</summary>

- **Verdict** — spread the system across several regions.
- **Reasoning** — the datacenters in one city are the [zones](#region-vs-zone--what-is-each) of one region. Multi-zone
  survives losing one of them, not all at once.
- **Trade-off** — [higher latency, lower throughput, bigger network bills](#multi-region--what-does-it-cost). If
  losing one datacenter is the only risk to cover, multi-zone is enough and almost free.

</details>

### A comment appears, then vanishes — why?
<details><summary>Show answer</summary>

A user see data "move backward in time". A user refreshes a page twice, and each request goes to a random follower.
The first follower is nearly up to date and shows a new comment;
the second [lags more](#what-is-replication-lag) and doesn't have it yet. The comment appears, then disappears.

Never seeing it would be fine. Seeing it and then losing it is the problem.

</details>

### Which guarantee stops time going backward?
<details><summary>Show answer</summary>

**Monotonic reads**: after a user has seen newer data, their later reads never return older data, which fixes
[disappearing comments](#a-comment-appears-then-vanishes--why).
A read can still be old, just never older than the one before.
Stronger than [eventual consistency](#what-is-eventual-consistency), weaker than strong consistency.

</details>

### Monotonic reads — how to get them?
<details><summary>Show answer</summary>

To prevent a user from bouncing between fast and slow replicas, ensure that a specific user **always reads from the
same replica**. Different users can use different replicas. Pick the replica by a hash of the user ID, not at random.

**Limit:**
If the user's dedicated replica crashes, their traffic must be rerouted to a new replica.
If the new replica happens to be further behind than the crashed one, the user will temporarily see time go backward,
breaking the guarantee.

</details>

### Reply visible before the message — why?
<details><summary>Show answer</summary>

- **The write** — a user posts a message; someone reads it and writes a reply.
- **The routing** — the data is sharded, so the message and the reply land on different shards, each with its own
  followers.
- **The anomaly** — a third user reads both. If the reply's shard replicates faster, they see the reply before the
  message was ever posted.

The reply depends on the message (one caused the other). Seeing them in the wrong order is a **causality violation**.

</details>

### Which guarantee keeps replies after messages?
<details><summary>Show answer</summary>

**Consistent prefix reads**: if writes happen in a certain order, every reader sees them in that order. This fixes
[replies before messages](#reply-visible-before-the-message--why).

The anomaly shows up in sharded databases: shards replicate independently, so there is no global order of writes.

How to implement it:
- **Same-shard routing** — store writes that depend on each other (a message and its replies) on the same shard;
  not always efficient.
- **Dependency tracking** — the database records which write depends on which, so reads never show them out of order.

</details>

### Replication lag — how to deal with it?
<details><summary>Show answer</summary>

Who carries the work: the database or the app.

- **Database level (strong consistency)** — choose a database with **linearizability** (replicas act like one copy of
  the data) and **ACID transactions**. The cluster acts like a single node, so lag is hidden. Early NoSQL claimed
  this can't scale; **NewSQL** databases later showed it can.
    - **Pros:** simplest programming model; developers can ignore replication lag.
    - **Cons:** more overhead, and copes worse with network breaks.
- **App level (weaker guarantees)** — accept [eventual consistency](#what-is-eventual-consistency) and add in app code
  each guarantee you need:
    - [read-after-write](#which-guarantee-fixes-missing-own-writes),
    - [monotonic reads](#which-guarantee-stops-time-going-backward),
    - [consistent prefix](#which-guarantee-keeps-replies-after-messages).
    - **Pros:** lower latency and overhead; keeps working better when the network breaks.
    - **Cons:** complex code; developers manage the routing themselves (leader reads, user-ID hashes, write positions).

</details>

### Saved in Spring, reload shows old data — why?
<details><summary>Show answer</summary>

Setup: an `AbstractRoutingDataSource` sends `@Transactional(readOnly = true)` calls to a replica, the rest to the primary.

- **Verdict** — [read-after-write](#which-guarantee-fixes-missing-own-writes) break: the save went to the primary,
  the reload's read-only call went to a replica that hasn't got the write yet.
- **Reasoning** — the routing checks only the read-only flag, never whether this user just wrote.
- **Fix** — for a short time after a user writes, route their reads to the primary
  ([route by time](#user-can-edit-almost-everything--how-to-read)); keep the last-write time in a shared store, not
  the session, so [other devices](#how-do-multiple-devices-complicate-read-after-write-consistency) see it too.
- **Trade-off** — more reads on the primary; if most reads follow a write, the replica stops helping.

</details>
